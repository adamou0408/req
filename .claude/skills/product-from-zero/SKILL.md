先讀 `docs/methodology/00-core.md`（目標、五條策略、修正規則）。下面的步驟是做法，與核心衝突時以核心為準。


# 用 AI 從零做出產品

原則與理由在 `docs/methodology/README.md`（動手前讀第 2 節）。這裡是執行步驟，各步驟的完成條件只寫在這裡。範本在 `docs/methodology/templates/`（`templates/README.md` 列出每份複製到哪、哪一步建立），工作流程腳本與立場清單在 `docs/methodology/workflows/`。

「負責人」指提出需求、做最後決定的人。標〔未驗證〕的步驟還沒有實戰走過，回報時要說明。

## 步驟

每一步滿足完成條件才往下。規模（小／中／大）在步驟 0 決定，各步驟可以省略或合併什麼見 README 第 3 節的表。

### 0. 釐清

1. 讀 `docs/methodology/lessons-log.md`，列出和這個專案相關的教訓，帶進後面的步驟。
2. 用第一性原理往回推到目的，寫出「必須成立的條件」清單，每條附檢驗方式。
3. 一次問完，每題附建議做法與「沒有回答時採用的假設」：
   - 衝突題（方向上的取捨）≤5 題，小專案 ≤3 題。
   - 事實題（只有負責人知道的事）≤5 題，至少涵蓋：用什麼裝置看成品；AI 用量限制與用量去哪裡看；技術選型的前提（部署環境、既有技術、資料量）；規模與時程。
4. 訂出：終極目標與檢驗條件、不做的事、優先順序（只比品質面向）、規模級別、各階段的用量與時間估計。

產出：`docs/platform-vision.md`；每個衝突題在 `docs/decision-log.md` 記一筆，未回答的狀態為「待確認」。

完成條件：負責人確認衝突題。負責人不在時可以先做步驟 1–2，依假設寫的內容標〔待確認〕；步驟 3 開始前必須確認。

### 1. 定規範

從範本建立：`CLAUDE.md`、`docs/engineering-standards.md`（技術選型標「暫定」，探針後定案）、`docs/decision-log.md`、`docs/ux-acceptance.md`、`.gitignore`、`docs/pending-amendments.md`（空白）、`tools/install-dev-tools.sh`、`tools/check.sh`。工具依規模取捨。

完成條件：
- `tools/check.sh` 在這個幾乎是空的專案跑完並通過。
- `tools/install-dev-tools.sh` 實際執行過；環境不允許安裝時，在回報標「未執行」並寫明原因（「寫好腳本」不等於「跑過腳本」）。
- `CLAUDE.md` 裡尚未建立的文件旁標「步驟 N 建立」。
- 以上已提交。

### 2. 調查（依規模）

依主題分給多個代理，每份由沒參與的代理查核關鍵論點；用 `workflows/research-and-verify.js`。一手來源優先；每個事實附來源；查不到就寫查不到；分清楚強制、建議、實務。綜合成 `docs/research/00-synthesis.md`，並建立 `docs/control-matrix.md`，填「要求」與「依據」兩欄。小專案只查競品與痛點，不另做查證。

完成條件：關鍵論點都查核過（小專案免）；綜合結論標明哪些依據可以對外使用。

### 3. 骨幹初稿

用 `templates/spine.md` 寫 `docs/contract/00-spine.md`（標「初稿」），只寫做探針需要的：命名、核心實體、狀態、介面、目錄結構、模擬環境。同時用 `templates/handoff.md` 建立 `docs/handoff/probe.md`，列出架構風險清單：每項寫「如果錯了會怎樣」與「探針怎麼證明」。契約之前不再加深設計（README 原則 15）。

完成條件：初稿與風險清單已提交；每個風險都有證明方式。

### 4. 架構探針〔未驗證〕

挑一個使用者任務，涵蓋最多的骨幹層與外部 port，做出從頭到尾的最窄路徑，對著真實協定的模擬環境跑。技術選型在這裡定案。探針失敗就退回步驟 3 改初稿，並記一筆決策。

完成條件：`probe.md` 的每個風險標「已證明」或「已推翻並改了初稿」，附指令與結果；`check.sh` 的格式、lint、測試段已設定（輸出沒有「未設定」）並通過。

### 5. 情境檢查

用 `workflows/reality-check.js`，`readFirst` 放產品定位、骨幹初稿、`docs/handoff/probe.md`、決策紀錄、驗收標準。立場從 `workflows/README.md` 的立場表挑：必選的全部，其餘依條件挑；挑選理由記進決策紀錄。數量依規模。

完成條件：每個選定立場都有具體情境（誰、何時、做了什麼、系統怎麼反應、結果），每個情境標頻率與影響。

### 6. 裁決

輸入：`docs/reality-check/*.md` 與 `reality-check.js` 的回傳值。先用較省的模型去重分群：影響對象相同且根因相同就合併成一個議題。依頻率乘影響排序，再由最好的模型逐項裁決，寫進 `docs/rulings.md`（`templates/rulings.md`），同時檢討既有的每一筆決策。小專案與步驟 7 合併成 `docs/design.md`。

完成條件：每個議題都有決定、範圍與骨幹修改；決策紀錄已更新。

### 7. 骨幹定稿

把裁決寫進骨幹，版本改為 v1。第 5 節「核心規則」加各契約的規則章節就是規則代碼的唯一來源。寫出契約切分。填目標對照表的「做法」欄。主代理自己複核安全與信任邊界。

完成條件：之後的契約都能只依骨幹撰寫、互不衝突；每條規則有代碼；目標對照表每列有做法，或已列進待增修清單。

### 8. 契約

依骨幹的切分平行撰寫，每份用 `workflows/contract-draft-attack-revise.js`（撰寫 → 對立審查 → 修訂 → 確認）。對外介面用機器可讀的格式（OpenAPI、JSON Schema）當唯一來源。作者的骨幹修改建議由主代理集中處理。接著由最好的模型把驗收案例寫成可執行、目前會失敗的測試。小專案契約併入設計文件，由一位沒參與的代理審查。

完成條件：腳本回傳的 `unresolved` 為空（blocker、major 都經審查方確認已修）；驗收案例都是會失敗的測試，名稱含規則代碼；目標對照表「測試」欄沒有空格。

### 9. 擴展〔未驗證〕

依契約切分的相依順序做，相依的先做。一個代理把一塊從寫到測到修做完。實作代理不得修改步驟 8 的測試；認為測試錯了就回報。

完成條件（每一塊）：`check.sh` 通過；該塊的契約測試通過；目標對照表對應列的「證據」欄已填；`docs/handoff/<工作塊>.md` 已寫（工作塊名稱同契約切分）。

### 10. 驗收〔未驗證〕

照 `docs/ux-acceptance.md` 第 4 節：自動檢查 → 獨立審查看真實畫面 → 負責人看走查頁（必填項見第 5 節）。依實測調整任務步數上限。

完成條件：負責人確認；目標對照表沒有空格。

## 流程之外的情況

- **需求中途變更**：先在決策紀錄記一筆，附影響清單（受影響的骨幹章節、契約、測試、目標對照表列、程式）。改變目標、優先順序、規模，或要丟掉已完成的工作時，由負責人核准。核准後骨幹版本加一，影響項目列進待增修清單逐項處理，最後跑 `check.sh`。
- **時程與里程碑**：每個步驟結束就是里程碑。步驟 0 估各步驟的用量與時間，記在產品定位；實際值記進教訓紀錄。超出估計時照停損處理。
- **多人或多個 AI 協作**：每個人或代理負責的範圍（檔案、模組）寫在交接紀錄，只改自己的範圍。骨幹只由主代理修改。決策紀錄填「決定者」；多人時加核准人。每塊工作走分支，`check.sh` 通過並由沒寫它的人或代理審查後才合併。
- **技術債**：只記在 `docs/tech-debt.md`（`templates/tech-debt.md`），每筆有影響、償還的觸發條件、負責人。程式裡不寫 TODO，需要標示就寫債務編號 `TD-<n>`；`check.sh` 檢查每個編號都已登記。
- **上線與維運**〔空白，尚未走過〕：至少做到備份與還原演練、回滾演練、關鍵指標與告警有測試、資料遷移演練；上線後第一週回顧，問題記進教訓紀錄。走過之後補成正式步驟。

## 管理子代理

啟動前確認四件事，答不出來就不啟動：現在做合理嗎（依賴的東西定案了沒）；用哪一級模型；預期產出什麼；怎麼驗收。

| 等級 | 工作 | 目前對應（2026-11；會變動，以 Claude Code 的模型清單為準） |
|---|---|---|
| 最好的 | 目標、裁決、骨幹、核心契約、審查、驗收測試、最終查證 | Opus（腳本別名 `opus`） |
| 次一級 | 一旦寫錯就影響目標的核心實作；情境產生；由最好的模型驗收 | Sonnet（`sonnet`） |
| 較省的 | 照契約就能完成的工作、大量閱讀與蒐集、去重分群 | Haiku（`haiku`）或 Sonnet |

- 提示詞精簡、條列：目標、範圍、驗收條件、回報格式。共用背景放最前面且每個代理相同；規範引用 repo 裡的文件，不重貼。
- 一個代理把一塊工作從寫到測到修做完；完成時寫交接紀錄。
- 執行中定期確認它在寫檔或有產出。結束後自己驗證產出，不只看回報。

停損，出現任何一種就停掉並記進教訓紀錄：
- 它依據的前提已經改變。
- 實際用量超過估計的 1.5 倍。
- 30 分鐘內沒有寫檔或提交，或連續三次重複同樣的動作。
- 用了比分級表高的模型。

## 用量

- **一開始就量消耗率**：請負責人隔 5–10 分鐘看兩次用量。訂閱方案在 Claude Code 執行 `/usage`（或 claude.ai 設定裡的用量頁），看目前時段與每週上限的已用百分比；API 計費用 `/cost` 或 Console 的用量頁，看金額。兩次相減除以分鐘數就是消耗率。
- 負責人不在時：記「未取得用量」，依規模採保守估計，每個步驟結束都停下來回報。
- 每個步驟開始前估用量並告知；超出估計照停損處理，用量不夠時照 README 第 2 節的取捨規則交給負責人決定。
- 大量閱讀交給較省的模型，最好的模型只讀彙整後的結果。對話很長時，把幾件事合併在同一輪處理。

## 每個步驟結束時

1. 把狀態、決定、下一步寫進 repo 並提交。
2. 更新決策紀錄與待增修清單。
3. 回報：做了什麼、驗證到哪一級（已由可執行的測試證明／有文件依據／推論）、需要負責人知道的取捨。分析先講結論，用表格比較，不用內部代號；成品用負責人的裝置能讀的格式。
4. **提煉**：把這一步教訓紀錄裡的新條目，依 README 第 6 節的優先順序變成自動檢查、範本必填項、SKILL 步驟或完成條件，並在紀錄寫明提煉到哪裡。
5. 在教訓紀錄記這一步的估計與實際用量。

## 專案結束時

1. **統計**：負責人糾正次數、重做的工作量、同類錯誤是否再犯、各步驟估計與實際用量，寫進教訓紀錄的專案統計表，和上一個專案比較。
2. **淘汰**：連續兩個專案沒擋下任何問題的規則，合併或刪除；同類錯誤再犯的，往上一層提煉。
3. 把通用的修改提交回方法論所在的位置（不屬於單一專案）。
