# 用 AI 從零做出產品

完整的原則與理由在 `docs/methodology/README.md`。這裡是執行步驟。範本在 `docs/methodology/templates/`，工作流程腳本在 `docs/methodology/workflows/`。

## 一律遵守

- 選現實中行得通的最佳解，不選省事的。「之後再做」只有在現在做反而會做錯時才成立。
- 每種資訊只有一個來源。會變的東西做成抽象層，不寫死任何單位、人名或門檻。
- 靠機制把關：規則有測試、規範有自動檢查、重要設計有獨立審查、對外介面用真實環境實測。
- 如實回報：分清楚文件完成、程式寫完、驗證通過。
- 方向衝突自己先判斷並記進決策紀錄。只在兩種情況問使用者：只有他知道的事實；無法回頭或成本很大的動作。
- 有進度就存進 repo。每個階段結束都是可以停的點，狀態寫在 repo。

## 步驟

每一步滿足「完成條件」才往下。會被後面推翻的東西不要先做；彼此不相依的才平行。

### 0. 釐清

1. 用第一性原理分析：使用者說的是手段，往回推到目的，拆成「必須成立的幾件事」。
2. 找出方向上的衝突（通常只有三到五個），其餘細節多半可以由它們推出。一次問完，每題附建議。
3. 確認使用者用什麼裝置看成品、額度有沒有限制。
4. 訂出：終極目標與可檢驗的條件、不做的事、衝突時的優先順序。

完成條件：使用者確認。

### 1. 定規範

從範本建立並提交：`CLAUDE.md`、產品定位、工程規範、決策紀錄、驗收標準、忽略清單。安裝檢查工具並把安裝步驟寫成腳本。

完成條件：規範在 repo；新的子代理啟動時會讀到。

### 2. 調查

依主題分給多個代理：法規、競品、痛點、標準。每份完成後由沒參與的代理重新查核關鍵論點並補漏。用 `workflows/research-and-verify.js`。再綜合成需求清單與目標對照表。

規定：一手來源優先；每個事實附來源；查不到就寫查不到；分清楚強制、建議、實務。

完成條件：關鍵論點都查核過；綜合結論寫明哪些依據可以對外使用。

### 3. 情境檢查

多個代理各扮演一個真實角色，列出上線後一定會遇到的具體情境、對照現有設計、提出最佳解與替代方案，並檢討既有的決定。用 `workflows/reality-check.js`。立場至少包含：各種使用者、內外部稽核或驗收方、資安、想走捷徑或舞弊的人、維運、組織異動、法遵與法務、導入顧問、採購方。

完成條件：每個立場都有具體情境，不是空泛的類別。

### 4. 裁決

先用較省的模型把情境去重、分成議題；再由最好的模型逐項裁決：決定、理由、放棄的替代方案、範圍、對骨幹的修改。同時檢討既有的每一筆決策。

完成條件：每個議題都有決定；決策紀錄已更新。

### 5. 骨幹

把裁決寫成骨幹：命名、核心概念與關鍵欄位、狀態、規則代碼、介面、參數命名、範圍與不做的事、接下來的契約怎麼切分。主代理自己複核，特別是安全與信任邊界。

完成條件：之後所有契約都能只依骨幹撰寫，互不衝突。

### 6. 契約

依骨幹的切分平行撰寫。每份契約由沒參與的代理從對立角度審查（攻擊者、要串接的人、要照著實作的人），再修訂。用 `workflows/contract-draft-attack-revise.js`。作者回報的骨幹修改建議集中處理，不要各自改骨幹。

完成條件：審查的重大問題都已處理；規則對照表沒有空格。

### 7. 最窄路徑

只做一條從頭到尾的完整路徑，對著真實協定的模擬環境跑過。目的是驗證架構，不是做完功能。

完成條件：這條路徑的測試通過；架構的主要風險已經實際驗證。

### 8. 擴展

依序加入其餘功能。每一塊都通過品質關卡才算完成。

### 9. 驗收

自動檢查 → 獨立審查看真實成品 → 使用者確認。成品做成手機可讀的 HTML 走查頁。

## 管理子代理

啟動前確認四件事，答不出來就不啟動：

1. 現在做合理嗎？依賴的東西定案了沒？
2. 用哪一級模型？
3. 預期產出什麼？
4. 怎麼驗收？

模型分級：

| 工作 | 模型 |
|---|---|
| 目標、裁決、骨幹、核心契約、審查、最終查證 | 最好的 |
| 一旦寫錯就影響目標的核心實作 | 次一級，由最好的模型驗收 |
| 照契約就能完成的工作、大量閱讀與蒐集 | 較省的 |

提示詞：精簡、條列；寫目標、範圍、驗收條件、回報格式；共用背景放最前面且每個代理相同；規範引用 repo 裡的文件，不重貼。

停損，出現任何一種就停掉：

- 依據的前提已經改變，做完也要重來。
- 花費明顯超過這件工作該有的規模。
- 長時間沒有產出或在重複。
- 用了不必要的高階模型。

結束後自己驗證產出，不只看回報。

## 額度

- 一開始就請使用者隔幾分鐘提供兩次用量，算出每分鐘的消耗。
- 每個階段開始前估用量並告知；超過就停下來回報。
- 大量閱讀交給較省的模型；最好的模型只讀彙整後的結果。
- 對話很長時，把幾件事合併在同一輪處理。

## 每個階段結束時

1. 把狀態、決定、下一步寫進 repo 並提交。
2. 更新決策紀錄與待增修清單。
3. 向使用者回報：做了什麼、驗證到什麼程度、把握多高、需要他知道的取捨。
4. 這個階段有新的教訓，就補進 `docs/methodology/README.md` 的「犯過的錯與對應的規則」。
