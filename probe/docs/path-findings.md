**路徑通了（跑過且通過）。** 林怡君在手機寬度的頁面送出申請；陳建宏用真的 Chromium WebAuthn（CDP 虛擬驗證器）核准，資料庫自己驗章、從憑證得出是誰；黃淑芬查得到這張單，她的瀏覽器從創世重算整條鏈、比對外部錨點、重驗核准的簽章，顯示「驗證通過」。資料庫最高權限者改了核准紀錄後，同一個畫面顯示「驗證失敗」。後端沒有任何業務判斷。

## 4. 哪裡比預期難

1. **資料庫測試留下的資料會干擾端對端。** 資料庫測試替主管登記了軟體通行金鑰，畫面因此不顯示「需要登記」，瀏覽器裡的虛擬驗證器也沒有那把金鑰。解法：`run-all.sh` 跑完資料庫測試後再重建一次乾淨的資料庫。正式做法應該讓兩種測試各用一個資料庫。
2. **用 jsonb 的文字輸出當雜湊原文，瀏覽器無法自己重算。** 內容雜湊與證明雜湊是 `sha256(jsonb::text)`，瀏覽器拿到的是解析過的 JSON，排不回原本的位元組。只好讓 `api.audit_case` 另外回傳 `content_text`、`raw_text` 原文。這是 db-findings §7「RFC 8785 要在正式 DDL 前決定」的具體代價：每個要被第三方重驗的雜湊，都要連同它的原文位元組一起保存與匯出。
3. **型別在資料列與 jsonb 之間不一致。** `case_create` 回傳的 `case_no` 是 bigint，`pg` 給字串；`case_list_mine` 回傳的 jsonb 裡是數字。畫面比對時出錯，花了一輪除錯。這正是工程規範要「由 `pg_catalog` 產生 TypeScript 型別」的理由；探針沒有產生器。
4. **登記通行金鑰要再登入 Dex 一次。** nonce 要綁定公鑰，所以一定要一次新的授權往返。Dex 不保留登入狀態，使用者必須再輸入密碼，這也正是安全性的來源。換成有單一登入狀態的正式 IdP 時，這次往返可能不再要求輸入密碼，登記就只靠「IdP 上有登入狀態」。屆時要加 `prompt=login` 或 `max_age=0`，並確認 IdP 會照做。
5. **竄改報告會連鎖。** 改了第 7 筆，驗證從第 7 筆到鏈尾每一筆都報錯（因為從創世重算）。對稽核人員來說太吵，應該改成在第一個不一致處標示「從這裡開始不可信」。
6. **流程上：有另一個代理同時寫同一批檔案。** 開工時 `probe/api/src/` 有前一次嘗試留下的檔案（後端自己驗 WebAuthn），之後又有另一個代理改寫了 `server.ts`。改寫的設計和我的相同，所以沿用了檔案上當時的版本；那些檔案後來被移到 `frontdoor/`。已向主對話回報。

## 5. 商業邏輯全放資料庫：做完之後的觀感

**好寫的：**
- **後端幾乎是空的。** 412 行 TypeScript，裡面沒有任何 `if 狀態` 或 `if 角色`；路由表 29 行，新增一個功能就是一行加一個 function。錯誤代碼、訊息、HTTP 狀態都從資料庫來。
- **畫面依 `actions` 與 `capabilities` 決定顯示什麼。** 待簽清單就是「我有可執行動作的單」，由轉移表算出。畫面不需要知道誰是主管、什麼狀態能核准。
- **安全性來自結構，不靠小心。** 沒有「憑工作階段就決定」的路由，後端拿到什麼都做不出決定；端對端測試直接證明了這一點。

**彆扭的：**
- **「誰能做什麼」寫了兩次。** 可執行動作清單（`sgn_internal.case_actions`）和每個 api function 裡的檢查（`challenge_issue` 的 SELF_APPROVAL、NOT_APPROVER，`case_submit` 的 NOT_APPLICANT）表達的是同一條規則，卻是兩份程式碼，可能走樣。應該讓每個動作 function 都先呼叫同一個「這個人能不能對這張單做這個動作」的入口，清單也從它算出（工程規範要求「授權檢查只有一個入口」；探針沒做到）。
- **一個畫面動作要拆成兩次呼叫。** 「送出申請」是 `case_create` 再 `case_submit`，兩個交易；第二步失敗會留下草稿。照「邏輯在資料庫」的原則，每個使用者動作應該對應一個 function（例如 `case_create_and_submit`），而不是讓前端串流程。
- **jsonb 回傳沒有型別。** `api.me`、`inbox_list`、`audit_case` 都回傳 jsonb，前端靠欄位名稱，打錯只會在執行時發現。要嘛改用 `returns table`，讓產生器拿得到欄位，要嘛為 jsonb 定義 schema。
- **SQL 讀起來偏長。** `audit_case` 一個 function 組三段 jsonb，約 60 行；同樣的事在 TypeScript 大概一半長。可讀性還可以，但要靠拆小 function 與註解撐住。
- **測試沒辦法只靠 SQL。** 登入與簽章都在資料庫外產生，資料庫規則要用 Node 驅動測試，畫面要用真的瀏覽器。「測得動」成立，只是測試基礎建設比預期重（Dex、虛擬驗證器、兩次建庫）。
- **稽核端的驗證刻意不放資料庫。** `verify.js` 有 143 行密碼學與比對邏輯在前端，看似違反「業務判斷只在資料庫」。但這是「不相信資料庫」的獨立驗證，本來就該在資料庫以外，而且應該和 `probe/db/tools/chain-lib.mjs` 共用同一份實作；目前兩份是分開寫的，違反單一來源。

整體來說，第三個賭注在這條路徑上**成立**：規則沒有變得難讀，也測得動。條件是要把上面的「授權單一入口」與「一個動作一個 function」補成規範，否則規則會在 SQL 裡被寫第二次。

## 6. 對四個賭注的看法

| 賭注 | 看法 | 根據 |
|---|---|---|
| 一：資料庫自己驗證「決定來自本人」 | **成立（在這條路徑上）** | 真實瀏覽器的 WebAuthn 由資料庫驗章，後端單次 25 ms；後端沒有任何能不經證明就做決定的路徑（端對端測試證明）。殘餘風險同 db-findings §2.6：資料庫最高權限者，以及使用者操作當下前端與後端同時被控制 |
| 二：雜湊鏈 + 外部錨點 | **有條件成立** | 稽核人員的瀏覽器抓得到竄改（已測）。條件：(1) 最後一個錨點之後的紀錄只靠資料庫保護（這次的缺口最多 2 秒）；(2) 探針的錨點檔與驗證程式（`verify.js`）都由後端送到瀏覽器，被攻破的後端可以送假的錨點或假的驗證程式。正式環境的稽核工具與錨點要走獨立管道（例如另一個網域的唯讀物件儲存，加上離線驗證工具） |
| 三：商業邏輯全放資料庫 | **成立，附兩個條件** | 見第 5 節：授權檢查要單一入口；每個使用者動作對應一個 function |
| 四：手機用通行金鑰幾步內完成 | **剛好達標，未在真機驗證** | 4 步＝T2 上限。首次要登記通行金鑰，多一次 Dex 登入。全部在 390px 寬、Chromium 行動模式、虛擬驗證器下測；沒有在 iOS Safari 或 Android Chrome 上試過，也沒試過同步型通行金鑰（iCloud、Google 密碼管理工具） |

## 7. 對架構的建議

1. **維持 db-findings 的架構**：決定走 (a)，登入與登記走 (b)，後端只轉送。這次接下來沒有遇到需要推翻它的地方。
2. **授權單一入口**：`sgn_internal.can_act(person, case, action)` 由轉移表與簽核人規則算出；每個 api 動作 function 先呼叫它，`actions` 清單也由它產生。
3. **一個使用者動作一個 api function**，前端不串多步流程。
4. **雜湊原文的格式在寫正式 DDL 前定案**（RFC 8785 或「保存原始位元組」），每個要被第三方重驗的雜湊都要能匯出原文。
5. **驗證程式只有一份**：鏈與證明的驗證寫成一個不依賴 Node 的 ES module，離線工具、錨定程式、稽核頁共用；稽核頁從獨立來源載入它與錨點。
6. **產生器先做**：由 `pg_catalog` 產生路由表的參數與回傳型別，避免第 4 節第 3 點那類錯誤。
7. 測試用兩個資料庫：資料庫測試一個、端對端一個。

## 8. 沒做到

- **真機**：沒有在真的手機與真的通行金鑰上試過（只有 Chromium 行動模式與 CDP 虛擬驗證器）。
- **UI 自動檢查只做了兩項**：390px 沒有水平捲動、可點擊元素至少 44×44。axe-core、對比、只用鍵盤、標籤檢查，以及電腦寬度，**都沒做**。也沒有獨立審查與畫面走查頁。
- **「退回」**：畫面會依 `actions` 顯示退回按鈕，程式路徑和核准相同，但**沒有端對端測試**；申請人修改退回的單的畫面**沒做**。
- **「尚未錨定」的畫面**：寫了，但這次執行剛好已經錨定，沒有跑到那個分支。
- **登出**只清掉瀏覽器的 cookie，資料庫裡的工作階段仍然有效到過期（沒有 `api.session_close`）。
- OIDC 往返的暫存（state、PKCE）放在後端記憶體，只能單一行程。
- 後端沒有單元測試（只有端對端）；ESLint、Prettier、sqlfluff、plpgsql_check 都沒跑，只跑了 `tsc --noEmit` 與 shellcheck。
- 身分提供者再驗證的決定（`case_decide_idp`）沒有接到畫面。
- 稽核頁每次都從創世重算整條鏈，探針資料量下 62 ms；大量資料要改成從最近的錨點或封印開始，**沒做**。
