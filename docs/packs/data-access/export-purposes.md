# 匯出目的的探索

**提案，待負責人裁決。** 依據：裁決 D91 (5)。定案前維持現況：L4 不能申請匯出，其他級別的「可否匯出」是一個是否欄位。這份文件不修改 [rules.md](rules.md)。

## 1. 為什麼先問目的

現在的申請單只問「可不可以匯出」。簽核人看不出資料要帶去哪裡、做什麼，只能憑感覺同意或拒絕；資料一旦離開使用方系統，欄、列、期間、到期這些限制全部失效，撤銷也收不回來。

多數「我要匯出」其實是「我要完成某件事」。先把那件事問清楚，很多可以在系統內完成，不必讓資料離開；剩下真的要帶走的，再依目的給最小的形式。

## 2. 人們為什麼要匯出

| 代碼 | 目的 | 真正需要的是什麼 | 不匯出能不能滿足（系統內的替代做法） | 不能時，最小的匯出形式 | 平台能留下的證據 |
|---|---|---|---|---|---|
| `external_handover` | 交給外部單位（會計師、主管機關、客戶、廠商） | 對方拿到指定範圍的資料，而且事後能證明給了什麼 | 部分可以：讓對方的人以外部人員身分成為被授權者的成員，在系統內查看；主管機關的制式申報做不到 | 只含申報或合約要求的欄位；指名收件單位；檔案加密、帶序號與浮水印 | 收件單位、依據（函文或合約編號）、檔案雜湊、欄位與筆數、交付時間 |
| `offline_analysis` | 離線分析（Excel、統計軟體、筆電上的工具） | 用系統沒有的工具算東西 | 多數可以：使用方系統提供分析環境或查詢介面，工具連進來算，資料不落地 | 去識別或彙總後的資料集；限筆數；保留期限到期要回報已刪除 | 資料集的欄位與筆數、雜湊、去識別方式、保留期限、刪除回報 |
| `report_slides` | 做簡報或報表 | 幾個數字、一張圖 | 可以：在系統內產出彙總與圖表，帶走的是結果不是明細 | 只有彙總值（設定最小群組人數，避免回推個人）；不含明細列 | 彙總的定義（維度、指標）、最小群組人數、產出時間 |
| `system_feed` | 匯入另一個系統（上下游系統、報表工具、模型訓練） | 另一個系統持續拿到資料 | 可以，而且應該：那個系統自己當被授權者（agent 或服務帳號）申請，走同一套規則直接讀 | 不提供匯出檔；一次性的資料搬移另案處理 | 那個系統自己的授權、使用紀錄與對帳 |
| `retention_copy` | 留存備查（「以後稽核要看」「怕資料被改」） | 某個時間點的資料樣貌可以被證明 | 可以：由使用方系統保存快照或查詢結果的雜湊，個人不需要留副本 | 只留雜湊與查詢條件，不留資料 | 查詢條件、結果雜湊、時間 |
| `manager_review` | 主管要看 | 主管看到內容並做決定 | 可以：主管加入被授權者的成員，或在系統內分享一個唯讀的檢視 | 彙總或截圖等級的摘要，帶浮水印（查看者、時間） | 誰在什麼時候看了哪個檢視 |
| `legal_hold` | 法務、訴訟或調查的證據保全 | 完整、未經修改、可證明來源的資料 | 不能：必須交出原始資料 | 指定案號與範圍的完整匯出；加密、序號、雙人交付 | 案號、範圍、檔案雜湊、交付與接收人 |
| `other` | 其他（需說明） | 不明 | 由簽核人判斷 | 依簽核人要求 | 說明文字 |

觀察：

- 八個目的裡，`system_feed`、`retention_copy`、`manager_review`、`report_slides` 四個原則上不需要讓明細離開系統。
- 真的需要明細離開的是 `external_handover`（部分）與 `legal_hold`；`offline_analysis` 取決於使用方系統有沒有分析環境。
- 這張表是從一般情況整理的，不是從本公司的實際申請整理的。需要負責人或 MIS 以最近的實際案例核對（見第 6 節）。

## 3. 建議方案

把「可否匯出」從一個是否欄位，改成「匯出目的」的結構化欄位。不同目的導向不同的處理。

### 3.1 欄位

- 新增代碼表 `pack_data_access.export_purpose`，做法與既有的使用情境分類（`purpose_category`）相同：代碼、名稱、是否需要說明、排序、是否啟用，另加下表的處理欄位。代碼表是唯一來源，畫面、驗證、交付內容都讀它。
- 申請內容的 `export_allowed`（是否）改為 `export`：`null`（不匯出）或 `{"purpose", "form", "description", "recipient"}`。`form` 是匯出形式的代碼（見 3.2），`recipient` 只在目的要求時填。
- 選了目的之後，畫面先顯示該目的的「系統內替代做法」；申請人要明確選「替代做法不適用」並說明原因，才能繼續申請匯出。這段文字放在代碼表（顯示用），不寫在前端。

### 3.2 每個目的的處理

| 目的 | 預設導向 | 允許的匯出形式（`form`） | 額外必填 |
|---|---|---|---|
| `system_feed` | 不給匯出；引導改以那個系統為被授權者另提申請 | 無 | — |
| `retention_copy` | 不給匯出；改留雜湊 | `hash_only` | — |
| `manager_review` | 引導加入成員或分享檢視 | `summary` | — |
| `report_slides` | 系統內彙總 | `aggregate` | 彙總的維度 |
| `offline_analysis` | 有分析環境時不給匯出 | `deidentified`、`aggregate`、`row_limited` | 保留期限 |
| `external_handover` | 允許 | `field_subset`（加密、序號、浮水印） | 收件單位、依據 |
| `legal_hold` | 允許 | `full`（加密、序號） | 案號 |
| `other` | 由簽核人判斷 | 申請人自選 | 說明 |

匯出形式由使用方系統執行，所以要納入它的能力宣告（[pending-amendments.md](../../contract/pending-amendments.md) 的 D91-c）：做不到某個形式的系統，那個形式不能選。交付的規則帶 `export.purpose` 與 `export.form`；使用方系統的使用紀錄逐筆回報匯出（筆數、形式、檔案雜湊），平台據此核對實際匯出有沒有超出核准的形式。

### 3.3 可以先做、不必等裁決的部分

- 代碼表與第 2 節的替代做法文字（純資料）。
- 申請畫面在勾選「可匯出」時先顯示替代做法（不改規則，只多一步引導）。
- 使用紀錄區分查詢與匯出（[06-consumer-obligations.md](../../contract/06-consumer-obligations.md) 的 6.3）。

真正改變「能不能匯出」的部分（3.2 的導向與形式）要等第 5 節的裁決。

## 4. 與 `rules.md` 的關係

| 規則 | 關係 | 有沒有衝突 |
|---|---|---|
| `DA-NO-MEDIUM`（申請單不記錄媒介；簽核的對象是資料本身） | 目的問的是「資料離開管控之後要做什麼」，不是「用哪個工具存取」，原則上不是媒介。但 `system_feed` 要指名另一個系統、`external_handover` 要填收件單位，都很接近「記錄去向」 | **可能衝突，需要裁決**：`rules.md` 的理由是所有管道都套同一條規則；匯出之後的去向已經不在任何管道內，是否算「媒介」沒有寫 |
| `DA-EXPORT-TIER`（查看和帶走分開；L4 不能申請匯出） | 不變。L4 維持不能申請任何匯出形式，包含 `aggregate` 與 `hash_only` | 無。但 L4 的彙總值、雜湊是否也算「匯出」，`rules.md` 沒有寫，見第 5 節 |
| `rules.md`「可否匯出：若 DC 無法區分，這個欄位就關閉」（M5） | 沿用：使用方系統宣告做不到匯出區分時，整個匯出欄位關閉；做得到區分但做不到某個形式時，只關那個形式 | 無 |
| `DA-CHANGE-COMPARE`（可匯出改為不可匯出算縮小；無法判定算擴大） | 延伸：匯出改為不匯出是縮小；改目的、改成限制較少的形式是擴大；形式之間的寬嚴順序要定義（建議 `hash_only` < `aggregate` < `summary` < `deidentified` < `row_limited` < `field_subset` < `full`） | 無，但順序是新的業務規則 |
| `DA-CHANGE-PURPOSE`（修改使用情境算擴大） | 比照：修改匯出目的算擴大 | 無 |
| `DA-PURPOSE`（使用情境＝分類＋說明） | 匯出目的是另一個欄位，不取代使用情境：使用情境說明為什麼要這份資料，匯出目的說明為什麼要帶走 | 無 |
| 「稽核：可查詢全公司所有的單並匯出」 | 那是平台自己的匯出（骨幹 `K-EXPORT`：必選用途、加密、序號、浮水印），不是資料授權的匯出。這份提案刻意用相同的概念（必選用途），但兩張代碼表分開 | 無 |

## 5. 要負責人決定的事

| # | 問題 | 建議 |
|---|---|---|
| E1 | 匯出目的與去向算不算 `DA-NO-MEDIUM` 說的「媒介」 | 不算：媒介是存取管道，目的是離開管控的理由。需要在 `rules.md` 補一句 |
| E2 | 第 2 節的目的清單對不對、少了什麼 | 以最近的實際申請核對後定案 |
| E3 | `system_feed`、`retention_copy` 是否一律不給匯出 | 是 |
| E4 | L4 的彙總值與雜湊算不算匯出 | 算（維持從嚴）；之後要放寬屬放寬類設定變更 |

| E6 | 匯出形式的寬嚴順序（第 4 節） | 如建議 |

## 6. 這份提案沒有做的事

- 沒有訪談實際申請人，目的清單沒有對過本公司的真實案例（`open-questions.md`「待使用者提供」的 3–5 張真實申請還沒有）。
- 沒有確認使用方系統做得到哪些匯出形式（去識別、彙總、限筆數、浮水印）；負責人說明使用方系統由他開發，形式清單應該由他依實作成本刪減。
- 沒有設計匯出檔的格式與加密方式。
