# 方向

這一頁是整個專案最上層的依據。其他文件都是為了它而存在；與它衝突時，以這一頁為準。

## 目標

使用這個平台的公司，在簽核與權限這一塊的稽核能過關，而且每一種使用者都願意用。

怎樣算達成：一張申請從送出到生效，稽核會查的控制都由系統強制執行、證據自動產生、例外自動浮現，稽核人員自己查得到；申請人和簽核人在手機上幾步內完成。

## 策略

| # | 槓桿 | 意思 |
|---|---|---|
| 1 | 決定可問責 | 每個決定都能證明是誰做的，而且他有資格做 |
| 2 | 內容不走樣 | 核准的內容和最後執行的內容是同一份 |
| 3 | 紀錄改不掉 | 包含有最高權限的人也改不掉而不被發現 |
| 4 | 核准之後繼續把關 | 執行、驗證、到期、撤銷、對帳、複查 |
| 5 | 好用 | 難用就會被繞過，前四項就失效 |

通用平台（核心加流程包）是達成這五項的方式，不是目標本身。

## 目前的賭注

設計已經做得夠深，現在最大的不確定不在「該做什麼」，而在「這個架構做不做得出來」。所以先做一條最窄的完整路徑來驗證，再擴展。

| 賭注 | 怎樣算賭錯 |
|---|---|
| 資料庫可以自己驗證「這個決定真的來自這個人」，不必相信後端 | 做不到，或慢到不能用 |
| 雜湊鏈加上外部存放的摘要，能抓到竄改與整條重算 | 有繞得過去的方法 |
| 商業邏輯全部放在資料庫，仍然寫得出來、測得動 | 路徑做完後，規則變得難讀或難測 |
| 手機上用通行金鑰核准，幾步內完成 | 流程卡住或步數超過驗收標準 |

賭錯任何一項，就回頭改架構，而不是繼續往下做。

## 修正的規則

- 負責人的每一次介入，都代表系統有一個地方沒做好。
- 出錯時先問是哪一層的問題：目標沒對齊、策略不對，還是做法不對。只修做法，同類的錯會換個樣子再出現。
- 修的方式依序是：改成自動檢查 → 改流程的進入條件 → 最後才是多寫一條規則。
- 設計文件不再加深，除非最窄路徑證明需要。
- 每完成一條路徑，回來檢查這一頁的賭注，並更新。
