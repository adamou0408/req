# 真實情境檢查 04：想舞弊或走捷徑的內部人員

立場：上市櫃公司（或集團子公司）裡想拿到不該有的權限、或讓不該過的單通過的人。可能是業務、財會、MIS、主管，也可能是平台的系統管理員。我不想留下明顯痕跡；最好的結果是每一步在系統裡看起來都「合規」，稽核抽到也挑不出毛病。

對照的文件版本：`platform-vision.md`、`contract/00-spine.md`、`decision-log.md`（D1–D24）、`validation-cases.md`、`contract/pending-amendments.md`（A1–A22）、`packs/data-access/rules.md`、`packs/seal/rules.md`、`contract/03-pack-seal.md`、`contract/seed-directory.md`、`ux-acceptance.md`。`01-kernel.md`、`02`、`04`、`05` 尚未撰寫，以骨幹為準。人物沿用 `seed-directory.md`。

已被其他立場詳細處理、而且從舞弊者角度沒有新增攻擊面的題目（例如以 `sgn_app` 連線冒用身分、DBA 重算雜湊鏈、假時鐘、上線期初資料），這裡不重複列出。已完整涵蓋的情境也不列。

判斷「擋不擋得住」的標準：**事前擋住** ＞ **事後一定浮現為例外並有人追** ＞ **只在紀錄裡查得到（要有人剛好去查）** ＞ **沒有痕跡**。只做到第三級的，對舞弊者來說等於沒擋，因為稽核抽樣抽不到就不會有人看。

## F01 兩個資料擁有者互簽對方部門的申請

**情境**：2027 年 2 月。張美玲（財務部經理，「銷售訂單」與「產品成本明細」的資料擁有者）想讓財務部看「客戶主檔」，周文傑（業務管理部經理，「客戶主檔」的擁有者）想讓業務管理部看「產品成本明細」。兩人在午餐時講好：「你的我簽，我的你簽，不要退。」各自叫下屬送單，對方都在擁有者那一關幾分鐘內核准，意見欄寫「業務需要」。一年下來兩人互簽了 11 張。

**系統現在**：`K-SOD-DISTINCT` 只檢查同一張單裡每一關是不同的人，每張單本身都合規。系統沒有跨單的關係分析，也沒有「誰常常核准誰」的視角。

**結果**：每張單都乾淨。稽核抽樣抽到一兩張，看不出問題；「互相放行」只有把母體全部攤開、做交叉表才看得到，而內部稽核通常不會這樣做。

**涵蓋**：沒涵蓋。骨幹第 5 節只有單張單內的職責分離；platform-vision「例外自己浮現」列的例外種類沒有共謀型態。

**替代方案**：
- (a) 直接禁止：A 核准過 B 部門的單之後，B 不能核准 A 部門的單。缺點：中小規模的公司每個領域只有一位擁有者，互相核准是常態，全面禁止會讓流程卡死，人就會轉去 email。
- (b) 只在稽核查詢提供「核准人 × 申請人／申請部門」交叉表，讓稽核自己找。缺點：舞弊者只怕「一定會有人看」，查得到不等於會被看。
- (c) 系統定期計算「互惠核准」指標（A 核准 B 方的次數與 B 核准 A 方的次數都超過門檻、核准時間短、零退回），超過就自動產生例外，**派給稽核角色而不是兩人的主管**，並在簽核畫面上給第三關（例如資安長）一個提示「這兩位擁有者近 90 天互相核准 6 次」。

**最佳解**：(c)。理由：稽核過關要的是「例外自己浮現」，而互惠核准是內控準則所說「職責分離失效」最常見的實際型態；用例外而不是硬擋，才不會在小公司卡死流程。例外派給稽核，是因為兩人的主管可能就是同一位副總，也可能知情。門檻（次數、期間、平均核准秒數）做成參數，但「關掉這個偵測」屬於放寬控制，要走 F19 的嚴格設定變更。

## F02 主管叫下屬當人頭申請人，自己簽給自己負責的團隊

**情境**：陳建宏（業務分析部經理）想看「員工薪資」裡業務人員的獎金，作為談薪的籌碼。他知道自己送單會很顯眼，於是請林怡君用「業務分析部」這個 team 送單，使用情境選「報表與分析」。被授權者「業務分析部」的負責人正是陳建宏，他也是這個團隊的成員。路徑第一關「申請人主管」解析到陳建宏，他核准。

**系統現在**：`K-SOD-APPLICANT` 只看申請人；`K-SOD-DISTINCT` 只看關卡之間。簽核人是被授權者的負責人或成員（也就是實際受益人），系統不知道也不擋。

**結果**：受益人親手核准了自己的權限。紀錄上看起來是「主管核准下屬的申請」，完全合規。

**涵蓋**：沒涵蓋。骨幹第 5 節無受益人的規則；`principal_member` 存在，但沒有被職責分離使用。（05-executive-approver E16 從簽核人立場提出同一問題，這裡補上「刻意找人頭」的攻擊型態。）

**替代方案**：
- (a) 簽核人是被授權者的成員或負責人時，只顯示警示，仍可簽。缺點：舞弊者本來就知道自己是受益人，警示沒有約束力。
- (b) 擋下並改由上一層主管簽（和 `K-SOD-DISTINCT` 撞到時一樣的處理）。
- (c) 把被授權者整體視為「申請方」：被授權者的負責人與在職成員一律比照申請人，不能在任何一關簽核；撞到時依 `K-SOD-DISTINCT` 的方式往上找。

**最佳解**：(c)，並新增規則代碼 `K-SOD-BENEFICIARY`。理由：資料授權的被授權者一定是團隊、專案或 agent，「申請人」只是填表的人，真正的受益人是被授權者的成員；職責分離若只看填表的人，就形同可以用人頭繞過。改由上一層主管簽和既有規則的處理方式一致，簽核人不用學新東西。成員很多的大團隊（例如整個業務處）會讓主管關常常往上跳，這是正確的結果：主管給自己所在團隊開 L4 資料，本來就應該由他的上一層決定。紀錄裡寫明「因簽核人是被授權者成員而改派」。

## F03 自己設代理、代理給下屬或共謀者、回溯設定代理

**情境**：
1. 蘇慧敏（財務長）出國兩週，把代理人從張美玲改成吳家豪（財務專員，張美玲的下屬）。財務部的邱冠廷送了一張 180 萬的用印申請：`manager` 關是張美玲，`cfo` 關由吳家豪代簽。`K-SOD-DISTINCT` 不會擋（兩關是不同的人），結果是張美玲的下屬替財務長核准了張美玲部門的重大合約，而吳家豪不可能退回自己主管部門的單。
2. 謝明哲（系統管理員）在週一補了一筆「上週四到週五，賴政達代理人為許文豪」的代理紀錄，讓許文豪上週五已經簽的 L4 單看起來有依據。

**系統現在**：骨幹只有 `delegation`（委託人 → 代理人，期間、原因）。誰可以建立、能不能回溯、代理人要符合什麼資格、代理範圍，都沒有規定；D12 把「角色指派」納入設定變更，但沒有把代理納入。

**結果**：代理變成不經核准的權限移轉；回溯建立的代理可以把任何越權簽核「合法化」。

**涵蓋**：部分。`K-DELEGATE`、`K-SOD-DISTINCT` 只保證紀錄寫明誰代誰簽、代理人也要遵守職責分離。（01-internal-audit #21、02-external-it-audit #17 提過代理濫用；這裡補充「回溯」與「代理給下屬」兩種攻擊。）

**替代方案**：
- (a) 代理一律走設定變更申請單（D12）。缺點：主管臨時請病假時來不及，結果就是不設代理，讓單被升級，或把帳號密碼交給祕書（更糟）。
- (b) 代理由委託人本人設定即可，系統只記錄。缺點：等於現況，擋不住代理給下屬。
- (c) 委託人本人設定（需 MFA），或委託人的直屬主管代為設定；**生效時間不得早於建立時間**；代理人資格由規則檢查：不得是委託人的下屬鏈、不得在同一張單前面的關卡簽過、單一持有人角色（資安長、財務長）的代理人必須是事先登記在該角色上的「指定代理人」名單（這份名單才走 D12 的設定變更）；代理可限定流程類型與級別；每次代簽都即時通知委託人，回國後給一份「代簽清單」要求確認。

**最佳解**：(c)。理由：稽核要的是「代理有授權依據、不能事後補」，而簽核人的速度要求代理能在幾分鐘內設好；把「誰有資格當代理人」放在事先核准的名單，把「這次啟用代理」留給本人，兩者兼顧。禁止回溯是硬性規則，不提供參數；確實有事後補登的需求（例如當事人失聯），走例外申請單，由稽核看得到。代理人是委託人下屬時擋下，是因為下屬無法獨立於主管做判斷，而且代簽的單常常就是上司的部門送的。

## F04 轉簽給「好說話」的人

**情境**：葉佳蓉（法務專員）認領了一張用印單，發現合約的違約條款明顯對公司不利，她要求修改，申請人何宗翰不想改。何宗翰去找簡志豪（法務主任）抱怨，簡志豪請葉佳蓉「轉給我處理」。或者反過來：資料擁有者周文傑不想為一張有疑慮的單負責，轉簽給他的下屬（不是資料擁有者），下屬照主管的暗示核准。

**系統現在**：D16 只寫「轉簽（改由他人簽，對象要有資格並通過職責分離檢查）」。「有資格」沒有定義；轉簽前的意見會不會保留、被轉出的人能不能不留意見就轉，沒有規定。

**結果**：轉簽成了「換人簽到過為止」的工具；被轉出的那位專業判斷沒有留下紀錄，或者責任被轉給沒有資格判斷的人。

**涵蓋**：部分（D16 有方向，沒有規則）。

**替代方案**：
- (a) 只允許轉給同一個 resolver 會解析出的人（同角色、同範圍）。缺點：單一持有人的關卡（資料擁有者、資安長）沒有人可轉，只能升級。
- (b) 允許轉給任何人，但轉出時必須填原因。缺點：原因是自由文字，擋不住轉給下屬。
- (c) 轉簽對象必須「能被這一關的 resolver 解析到」，或是該角色登記的指定代理人；單一持有人關卡只能轉給指定代理人；轉出時必填原因，而且**轉出者當時已勾選的檢查清單與已寫的意見保留在紀錄並顯示給接手的人**；同一張單同一關最多轉一次；轉簽對象不得是申請人或被授權者成員（F02）。

**最佳解**：(c)。理由：「有資格」若不綁 resolver，就無法被測試驗證，也就不是「事前擋得住」。保留轉出者的意見是關鍵：稽核要能看到「原本的審查人有疑慮，後來換人核准」這個事實；接手的人也會因為看到前一位的疑慮而更謹慎。轉一次為限，避免一路轉到找到願意簽的人。

## F05 用加簽把機密單的內容開給局外人看

**情境**：楊淑惠（人資經理）在一張薪資資料的授權申請上是資料擁有者。業務副總方國華想知道業務處某位主管的薪資，請熟識的資料擁有者周文傑幫忙。周文傑不在路徑上，但林怡君送的另一張 L4 薪資單到了陳建宏手上時，陳建宏用「加簽」把周文傑加進來「請業務管理部確認需求」。周文傑因此成為被指派的簽核人，看得到整張單的內容與附件（包含申請人附上的薪資欄位樣本截圖）。

**系統現在**：A3 規定保密的申請單只有「申請人、被指派的簽核人與執行人、稽核」看得到內容。加簽產生的工作也是指派，加簽的人就成為「被指派的簽核人」。D16 只說加簽「只增不減」，沒有限制加簽對象。

**結果**：加簽成了繞過保密的合法管道；查閱紀錄會記下周文傑看過，但他有「被指派」的正當理由。

**涵蓋**：沒涵蓋（A3、A4、D16 之間的交集沒有處理）。

**替代方案**：
- (a) 保密的流程類型禁止加簽。缺點：人資單確實常需要請法務或個資窗口看一眼，禁止就會改用 email 轉寄整張單，洩漏更嚴重。
- (b) 加簽對象限於預先登記的「可加簽角色」（例如法務、個資窗口、資安），由流程定義宣告；保密單的加簽人只看得到加簽者勾選要給他看的欄位，看不到機密欄位（A19）與附件，除非流程定義允許。
- (c) 加簽需要該關的資料擁有者或流程管理者同意。缺點：多一個等待，加簽本來就是要快。

**最佳解**：(b)。理由：把「可以加簽給誰」變成流程定義裡的宣告資料，既可測試又可稽核；欄位層級的可見範圍讓「請法務看一眼條款」與「不讓局外人看到薪資數字」同時成立。加簽事件的紀錄要寫明加簽人看得到哪些欄位，稽核才能回答「這張單的薪資數字有誰看過」。

## F06 用印拆單：一份合約拆成三張、換三個申請人

**情境**：2027 年 3 月，劉俊傑要和「大昌通路」簽一份 240 萬的經銷合約，金額過門檻會到財務長，蘇慧敏一定會問為什麼給這麼好的條件。他請對方把合約拆成「北區經銷合約」「中區經銷合約」「南區經銷合約」三份，各 80 萬，用合約專用章；三份分別由他、何宗翰、林怡君送出（何宗翰是他的下屬，林怡君是同處室同事）。

**系統現在**：`SEAL-TIER` 每張單獨立判定 → 三張都是 `standard`，路徑是主管 → 法務 → 用印，不經財務長。`SEAL-OVERLAP` 只比「同一申請人、同一合約名稱與對象」（附錄 A-6 已承認），三張單名稱不同、申請人也不同，都回 `none`。法務的檢查清單 `declared_matches_file` 只確認「填的金額和這份檔案一致」，每份檔案確實都是 80 萬。

**結果**：240 萬的合約繞過財務長。三張單各自完全合規，沒有任何例外產生。

**涵蓋**：沒涵蓋。`03-pack-seal.md` 附錄 A-6 只記錄了限制，沒有解法；核心的「核決權限表」（validation-cases、A8）沒有累計的概念。

**替代方案**：
- (a) 法務檢查清單加一項「確認沒有拆單」。缺點：靠人自律，法務看不到其他申請人的單，也不知道要找什麼。
- (b) 重複檢查改成不限申請人，只比合約對象。缺點：對象是自由文字（「大昌通路股份有限公司」「大昌通路(股)」），比對不可靠；而且「找到重疊」只是要求填原因，不改變路徑。
- (c) 合約對象改為結構化（統一編號或供應商主檔代碼，自由文字只作顯示）；核心提供宣告式的**累計分級**：「同一合約對象、在 N 天內、同一公司別所有申請單（不分申請人、排除已取消與駁回）的金額合計達門檻，則本單的級別升為重大」，並在簽核畫面列出被累計的其他單；累計觸發時產生一筆「疑似拆單」例外派給流程管理者與稽核。

**最佳解**：(c)。理由：拆單規避核決權限是上市櫃公司內控缺失最常見的型態之一，必須「事前擋得住」，而不是只留痕跡。把它做成核心的宣告能力（D14），付款核決、供應商、採購等其他流程包都能直接使用，符合通用性。累計期間與門檻是參數；放寬屬於 F19 的嚴格設定變更。合約對象結構化會讓申請人多一個選擇動作，但選擇可以從供應商主檔搜尋，比打字還快。

## F07 資料授權拆單：分區、分欄位、分被授權者，合起來等於 L4

**情境**：林怡君想要整份客戶主檔（含姓名、電話、身分證後四碼、消費紀錄）。整張申請會是 L4，要資安長簽。她改成：
1. 用專案「北區客戶流失分析」申請「客戶姓名＋消費紀錄」（L3）；
2. 用 agent `sales-report-bot`（負責人也是她）申請「客戶編號＋電話」（L3）；
3. 兩個月後用 team「業務分析部」申請「客戶編號＋身分證後四碼」（L3）。

每張單都只有 L3 欄位；列條件都不同或被授權者不同，`find_overlaps` 不認為重疊。三份資料用客戶編號一接，就是一份完整的可識別個資檔。

**系統現在**：`classify_tier` 只看單張單的內容；重疊檢查以被授權者為單位。系統不知道三個被授權者背後是同一個自然人。

**結果**：L4 等級的資料組合以三張 L3 單取得，資安長從未看過。

**涵蓋**：沒涵蓋（`packs/data-access/rules.md` 的分級是逐欄位；重疊檢查沒有跨被授權者）。

**替代方案**：
- (a) 每個被授權者只能有一張有效授權，強迫合併。缺點：與續期、部分重疊的設計衝突，也不解決跨被授權者的問題。
- (b) 由資料擁有者宣告「組合規則」（例如「同一主體同時取得 姓名或電話 與 身分證後四碼 → 視為 L4」），判定時把**同一自然人可觸及的所有有效授權**（他是成員或負責人的所有被授權者）加上本單一起評估；組合觸發時本單升為 L4。
- (c) 只在簽核畫面顯示「這位申請人（與被授權者的負責人）目前已經可以看到的資料」，讓簽核人自己判斷。

**最佳解**：(b)，同時做 (c) 的顯示。理由：個資法與資安的實務重點是「可識別的組合」，不是單一欄位；只靠簽核人看清單判斷，對手機上幾秒做決定的簽核人不公平，也不是事前擋得住。組合規則是流程包的資料（由資料擁有者維護、走設定變更），核心只提供「以自然人為單位聚合有效授權」的查詢——這個查詢也正是稽核要的「知悉人員名單」反過來看，一次做兩用。

## F08 MIS 執行時多開欄位，自動驗證只抽測核准的部分

**情境**：李志偉（MIS 工程師）認領一張已核准的單：業務分析部可看「銷售訂單」的 8 個欄位、北區。他在 DC 上設定時多開了「單位成本」欄位（他的朋友蔡佩珊想看毛利），並把列條件寫成北區＋中區。`build_verification_cases` 依核准內容產生測試：8 個核准欄位「查得到」、幾個 L4 欄位與南區「查不到」——全部通過。申請人林怡君確認驗證結果（她也樂見多看到東西）。對帳若用檔案方式，匯出檔也是李志偉自己上傳。

**系統現在**：骨幹的驗證是「依核准內容產生測試案例並執行」（`build_verification_cases`），本質上是抽測，測不到「多給」的部分。D21、A21 的人工獨立驗證只用於沒有 API 的系統。對帳由誰上傳沒有限制。

**結果**：實際權限大於核准；驗證全部通過，留下「已驗證」的證據，反而替越權背書。

**涵蓋**：部分。01-internal-audit #22、02-external-it-audit #14 提過對帳檔由當事人上傳的問題；這裡的新問題是**自動驗證在結構上只能證明「核准的有給」，證明不了「沒核准的沒給」**。

**替代方案**：
- (a) 增加更多「查不到」的測試案例（例如所有非核准欄位都測一遍）。缺點：列條件的空間是無限的，測不完；對沒有 API 的系統做不到。
- (b) 驗證改為「讀回實際設定並與核准內容做完全比對」：執行完成後，由平台（API 方式）或由**執行人以外的人**（檔案方式）取得該被授權者在該系統上的完整權限設定，與 `describe_entitlements` 的核准結果做集合相等比較，多一項就是失敗；原有的查詢測試保留作為第二層。
- (c) 只依賴定期對帳發現。缺點：對帳是週期性的，越權期間資料已經被看了。

**最佳解**：(b)。理由：核准與實際的一致性是稽核「核准的內容和執行的內容是同一份嗎」這題的直接證據，必須是完全比對而不是抽測。讀回設定並比對是 IGA 產品的標準作法，也和 00-spine 第 11 節的對帳共用同一套比對邏輯，不必另寫。執行人與讀回的人必須不同（API 方式由平台讀，自然滿足），這條寫成核心規則 `K-VERIFY-INDEPENDENT`，不能由流程包關閉。

## F09 緊急路徑「用完就收」，收回後不必補簽

**情境**：週五晚上 9 點，李志偉以「正式環境訂單資料異常、需緊急查修」為由，走緊急路徑取得 ERP 正式資料庫的特權帳號 4 小時。他在這 4 小時內匯出了客戶主檔。10 點半他自己按「撤銷」把緊急權限收回，原因寫「已修復」。validation-cases 寫的是「先執行、限時內補簽核與複核，逾期自動收回並列為例外」——他的權限沒有逾期，是自己收回的。

**系統現在**：緊急路徑的細節還沒寫進契約（A8）。如果把「補簽」設計成「還在使用中的緊急權限，要在期限內補簽，否則收回」，那麼提前收回就沒有東西需要補簽。誰可以宣告緊急、一個人一年能用幾次，也沒有規定。

**結果**：緊急路徑成為「免簽核的特權」：只要用完立刻收，就沒有任何人事前或事後審查過。

**涵蓋**：部分。validation-cases「緊急路徑」、D13；01 #9、02 #21 提過緊急變成常態，這裡是「提前收回即可免審」的漏洞。

**替代方案**：
- (a) 緊急權限一律在期限內補簽，不論是否已收回。缺點：補簽人只看得到申請理由，看不到期間做了什麼，補簽淪為形式。
- (b) 緊急路徑改成事前要一位值班主管即時核准（手機 MFA）。缺點：深夜找不到人時會真的耽誤事故處理。
- (c) 宣告緊急時就必須指定一位「見證人」（值班主管或資安值班，可以是事後幾分鐘內在手機上確認，確認前權限仍可生效）；權限結束（不論到期或提前收回）後，**一律產生事後複核工作**，複核人不得是宣告人、見證人或其下屬；複核畫面附上期間的實際活動紀錄（由受管系統回報，例如 DC 的查詢紀錄、特權帳號工作階段紀錄；拿不到時要求執行人上傳並標示「自報」）；同一人在 90 天內緊急使用超過參數次數，自動產生例外給其主管與稽核。

**最佳解**：(c)。理由：緊急路徑的價值在於「不擋」，控制必須全部放在事後，而事後控制唯一有意義的證據就是「期間做了什麼」。複核由「權限結束」觸發而不是由「逾期」觸發，關掉了提前收回的漏洞。見證人的確認不擋權限生效，所以不影響事故處理速度。

## F10 用印時換掉紙本的某幾頁

**情境**：法務核准的合約檔案（`h1`）第 7 頁違約金是 10%。申請人何宗翰把第 7 頁換成 2% 的版本印出來，連同其他頁一起交給印鑑管理人游志明。游志明那天有 14 張單要用印，每張單逐頁核對 40 頁不切實際，他翻了第一頁和簽名頁，勾了 `paper_matches_approved_file`。

**系統現在**：`03-pack-seal.md` 的 `sealing` 關以人工檢查清單「紙本合約和核准版本的合約檔案一致」把關；系統只保證電子檔的雜湊不變，紙本與電子檔之間沒有任何技術連結。

**結果**：核准的是 A，蓋印的是 B；紀錄上卻有一個勾，證明「已核對一致」。

**涵蓋**：部分（有控制點，但完全依賴人工逐頁核對，實務上做不到）。

**替代方案**：
- (a) 要求印鑑管理人逐頁核對並簽名。缺點：做不到就會假勾，控制點只增加形式。
- (b) 用印的紙本必須由**系統從核准版本產生**的「用印版 PDF」列印：每頁頁尾印上單號、頁碼／總頁數、核准版本雜湊的短碼與 QR code；印鑑管理人用手機掃每頁的 QR（或只掃首頁、末頁與騎縫處，其他頁靠頁碼連續），系統確認是同一份核准版本、總頁數相符；用印後上傳掃描檔，存為執行證據。
- (c) 用印後上傳掃描檔，由系統以 OCR 與核准版本比對文字差異。缺點：OCR 的誤差高，結果會變成大量誤報；而且是事後發現。

**最佳解**：(b)，並把用印後的掃描檔上傳列為完成回報的必填（(c) 的掃描檔留作證據，不依賴 OCR 判斷）。理由：要讓「核准的內容和執行的內容是同一份」在紙本世界也成立，唯一可行的方式是讓紙本只能來自系統。頁碼／總頁數加上每頁的核准短碼，讓換頁或插頁一眼可見，印鑑管理人不必讀內容。這是流程包 `build_fulfilment` 的能力（產生用印版），核心只需要提供「依核准版本產生可列印檔」的通用 port，其他需要紙本的流程（例如銀行帳號變更的紙本授權書）也用得到。

## F11 把「平移」或「換一組」偽裝成縮小

**情境**：
1. 陳建宏是某張單的主管關簽核人，申請內容是「區域 in（北、中），2026-12-01 到 2027-05-31」。資料擁有者周文傑核准前，陳建宏用「縮小」把列條件改成「區域 in（南）」，期間改成「2027-01-01 到 2027-06-30」——值的數量變少、期間長度一樣，他宣稱是縮小。
2. 申請人被退回後，把使用情境的「說明」從「季報表」改成「季報表與模型訓練」，同時縮短期間，宣稱只做了縮小，從退回的那一關繼續。

**系統現在**：`K-CHANGE-REDUCE` 與 `K-RETURN` 依賴流程包的 `compare_content`。用印流程包已經嚴謹定義（`03-pack-seal.md` 5.4），但資料授權的 `compare_content` 契約（02）還沒寫。如果實作成「值的個數變少就是縮小」「期間天數變短就是縮小」，上面兩招都會被判為縮小。

**結果**：沒有經過重簽就換成另一組資料、另一段期間，或新增了使用目的。

**涵蓋**：部分（規則有，資料授權的判定語意沒寫；`rules.md` 說「修改使用情境也算擴大」，但沒有說列條件與期間怎麼判定）。

**替代方案**：
- (a) 資料授權的簽核人一律不能修改，只能退回。缺點：違反既定規則③，也讓簽核人為了縮短一週而退回整張單。
- (b) 嚴格的集合包含語意：新版的每一個維度都必須是舊版的子集（欄位集合 ⊆、每個列條件的值集合 ⊆、新期間 ⊆ 舊期間、可否匯出只能由可變不可），任一維度不是子集就是 `expand`；任何文字欄位有差異都是 `expand`；並把 18 組左右的邊界測試（平移、換組、空集合、條件型別改變）寫進契約，比照用印流程包。
- (c) 由簽核人自行勾選「這是縮小」。缺點：等於沒有控制。

**最佳解**：(b)。理由：縮小免簽是讓簽核變快的關鍵，也正因此它是最值得攻擊的地方，只有可證明的子集語意才不會被濫用。「無法判定就是擴大」（`K-CHANGE-EXPAND`）已經在骨幹裡，把它在資料授權契約裡逐維度落實並列出測試即可。另外，簽核畫面的差異顯示（`diff_content`）要能顯示「北、中 → 南」為 `expanded` 加 `removed`，不能只寫「縮小」。

## F12 離職或調職前最後幾天大量放行

**情境**：周文傑 2027 年 6 月 30 日離職，已經拿到新公司的 offer（競爭對手）。6 月最後一週，他以「客戶主檔」資料擁有者身分核准了 9 張他平常會退回或縮小的單，其中 3 張是幫業務處的朋友開「可匯出」。7 月 1 日人資關閉帳號，新的擁有者接手時這些授權已經生效，沒人會回頭看。

**系統現在**：系統沒有「即將離職」的概念；簽核行為的異常（核准率、可匯出比例突然上升）沒有偵測；擁有者異動時不會重新檢視前任最近核准的授權。

**結果**：離職前的放水完全合規，而且責任人已經不在公司。

**涵蓋**：沒涵蓋（`K-OWNER-CONTINUITY` 只處理被授權者負責人離職，不處理簽核人離職前的決定）。

**替代方案**：
- (a) 人資登錄離職日後，該員不得再簽核。缺點：交接期正是需要他簽的時候，會讓流程停住；而且離職日常常最後一週才進系統。
- (b) 角色持有人（資料擁有者、資安長、法務）異動時，系統自動為繼任者產生「交接複查」：列出前任在異動前 30 天（參數）核准的所有仍有效的授權，繼任者逐筆確認保留或撤銷，未確認視同複查逾期（例外）。
- (c) 對每位簽核人做行為基準，偏離過大就告警。缺點：需要歷史資料，第一年沒有基準；誤報多。

**最佳解**：(b)，並在人資提供預定離職日時，於簽核畫面對其他關的簽核人顯示「此簽核人預定於 X 日離任」。理由：交接複查是 access review 的一種，直接用 00-spine 第 11 節的 `access_review_campaign` 實作，不必另做機制；它把「前任的決定」變成「現任的責任」，稽核也能拿到明確的證據。(c) 可以之後加，但不能替代 (b)。

## F13 調職後帶著舊團隊的權限到新單位，形成職責衝突

**情境**：何宗翰 2027 年 1 月從通路業務組（可建立客戶與報價）調到財務部（應收帳款沖銷）。AD 群組由各部門的助理維護，通路業務組的助理拖了兩個月才把他移出群組；團隊「通路業務組」的授權仍然涵蓋他。這兩個月他同時能建立客戶、又能沖銷應收帳款——他用一個假客戶沖掉了一筆呆帳。

**系統現在**：團隊（`principal` type team）成員來源沒有定義（open-questions M6 假設「AD 群組加上 HR 組織樹」）。職責衝突矩陣（validation-cases、A8）是「同一主體不得同時持有互相衝突的授權」，但兩份權限分屬兩個 team，主體不同。

**結果**：個人層級的職責衝突在「團隊」這一層被隱藏。

**涵蓋**：部分（衝突矩陣有規劃，但以被授權者為單位；團隊成員的來源與更新時效沒有定義）。

**替代方案**：
- (a) team 的成員一律由人資組織樹推導（`org_membership` 生效期間），不用 AD 群組。調職生效日就自動移出。缺點：專案型的跨部門團隊無法表達（但那些本來就應該是 project）。
- (b) 保留 AD 群組，但每日比對 AD 群組與人資組織，差異列為例外。
- (c) 職責衝突矩陣的檢查改以**自然人**為單位：把他經由所有 team、project、agent（他是負責人）取得的權限聚合後評估。

**最佳解**：(a) ＋ (c)。理由：team 的定義就是組織單位，以人資的生效日期為準最可靠，也讓調職當天就失效，沒有空窗（舞弊者最喜歡的就是空窗）。衝突檢查以自然人聚合，和 F07 的組合規則共用同一個「自然人可觸及的權限」查詢。人資資料晚到（02 #9）造成的回溯，依生效日期重新評估，並把空窗期間發生的存取列為例外。

## F14 負責人離職的寬限期內，繼續用 agent 的金鑰

**情境**：吳家豪是 agent `ap-recon-bot` 的負責人，2027 年 4 月 15 日離職。`grant.owner_grace_days` 是 14 天，期間授權照常有效。他離職前把 bot 的服務帳號金鑰存到自己的筆電。4 月 16 日到 29 日，他在家裡用這把金鑰繼續查應付帳款資料。主管張美玲第 13 天把負責人改派給邱冠廷，授權延續，金鑰沒有換。

**系統現在**：`K-OWNER-CONTINUITY`：負責人異動給寬限期改派，逾期才撤銷。寬限期內授權維持 `active`；改派之後也沒有要求更換憑證。

**結果**：離職者在寬限期內（甚至改派之後）透過 agent 繼續存取，紀錄上一切合法。

**涵蓋**：部分（規則保證「最終會有人負責」，但沒處理寬限期內的使用與憑證）。

**替代方案**：
- (a) 負責人離職當天立即撤銷所有相關授權。缺點：team 的授權若因主管離職就全斷，整個部門停擺；這正是寬限期存在的原因。
- (b) 依被授權者類型區分：**team、project 維持寬限期**（成員是人，各自有自己的帳號，離職者本人的帳號已被停用）；**agent 與服務帳號在負責人離職當天自動暫停**（`suspended`，判定介面回拒絕），改派完成且新負責人確認「憑證已更換」（受管系統回報新的憑證識別碼或輪替時間）後才恢復。
- (c) 寬限期內照常有效，但記錄所有存取。缺點：只是留痕跡。

**最佳解**：(b)。理由：非人類主體的憑證是可以被帶走的，負責人離職是憑證外洩風險最高的時刻；暫停 agent 對業務的影響遠小於暫停整個團隊。憑證輪替的證據由受管系統回報，平台只存「已輪替」的事實與時間，不存憑證本身（符合 D20）。授權狀態需要新增 `suspended`（骨幹第 4 節目前只有 `active`、`expired`、`revoked`），判定介面要把它當成拒絕。

## F15 批次核准夾帶：內容無差異，但被授權者成員或資料分級已經變了

**情境**：2027 年 5 月是續期高峰，周文傑的待簽清單有 37 張續期單，全部顯示「與前案無差異」，他在電腦上一次全選核准（T8，3 步）。其中一張是專案「北區客戶流失分析」的續期：前案核准時專案有 3 位成員，現在是 26 位（林怡君陸續加人，見 F21）；另一張的「身分證後四碼」欄位，資料目錄在 3 月已由 L3 改為 L4，但前案的級別是 L3。

**系統現在**：`K-BATCH`、D3：只有「與來源單無差異」的續期可以批次核准。「無差異」只比較申請內容（`compare_content`），不比較情境：被授權者成員數、資料分級、負責人、對帳發現、未結案例外。

**結果**：實質上擴大很多的續期，以「無差異」之名混在批次裡被放行；而且因為分級已改，本該多走資安長一關也被跳過。

**涵蓋**：部分（批次的範圍已限縮，但「差異」的定義只有內容）。

**替代方案**：
- (a) 取消批次核准。缺點：續期高峰時簽核人會逐張快速點過，結果更差；D3 已經判斷批次值得保留。
- (b) 批次資格除了內容無差異，還要**情境無差異**：依目前規則重新判定的級別與前案相同、被授權者成員增減不超過參數（例如 20% 或 5 人）、負責人相同、該授權沒有未結案的對帳差異或例外、資料分級沒變；任一項不符就踢出批次，並在畫面上寫明原因（例如「成員從 3 人變 26 人」）。
- (c) 允許批次，但在批次畫面顯示情境差異讓簽核人自己決定。缺點：37 張全選時沒有人會看。

**最佳解**：(b)。理由：簽核人做決定時真正在乎的是「誰能看、看什麼、風險等級」，內容 JSON 相同不代表這些相同。情境資料系統本來就有，把它變成批次的資格條件，是「事前擋得住」而不是「留給人判斷」。踢出批次的單仍然可以單張快速核准，簽核人的速度損失只發生在真的有變化的單上——正是應該慢下來的地方。

## F16 被駁回後換個名字重送，等別人認領；或挑主管請假時送審讓它升級

**情境**：
1. 何宗翰的用印單被葉佳蓉駁回（條款不利）。他隔天把合約名稱從「北區經銷合約」改成「北區通路合作協議」，重送。法務是群組認領，這次被簡志豪認領——簡志豪不知道這份合約上週被駁回過，核准。
2. 林怡君知道陳建宏下週二到週五出差、不會看手機，週一晚上送單。3 個工作天後催辦、再 2 個工作天升級給方國華；方國華手上一堆被升級的單，平均每張看 20 秒。

**系統現在**：骨幹第 4 節的申請單狀態沒有「駁回」（D16 新增了動作，狀態機還沒更新），若實作成 `cancelled`，`SEAL-OVERLAP` 的比對條件「排除草稿與已取消」會把被駁回的單排除；而且比對要求申請人、名稱、對象三者相同。升級時，升級對象看不到「原簽核人在休假」與「申請時點」。

**結果**：駁回沒有約束力，只要換個說法、換個時間，就能換到願意核准的人。

**涵蓋**：沒涵蓋（D16 的「駁回」缺狀態與後續規則；`03-pack-seal.md` 5.7 的排除條件）。

**替代方案**：
- (a) 被駁回的申請人在 N 天內不能送同類型的申請。缺點：誤傷正常的修正重送，也擋不住換申請人。
- (b) 新增狀態 `rejected`（終局、不可重開），重複檢查把它視為「有效的前案」；重送時若找到被駁回的前案（以結構化的合約對象、或資料授權的被授權者＋資料範圍比對），**強制連結前案**，駁回意見顯示在新單每一關的簽核畫面頂端，並且原駁回人自動被列為該關的必經簽核人之一（若他仍在職且有資格）。
- (c) 只顯示「此申請人近期有被駁回的單」。缺點：資訊太模糊。

**最佳解**：(b)。對升級的部分另外處理：升級畫面顯示「原簽核人狀態（休假／出差／無回應）」與「送審時原簽核人已知不在」（依代理與行事曆資料）；若送審時原簽核人已設定不在且沒有代理，系統應在送審當下就提示申請人並直接改走代理或上一層，而不是讓單子空等 5 天後以「逾時升級」的形式抵達（逾時升級本身是一個負面訊號，不應被當成路徑）。理由：駁回與退回的差別就在於駁回是有效的判斷，必須在後續被看見；讓原駁回人重新參與，是讓「換人簽」失效的最直接方式。

## F17 釣到密碼後在電腦上簽，或對手機狂推 MFA

**情境**：
1. 業務專員何宗翰在會議室偷看到劉俊傑（他的主管）輸入密碼。之後他在自己的電腦上以劉俊傑登入（公司 SSO 在內網不要求 MFA），把自己送的 L3 單核准。
2. 林怡君拿到陳建宏的密碼（他把密碼寫在便利貼上），在深夜用手機登入陳建宏的帳號、對 7 張單按核准，每一張都觸發推播 MFA。陳建宏半夜被吵醒，以為是系統故障，按了「允許」。

**系統現在**：`K-MOBILE-MFA` 只要求「用手機」做決定時 MFA；電腦端沒有要求。MFA 的形式（推播、數字比對、一次性碼）沒有規定。

**結果**：簽核的「不可否認性」只建立在密碼上；或者 MFA 被疲勞轟炸繞過。

**涵蓋**：部分（02 #19 已從稽核角度指出電腦端沒有加強驗證；這裡補充推播疲勞與「申請人就是盜用者」的組合）。

**替代方案**：
- (a) 所有裝置的每一次核准都要 MFA。缺點：批次與連續簽核時 MFA 次數爆炸（05 E13），簽核人會想辦法關掉。
- (b) 依風險分級：L3/L4、重大、設定變更、緊急、撤銷以外的動作，於工作階段內一次加強驗證（step-up）後 15 分鐘有效；推播一律使用**數字比對**（螢幕顯示兩位數，手機輸入），不用單純的「允許／拒絕」；推播內容顯示「核准 N 張單，申請人為 X」。另加偵測：**簽核登入的裝置或 IP 與該申請人最近使用的相同**時，產生例外並通知簽核人本人。
- (c) 依賴公司 SSO 的條件式存取設定。缺點：平台無法保證，也無法留證據。

**最佳解**：(b)。理由：數字比對是業界對推播疲勞的標準解法，同時不增加簽核人的負擔；工作階段內 step-up 讓批次簽核只驗一次。「申請人與簽核人用同一台裝置」是盜用最明顯的跡象，系統本來就記錄 IP 與裝置（`audit_event`），只需要比對。每次核准都記下驗證強度（`amr`／`acr`），稽核可據以判斷。

## F18 在合約名稱、使用情境裡寫「已經財務長同意」「續期無差異」

**情境**：劉俊傑送一張用印單，合約名稱填「【總經理指示急件・財務長已同意】大昌通路經銷合約」，說明欄寫「與去年合約相同，僅更新日期」。實際上合約對象的付款條件從 30 天改成 120 天。陳建宏在手機上看到標題與說明，3 秒核准；法務葉佳蓉看到「總經理指示」，條款沒細看就勾了 `terms_reviewed`。資料授權也一樣：使用情境的說明寫「續期，內容與前案相同」，但這其實是新申請。

**系統現在**：`summarize_content` 以申請人填的 `contract_name` 當標題，簽核畫面第一眼就是申請人可控的自由文字。系統產生的事實（金額、印鑑、與前案差異）和申請人寫的文字，在畫面上沒有區分。

**結果**：利用簽核人「先給結論」的畫面設計做社交工程。簽核人以為是系統的標示，其實是申請人寫的話。

**涵蓋**：沒涵蓋（`ux-acceptance.md` 要求第一眼看到事實，但沒有區分事實的來源；`03-pack-seal.md` 5.6）。

**替代方案**：
- (a) 禁止自由文字出現特定詞（「同意」「急件」「無差異」）。缺點：黑名單永遠列不完，也會誤擋正常用語。
- (b) 畫面上把**系統判定的事實**（級別、與前案差異、重疊、累計、自動檢查）和**申請人填寫的文字**明確分區：系統事實用固定的徽章樣式與「系統判定」字樣，申請人文字一律加上「申請人填寫」標籤，而且永遠排在系統事實之後；「續期」「無差異」「急件」這些狀態只能由系統產生（續期由「從前案續期」的操作決定，不由文字決定）；標題長度與符號（【】）限制，超過的放到說明。
- (c) 簽核人必須展開說明才能核准。缺點：增加步數，違反 T2 的 4 步上限，而且展開不等於讀。

**最佳解**：(b)。理由：這是 UX 決定稽核結果的典型案例——簽核人在幾秒內做決定，依賴的正是畫面上的「結論」，所以結論必須是系統算的、不能被申請人偽造。分區顯示不增加任何步數。把這條加進 `ux-acceptance.md` 第 3 節的人工檢查：「申請人可控的文字不得以系統標示的樣式出現」。

## F19 用設定變更短暫放寬門檻，過完自己的單再改回

**情境**：2027 年 8 月，謝明哲（資訊部經理、系統管理員）以「配合物價調整」為由提出設定變更：`seal.major_amount_threshold` 從 100 萬改為 300 萬，影響試算顯示「過去 90 天有 4 張單會從重大改為一般」。核准人是他的下屬林冠宇（D12 只要求「提出人以外的人」）。生效後的 3 天內，他的部門送了一張 250 萬的系統維護合約，走一般路徑通過。第 4 天，他再送一張設定變更改回 100 萬，理由是「財務長意見：維持原門檻」，同樣由林冠宇核准。

如果流程管理已依 A20 委派給業務單位，同樣的手法也可以由業務處的流程管理者對業務相關流程使用。

**系統現在**：D12：設定變更走簽核、雙人覆核、有版本與試算、可回復。沒有規定覆核人的資格（不能是下屬？要不要是控制的負責人？）、沒有區分「放寬」與「收緊」、沒有偵測「改了又改回」。

**結果**：控制被合法地短暫關掉。每一張設定變更單都合規，那張 250 萬的用印單也合規（用的是送審當時的門檻）。

**涵蓋**：部分（D12、A10 的方向正確，但覆核人資格與放寬的處理沒有規定；02 #5、#6 從會計師角度提過參數能關掉控制）。

**替代方案**：
- (a) 控制相關的參數完全不可在畫面上改，只能升版。缺點：退回 D8 的舊判斷，D12 已經說明這是錯的。
- (b) 每個參數在定義時標示**控制方向**（調高門檻、延長期限、關閉偵測＝放寬）與**控制負責人**（例如用印門檻 → 財務長；資料授權上限 → 資安長）。放寬的變更必須由控制負責人核准，且覆核人不得在提出人的上下屬鏈中；放寬生效時通知稽核角色。收緊的變更維持雙人覆核即可。設定在 N 天內（參數，預設 90 天）被改回、或同一參數一年內改超過 2 次，自動產生例外；**放寬期間內依新設定判定、而在舊設定下會更嚴的申請單**自動列成清單附在例外上。
- (c) 所有設定變更都要稽核核准。缺點：稽核不應成為控制的執行者（01 #15），會破壞獨立性。

**最佳解**：(b)。理由：稽核看的是「改控制的人有沒有利益衝突、改的期間有沒有人得利」，(b) 把這兩件事都變成系統事實。放寬與收緊的不對稱處理，讓日常的收緊不受拖累。控制方向與負責人是 `setting_definition` 的兩個新欄位，流程包定義參數時一併宣告，客戶新增的參數沒有宣告時預設視為「放寬敏感」。

## F20 系統管理員改主管關係或手動維護組織資料，決定誰來簽

**情境**：林怡君的主管陳建宏對她的申請很嚴格。謝明哲（系統管理員，與林怡君熟識）在平台的人員管理畫面，把林怡君的 `reporting_line` 暫時改成「直屬主管：周文傑」，理由寫「矩陣組織專案期間」。她送的單第一關變成周文傑，周文傑核准。兩週後再改回。人資系統裡林怡君的主管從頭到尾都是陳建宏。

另一種：謝明哲把某位已離職主管的 `person.status` 改回在職一天，用他的名義讓一張單「依原路徑」完成（搭配 F03 的回溯代理）。

**系統現在**：骨幹定義了 `person`、`org_membership`、`reporting_line` 的資料表，來源是可替換的介面（LDAP／HR）。平台內能不能手動修改、誰能改、改了要不要簽核，沒有規定。D12 把流程、路徑、參數、角色指派列入設定變更，**沒有列入組織與主管關係**。

**結果**：路徑是固定的，但「誰是主管」可以被改，等於可以挑簽核人。resolver 沒有記錄當時解析依據的主管關係版本，事後很難發現。

**涵蓋**：沒涵蓋。

**替代方案**：
- (a) 組織資料只能由同步介面寫入，平台內完全不能改。缺點：人資資料常常晚到或錯誤（矩陣組織、兼任、代理主管），完全不能改會讓單子卡住，管理員就會到資料庫直接改，更糟。
- (b) 組織資料以人資來源為準；平台內的手動覆寫是一張「組織資料覆寫申請單」，由人資角色核准（提出人不得是當事人或其上下屬鏈），有生效與到期時間（預設最長 30 天），到期自動回到來源值；每日比對平台的有效值與人資來源，差異列為例外。
- (c) 允許手動改但留紀錄。缺點：只留痕跡。

**最佳解**：(b)，另外 `case_task` 記下 resolver 解析時使用的主管關係與其來源（「人資同步 2027-03-02」或「覆寫單 #123」），讓稽核從任何一張單都能追到「為什麼是這個人簽」。理由：resolver 的輸入如果能被單方修改，職責分離就失去意義。把組織覆寫納入簽核，和 D12「平台用自己的簽核能力管自己」的精神一致；人資是組織資料的業務擁有者（D19 的邏輯），由人資核准最合理。

## F21 授權核准後，往專案（被授權者）裡加人

**情境**：林怡君建立專案「北區客戶流失分析」（負責人：自己，結束日 2027-06-30），成員只有她和王志明。L4 客戶資料的授權經過主管、資料擁有者、資安長核准後生效。之後兩個月，她陸續把業務處 8 位同事、行銷外包公司的 2 位人員（以外部帳號）加入專案成員。他們全部取得了 L4 客戶資料的存取，沒有任何人簽核。

**系統現在**：`principal_member` 存在，但成員的增減不屬於任何流程；`rules.md`：「專案任何人都可以在本站建立……專案本身不帶任何權限。」授權給的是專案，所以成員一加入就繼承了全部授權。

**結果**：簽核只審了「給這個專案」，沒有審「這個專案有誰」。被授權者成了權限的轉運站。

**涵蓋**：沒涵蓋（這是資料授權流程「不直接授權給個人」設計的反面；稽核問「誰能看 L4 客戶資料」，答案取決於一個沒有控制的名單）。

**替代方案**：
- (a) 每次加成員都走完整的資料授權路徑。缺點：太重，專案開始時加十個人就要十張單。
- (b) 成員的增加視為授權的**擴大**：被授權者持有 L3/L4 有效授權時，加入成員要由該授權的資料擁有者核准（每個資料擁有者一關，並行；L4 加資安長）；一次可以加多人；新成員的主管會收到通知。移除成員不需核准（縮小）。外部人員（A18）加入時必須有內部保證人，且不得超過保證期間。
- (c) 授權直接帶成員名單（核准時的名單凍結），名單外的人不繼承。缺點：成員異動就要重送整張單，而且跟 team 的動態性衝突。

**最佳解**：(b)。對 team（由人資組織樹推導，見 F13）不適用，因為成員由組織異動決定，組織異動本身已有人資流程；對 project 與 agent 的「使用者」（見 F22）適用。理由：這符合既有的原則③「擴大就重簽」——成員增加就是可存取的人變多，是擴大；只是簽核的對象縮到「加了誰」，簽核人在手機上看名單幾秒就能決定。

## F22 把 agent 當成資料的轉運站，讓沒授權的人間接取得資料

**情境**：林怡君是 `sales-report-bot` 的負責人，這個 agent 有銷售訂單與客戶主檔的 L3 授權。她把 bot 接到公司的聊天群組「業務處全體」（120 人），任何人在群組裡打「查某客戶近一年訂單」，bot 就回傳結果。行銷部的人沒有任何授權，卻透過 bot 每天查客戶資料。

**系統現在**：骨幹與 `rules.md` 對 agent 的要求只有「必須有一位負責人」。agent 對誰提供服務、輸出流向哪裡，不在申請內容裡。`rules.md` 寫「申請單不記錄媒介……前提是所有存取管道都經過 DC」，但 agent 拿到資料後轉給誰，DC 不知道。

**結果**：一張 agent 的授權等於對「所有能對 agent 下指令的人」授權，而簽核人以為只是給一個自動化程式。

**涵蓋**：部分（validation-cases 有 AI agent 情境，著重負責人；沒有處理 agent 的使用者範圍）。

**替代方案**：
- (a) agent 只能輸出給負責人本人。缺點：不符合實際用途，大多數 agent 本來就是給團隊用的。
- (b) agent 的申請內容必須宣告**使用對象**（一個 team 或 project，或「僅負責人」），使用對象視同被授權者的成員：簽核畫面顯示「實際能取得資料的人數」，F21 的成員擴大規則一體適用；職責分離 `K-SOD-BENEFICIARY`（F02）也看使用對象。判定介面（`check`）在 agent 代表某位使用者查詢時，要求傳入使用者身分，平台依「使用對象」判定，並記錄（on-behalf-of）。
- (c) 只要求負責人簽一份使用切結。缺點：沒有控制力。

**最佳解**：(b)。理由：agent 是平台明列要管、而現有工具多半沒管到的新興需求（validation-cases），這正是市場缺口；它的風險核心是「代誰查」。以 on-behalf-of 的方式讓判定介面知道最終使用者，是 OAuth 2.0 token exchange 等公開標準已有的作法，符合 00-spine 第 11 節「盡量採用公開標準」。平台無法保證 agent 自己的程式不轉送資料（D10 的界線），但可以讓「宣告的使用對象」成為簽核內容並與對帳比對。

## F23 「用完就撤」：拿到 L4、匯出後自己撤銷，躲過定期複查

**情境**：蔡佩珊用專案「季度業績看板」申請了一份 L4 的成本明細，可匯出，期間 3 個月，理由寫得很漂亮，順利核准。生效第二天她匯出全部資料，第三天以「需求取消」為由自己撤銷（`K-REVOKE` 允許申請人直接撤銷，只要填原因）。季度的定期複查只列「目前有效的授權」，她的那筆已經不在了。半年後她離職到競爭對手。

**系統現在**：`K-REVOKE` 讓撤銷不需簽核（正確，因為是縮小）。定期複查（`access_review_campaign`）的範圍沒有定義；直觀的實作是「目前有效的授權」。查詢紀錄（A4）只記錄「看申請單」，不記錄「用授權存取資料」。

**結果**：最危險的短期高權限，正好躲過最常見的檢查；撤銷讓它看起來像「申請人很自律」。

**涵蓋**：部分（「知悉人員名單」由授權查詢提供，理論上包含已撤銷的；但複查範圍與使用紀錄沒有定義）。

**替代方案**：
- (a) 禁止申請人自行撤銷 L4。缺點：違反原則③，而且鼓勵大家不撤銷，讓權限掛著更糟。
- (b) 定期複查與知悉人員名單的範圍都是「期間內**任何時點**有效的授權」，不只是現存的；並增加一類自動例外：L4 且可匯出的授權在生效後 N 天內（參數，預設 7 天）被撤銷或縮小，或受管系統回報的實際使用量在短期內異常集中（例如匯出量），列給資料擁有者確認。受管系統能回報使用紀錄時，平台把它附在授權的證據頁（只存統計與事件，不存資料本身）。
- (c) 撤銷時要求上傳「資料已刪除」的切結。缺點：自我聲明，沒有驗證力。

**最佳解**：(b)。理由：稽核問「這段期間誰拿得到這份資料」，答案必須包含已撤銷的人；這也是財報公告前「知悉人員名單」的法遵要求（validation-cases 財會領域）。短期撤銷本身不是錯，但「拿到可匯出的 L4 後馬上撤」是極少見的正常行為，值得讓資料擁有者看一眼。

## F24 MIS 群組成員認領機密單偷看，再放回群組

**情境**：林冠宇（MIS 工程師）對一張人資的機密單（某主管的薪資調整查詢授權）很好奇。A3 規定 MIS 群組「未認領前只看得到必要資訊」，他就按「認領」，看完內容與附件後按「放回群組」（或等它被重新指派），再由李志偉認領執行。

**系統現在**：`K-CLAIM` 只規定認領人不得在前面的關卡簽過這張單；認領的條件、能否放回、放回要不要原因、認領後看得到哪些內容，都沒有規定。A3、A4 規定了保密與查閱紀錄，但「認領」本身就是取得查閱資格的正當方式。

**結果**：群組認領變成閱覽機密內容的後門；查閱紀錄上他是「認領人」，有正當理由。

**涵蓋**：沒涵蓋（`K-CLAIM` 與 A3 的交集）。

**替代方案**：
- (a) 認領後不能放回。缺點：真的認領錯或臨時請假時，單子會卡住。
- (b) 執行人（認領者）只看得到 `build_fulfilment` 產生的執行內容（要設定的規則），看不到申請理由、使用情境說明與附件；機密欄位（A19）只在執行內容確實需要時解密給他。放回群組要填原因，放回事件連同「認領期間檢視了哪些內容」一起寫入紀錄；同一人對機密單「認領後放回」的次數超過參數，產生例外給資安與稽核。
- (c) 機密單改為指派給特定執行人，不走群組認領。缺點：單一執行人請假時沒有備援；而且違背 D19「依受管系統指派管理人」的彈性。

**最佳解**：(b)。理由：最小權限原則——執行人需要知道「要設定什麼」，不需要知道「為什麼要」與「誰的薪資」。這同時也減少 MIS 看到人資資料的機會，符合 D20 的方向。放回有原因、次數有偵測，讓「為了看而認領」變成會被看見的行為。

## F25 集團多公司：挑門檻較寬、簽核人較少的公司別送單

**情境**：集團母公司的用印重大門檻是 100 萬，子公司（同一套平台）是 300 萬，子公司的財務長由母公司財務部的張美玲兼任。母公司業務處的劉俊傑想用印一份 250 萬的合約，對象同時與母公司和子公司都有往來。他把申請的「公司別」選成子公司——他在子公司也有一個兼任的業務角色——路徑變成一般級別。

**系統現在**：D15 決定「公司別是核心的一個維度，流程、路徑、參數……都可以依公司別區分；跨公司的申請與簽核要能表達」。申請單的公司別由誰決定（申請人自選？由申請人的主要任職公司決定？由合約或資料的歸屬決定？）沒有規定。

**結果**：申請人可以挑選對自己最有利的規則集合，所有規則都正確執行，結果卻是錯的。

**涵蓋**：沒涵蓋（D15、A12 只有方向）。

**替代方案**：
- (a) 公司別一律等於申請人的主要任職公司。缺點：兼任者確實會替子公司送單；資料授權的資料可能屬於另一家公司。
- (b) 公司別由**內容的歸屬**決定，而不是由申請人選：用印依「簽約主體」（結構化的公司別欄位，由法務在檢查清單中確認與合約一致）、資料授權依「受管系統或資料目錄的所屬公司」；申請人只能選他有任職或兼任的公司，且選擇不同於主要任職公司時要填理由並顯示在簽核畫面上。跨公司（簽約主體與申請人所屬公司不同、或資料屬於另一家公司）時，**兩家公司的路徑取較嚴者**，並各自需要該公司的必要關卡（例如資料擁有者）。
- (c) 跨公司的單一律送集團總部再審一次。缺點：多一關，且不是所有跨公司情境都需要總部。

**最佳解**：(b)。理由：規則集合必須由「這件事屬於誰」決定，而不是由「誰來申請」決定，否則任何多公司兼任者都能挑規則；取較嚴者是「一律從嚴」原則（`rules.md` 原則①）在多公司下的自然延伸。簽約主體寫進合約條款，法務本來就要核對，不增加額外工作。

## 對決策紀錄的意見

從舞弊者的角度逐筆檢查 D1–D24。只列有意見的；D1、D2、D5、D6、D7、D8、D9、D11、D17、D18、D22、D23、D24 屬於產品或開發方式的決定，從這個立場看沒有可利用之處。

| 決定 | 意見 | 對應情境 |
|---|---|---|
| D3 批次核准限無差異的續期 | 方向正確，但「無差異」只比內容；被授權者成員、資料分級、負責人、未結案例外的變化都能混進批次。應把情境差異納入批次資格 | F15 |
| D4 並行做成路徑的能力 | 並行時各關卡同時看到單，沒有彼此的意見；共謀者可以約好同時核准。並行本身沒錯，但 `K-PARALLEL-ALL` 之後應讓最後一關看得到其他並行關的意見與核准時間（幾秒內全部核准是訊號） | F01 |
| D10 系統管不到的用例外浮現 | 同意，但目前定義的例外種類（逾期、未複查、對帳差異、負責人離職）都是「被動」的；缺少「行為型」例外（互惠核准、拆單、改了又改回、用完就撤、認領後放回）。舞弊者最在意的正是這一類 | F01、F06、F19、F23、F24 |
| D12 設定變更走簽核 | 雙人覆核沒有限制覆核人資格（下屬可以核准主管的放寬）；沒有區分放寬與收緊；沒有偵測短期改回；組織資料與代理不在範圍內 | F19、F20、F03 |
| D13 五種流程與緊急路徑 | 緊急路徑若以「逾期收回」觸發補簽，提前收回就免審。事後複核應由「權限結束」觸發，並附期間活動紀錄 | F09 |
| D14 宣告優先 | 宣告式的分級只看單張單；需要加上「累計分級」與「組合規則」兩種宣告，才擋得住拆單 | F06、F07 |
| D15 集團多公司 | 公司別若由申請人選，等於讓申請人挑規則。應由內容歸屬決定，跨公司取較嚴者 | F25 |
| D16 補齊簽核動作 | 五個新動作都是可攻擊面：駁回沒有狀態、重送不連結；轉簽「有資格」沒定義；加簽沒限制對象、會打開機密內容；撤回沒問題。建議每個動作都在 01-kernel 寫明「對象資格、可見範圍、次數上限、紀錄內容」四項 | F04、F05、F16 |
| D19 每個受管系統有自己的管理人 | 業務單位與廠商的管理人通常同時負責執行與回報；人工整合時「執行」與「驗證」容易是同一批人。應把 `K-VERIFY-INDEPENDENT` 做成核心規則，不能由流程包或受管系統設定關閉 | F08 |
| D20 平台管理角色分離 | 方向正確。補充：群組認領的執行人也應只看執行內容，不看申請理由與附件，否則認領就是閱覽後門 | F24 |
| D21 檔案與人工整合 | 對帳檔與讀回設定不得由執行人提供，這條要寫成規則，不是建議 | F08 |

## 骨幹層級需要的新增（彙整）

| 項目 | 內容 | 對應情境 |
|---|---|---|
| `K-SOD-BENEFICIARY` | 被授權者的負責人與成員（含 agent 的使用對象）比照申請人，不得簽核 | F02、F22 |
| `K-VERIFY-INDEPENDENT` | 執行結果的讀回與比對不得由執行人提供；比對為集合相等 | F08 |
| 代理規則 | 本人或直屬主管設定、不得回溯、單一持有人角色只能代理給事先登記的名單、不得代理給下屬鏈 | F03 |

| `rejected` 狀態 | 駁回為終局狀態；重送強制連結前案、原駁回人重新參與 | F16 |
