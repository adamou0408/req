## 一、證據與紀錄完整性

### RA-01 外部錨定與整條重算／截尾

- **問題**：持有 `sgn_owner` 或 PostgreSQL superuser 的人可以停用 trigger、刪除後段事件並重算之後全部雜湊，或從備份還原截掉尾端；鏈仍「驗證通過」。（01-2、02-2、03-12、07-4、07-14、10-P15、12-B23）
- **對稽核過關的影響**：會計師會判定雜湊鏈「只防外行人」，「紀錄改不掉」不成立；訴訟中對方可主張紀錄是事後製作（10-P15）。
- **各立場的解法**：
  - 定期產生檢查點（最後序號、鏈頭雜湊、筆數、時間），寫回鏈上，並推送到平台維運與 DBA 都改不了的外部位置：SIEM／syslog、WORM 物件鎖定儲存、RFC 3161 時戳服務、每日 email 給稽核室（01-2、02-2）。
  - 錨點本身串成鏈；驗證工具除內部一致外要比對外部錨點，序號減少、鏈頭不符、錨點中斷列為最高等級例外（02-2）。稽核可下載歷次檢查點自行保存，驗證時拿自己保存的檢查點對照（01-2）。
  - 未設定外部錨定位置時，稽核準備度顯示為未結案例外（01-2）。
  - 月封存的檢查點加 RFC 3161 時戳（07-4、07-14）；每日把鏈頭交給外部時戳服務並把回執存入鏈中（10-P15）；每個決定事件以平台金鑰簽章並定期取得時戳（12-B23）。
  - **衝突**：錨定頻率——01-2「每日（最長 24 小時）」、02-2「例如每小時」、10-P15「每天」。外部位置——01-2「三選一或多選」，02-2「至少兩處、由不同單位控制」。RFC 3161——01-2、02-2 列為選配（地端常不允許外連），10-P15、12-B23 列為每日必做。
- **相關**：K-AUDIT-CHAIN、platform-vision「雜湊鏈可由第三方驗證」、A2；與 RA-05（還原）、RA-12（多公司鏈）相依。

### RA-02 雜湊的可重算性與長期驗證

- **問題**：`jsonb` 的鍵序、數字格式、時間精度在匯出時與雜湊時不同，第三方算不出相同雜湊；PostgreSQL 大版本升級後平台自己也驗不過。換系統後十年保存期的證據無法離開平台驗證。（02-12、01-2、12-B14、07-17）
- **對稽核過關的影響**：第三方無法重算，「可由第三方驗證」不成立；升級造成的驗證失敗在稽核眼中與竄改無法區分；退場時客戶被迫續約舊平台。
- **各立場的解法**：
  - 每筆事件保存「被雜湊的那串 bytes」（RFC 8785 JCS 正規化），驗證只需 bytes 與 SHA-256；雜湊演算法帶版本（02-12）。
  - 公開演算法文件與測試向量，附不依賴平台程式碼、可離線執行的獨立驗證腳本（01-2、02-12），開源（12-B14）。
  - 完整匯出格式：每類資料一個 JSON Lines 檔、附件原檔、清單檔（筆數與 SHA-256），整包簽章並附時戳；唯讀封存模式，授權到期不影響查詢與驗證（12-B14）。
  - 判斷邏輯也要可重現：事件記下 hook 或宣告規則的版本與雜湊，舊版原始碼依發行版封存並提供離線重現工具（07-17，另見 RA-08）。
- **相關**：K-AUDIT-CHAIN、A2；12-B14 的匯出格式與 RA-09（保存）、RA-11（金鑰交付）相依。

### RA-03 繞過 `api` 的直接改庫

- **問題**：DBA 依口頭要求直接 `update sgn.grant set valid_to = …`、或用 `psql` 改 `setting_value`；業務表與稽核事件不一致，`check` 依業務表繼續回「允許」。（02-3、01-13、02-2、03-12、11-7）
- **對稽核過關的影響**：會計師以事件重建狀態與畫面對照，抽到一張不一致就擴大樣本並判定「資料修正」程序無效；設定變更母體也不完整（RA-33）。
- **各立場的解法**：
  - 每日一致性檢查：由事件重播出應有狀態與業務表比對；每列帶「最後一筆事件序號＋列內容雜湊」，全量比對可行；結果寫事件並進稽核準備度（02-3）。
  - 資料庫層記錄：`pgaudit` 或 event trigger 記錄所有非 `sgn_owner` 升版、非 `sgn_app` 的 DDL／DML，以及 `session_replication_role` 變更、停用 trigger，送到外部（01-13、02-2、02-3、03-12）。
  - 設定指紋：控制相關資料表每日計算雜湊，與最後一筆核准設定變更後的預期雜湊比對（01-13）。
  - 提供正式的「資料修正申請」，讓 DBA 沒有理由直接改（02-3，詳 RA-04）。
  - 02-3 明確不採用「完全事件溯源」與「業務表加 trigger」兩種做法。
- **相關**：K-AUDIT-APPEND 只保護稽核表；D20 處理「看不到」未處理「改不了」（02 對 D20 的意見）。

### RA-04 錯誤狀態的正式更正

- **問題**：bug 讓 27 張 L4 單少走資安長關、印鑑管理人誤按「用印完成」、參數生效時間設錯一天；只增不改的設計下沒有正式更正途徑，實務上只剩直接改庫。（07-11、02-3、11-19）
- **對稽核過關的影響**：錯誤一直留著（少簽一關的授權繼續有效），或被默默修掉且修正本身沒有核准紀錄。
- **各立場的解法**：
  - 核心新增「資料更正申請單」：說明錯誤、影響的單、依據（bug 編號或誤操作事件），選擇核心內建且有測試的更正動作（重新開啟缺漏關卡並視需要暫停授權、撤銷錯誤的完成標記、依正確參數縮短有效期間），流程包可登記專屬更正；更正是新事件並引用原事件序號（07-11）。
  - 未知類型的更正包裝成更正 migration，隨發行版走程式變更上線（07-11）。
  - 規則錯誤造成的大量影響，走「控制瑕疵修正」（11-19，詳 RA-36）。
  - **衝突**：核准人——02-3「資料擁有者與另一位非執行人」；07-11「流程管理與另一位未參與者，稽核收到通知但不簽」。
- **相關**：D12 只管設定不管資料更正；與 RA-03、RA-36、RA-43（更正列為例外類別）相關。

### RA-05 備份還原、主備切換與還原副本

- **問題**：(1) 從凌晨備份還原，上午的核准與撤銷消失，DC 上卻已套用；鏈只是少了尾巴，驗證通過。(2) 非同步異地切換遺失最後幾筆。(3) 還原演練或複製到測試環境的副本，排程補跑對真人寄信、對正式 DC 撤銷權限，事件寫在副本的鏈上。(4) 測試環境的證據頁被拿去冒充正式證據。（01-3、02-2、07-2、12-B04、03-20、10-P14）
- **對稽核過關的影響**：「遺失而不自知」；執行系統上有找不到核准的權限；外部系統狀態與正式平台對不上；還原演練沒有可用證據。
- **各立場的解法**：
  - WAL 連續歸檔與即時複寫降低遺失（01-3）。
  - 啟動時比對本機最大序號與外部最後見到的序號（檢查點、outbox 接收端），落後就進入唯讀「還原待處理」並產生例外；重建事件標示「還原重建」並帶原始時間與重建人；立即對所有受管系統對帳（01-3）。
  - 還原或切換後第一筆事件必須是「已從 X 時點還原／切換，遺失序號 N–M」，不重算、不偽裝連續，列為例外由稽核室結案（02-2、12-B04）。
  - 環境身分：安裝時產生環境識別碼寫入資料庫並與部署設定綁定；不一致時進入隔離模式（排程不跑、outbox 不送、對外寫入 adapter 改接「記錄不送出」）；副本正式接手需技術維運與流程管理各一人確認；一鍵產出還原演練報告（RTO、RPO、鏈驗證、與外部檢查點比對）（07-2）。
  - 環境 id 寫入鏈的起點與每頁證據頁，測試環境的鏈不能匯入正式環境，畫面加「測試環境」浮水印；正式環境啟動時環境 id 不符則拒絕啟動（03-20）。去識別化複製工具產生的副本鏈標為「測試鏈」（10-P14）。
  - 一主多備的參考架構、排程以 advisory lock 選單一執行者、切換後自動做外部狀態對帳、提供演練腳本並把結果寫入事件（12-B04）。
  - **衝突**：02-2 要求還原例外「由稽核室結案」，與 RA-48（稽核不得參與例外結案，01-10、01-15）衝突。
- **相關**：骨幹未定義環境；與 RA-01、RA-39（假時鐘由環境身分決定）相依。

### RA-06 母體完整性與母體定義

- **問題**：單號跳號（sequence 回滾、草稿刪除）無法區分技術跳號與被刪；「期間」指送審、核准、生效或任一時點有效未定義；1 月與 3 月匯出結果不同；退回後無人理的單永不結案；「用完就撤」的授權不在只看現存授權的母體裡。（01-1、01-4、02-11、09-F06、06-19、04-F23）
- **對稽核過關的影響**：IPE 無法驗證完整與正確，會計師不能直接用作抽樣母體，需另做替代程序；「一鍵稽核資料包」的價值打折。
- **各立場的解法**：
  - 單號在送審時於同一交易內無間隙取號，草稿只有內部 id 不進母體；取號本身是事件並與雜湊鏈序號勾稽；草稿刪除也寫事件（01-1）。
  - 資料包列出每張單「建立事件」的序號，與期間內所有建立事件一一對應並與錨點事件數一致；單號仍改用不跳號計數器（02-11）。
  - 多種母體定義（送審／核准／生效於期間內、期間內任一時點有效、期末時點有效）加上以事件序號表示的 as-of 截止點，同定義同截止序號任何時候匯出結果相同（01-4）；授權查詢支援 `as_of` 與期間（09-F06）。
  - 報表規格（以哪個事件時間為準、納入哪些狀態、時區）寫在 `docs/audit/`、有版本，資料包第一頁列出；產出記錄規格版本、參數、產出人、筆數、檔案雜湊並寫事件；提供 JSON Lines 原始事件匯出（02-11）。
  - 退回逾時自動取消、申請人離職時處理其進行中的單，讓每張單都有終點（06-19）。
  - 複查與知悉名單的範圍是「期間內任何時點有效」，不只現存（04-F23）。
  - **衝突**：單號的角色——01-1 以「筆數＝最大號－最小號＋1」為核心證明；02-11 認為「單號跳號因此不再重要」，以建立事件序號為證明，單號無間隙只是避免解釋。取號時點——01-1 送審時取號；02-11 以「建立申請單」事件為準，未明定是建立草稿或送審。
- **相關**：A2「可證明沒有遺漏」只有目標沒有機制；與 RA-07、RA-12（依法人產出母體）、RA-42（跨切換日母體）相依。

### RA-07 可重現抽樣

- **問題**：稽核用 Excel RAND() 抽樣，會計師要求重新執行證明不是挑過的，做不到；內控自評要說明抽樣方法。（01-23、09-F17）
- **對稽核過關的影響**：會計師降低對內稽工作的依賴、擴大自己的測試。
- **各立場的解法**：平台內建抽樣：對 RA-06 定義的母體（含 as-of 序號）以指定種子與公開演算法（例如種子＋單號的 SHA-256 排序取前 N）產生樣本，支援分層與指定必抽；抽樣本身寫入事件（母體定義、母體雜湊、種子、樣本），平台外可重算（01-23、09-F17）。無衝突。
- **相關**：A2；RA-51。

### RA-08 決定當時的證據快照

- **問題**：(1) 人資回溯調整組織後，過去的簽核看起來由「非直屬主管」核准；簽核人改名、離職、帳號刪除後證據頁顯示目前姓名或「已停用」。(2) 簽核人主張「我看到的畫面沒寫可匯出」「英文摘要與中文不一致」。(3) 批次核准拿不出每張當時顯示的內容。(4) 升版改了 `compare_content`，無法重現當時為何判為縮小。(5) 稽核事件的 IP 取自可偽造的 `X-Forwarded-For`，裝置是自報的 User-Agent。（01-19、08-3、08-20、08-H6、10-P15、10-P16、01-12、02-15、05-E17、07-17、03-14）
- **對稽核過關的影響**：無法驗證「簽核當時是否有資格」「核准時看到什麼」；證據會隨主檔資料漂移；判斷結果無法重現；事故調查與訴訟中來源欄位不可依賴。
- **各立場的解法**：
  - 組織、人員、角色資料採雙時間（生效時間與平台得知時間），回溯修改是新增不覆蓋（01-19、08-H3）。
  - 每個指派、簽核事件快照判斷與辨識所需的最少欄位：姓名、員工編號、公司、單位、職稱、與申請人的關係、resolver 與解析依據（人事事件或同步批次），納入雜湊；證據頁以快照呈現、旁註目前狀態（01-19、08-H6、08-20）。
  - 顯示快照雜湊：摘要事實、差異、重疊警示、自動檢查結果、介面語言、附件雜湊；批次時每張都記，並記停留或展開狀態；流程類型宣告以哪個語言版本為準（10-P15）。批次記批次 id、每張內容版本雜湊與顯示摘要雜湊（01-12）。複查每筆記呈現的事實與決定時間（02-15）。偏離常態時的核准理由連同當時的參考數據快照存入事件（05-E17）。
  - 每次 hook 或宣告規則判斷時，事件記下流程包發行版號、函式或規則雜湊、輸入輸出摘要（07-17）。
  - IP 只從可信代理清單附加的那一段取，保留原始標頭；裝置欄位分「自報」與「已驗證」（WebAuthn 憑證 id、MDM 裝置 id）；全程帶關聯 id；時間以資料庫時鐘為準（03-14）。
  - **衝突**：快照放哪裡——08-20、08-H6 主張快照欄位「納入雜湊」；10-P2 主張鏈上只放不可識別內容（內部 id、個資欄位的加鹽雜湊），姓名、IP、裝置、意見文字放在可銷毀金鑰加密的欄位（為了能依法抹除，見 RA-09）。人員資料保存——01-19「人員資料永不刪除，只標示狀態」；10-P16 主張離職後分階段最小化，證據必要部分保留到最後一張單保存期滿後抹除。
- **相關**：K-VERSION-BOUND、`audit_event` 欄位（骨幹第 2 節）、D17（語言版本）、D3。

### RA-09 保存期限與銷毀

- **問題**：`audit.retention_years = 10` 是單一全域值、無起算點、無刪除機制；直接刪除會斷鏈；不同流程與紀錄類別的法定保存期不同；個資法要求期滿刪除；IP 與裝置保存 10 年不符比例原則；有人把保存年限從 10 改成 2 或 3 以節省空間。（01-25、02-5、07-4、09-F08、10-P2、10-P3、10-P10、10-P19）
- **對稽核過關的影響**：要嘛違法超期保存，要嘛刪除後破壞證據與母體，屆時只能二選一；保存年限被調降會造成證據提早銷毀。
- **各立場的解法**：
  - 依期間分段（例如年度），每段結束產生段落封印並外部錨定；期滿整段移除，保留封印與「依保存政策刪除」事件，下一段從封印開始驗證；事件中的個人識別資料以假名 id 存、對照表另存，刪除只刪對照表（01-25）。
  - 依月分區封存，刪除以封存月為單位，在主鏈留下「某月已依保存年限銷毀，檢查點雜湊為 X」（07-4）。
  - 內容與骨架分開：雜湊只對骨架與內容雜湊計算，期滿刪除內容（版本、附件、機密欄位金鑰）保留骨架；每張單獨立的資料金鑰，銷毀即丟棄金鑰（crypto-shredding）；保存年限依流程類型與紀錄類別設定，新增 `retention_basis`（結案日、失效日、年度決算日）（09-F08）。
  - 鏈上只放不可識別部分，個資以人或申請單為單位的金鑰加密，抹除是新增「抹除」事件；新增「限制處理」狀態（10-P2）。`retention.years_after_closure` 預設 5 年、從進入終止狀態起算，排程每月產生銷毀單（10-P3）。IP、裝置另設較短保存期（10-P10）。
  - 保存年限設硬下限，調降需較高層級核准；清除只刪「已錨定、已匯出長期保存、且超過年限」者（02-5）。低於下限插入法務關卡（10-P19）。
  - 必須現在就在資料結構上決定，上線後改會動到所有既有雜湊（01-25、10-P2）。
  - **衝突**：(1) 預設年限——10-P3 主張 5 年並認為 10 年無法源；09-F08 主張個資相關 5 年、會計憑證決算後 10 年、董事會紀錄永久；02-5 舉「例如 7 年」為下限；骨幹與資料授權規則目前寫 10 年。(2) 銷毀方式——整段移除（01-25、07-4）對比刪內容留骨架／金鑰銷毀（09-F08、10-P2）。(3) 個資去識別——假名對照表（01-25）對比加密後銷毀金鑰（10-P2）。(4) 銷毀核准人——01-25「由設定變更核准」；09-F08「紀錄擁有單位（法遵或稽核）核准」；10-P3「個資窗口 → 稽核兩人都要核准」；後兩者讓稽核參與核准，與 RA-48 衝突。
- **相關**：骨幹第 8 節 `audit.retention_years`、K-AUDIT-APPEND、D20、A19；與 RA-10、RA-11、RA-12 相依。

### RA-10 法律保全

- **問題**：訴訟或調查中的紀錄到期照常銷毀；由 MIS 手動停排程沒有範圍、決定人與解除紀錄。（01-25、09-F07、10-P4）
- **對稽核過關的影響**：訴訟中銷毀證據可能被認定妨礙舉證或滅證；全面停止銷毀又違反個資最小保存。
- **各立場的解法**：核心的 `legal_hold`：宣告範圍（申請單、人員、供應商、流程類型、期間）、依據案號、預計檢討日；範圍內不得銷毀與當事人刪除，銷毀排程先排除並記錄排除筆數；建立時試算凍結筆數；證據頁顯示「保全中」；技術維運不能建立或解除；每 6 個月提醒檢討，逾期列入稽核準備度（09-F07、10-P4、01-25）。
  - **衝突**：核准人——09-F07「法遵或法務主管以外的人核准」；10-P4「法務提出、法務主管核准」。
- **相關**：RA-09；骨幹無此實體。

### RA-11 機密欄位金鑰的生命週期

- **問題**：D20 的金鑰由維運以外的「人」保管；保管人離職、交接遺漏、輪替銷毀舊金鑰、DR 時保管人不在場、法院調閱時保管人拒絕或私下解密；雜湊算在密文還是明文未定義。（01-18、02-22、07-3、09-F09、10-P2、12-B14、12-B18）
- **對稽核過關的影響**：保存期內讀不出來等於沒有證據；DR 時保管人在電話裡念密碼給維運，D20 前提當場失效且無紀錄。
- **各立場的解法**：
  - 資料金鑰以主金鑰包裝，主金鑰由 HSM／KMS 或 M-of-N 分持；輪替只產生新版本，舊版在保存期內保留（只解密）；每季（01-18）或每年（02-22）抽一筆舊資料做可解密性檢查，失敗列例外。
  - 保管人是角色而非個人，異動走設定變更並比照 K-OWNER-CONTINUITY（02-22、09-F09、07-3）。
  - DR：金鑰 port 支援以 M 份分持還原 KEK，每位分持人以自己身分加 MFA 提交，維運只啟動流程；年度還原演練必須包含金鑰還原，由不同分持人組合完成（07-3）。
  - 合法調閱：「機密內容調閱」做成宣告式流程類型（法務提出 → 資料擁有單位主管與法遵核准 → 兩位保管人執行），記錄範圍、用途、接收者（09-F09）。
  - 退場時加密匯出，金鑰由客戶保管人交付、不經原廠（12-B14）。
  - **衝突**：(1) 分持人組成——01-18 例「人資主管、資安長、稽核主管三取二」並認為稽核列入合理；02-22「人資、稽核室、資安室各一，3 取 2」；07-3「資安、稽核、人資、財務、法務各一，5 取 3」；12-B18 例「法務或稽核等非資訊人員」。稽核持有分持是否影響獨立性未被討論（見 RA-48）。(2) 雜湊對象——02-22 鏈對密文計算、另存明文雜湊；10-P2 鏈上只放加鹽雜湊與不可識別內容，個資本體另加密；兩者在「金鑰銷毀後是否仍可驗證」上結論相同，但結構不同。
- **相關**：D20、A19；與 RA-09（crypto-shredding 依賴金鑰設計）、RA-49（稽核如何讀取機密）相依。

### RA-12 多公司的證據切分與移交

- **問題**：所有公司共用一條鏈；子公司的會計師只能看子公司資料卻要能自己驗證完整性；出售子公司要移交可驗證的紀錄且不得含其他公司資訊；跨公司單應出現在哪家公司的母體。（07-23、10-P18、01-24、09-F14、12-B05）
- **對稽核過關的影響**：只取子集合鏈就斷；整條交出又洩漏他公司資料；兩家公司的稽核都以為對方查過。
- **各立場的解法**：
  - 跨公司單同時出現在申請人所屬公司與資源所屬公司的母體，匯出標示角色（01-24）；稽核資料包可依法人產出，跨公司單在兩邊母體都出現且編號一致（09-F14）。
  - 每家公司一條自己的鏈，加一條集團主鏈只錨定各公司鏈的檢查點；跨公司事件在每家相關公司的鏈上各記一筆、互相引用；產生「公司資料移交包」（07-23）。
  - 維持單一主鏈，每日依公司別建 Merkle 樹、樹根寫入主鏈並送外部時戳；移交時給該公司事件、各日樹根與包含證明；公司移出是一張設定變更單（10-P18）。
  - 需要資料落地的子公司另外獨立部署，部署之間以「聯盟」交換身分、簽章請求與事件雜湊，總部只收彙總指標（12-B05）。
  - 必須在第一版決定，事後拆鏈等於重建歷史雜湊（07-23）。
  - **衝突**：每公司一條鏈＋主鏈（07-23）對比單一主鏈＋每日公司別 Merkle 樹（10-P18）。另，12-B05 指出 platform-vision「多公司不在第一版範圍」與 D15 文字矛盾。
- **相關**：D15、A12；RA-06、RA-29。

## 二、身分與冒用

### RA-13 後端連線帳號冒名

- **問題**：持有 `sgn_app` 密碼的維運人員可用 `psql` 呼叫 `api.approve_task(p_actor => 財務長的 id, …)`；資料庫完全信任後端傳入的 `p_actor`，紀錄與雜湊鏈都正常。`sgn_app` 密碼放在 `.env`，被複製進備份與廠商工單。（02-1、03-11）
- **對稽核過關的影響**：會計師判定「簽核紀錄的歸屬不可依賴」，連帶所有核准證據失效；02-1 稱之為「整個平台最根本的一條」。
- **各立場的解法**：
  - `api` function 改收 `p_session`，actor 由資料庫依 session 查出；session 只能由登入流程建立，且需帶可由資料庫驗證的身分提供者資料（金鑰不在應用伺服器）；決定類動作另需一次性決定憑證（MFA 結果）；事件記錄 `session_user`、`application_name`、session id；架構測試：無有效 session 時決定類 function 必定失敗（02-1）。
  - 基本做法（vault、輪換、限制來源 IP）必要但不足（02-1）；機密來源 port、短效資料庫憑證、輪替程序、正式環境用檔案型機密列為例外（03-11）。
  - 交易綁定的 WebAuthn 簽章（RA-14）讓冒名需要同時取得使用者裝置（03-1）。
- **相關**：骨幹第 1 節 `sgn_app` 只能 `EXECUTE api`；K-SOD-*、K-AUDIT-CHAIN 都以 `p_actor` 正確為前提；D20「看不到」不等於「冒不了名」。

### RA-14 決定的驗證強度（MFA、passkey、交易綁定）

- **問題**：`K-MOBILE-MFA` 只要求手機，電腦只靠 SSO（會議室沒鎖的筆電、偷看到的密碼）；OTP 與推播可被 AiTM 釣魚代理與 MFA 疲勞轟炸繞過；30 張單 30 次驗證碼讓人改用電腦；中國出差收不到推播；ADFS（SAML）與 Entra 並存，平台不知道「MFA」記的是什麼；`approval.mobile_mfa_required` 可被參數關掉，月結當天 MFA 服務中斷時一定會被關。（02-5、02-19、03-1、03-18、04-F17、05-E12、05-E13、10-P15、12-B01、12-B23、11-18）
- **對稽核過關的影響**：「按下核准的是本人」無法證明；證據完美但可能是假的（03-1）；訴訟中「別人用我的電腦」抗辯難以推翻（10-P15）。
- **各立場的解法**：
  - 不分裝置，決定類動作要求近期強驗證（IdP 回傳 `acr`／`amr`／`auth_time`），N 依級別設定且有硬上限；每筆決定記錄驗證方式、時間、裝置類型（02-19）。
  - 防釣魚驗證器（FIDO2／passkey）；L4、重大、設定變更、撤銷他人授權、轉簽、代理設定一律 WebAuthn 交易簽章，挑戰值綁 `case_version` 雜湊與決定種類，直接對平台簽、不經 IdP；推播必須數字比對，不支援的 IdP 只能用在 L3 以下；最低強度寫成核心規則（03-1、04-F17）。
  - 每個決定都做一次 passkey 使用者驗證（生物辨識一觸），挑戰值含單號、版本雜湊、決定種類；無 passkey 者退回 TOTP，5 分鐘內涵蓋連續決定；電腦也要求（05-E13）。MFA 優先 passkey，其次離線可用的 TOTP，推播與 SMS 只作備援；決定送出帶冪等鍵；不支援離線決定（05-E12）。
  - `K-MOBILE-MFA` 改為 `K-DECISION-STEPUP`：L4、重大、特權類不論裝置要 MFA，可在短時間（例如 10 分鐘）內免重複（10-P15）。
  - 同時支援 OIDC 與 SAML 2.0；優先用 IdP 的 step-up（`acr_values`／`max_age`、`RequestedAuthnContext`／`ForceAuthn`），原樣記錄回傳強度；強度不足或 IdP 不支援時才用平台 passkey；可接受的來源是參數，走 D12（12-B01）。
  - 依級別可要求個人憑證（工商、自然人憑證）或 passkey 對決定內容簽章，預設不開（12-B23、10-P15）。
  - 降級矩陣：MFA 服務失效時決定類動作擋下，允許預先登記的備援因子；不提供關閉 MFA 的參數；無法等待的事走緊急路徑（03-18）。
  - 上線前簽核人就緒度檢查（帳號、MFA 註冊、代理），未達門檻不得切換（11-18）。
  - **衝突**：(1) 粒度——每個決定都驗（05-E13）對比一次 step-up 後 N 分鐘內有效（02-19、04-F17 為 15 分鐘、10-P15 為 10 分鐘）。(2) 誰做驗證——平台直接收 WebAuthn 交易簽章（03-1）對比優先信任 IdP step-up、平台 passkey 只作備援（12-B01）。(3) 參數——移除 `approval.mobile_mfa_required`（02-5、03-18）對比改名為 `approval.decision_user_verification`、依流程類型與級別可設（05-E13）、L3 與一般流程的電腦簽核由流程類型參數決定（10-P15）。(4) 批次——一次 step-up 涵蓋整批（02-19、04-F17）對比挑戰值必須包含整批每張的版本雜湊（03-1、05-E20）。
- **相關**：K-MOBILE-MFA、骨幹第 8 節 `approval.mobile_mfa_required`（與第 5 節「核心規則不能關閉」矛盾，02-5）、D3、D22；RA-32。

### RA-15 驗證器註冊、裝置遺失、離職當下的 session

- **問題**：手機遺失時 SSO、通知信、驗證器都在同一支手機；攻擊者冒充出差中的財務長打給服務台重設 MFA；上午被解僱的人，平台 session 晚上仍有效，在電梯裡核准；SSO token 有效期間離職者仍能簽。（03-2、03-3、03-7、02-9、08-1）
- **對稽核過關的影響**：離職後的決定被當成有效核准；無法依裝置圈定遺失期間的決定。
- **各立場的解法**：
  - 決定用驗證器必須 `userVerification=required`；平台登記決定用 WebAuthn 憑證，每筆決定記憑證 id；新增「作廢裝置」動作，並列出該憑證指定期間內的決定交資安確認（03-2）。
  - 新登記的決定用憑證有冷卻期（參數，有下限），冷卻期內不能做 L4、重大、設定變更、銀行帳號變更與轉簽；登記需另一人（主管或資安）確認，並通知本人原有 email 與直屬主管（03-3）。
  - 平台 session 與 IdP 綁定（back-channel logout、CAEP／SSF）；決定依「當下的強驗證」，帳號停用即無法完成；收到停用事件時改派其待簽工作（03-7）。離職生效時撤銷該人所有平台 session（02-9）；每次決定重新檢查雇用狀態（08-1）。
- **相關**：K-MOBILE-MFA；人事異動的回溯偵測屬另一份彙整（08-1、02-9）。

### RA-16 帳號被盜後的持久化與事故圈定

- **問題**：攻擊者取得 session 後先自設代理給內應、把待簽單轉簽給同夥、改通知 email；事後發現帳號被盜三週，140 個決定無法圈定，授權只能撤銷（終局）或不動；凌晨 agent 外洩資料，SOC 不在 `K-REVOKE` 可撤銷名單內；懲戒解僱者過去經手的驗證沒人回頭看。（03-4、03-5、03-6、08-6、04-F14）
- **對稽核過關的影響**：盜用幾分鐘造成一年的權限移轉且全是「合法代理簽核」；止血永遠不會發生，事故以「不動」結案。
- **各立場的解法**：
  - 代理、轉簽、加簽列為高風險動作，套用交易綁定強驗證與敏感變更後的冷卻期；平台內不提供修改通知 email；每次設定即時通知本人與主管（03-4）。
  - 授權新增可恢復的 `suspended` 狀態，`check` 回拒絕並通知下游（03-5、04-F14、08-6）。
  - 事故保留（incident hold）：對「某人、某期間」開立事故案件，列出所有決定、受影響的單、授權與設定變更，可批次暫停；逐筆由本人以外的人複核後恢復或撤銷；開立需資安長與一位非資訊部主管兩人（03-5）。
  - 資安緊急停權角色：只能暫停不能核准，事後 1 個工作天內資安長覆核；暫停在 N 分鐘內推送並自動做拒絕驗證查詢（03-6）。
  - 立即處置的離職：唯一負責人的授權凍結、待簽改派，並產生過去 90 天經手清單交資安與稽核指定的人覆核（08-6）。
  - **衝突**：08-6 的回查清單交「資安與稽核角色指定的人」覆核，稽核是否只指定不覆核未明，與 RA-48 相關。
- **相關**：骨幹第 4 節授權狀態只有 active／expired／revoked；K-REVOKE 可撤銷者不含資安；D13 緊急路徑是「給權」，03 對 D13 的意見要求另有「止血用的暫停」。

### RA-17 身分對應與「一個自然人一個 person」

- **問題**：同名新進員工沿用舊帳號或回收的 email 而直接成為舊 person；身分提供者管理員把某 `external_id` 改指向財務長；集團內調到子公司變成兩個 person，`K-SOD-DISTINCT` 擋不到；再雇用時舊角色與代理復活；人資依規定刪除離職者資料，同步後證據的簽核人變成無名氏；期初帳號中有共用、服務、離職、回任多帳號。（02-8、08-12、08-18、08-19、10-P16、05-E14、11-2）
- **對稽核過關的影響**：責任掛到錯的人；職責分離以「工號」判斷時，同一自然人可簽兩關；證據力因 actor 失去可辨識性而歸零。
- **各立場的解法**：
  - 對應只增不改：一個 `external_id` 對應過某 person 就不得改指他人（資料庫層拒絕）；任何對應變更通知當事人與主管；重新啟用已離職 person 需人資核准（02-8）。
  - `external_id` 必須是身分提供者宣告永不重用的屬性（`objectGUID`、`oid`、確認不重用的 `sub`），登記時由技術維運以外的人確認；對到已離職雇用時拒絕登入並列例外；選人元件顯示「姓名＋單位＋職稱＋工號後四碼」並標示同名（08-19）。
  - `person`（自然人）與 `employment`（公司、工號、類型、起迄）分離；集團內調動由調出與調入公司兩位人資「連結」；職責分離、查閱紀錄、負責人以 person 判斷，主管關係與簽核資格以 employment 判斷；疑似同一人以人資提供的比對鍵雜湊檢查（08-12、05-E14）。
  - 再雇用沿用 person、建立新 employment，舊權限一律不自動恢復（08-18）。
  - 上游刪除不刪 person，只觸發最小化流程；身分合併由人資確認（10-P16）。
  - 期初身分對應報告，對不上的帳號分四類處理並留紀錄（11-2，另見 RA-41）。
- **相關**：骨幹第 2 節 `person_identity`；K-SOD-DISTINCT；D15、A12。

### RA-18 共用帳號與外部人員的具名帳號

- **問題**：廠商三位工程師共用本機帳號「vendor_hr」；新駐點工程師直接沿用前任帳密與簡訊門號；外部稽核借內稽帳號；按人頭計價誘使共用帳號；外部人員的保證人離職後廠商仍執行兩個月；派遣、實習生不在人資系統，借正職同事帳號。（03-21、07-19、02-16、12-B16、08-25、08-16、06-16、05-E02、11-16）
- **對稽核過關的影響**：執行紀錄無法歸屬自然人，是 ITGC 最常開的缺失之一。
- **各立場的解法**：
  - 外部人員走獨立身分來源（B2B guest 或廠商 IdP 聯盟），平台不存密碼；必須是具名個人帳號（平台拒絕建立無對應自然人的帳號），強制防釣魚 MFA；核心不提供本機密碼登入（只有初始化與緊急帳號例外）；外部帳號建立本身是一張申請單（03-21）。
  - 有效期不超過合約到期日且單次最長 6 個月；保證人每月確認「仍是同一人」，未回應即停用；MFA 只能綁個人裝置，註冊時保證人在場；首次與新裝置登入通知保證人；管理人清單本身是一筆授權（07-19）。
  - 保證人離職、留停、調職時外部人員資格立即暫停（08-25）；外部帳號連到有效的委外合約（10-P13，屬另一份彙整的個資委外主題）。
  - 非正職人員由用人單位登記、人資或總務確認，不能是負責人、單一持有人角色或簽核人（08-16）。
  - 偵測共用：同一裝置在短時間內替多位主管做 MFA、助理與委託人在同一裝置切換、簽核裝置與申請人最近使用的相同，列為例外（11-16、05-E02、04-F17）。
  - 計價不按人頭，避免共用誘因（12-B16）。
  - **衝突**：保證人確認頻率——07-19 每月；03-21「期限前重新確認」。保證人異動時——08-25 立即暫停；03-21 套用 K-OWNER-CONTINUITY（有寬限期）。
- **相關**：A18、D19；RA-19。

### RA-19 助理、代填與代送

- **問題**：秘書用總經理的電腦與桌上手機按核准；助理代填時助理成為申請人、主管關變成助理的主管；主管替部屬填單後自己成為申請人；MIS 依 email 直接在 DC 開；ERP 要發起申請單；視障同仁無法自行完成而請人代填。（05-E02、06-8、11-16、12-B08、12-B21）
- **對稽核過關的影響**：「誰做的決定」失真且系統看不出來；需求的真正主人不在紀錄上；秘書看得到 L4 機密內容。
- **各立場的解法**：
  - `assistant_link`（委託人 → 助理，期間、可見範圍）：建立走設定變更並由委託人本人加 MFA 確認；助理可看清單、代提問、加準備備註、標記建議，不能做任何決定；決定綁本人裝置 passkey；保密流程類型預設排除（05-E02）。
  - 「填單人」與「申請人」分開（`drafted_by`）：任何人可替他人建草稿，申請人確認後才送審；K-SOD-* 同時檢查兩者；參數 `approval.drafter_may_approve` 預設 false；允許以未來生效的 HR 預建人員為申請人（06-8）。
  - MIS 代為建立申請、申請人確認送出（11-16）；外部系統以 `api_client` 代表申請人建草稿，不得直接送審（12-B08）。
  - 實際用螢幕報讀軟體走完關鍵任務，避免因無法自行操作而代填（12-B21）。
- **相關**：骨幹只有一個「申請人」；D16（11 對 D16 的意見要求代建）；A3（保密）；RA-18（共用偵測）。

### RA-20 平台自身的特權存取與破窗帳號

- **問題**：DBA 以 `postgres` 登入正式資料庫兩小時無人知道做了什麼；備份被帶回家「測試還原」；DBA 為省事把 `sgn_owner` 設成 superuser；SSO 中斷一整天時維運開本機管理員帳號「暫時代簽」；平台當機時最需要特權存取，若特權存取走平台自己的流程會循環依賴。（03-12、07-1、07-8、02-2）
- **對稽核過關的影響**：專門管特權的平台，自己的特權沒被管，稽核與資安都會第一個問。
- **各立場的解法**：
  - 平台的特權存取平常走自己的特權權限流程（小時計、事後複核）；平台不可用時用預先封存的緊急帳號（密碼分持或保險箱、使用即告警），事後在平台補登並由資安複核；`pgaudit` 記錄所有非 `sgn_app` 連線送外部 SIEM；每日讀取 `pg_roles`／`pg_auth_members` 與 OS 特權群組與平台核准比對；備份加密、金鑰與主機分開、取用列入特權存取（03-12）。
  - 安裝分成「DBA 腳本」（需 superuser、一次性）與「平台腳本」（以 `sgn_owner` 執行）；架構測試檢查 `sgn_owner` 不是 superuser（07-1）。
  - 破窗帳號：平台本機帳號、密碼分持、使用時通知稽核與資安，權限檢查層就沒有簽核、執行、設定變更能力（07-8）。
- **相關**：骨幹第 1 節資料庫角色；RA-03、RA-30。

## 三、職責分離與利害關係

### RA-21 受益人簽核

- **問題**：主管叫下屬當人頭申請人，自己以被授權團隊負責人與成員身分在主管關核准；資安長核准自己所在監控團隊的資料；人資經理以資料擁有者身分核准包含自己薪資的申請；agent 的使用對象（整個聊天群組）實際取得資料；執行人就是申請人或被授權者成員；升遷後複查自己申請、自己在用的授權。（03-8、04-F02、04-F22、05-E16、07-21、08-21）
- **對稽核過關的影響**：職責分離只看填表的人，形同可用人頭繞過；稽核一看就會問，且是內部人取得權限最自然的路線。
- **各立場的解法**：
  - 新增 `K-SOD-BENEFICIARY`：被授權者的負責人與在職成員比照申請人，任何一關都不能簽，撞到時依 K-SOD-DISTINCT 往上找；以送審時成員為準；生效後新成員若是該單簽核人也觸發處理（03-8、04-F02）。
  - 受益人是資安長時改由其上一層主管或路徑設定的替代簽核人，**不可**由其代理人（通常是下屬）簽（03-8）。
  - 偵測可判定的受益關係（成員、負責人、資料擁有者自己在資料範圍內〔需流程包 hook 回答〕、合約對象的關係人）並在決定按鈕上方提示；簽核人選「迴避，轉給上一層」或「揭露後仍由我簽」（必填理由、進例外報表）；流程類型或級別可宣告強制迴避；任何簽核人可主動迴避（05-E16）。
  - agent 的申請必須宣告「使用對象」，視同被授權者成員，受益人規則也看使用對象；`check` 以 on-behalf-of 傳入最終使用者（04-F22）。
  - `K-SOD-FULFIL`：執行人不得是申請人、該單任一簽核人、被授權者負責人或成員（07-21，另見 RA-23）。
  - `K-REVIEW-SOD`：複查人是該授權的申請人、成員或使用者時改由其直屬主管或指定替代複查人（08-21）。
  - **衝突**：處理方式——強制擋下並往上找（03-8、04-F02）對比預設「提示＋迴避或揭露後簽」、強制迴避只用於宣告的高風險類別（05-E16）。撞人時的替代者——03-8「不可由其代理人簽」；08-10 主張 K-SOD-DISTINCT 撞人時角色關「先找角色代理人」，兩者對代理人能否接手相反。
- **相關**：骨幹第 5 節 K-SOD-APPLICANT、K-SOD-DISTINCT；`principal_member`；RA-22、RA-25。

### RA-22 被授權者成員擴大

- **問題**：L4 授權核准給專案後，負責人陸續加入 8 位同事與 2 位外部人員，全部繼承授權而沒人簽；批次續期「內容無差異」但成員從 3 人變 26 人；改組時舊團隊授權直接轉給 40 人的新部門；外部顧問被塞進專案成員；資遣者的專案成員資格留到專案結束。（04-F21、06-7、06-16、08-13、08-17、04-F15、08-25）
- **對稽核過關的影響**：簽核只審了「給這個專案」沒審「這個專案有誰」；稽核抽查「實際可存取的人與核准是否一致」時最容易被打到；06 稱為「最大的擴大不重簽漏洞」。
- **各立場的解法**：
  - 成員增加視為授權擴大：由該授權的資料擁有者核准（每個擁有者一關並行，L4 加資安長），一次可加多人，新成員主管收通知；移除免簽；外部人員加入需保證人；team（由人資組織樹推導）不適用；agent 的使用對象適用（04-F21）。
  - 成員異動是一種核心內建流程類型「被授權者成員異動」：新成員的主管 → 每筆授權的資料擁有者，L3 只通知、L4 才簽（參數）；跨公司成員加跨公司關卡；team 成員變動通知擁有者並列入複查；新規則 `K-PRINCIPAL-MEMBER-EXPAND`、`K-PRINCIPAL-MEMBER-REDUCE`（06-7）。
  - 改組時登記舊單位 → 新單位對應：成員為子集或相同則自動承接；擴大則以舊名單凍結成有迄日的「過渡團隊」並自動產生以新團隊為被授權者的續期草稿（08-13）。
  - 成員資格隨離職、留停、調職事件自動移除並通知負責人（08-17）。
  - 成員變化納入批次資格（RA-45）。
  - **衝突**：路徑——04-F21 由資料擁有者核准（L4 加資安長），不經新成員主管；06-7 新成員主管 → 擁有者，且 L3 只通知不簽。
- **相關**：DA 規則「專案任何人可建立、不帶權限」；原則③（擴大重簽）；K-BATCH；D3。

### RA-23 執行、驗證、對帳的職責分離

- **問題**：MIS 執行時多開欄位，`build_verification_cases` 只測核准部分，全部通過反而替越權背書；人工整合的「獨立驗證人」是同組同事、30 秒確認；管理人刪掉 3 個帳號後才上傳對帳檔，或用篩選條件排除私下開的帳號；截圖當執行證據；外購系統沒有唯讀角色就給整個模組；BEC 詐騙中回撥號碼取自詐騙信本身；單一管理人既是資料擁有者又是執行人；機密單的 MIS 群組成員「認領後放回」以偷看。（04-F08、01-22、02-14、07-18、07-20、07-21、09-F15、04-F24）
- **對稽核過關的影響**：對帳母體由被稽核者自己提供，會計師不依賴；「核准的內容和執行的內容是同一份」在外購系統落空；D19 想補的盲區沒有補起來。
- **各立場的解法**：
  - 驗證改為讀回實際設定並與 `describe_entitlements` 做集合相等比對，多一項就失敗；讀回由平台（API）或執行人以外的人（檔案）提供；核心規則 `K-VERIFY-INDEPENDENT`，流程包與受管系統不得關閉（04-F08）。
  - 驗證人不得與執行人同一直屬主管或上下級（可放寬，但放寬是設定變更並列入資料包）；對帳檔由驗證人自己匯出上傳並附原檔；驗證人要填至少一項實際看到的事實（01-22）。
  - 受管系統登記「對帳執行人」，不得與管理人、執行人重疊；標準匯出條件，偏離即例外；筆數前後期勾稽（上期＋核准新增－撤銷＝本期）；稽核室或會計師每年隨機挑期別現場重新匯出比對；截圖只當附件不當驗證（02-14）。
  - 匯出檔對應以宣告方式定義（含民國年、合併儲存格、欄名別名），有版本、走 D12；找不到必要欄位、未知角色、筆數驟降、列印日期過舊一律拒絕；無匯出系統用畫面盤點表加第二人核對（07-18）。
  - 受管系統登記角色目錄；執行完成要附對方系統的匯出檔並自動比對核准角色；不一致的例外送業務擁有單位主管，不送回執行廠商（07-20）。
  - `K-SOD-FULFIL`；受管系統至少兩位管理人；只有一位時允許執行，但證據由另一位獨立驗證人上傳並列為例外；管理人自己與同單位帳號的差異列最高優先例外（07-21）。
  - 回撥對象只取自供應商主檔變更前已存在 N 天的聯絡資訊，驗證用電話等於申請附件中的電話即自動檢查失敗（09-F15）。
  - 執行人只看 `build_fulfilment` 的交付內容，看不到申請理由與附件；放回群組須填原因並記錄期間檢視內容，次數超過參數列例外給資安與稽核（04-F24）。
  - **衝突**：對帳檔由誰取得——01-22 驗證人自己匯出；02-14 專設「對帳執行人」角色；07-21 管理人上傳時要求另一人 N 天內直接匯出比對。獨立性門檻——01-22「不同直屬主管且非上下級」；02-14「不得是同一單位的同一人或其下屬」。
- **相關**：D19、D21、A7、A17、A21、K-VERIFY、K-CLAIM。

### RA-24 共謀與行為型偵測

- **問題**：兩位資料擁有者約好互簽對方部門的申請，每張都合規；並行關卡約好同時幾秒內核准；設定被短暫放寬、過完自己的單再改回；拿到可匯出 L4 後馬上自己撤銷；主管關係被人資專員暫時改成好友後隔天用來簽核；申請人與簽核人用同一台裝置；離職前最後一週大量放行。（04-F01、04 對 D4 的意見、04-F19、04-F23、08-23、04-F17、04-F12）
- **對稽核過關的影響**：只在紀錄裡查得到、要有人剛好去查，對舞弊者等於沒擋；04 指出 D10 目前列的例外都是「被動」型，缺「行為型」。
- **各立場的解法**：
  - 互惠核准指標（雙向次數、核准秒數、零退回）超過門檻自動產生例外，**派給稽核**而不是兩人主管；第三關看到提示；關掉偵測屬放寬控制（04-F01）。
  - 並行關卡全部核准後，最後一關看得到其他並行關的意見與核准時間（04 對 D4）。
  - 設定在 N 天內被改回或一年內改超過 2 次自動產生例外，附上放寬期間在舊設定下會更嚴的申請單清單（04-F19，另見 RA-31）。
  - L4 可匯出授權在 N 天內被撤銷或縮小、或使用量異常集中，列給資料擁有者確認（04-F23）。
  - 主管關係異動後 N 天內被用來決定關卡、且 M 天內又改回，列例外交稽核；簽核畫面提示「你成為此人的主管才 1 天」（08-23）。
  - 簽核裝置或 IP 與申請人最近使用的相同，列例外並通知簽核人本人（04-F17）。
  - 角色持有人異動時為繼任者產生交接複查，列出前任異動前 30 天核准的仍有效授權（04-F12）。
  - **衝突**：例外派給稽核（04-F01、08-23）與 01-10、01-15「稽核在例外上只能留言、不能改狀態」是否相容未說明；屬 RA-48 的範圍。
- **相關**：D10、D4、D12；RA-43（例外種類需含行為型）。

### RA-25 利益衝突、關係人交易與迴避

- **問題**：供應商的董事長是本公司董事的配偶；簽核的採購經理是供應商股東；合約對象是財務長親屬開的公司；舞弊調查需調閱被調查人擁有的資料，路徑會先通知被調查人；被調查者的前部屬在 MIS 群組會看到待辦。（09-F13、05-E16、09-F19、10-P17）
- **對稽核過關的影響**：無法證明「所有關係人交易都被辨識並送到正確層級」；調查走漏、證據湮滅；改走 email 則高敏感存取完全沒紀錄。
- **各立場的解法**：
  - 核心「關係人名單」（股務或法務維護、走 D12、有版本，以統編比對）；宣告式分級可用「交易對象 ∈ 關係人名單」加關（審計委員會、董事會）；`K-SOD-INTEREST`：簽核人與交易對象有登錄的利害關係時改由上一層；簽核時併入一步確認「與此交易對象無利害關係」；董事與經理人每年申報，未更新列例外（09-F13）。
  - 簽核人可主動迴避（05-E16）。
  - `K-SOD-RECUSAL`：申請單可列「迴避對象」，不得成為簽核人、認領人、執行人、驗證人，也看不到這張單；只能由法務、內部稽核、個資窗口在送審時設定；不能用來排除不想讓他簽的正常簽核人；調查類流程可宣告通知延後（10-P17）。
  - 「調查用授權」路徑：法遵主管 → 審計委員會召集人或指定獨立董事 → 資安長 → MIS，排除資料擁有者；強制保密；被調查人與其上兩層主管不得被指派或看見；有效期短且不可續期；授權總覽對資料擁有者顯示「另有 1 筆受保密的授權」而非完全隱藏（09-F19）。
  - **衝突**：誰能設迴避——10-P17 列內部稽核為可設定者之一，09-F19 的路徑不經稽核；稽核設定迴避是否屬「參與決定」未討論（RA-48）。
- **相關**：K-SOD-*；A3；RA-21、RA-37（會議決議與關係人交易層級）。

### RA-26 代理

- **問題**：資安長設部屬為一年期代理，82% 的 L4 資安長關由代理人簽；代理給秘書、給委託人的下屬（不可能退回主管部門的單）；系統管理員回溯補一筆上週的代理讓越權簽核合法化；帳號被盜後自設代理作為後門；代理沒有範圍，代理人代簽了含自己薪資的單、母公司代理人代簽子公司的單；請長假忘了設代理，但 HR 系統已有職務代理人；留停期間代理無限延續；代理人調職後與受代理關卡的其他關同部門。（01-21、02-17、03-4、04-F03、05-E03、05-E04、06-6、08-7、08-15、08-10）
- **對稽核過關的影響**：代理等於不經核准的簽核權限移轉，「核決權限表形同虛設」；回溯代理可把任何越權合法化。
- **各立場的解法**：
  - 期限上限（參數，例如 30 天，可依角色）；代理人須持有被代理職位的代理角色（走 D12）；建立、修改寫事件並通知被代理人主管；代理簽核比例依人、依關卡列入稽核準備度；代理期間本人仍可簽（01-21）。
  - 代理人只能從事先核准的名單中選；超過 N 個工作天需委託人主管核准；資格由各關 resolver 定義（02-17）。
  - 本人（MFA）或直屬主管代設；生效時間不得早於建立時間（硬性、無參數）；代理人不得在委託人下屬鏈、不得在同單前關簽過；單一持有人角色只能代理給登記的「指定代理人」名單（名單走 D12）；可限定流程類型與級別；每次代簽即時通知，回來後給代簽清單確認；確需事後補登走例外申請單（04-F03）。
  - 列為高風險動作，套用交易綁定強驗證與冷卻期（03-4）。
  - 代理帶範圍（公司別、流程類型、級別、金額上限、是否含保密）、可多段；代理人是申請人、受益人或內容當事人時自動跳過；範圍外的工作留本人或依升級規則；手機兩步設代理、出差前提醒（05-E03、05-E04）。
  - 讀取 HR 的請假與職務代理資料，指派時若簽核人不在且有 HR 職務代理人直接指派給代理人（紀錄寫明來源是 HR）（06-6）。
  - 委託人或代理人發生離職、留停、調職任一事件時代理暫停，委託人一鍵重新確認（重跑職責分離與資格），委託人離職則代理失效；留停者給出的代理在留停開始日失效（08-15、08-7）。
  - 人令派代的「代理主管」與個人休假代理分開，前者在期間內就是單位主管，紀錄不出現「代離職者簽」（08-10）。
  - **衝突**：(1) 長期代理的控管方式——期限上限 30 天（01-21）對比超過 N 天需主管核准（02-17）對比不限期但代理人須在事先登記名單（04-F03）。(2) HR 職務代理人自動接手（06-6）對比單一持有人角色只能代理給平台事先登記的名單（04-F03）——HR 職代不一定在名單內。(3) 代理人是下屬——04-F03 擋下；01-21 的情境是代理給部屬，只要求資格角色與期限；08-10 主張撞人時先找角色代理人。
- **相關**：骨幹 `delegation`、K-DELEGATE、K-SOD-DISTINCT；D12（04 指出代理不在 D12 範圍）；研究 01 M4（代理範圍）。

### RA-27 轉簽、加簽與徵詢

- **問題**：被要求修改條款的法務專員被主任要求「轉給我處理」，原審查人的疑慮沒留下；資料擁有者把有疑慮的單轉給下屬；用加簽把局外人變成「被指派的簽核人」以看機密單內容；矩陣組織中主管關落在不知情的行政主管，轉給實際功能主管在規則上不成立；財務長只想請另一位法務給意見、不想讓他成為正式關卡，只好用 LINE 傳 PDF。（04-F04、04-F05、03-4、05-E21、05-E07）
- **對稽核過關的影響**：轉簽變成「換人簽到過為止」；加簽成為繞過保密的合法管道；徵詢在系統外發生，內容與意見都沒紀錄。
- **各立場的解法**：
  - 轉簽對象必須能被該關 resolver 解析，或是該角色登記的指定代理人；單一持有人關卡只能轉給指定代理人；轉出必填原因，轉出者已勾的檢查清單與意見保留並顯示給接手者；同一關最多轉一次；不得轉給申請人或被授權者成員（04-F04）。
  - 加簽對象限於流程定義宣告的「可加簽角色」；保密單的加簽人只看得到勾選給他看的欄位，看不到機密欄位與附件；紀錄寫明加簽人看得到哪些欄位（04-F05）。
  - 轉簽、加簽列為高風險動作（03-4）。
  - 主管線支援「功能主管」（虛線），轉簽合格對象包含申請人的所有有效主管，行政主管轉出後仍收知悉通知（05-E21）。
  - 新增「徵詢意見」：無否決權、不暫停計時、有查閱紀錄、意見進事件；保密單需簽核人確認同意讓對方看（05-E07）。
  - 04 對 D16 的建議：每個動作在 01-kernel 寫明「對象資格、可見範圍、次數上限、紀錄內容」四項。
  - **衝突**：轉簽對象——04-F04 限於 resolver 可解析者或指定代理人；05-E21 擴及「申請人的所有有效主管」。兩者相容與否取決於 resolver 是否納入功能主管。
- **相關**：D16、A13；RA-26。

### RA-28 頂層升級與簽核角色出缺

- **問題**：董事長、總經理、稽核主管等找不到上一層，或 K-SOD-DISTINCT 往上找到頂，依骨幹第 7 節升級給系統管理員群組，由資訊人員核准總經理的薪資資料存取或改派總經理的工作；資料擁有者離職、四成主題包沒有擁有者；部門主管出缺三個月；單一持有人角色（財務長）交接空窗；子公司沒有資安長；組織資料有循環或「主管是自己」。（01-20、02-18、05-E03、06-10、06-11、08-4、08-10、08-14、11-5、11-7、11-20）
- **對稽核過關的影響**：資訊人員做業務核准是查核必開的缺失；最高層的申請正是舞弊風險最高、稽核最關注的樣本。
- **各立場的解法**：
  - 每個公司別、流程類型設定「最終升級對象」（例如董事長的單給審計委員會召集人或指定獨立董事、總經理的單給董事長），走設定變更；未設定時案件停住並產生高優先例外；系統管理員只能被通知；過渡期由流程管理者（非技術維運）改派並受職責分離檢查（01-20）。
  - `approval_policy` 必須定義 `top_of_chain_resolver`，沒有定義的流程不得啟用；永不交給技術維運或流程管理角色；高階主管的申請列入「高風險人員」清單（02-18）。
  - 頂層升級對象為依公司別設定的參數（例如 `approval.top_escalation_role`），可為董事長指定的副總或「總經理職務代理人」；技術維運或流程管理永遠不能代為決定或改派（05-E03）。
  - 主管關解析順序：直屬主管 → 部門代理主管 → 直屬主管的主管；全部找不到時交流程管理者指定（指定本身是設定變更）；新規則 `K-ROLE-CONTINUITY`：簽核角色持有人也要隨時在職（06-10）。
  - 公司層級的「頂層替代簽核人」（董事長、母公司指定主管或稽核主管），頂層申請人的單生效時自動通知稽核主管並列入複查名單作為補償控制；稽核主管本人申請時替代人不可是稽核室成員（06-11）。
  - 簽核人離職或留停時待簽工作立即依 resolver 重新解析；`scoped_role`／`role_holder` 依目前持有人解析，找不到才升級直屬主管（08-4）。單位主管與代理主管都空缺時找上一層單位主管，到頂才進「出缺佇列」由人資 1 個工作天內指定（08-10）。角色變更可預約生效並以人事事件為條件；路徑定義宣告「出缺替代」（08-14）。
  - 擁有者空缺時由業務擁有單位主管暫代（`K-OWNER-FALLBACK`）並開例外；連業務擁有單位都沒有才不開放申請；上線就緒門檻（11-5）。resolver 解析失敗進「路徑解析例外」佇列，由流程管理者指定並受職責分離檢查；循環與「主管是自己」在同步時擋下（11-7）。子公司缺角色時以正式的跨公司服務角色指派（11-20）。
  - **衝突**：(1) 替代簽核人——審計委員會召集人或獨立董事（01-20）、董事長／審計委員會指定的人／獨立董事（02-18）、公司職務代理人或董事長指定的副總（05-E03）、董事長／母公司主管／**稽核主管**（06-11，與 01-15 稽核不得為簽核人衝突）。(2) 找不到人時——停住並列例外、不交給任何人（01-20、02-18）對比交流程管理者指定（06-10、11-7）對比交人資指定（08-10）；05-E03 明定流程管理角色不能改派，與 06-10、11-7 衝突。(3) 未設定時——流程不得啟用（02-18）對比停住並列例外（01-20）。
- **相關**：骨幹第 7 節「升級給系統管理員群組」、A20（已預告拆掉 `sys_admin` 但升級對象未改）、D20；RA-48。

### RA-29 跨公司職權

- **問題**：兼任者的單被升級給母公司總經理而非子公司董事長；母公司的代理人代簽子公司的單；母公司主管在子公司沒有職權卻簽了子公司的單；申請人挑門檻較寬、簽核人較少的公司別送單；子公司 MIS 只有一人，導入團隊把母公司 MIS 加進子公司群組。（05-E14、05-E04、09-F14、04-F25、11-20、06-22）
- **對稽核過關的影響**：子公司稽核不承認他公司的簽核；申請人可以挑規則集合，所有規則都正確執行、結果卻是錯的。
- **各立場的解法**：
  - 一個自然人一個 person；任職、主管線、角色、代理都帶公司別；每個簽核工作記錄「以哪家公司的什麼身分簽」；K-SOD-DISTINCT 以自然人判斷（05-E14）。
  - 在某公司簽核必須有該公司的職務或正式兼任／委任紀錄（`appointment`，附依據與期間）；resolver 解析出的人在該公司沒有職權時不得指派（09-F14）。
  - 公司別由內容歸屬決定（用印依簽約主體、資料授權依受管系統或資料目錄所屬公司），申請人選擇不同於主要任職公司時填理由；跨公司取兩家路徑中較嚴者並各自需要必要關卡（04-F25）。流程跟著資料、主管關跟著人、跨公司自動加關（06-22）。
  - 跨公司服務的角色指派走子公司的設定變更並限可見範圍（11-20）。
  - 無明顯衝突；04-F25 的「取較嚴者」與 06-22 的「依資料所屬公司決定流程」在跨公司時是否同時適用未說明。
- **相關**：D15、A12；RA-12、RA-17。

### RA-30 平台管理角色之間的職責衝突

- **問題**：資訊部經理同時是 `sys_admin`、MIS 群組成員、部屬的直屬主管，可提出設定變更讓部屬核准、認領 MIS 關卡、直接存取主機；越南子公司資訊人員只有兩位，湊不出 D20 的三種角色。（02-23、12-B18、02-6、04-F19）
- **對稽核過關的影響**：同一人能「改設定」與「核准設定」、或「維運主機」與「執行授權」時，會計師要求補償控制，否則開缺失；小公司只能做形式上的分離。
- **各立場的解法**：
  - 核心預載平台角色的衝突矩陣（技術維運 × 流程管理 × 稽核 × 設定變更核准人 × 執行人），指派時檢查；無法避免時以有期限的例外核准持有，並每月由其他人審其所有動作；設定變更核准人不得是提出人的直屬部屬（02-23）。
  - 角色分離以集團為單位滿足：子公司的技術維運、流程管理、金鑰保管可委派給集團或他公司；公布最小人力配置（單一公司至少三位不同的人）；客戶以設定變更明確接受的衝突組合列為永久例外並要求補償控制（12-B18）。
  - **衝突**：例外的期限——02-23「有期限的例外核准」對比 12-B18「永久例外」。
- **相關**：A20、D20、D13（職責衝突矩陣）；RA-20、RA-31。

## 四、設定與流程治理

### RA-31 設定變更的核准人資格與放寬／收緊

- **問題**：D12 只要求「提出人以外的人」：資訊部經理提出放寬、同部門下屬核准；兩位 MIS 互相核准把機密欄位改成一般欄位、把保存年限改成 3 年；總經理被列為核准人卻看到參數代碼；董事會修訂的核決權限表由任何人核准進平台。（02-6、04-F19、05-E24、10-P19、09-F10、02-5、01-15）
- **對稽核過關的影響**：同部門、上下級互相核准是最常見的形式化覆核；核准人看不懂則雙人覆核淪為形式；改控制的人有利益衝突時無從察覺。
- **各立場的解法**：
  - 設定變更是核心流程類型，路徑依設定所屬流程類型與 `control_effect` 決定：一般參數＝提出人以外的流程管理者；路徑、角色指派、削弱控制的參數＝流程擁有單位主管＋控制負責人，稽核知會不簽；設定變更路徑本身的修改需兩個不同單位的人（02-6）。
  - `setting_definition` 標示「控制方向」與「控制負責人」：放寬須控制負責人核准，覆核人不得在提出人上下屬鏈，放寬生效時通知稽核；收緊維持雙人覆核；客戶新增參數未宣告者預設視為放寬敏感（04-F19）。
  - `setting_definition` 加「控管類別」（一般、個資、證據保存、職責分離、安全），類別決定插入的關卡：個資類 → 個資窗口；證據保存類 → 個資窗口與稽核；職責分離與安全類 → 稽核或資安（10-P19）。
  - 依變更類型決定核准人：技術參數由流程管理者之間覆核，影響控管責任者由對應業務主管核准；摘要與影響試算以人話呈現（05-E24）。
  - 核決權限變更的核准人以 resolver 指到控管規則負責人，並必填依據文件（09-F10，另見 RA-37）。
  - **衝突**：(1) 分類軸——`control_effect`（02-5、02-6）、控制方向＋控制負責人（04-F19）、控管類別（10-P19）、變更類型（05-E24），四種分類並存未整合。(2) 稽核角色——02-6「稽核知會不簽」、04-F19「通知稽核」，對比 10-P19「證據保存類插入稽核關卡、職責分離與安全類由稽核或資安」及 02-5「保存年限調降需要稽核室的角色參與核准」；後兩者與 01-15 稽核不得為設定變更簽核人衝突。
- **相關**：D12、A10；骨幹 K-SETTING-ADMIN（仍寫「只有系統管理員能改」，與 D12 不一致，01-13）；RA-48。

### RA-32 可以關掉控制的參數

- **問題**：`approval.mobile_mfa_required` 被改成 false「提升效率」或在 MFA 故障時被關；`audit.retention_years` 從 10 改成 2，清除作業刪掉三年前的事件；互惠核准偵測、拆單累計期間可被調寬。（02-5、03-18、04-F01、04-F06、10-P19）
- **對稽核過關的影響**：只要能被兩個資訊部的人關掉，會計師就要測全年每一天的參數值；關過一天，那段期間的控制無效。
- **各立場的解法**：
  - `setting_definition` 增加 `control_effect`（none／strengthen_only／weakening_requires_control_owner）與 `hard_floor`、`hard_ceiling`；稽核資料包附期間內所有控制相關參數的值與變更歷程（02-5）。
  - 核心規則不得有關閉開關；真正無法等待的事走緊急路徑而不是關掉控制（03-18）。
  - 偵測與累計門檻可調，但放寬屬嚴格設定變更（04-F01、04-F06）。
  - 保存期類設定有下限，低於下限插入法務（10-P19）。
  - **衝突**：MFA 參數的存廢見 RA-14（移除對比改名後依流程與級別可設）。
- **相關**：骨幹第 5 節「流程包不能關閉」與第 8 節可設參數矛盾（02-5）；D12。

### RA-33 設定變更母體的完整性

- **問題**：全年 46 張設定變更單都有雙人覆核，但 (1) 廠商升版的 migration 拿掉了 L3 的資安合規檢查關卡；(2) MIS 用 `psql` 改了一筆 `setting_value`；(3) AD 群組同步直接給平台角色；(4) DC 端點、IdP issuer、MFA 服務、寄件網域等控制相關連線設定在環境變數裡，被半夜改指向模擬器忘了改回；(5) `api_client`、webhook 訂閱、可信代理清單、通知範本、機密輪替不在 D12 範圍；(6) 組織資料與代理不在 D12 範圍。（01-13、02-4、02-7、07-15、03 對 D12 的意見、03-22、02-20、04-F20、04-F03）
- **對稽核過關的影響**：雙人覆核只管到前門；07-15 指出這是一條「不需改資料庫、不需動雜湊鏈就能讓證據全部失真」的路。
- **各立場的解法**：
  - 升版帶來的定義變更自動產生「待生效」的設定變更單，由客戶流程管理者與另一人覆核後生效（01-13）；流程包升版腳本只能載入初始版本，之後一律走 D12（02-4）。
  - 設定指紋與 DDL／DML 稽核（RA-03）。
  - 控制相關連線設定移進平台成為受管設定，變更走 D12；故障時一人提出立即生效、24 小時內另一人複核，逾期自動恢復並列例外；每筆交付、驗證、MFA 結果的事件記下對方端點與憑證指紋，指紋不在登記清單上即視為失敗（07-15）。
  - `api_client` 建立、範圍、金鑰輪換走設定變更（02-20、03-15）；通知範本的連結由系統產生、範本作者不能寫任意網址，範本修改進事件（03-22）。
  - 外部同步進來的角色指派依敏感度處理（RA-38）。
  - **衝突**：連線設定的緊急變更——07-15 允許一人先生效、事後複核，與 D12「由提出人以外的人核准」的事前覆核不同。
- **相關**：D12、A10；骨幹 K-SETTING-ADMIN「路徑只能由升版變更」與 D12 矛盾（01-13、02-4）；engineering-standards「路徑只能透過 migration 變更」與 D12 矛盾（02-4）。

### RA-34 平台自身與流程包的升版

- **問題**：開發人員修 bug 時順手改了職責分離檢查，以 `wip:` commit 推上 main，自己用 `sgn_owner` 在正式環境執行 migration；正式環境跑哪個版本、誰核准上線無紀錄；升到一半失敗不能回復；CVSS 9.8 弱點地端客戶兩個月沒修，因為升版要走變更控制而變更控制就在平台上；升版改了 `compare_content`，進行中的 14 張單與過去的判斷無法重現；客戶自寫的 hook 以 `sgn_owner` 執行、核心升版後失效；每季升版都要重做兩週驗收。（02-4、03-19、03-23、07-1、07-17、12-B13、12-B19、12-B20）
- **對稽核過關的影響**：程式變更是 ITGC 三大塊之一；變更控制無效時，會計師不能依賴任何自動化控制（02-4）。
- **各立場的解法**：
  - 平台升版走自己的「程式變更上線」流程包：升版程序先檢查有已核准的申請單、核准人與上線人都不是開發人；套用前後寫事件含 migration 雜湊；每日資料庫物件定義指紋與最近核准版本比對，不一致為最高等級例外（02-4、07-1）。
  - 發行版與 main 分開：只有通過檢查與驗收的簽章標籤是發行版，附離線安裝包、SBOM、校驗碼；D7 只適用開發期（02-4、03-23、07-1、12-B19）。安全關鍵模組列為受保護路徑，需人工審查與專屬繞過測試；第三方滲透測試（03-23、12-B20）。
  - 單一交易升版、維護模式（進出寫事件）、只往前修、事前在還原副本演練（07-1）。
  - 緊急安全修補路徑：事前資安長即時核准、事後完整覆核；管理畫面顯示已知弱點與修補期限，逾期列例外；升級包驗證原廠簽章（03-19）。
  - 判斷邏輯變更時，升版工具先試算進行中的單「新舊結果不同」的清單附在程式變更單上；有差異的單標示「判斷邏輯已更新」（07-17）。
  - 長期支援版本（24 個月）、修補時限（CVSS 9 以上 7 天、7 以上 30 天）、每個版本附「控制影響說明」對應控制對照表（12-B19）。
  - 客戶 hook 介面帶版本並支援前一主版本；以權限受限角色執行（只讀核心視圖、不能寫核心表、不能連網）；流程包安裝與升版是一張設定變更單（12-B13）。
  - **衝突**：自我管理的循環依賴——02-4、07-1 要平台升版走平台自己的流程；03-12 指出平台不可用時正是最需要變更的時候，需要不依賴平台的緊急通道（見 RA-20）。
- **相關**：D7、D23（03 對 D23：安全關鍵模組需人工資安審查）、D13、D14；RA-08（判斷邏輯版本）、RA-36。

### RA-35 設定的生效時間、回溯與期限

- **問題**：設定變更的生效時間填成上個月 1 日，讓上個月已逾期的單變成未逾期；董事會 7/1 生效的核決權限 7/15 才進平台；上線期把升級天數暫時調大，事後忘了改回；新任財務長到職當天才開角色變更單，空窗三天；颱風假前一晚宣布，D12 雙人覆核的覆核人已睡了。（02-6、09-F10、11-14、08-14、07-6）
- **對稽核過關的影響**：回溯生效等於事後改寫依據；落差期間的單未依核決權限辦理且不會被找出來。
- **各立場的解法**：
  - 生效時間不得早於最後一關核准時間，資料庫層強制（02-6）。
  - 記錄「依據生效日」與「設定生效日」，有落差時自動產生落差期間的例外清單由權責主管追認或補簽（09-F10）。
  - `setting_value` 增加生效結束時間，到期自動回到原值並寫事件（11-14）。
  - 設定變更可預約生效，生效條件可引用人事事件（08-14）。
  - 行事曆「只延長時限」的變更由流程管理一人提出即生效，事後 2 個工作天內另一人覆核，不同意則恢復並重算；縮短時限仍走一般雙人覆核；依新行事曆撤回不該發生的升級（07-6）。
  - **衝突**：07-6、07-15 的「一人先生效、事後覆核」快速路徑，與 D12 事前雙人覆核不一致；是否擴大成通用的「只往嚴的方向變更」快速路徑未討論。
- **相關**：D12、A10；RA-37。

### RA-36 新版設定與進行中申請單的銜接

- **問題**：新路徑加了個資窗口一關，一張 4/28 退回的單 10 月才只做縮小重送，依 K-RETURN 從退回關繼續且仍用舊路徑；詐騙未遂後收緊規則，9 張高風險單照舊路徑跑完、40 筆 6 個月 L4 授權超過新上限；上線第二週發現級別規則設錯，210 張進行中、40 張已生效；草稿在改版後送不出去或被悄悄截短期間；開發者照 D12 字面把解析出的簽核人一起凍結，已不具資格的人仍可簽。（01-14、09-F11、11-19、06-23、08-9、08-24）
- **對稽核過關的影響**：新控制生效後仍有申請依舊程序核准；已知控制缺陷被版本規則掩蓋。
- **各立場的解法**：
  - 設定變更時宣告對進行中單的處理；預設「退回或擴大重簽時改用新版；沿用舊版超過 N 天（預設 30 天）自動補上新增關卡」；資料包可篩出「核准時用的路徑不是當時最新版」的單（01-14）。
  - 銜接方式由核心定義、由核准人一併核准：只適用新案／進行中補上新增關卡（只增不減，以加簽實作）／既有授權依新上限縮短或列入一次性複查；收緊預設「補關卡＋既有授權複查」，放寬預設「只適用新案」（09-F11）。
  - 「控制瑕疵修正」：說明瑕疵、試算影響；進行中的單依新規則重新判定，更嚴則插入缺少關卡（不從頭重簽），更寬則維持原路徑；已生效授權開補核，逾期撤銷；整件事是一筆例外；核准人多一位（例如內控主管）（11-19）。
  - 草稿一律用送出當時的版本，打開時以人話告知改了什麼；影響試算含受影響的草稿數（06-23）。
  - 「沿用送審時版本」只適用路徑與參數，不適用組織事實與角色持有人，它們在每關開始與決定時依目前事實解析（08-9、08-24）。
  - **衝突**：預設行為——01-14 以「沿用天數」觸發補關卡；09-F11 以「收緊或放寬」決定預設；11-19 另設「瑕疵修正」一類並多一位核准人。三者觸發條件不同。
- **相關**：D12「進行中的申請單繼續用送審當時的版本」、K-RETURN；RA-34（判斷邏輯變更的試算）。

### RA-37 核決權限表

- **問題**：董事會修訂的核決權限表與平台設定沒有連結；240 萬合約拆成三張 80 萬、換三個申請人繞過財務長；L4 個資組合以三張 L3 單分別取得；背書保證、資金貸與、重大資產取得處分的最後一關是董事會或審計委員會決議，只能讓董事會祕書代按；申請人挑門檻較寬的公司別。（09-F10、04-F06、04-F07、09-F12、04-F25）
- **對稽核過關的影響**：「未依核決權限辦理」是證期局常見缺失；拆單是上市櫃內控缺失最常見的型態之一；祕書代按使紀錄顯示核決層級不符。
- **各立場的解法**：
  - 核決權限表是有版本的受控文件：設定變更必須引用依據（文件版本、董事會或權責主管核准日、預定生效日）；核准人限定為該流程類型的控管規則負責人；預定生效日前未完成列例外；平台輸出「現行核決權限對照表」，財會主管每季簽核一次「平台設定與核決權限表一致」，作為內控聲明書佐證（09-F10）。
  - 合約對象結構化（統一編號或供應商主檔代碼）；核心提供宣告式「累計分級」：同對象、N 天內、同公司別所有單（不分申請人、排除取消與駁回）合計達門檻則升級，簽核畫面列出被累計的單，並產生「疑似拆單」例外給流程管理者與稽核（04-F06）。
  - 資料擁有者宣告「組合規則」，以自然人可觸及的所有有效授權加本單一起評估；這個查詢同時是知悉人員名單的反向查詢（04-F07）。
  - 關卡模式新增 `resolution`（會議決議）：議事單位登錄會議別、日期、議案編號、決議內容、出席與迴避、議事錄，決定者記為會議、登錄者記為紀錄人；登錄人與確認人不同；SLA 依下次會議日計算；`governance_meeting` 可對應多張單並比對單號與金額（09-F12）。
  - 公司別由內容歸屬決定、跨公司取較嚴（04-F25，見 RA-29）。
- **相關**：D13、A8（核決權限表做成 resolver 種類）、D14（04 建議加入累計與組合兩種宣告）、D16（09 指出缺「會議決議」這種決定者）；RA-25（關係人交易加關）。

### RA-38 權威來源的事實與平台設定

- **問題**：AD 群組 `GRP-MIS` 對應平台 `mis` 角色，AD 管理員把外包工程師加進群組，同步後即可認領 MIS 工作；系統管理員在平台改申請人的主管關係兩週以挑簽核人；人資專員把主管欄位暫時改成好友；資料擁有者由人資職位自動帶出，每次人事異動是否都要開設定變更單。（02-7、04-F20、08-23、08-24、08-14）
- **對稽核過關的影響**：平台角色實際由 AD 決定，AD 群組變更不在平台紀錄裡；resolver 的輸入能被單方修改，職責分離失去意義；若全部走簽核則改派卡死、人資與平台雙軌。
- **各立場的解法**：
  - 會影響控制的角色（`mis`、`auditor`、流程管理、技術維運、資安長、財務長、印鑑管理人、資料擁有者等）同步只能「提議」，平台內核准後生效；同步移除立即生效；一般屬性（部門、職稱）同步即生效並每日產生差異報表；角色定義新增 `assignment_source_policy`（02-7）。
  - 組織資料以人資來源為準；平台內手動覆寫是一張「組織資料覆寫申請單」，由人資核准（提出人不得是當事人或其上下屬鏈），預設最長 30 天到期回到來源值；每日比對差異；`case_task` 記下解析所用的主管關係與來源（04-F20）。
  - 把資料分兩類：權威來源的事實（雇用、單位、職位、主管、代理主管）平台不簽核，以雙時間、同步防護、短期異動偵測控管，並把來源登記為有負責單位的「受管來源」；平台的設定（路徑、參數、角色定義、角色與職位的對應規則）走 D12；角色可宣告「依職位推導」，推導規則走 D12，推導出的持有人隨人事事件改變不需每次開單、但寫事件並引用人事事件（08-24）。
  - 短期主管異動被用於簽核列例外（08-23，見 RA-24）；角色預約生效（08-14）。
  - **衝突**：控制角色的持有人改變——02-7「同步只能提議、平台內核准後生效」對比 08-24「依職位推導的持有人隨人事事件改變、不需每次開單」。平台內是否可覆寫組織資料——04-F20 允許經人資核准的覆寫單；08-24 主張平台不簽核權威事實、以偵測控管；11-7 主張解析失敗時由流程管理者逐單指定而非覆寫組織資料。
- **相關**：D12、A10、`role_assignment.來源`；RA-28。

### RA-39 假時鐘與時間來源

- **問題**：`system.allow_fake_clock` 是可經 D12 修改的參數，兩位熟識的維運人員可設成 true 再設 `sgn.fake_now` 讓逾期確認變準時；測試環境設定匯入正式環境；稽核事件時間是否吃 `fake_now` 未定義；虛擬機從快照回復時間倒退、TOTP 失敗；部分 function 用了後端傳入的時間。（01-5、02-5、03-20、07-2、07-14）
- **對稽核過關的影響**：時間可被操控時，所有時限控制（逾期、到期、催辦）的有效性都受質疑；序號遞增而時間倒退會被懷疑紀錄被插入。
- **各立場的解法**：
  - 拿掉參數，改為建置時常數或部署設定：正式安裝包不包含讀取 `fake_now` 的程式路徑；稽核事件時間一律取資料庫交易時間，另記「業務時間」欄位供測試（01-5、02-5）。
  - 架構測試確認正式組態下 `sgn.fake_now` 無作用；每筆事件同時記 `clock_timestamp()`（02-5）。
  - 正式環境啟動時檢查假時鐘必須為 false 且環境 id 與登記一致，否則拒絕啟動（03-20）；只有登記為測試的環境識別碼才能開假時鐘（07-2）。
  - 平台每次啟動寫事件記時間來源與 NTP 狀態，與外部檢查點時差超過門檻列例外（01-5）；後端傳入的時間只作「用戶端宣稱的時間」另存；時間早於前一筆照常寫入並另寫「時間異常」事件、不拒絕寫入；定期比對後端、資料庫與 NTP 偏差（07-14）。
  - 無明顯衝突。
- **相關**：骨幹第 1 節（假時鐘 GUC）、第 8 節 `system.allow_fake_clock`；RA-05（環境身分）。

### RA-40 啟動、初始基準與上線範圍

- **問題**：上線當天所有初始設定由導入顧問用腳本一次載入，沒有核准紀錄；上線前沒有人能擔任覆核人；試營運在正式環境送了 140 張單、60 張真的套用，MIS 想清空重來；依部門分批上線時，資料擁有者在尚未上線的部門；子公司從母公司複製流程；只納管了資訊部提供的 18 個系統，另外 11 個業務單位自購的系統是盲區；客戶不可能五種流程同時上線。（02-6、11-8、11-9、11-10、11-11、11-20、12-B17）
- **對稽核過關的影響**：設定母體的起點沒有核准紀錄，期初控制設定本身不可依賴；外部顧問實際決定全部控制規則卻不在紀錄上；同一份資料同時有兩套控制。
- **各立場的解法**：
  - 上線時產生「期初設定基準」申請單，內容是全部設定的快照與雜湊，由流程擁有者與控制負責人核准；此前的設定事件標為「導入期」（02-6）。
  - 「啟動模式」：只能指派第一批管理角色與提交初始基準；初始基準附人看得懂的基準報告（路徑圖、參數差異、角色與擁有者名冊、範圍聲明），由公司指定的兩位以上主管（例如流程負責人與內控主管）核准，導入顧問列為提出人，稽核只見證；核准後離開啟動模式且不可回到啟動模式；基準雜湊為鏈的第一個錨點（11-9）。
  - 試營運就是範圍受限的正式營運，不另設「不算數」模式（11-10）。
  - 依資源（受管系統或主題包）分批上線，上線範圍有版本、走 D12；未上線資源的申請不能送出（11-11）。流程類型可依公司別逐一啟用（12-B17）。
  - 受管系統範圍聲明：每個盤點到的系統標示已納管、排定納管（日期）、不納管（理由），變更走設定變更，排定到期未納管列例外，外部管理人無保證人不得為已納管（11-8）。
  - 子公司的初始基準報告標示與母公司的差異；上線前就緒檢查（11-20）。
  - **衝突**：初始基準的核准人——02-6「流程擁有者與控制負責人」；11-9「公司指定的兩位以上主管，例如流程負責人與內控主管」，並明定稽核只見證。
- **相關**：D12、D13、D19、D7（11 對 D7 的意見）；資料授權規則〈技術〉「上線範圍為全公司」與分批上線不符（11-11）。

### RA-41 既有權限的承接

- **問題**：DC 上 2,400 筆既有權限沒有申請單；MIS 為了畫面乾淨在 DC 端標記忽略，或導入顧問把它們建成正常的「生效中」授權；其中 1,650 條直接授給個人，而平台不允許授權給個人；37 個帳號對不到人（共用、服務、離職未停、回任）；擁有者一次收到 812 筆、20 分鐘全選保留；追認後的授權一年後同一天到期；第一次對帳出現 2,300 筆差異，大家開始忽略例外；上線第一天沒有前案與範本。（01-6、02-10、11-1、11-2、11-3、11-4、11-15、11-17）
- **對稽核過關的影響**：全部匯入成正常授權等於洗白；全部列為差異則例外清單失去意義；20 分鐘確認 812 筆會被判定複查無效，「限期轉正」只變成延後 90 天洗白。
- **各立場的解法**：
  - 匯入為特殊來源的「既有權限」，不冒充核准；有效期強制設為上線後 N 個月（預設 3 個月）；匯入當下自動開複查，由資料擁有者逐筆決定轉正式申請（預填、走完整路徑）或撤銷；期限到未處理者自動撤銷；匯入本身走 D12（01-6）。
  - 授權來源 `migrated`：記錄來源系統、匯入檔雜湊、匯入人、與來源報表的筆數核對；上線後 N 天（預設 90 天）內自動開複查，負責人確認保留即產生正式核准紀錄；報表上與正常授權分開呈現（02-10）。
  - 過渡型被授權者 `legacy_individual`（只能由匯入產生、強制結束日、不能續期、擴大或出現在新申請），規則 `K-LEGACY-TRANSITION`；匯入工具依「同單位、同主題包、同欄位」提出合併成團隊授權的建議（11-1）。
  - 身分對應報告，對不上的帳號分四類（離職者撤銷／共用帳號轉 agent 並限期拆分／服務帳號轉 agent／回任合併），每類處理都是設定變更單的一部分；90 天未登入預設建議撤銷（11-2）。
  - 追認分波分風險：L4、可匯出、離職者主管名下、90 天未使用者先；每位擁有者每波上限（預設 50 筆／週）；以分群後的群組為單位；擁有者確認＋被授權者負責人確認兩個不同的人，L4 再加資安長；90 天未用者不能批次；通過後產生來源種類 `ratified` 的單，起日為追認日、不回溯（11-3）。
  - 追認時錯開到期日（只縮不長）；到期量預測做成一般功能（11-4）。
  - 對帳差異分類（期初待追認、在途承接中、平台不管的技術權限、真正未核准）；「對帳排除項」有理由、負責人、最長一年到期、走 D12；稽核準備度分「轉換中」與「真正例外」，逾期轉為真正例外；第一次對帳結果存證為期初基準（11-17）。
  - 追認與承接的單可作為前案與範本來源（11-15）。
  - **衝突**：(1) 過渡期——3 個月（01-6）對比 90 天（02-10），而 11-3 的每週 50 筆上限在 812 筆時需約 16 週，超過兩者。(2) 誰決定——資料擁有者（01-6）、負責人（02-10）、擁有者＋被授權者負責人兩人且 L4 加資安長（11-3）。(3) 轉正方式——走完整申請路徑（01-6）、確認保留即產生正式核准（02-10）、產生 `ratified` 單（11-3）。(4) 期滿未處理——自動撤銷（01-6）對比「自動撤銷或列為例外」（02-10）。
- **相關**：D1（11 指出「規則完全不變」在期初做不到，需要有期限的轉換型態）、D3、D10、骨幹 `principal` 類型；RA-44、RA-45、RA-47。

### RA-42 舊系統在途單、歷史紀錄與跨切換日的查核

- **問題**：切換日 EIP 上還有 180 張在途單，核准後 MIS 照開而平台沒有紀錄；EIP 表單沒關，30 人繼續送、5 張兩邊都核准；EIP 下架時 6,000 張歷史紀錄要保存，轉成平台事件會讓「2021 年的事件在 2027 年才進鏈」；會計師查核期間跨過切換日，一鍵資料包只有平台上的單。（11-12、11-13、11-21、12-B17）
- **對稽核過關的影響**：切換前後的控制沒有書面依據；偽造了平台沒有見證過的事件；第一次查核就要人工整理兩段母體，會計師對平台的第一印象決定之後是否依賴。
- **各立場的解法**：
  - 每個資源上線當日舊系統對應表單改為「不能新送」並截圖存證；在途單在舊系統跑完，期限 N 天（預設 30）；舊系統核准以 `legacy_approval` 承接（附舊單號、核准軌跡檔與雜湊），由 MIS 以外的人執行，只能承接上線日存證的在途清單內的單，並跑重疊檢查（11-12）。
  - 歷史封存區：唯讀、可搜尋、整包與每檔雜湊、寫**一筆**事件；明確標示「內容正確性以舊系統當時的控制為準」，不納入資料包母體；匯入走雙人確認，核對人與匯出人不同；保存年限依原始單日期（11-13、12-B17）。
  - 稽核資料包跨越上線日時自動附「控制轉換說明」：每個資源哪一段由平台控制、舊方式期間的資料來源與筆數、切換證據；授權清單包含所有來源種類並可勾稽；提供「控制轉換備忘錄」範本由內控主管簽核（11-21）。
  - 無明顯衝突。
- **相關**：open-questions M10（第一版不整合舊系統）、A2；RA-06、RA-47（01-7 的線下決定登錄可部分借用，11-12 提及）。

## 五、例外管理與稽核作業

### RA-43 例外實體與生命週期

- **問題**：MIS 為了讓儀表板變綠一次全選 55 筆「已處理」、備註空白；例外由造成它的人自己結案；條件消失（帳號被刪）但問題沒處理；第一次對帳 2,300 筆淹沒真正的例外；內控自評需要缺失分級、改善計畫與追蹤；廠商執行不一致的例外被送回廠商自己結案；行為型例外不存在。（01-10、11-17、09-F17、07-20、04 對 D10 的意見、03-5）
- **對稽核過關的影響**：「例外自己浮現、追蹤到結案」只做了一半；缺失追蹤沒有根因與佐證，會被開「結案者與責任者為同一人」。
- **各立場的解法**：
  - 例外是核心實體：種類（各有規則代碼）、偵測時間、受影響對象、責任人（依受管系統或流程類型指派）、狀態（開立 → 處理中 → 待覆核 → 結案／接受風險）、結案分類、根因分類、佐證；條件消失時轉「待覆核」而非直接結案；結案或接受風險需非責任人覆核；接受風險限流程管理者以上且有到期日；同類再發自動關聯前案；不允許批次結案（可批次指派）；稽核只能留言不能改狀態；資料包含已結案者與其軌跡（01-10）。
  - 「轉換中」與「真正例外」分開顯示，轉換中逾期轉為真正例外（11-17）。
  - 缺失分級（缺失、重大缺失）、根因、改善措施、負責人、預定與實際完成日，逾期未改善升級到稽核主管（09-F17）。
  - 執行與核准不一致的例外送業務擁有單位主管，不送回執行者（07-20）。
  - 例外種類需含行為型（RA-24）、技術控制中斷（07-12 的自我檢查，屬另一份彙整）。
  - **衝突**：09-F17「逾期未改善升級到稽核主管」與 01-10「稽核不能改狀態」是否相容未說明（升級是通知或指派）。
- **相關**：D10、A2（稽核準備度畫面）；platform-vision「例外自己浮現」；RA-48。

### RA-44 定期複查的品質

- **問題**：資料擁有者週五 4:58–5:00 全選保留 312 筆，其中 23 筆被授權者已解散、11 筆半年未存取；撤銷了 12 筆但 DC 一個月後還在；季度複查一天湧進 300 筆加 40 張日常單；複查只看現存授權，「用完就撤」者不在範圍；升遷後複查自己的授權；期初追認 812 筆 20 分鐘按完。（01-11、02-15、05-E08、04-F23、08-21、11-3、12-B22）
- **對稽核過關的影響**：存取複查流於形式是 ITGC 最常見的缺失之一，會計師判定控制無效；只留「誰按了保留」無法支持精確度測試。
- **各立場的解法**：
  - 每筆顯示判斷所需的事實（最近使用時間、被授權者狀態、負責人是否在職、與核准差異、職責衝突）；有風險訊號的項目不能全選，必須單筆決定並填理由；無風險訊號者可整批保留；記每筆顯示內容雜湊、決定時間與方式；逾期升級或自動撤銷；複查人不得是被授權者成員或負責人本人；複查統計（全選比例、平均時間、撤銷率）列入資料包；無使用資料本身是風險訊號（01-11）。
  - 活動開始時凍結母體（快照、雜湊、筆數），結束時對帳；「未使用」「有職責衝突」「期初承接」項目不能批次；撤銷觸發核心撤銷並在下次對帳確認外部已移除；複查統計給控制負責人（02-15）。
  - 錯開發送、每人每日上限；被授權者負責人初審、副總只看初審結果與例外；不提供「全選」，低風險項目逐列勾選後一次確認；90 天未使用預設建議撤銷；不回應撤銷前 3 天通知負責人（05-E08）。
  - 範圍是期間內任一時點有效的授權（04-F23）；`K-REVIEW-SOD`（08-21）。
  - 複查畫面納入使用紀錄（最後登入、最後使用），使用紀錄只作參考（12-B22）。
  - **衝突**：(1) 全選——01-11 無風險訊號者「可整批保留」；05-E08「不提供全選」，逐列勾選後一次確認。(2) 複查人——01-11 以資料擁有者為複查人並排除成員與負責人本人；05-E08 由被授權者負責人初審。兩者對負責人能否參與複查結論相反。
- **相關**：骨幹第 11 節 `access_review_campaign`／`access_review_item`（細節在尚未撰寫的 05-integration）；研究 M5；RA-41（期初追認）。

### RA-45 批次核准

- **問題**：87 張續期批次核准，會計師問「他看到了什麼」；「無差異」只比內容，被授權者成員從 3 人變 26 人、資料分級已由 L3 改為 L4、負責人變了都混在批次裡；一次被盜的 session 可一次核准很多張；L4 未公告財報的續期一次按掉 20 張；25 張同一範本的新申請不能批次，第 15 張以後實際已不看；週期性需求的前案已到期，不算「續期」不能批次。（01-12、02 對 D3、03-1、04-F15、05-E20、06-13、08-25、09-F18、10-P15、11-3）
- **對稽核過關的影響**：「無差異」只證明內容沒變、不證明仍需要與風險沒變；09-F18 引用中信銀裁處書「核章但未留下覆核之軌跡」被裁罰。
- **各立場的解法**：
  - 批次事件記批次 id、每張內容版本雜湊、顯示摘要雜湊；可批次條件再加「前一期有使用紀錄且無未結例外」；單批上限（01-12）。批次時做一次強驗證（02 對 D3）；挑戰值涵蓋整批每張的版本雜湊（03-1）。
  - 情境無差異：依目前規則重判的級別相同、成員增減不超過參數（例如 20% 或 5 人）、負責人相同、無未結案對帳差異或例外、資料分級未變、所屬單位未改組；不符者踢出並寫明原因（04-F15、08-25）。
  - 內線事件資源或機密資源可宣告「不可批次」、預設不可批次但可逐張快速核准；批次畫面列出每張的成員異動摘要（09-F18）。
  - 同質批次：同一份擁有者標準範本、內容與範本無差異、期間不超過常態、無重疊、無受益人衝突、非最高級別；逐列勾選、無全選、一次 passkey；預設只開 L3，流程類型可關閉（05-E20）。
  - `K-BATCH` 的「續期」擴大為「與來源單無差異的申請，來源單到期在參數內（例如 120 天）也算」（06-13）。
  - 追認的批次只限「保留原樣」且排除 90 天未使用者（11-3）。
  - 每張單的顯示快照都要記錄（10-P15）。
  - **衝突**：方向相反——擴大批次適用範圍（05-E20 同質新申請、06-13 已到期前案、11-3 追認）對比收緊（01-12 要求前期使用紀錄、09-F18 內線資源預設不可批次）。01-8 另要求「追認型的單不得批次核准」，與 11-3 追認可批次衝突。
- **相關**：D3（「調查若顯示稽核不接受批次核准，再進一步限制」，09-F18 指出目前沒有觸發條件）、K-BATCH；RA-14、RA-22。

### RA-46 緊急路徑與急件

- **問題**：程式變更 31% 走緊急路徑，一位工程師占一半，補簽 100% 核准且平均在到期前 10 分鐘按下；緊急權限「用完就收」，提前收回後沒有東西需要補簽；會議上總經理口頭先准，MIS 先開權限、事後補單；主管機關要求週一前交資料，L4 路徑走不完；年度結帳要子公司總帳；資安需要的是止血用的暫停而不是給權；弱點修補與故障時的連線設定變更也需要緊急通道。（01-9、02-21、04-F09、05-E18、06-3、09-F03、03 對 D13、03-19、07-15）
- **對稽核過關的影響**：緊急常態化表示正常路徑的預防性控制被系統性繞過；補簽只看申請內容看不到「做了什麼」，覆核流於形式。
- **各立場的解法**：
  - 啟用必填事件編號；補簽畫面顯示實際操作紀錄（特權工作階段紀錄或受管系統回報，取不到時執行人上傳並由補簽人確認看過）；補簽人不得是啟用人或其同一直屬主管下的同事；緊急使用率依人、系統、流程類型列入稽核準備度；補簽拒絕即自動撤銷並啟動調查（01-9）。
  - 至少一人事前即時核准（不得是申請人或執行人）；有效期以小時計且不得續期；事後審查判定「確屬緊急」或「不應走緊急」，後者列入申請人與核准人的統計（02-21）。
  - 宣告緊急時指定「見證人」，可在事後幾分鐘內確認、確認前權限仍可生效；權限結束（不論到期或提前收回）一律產生事後複核，複核人不得是宣告人、見證人或其下屬，附期間活動紀錄（拿不到標示「自報」）；90 天內超過次數列例外給主管與稽核（04-F09）。
  - 緊急路徑通用化：流程類型宣告是否允許及誰可發起；有核決權的高階主管可在手機兩步「緊急核准，72 小時內補完」，執行可先進行，逾期自動收回並列例外；使用頻率報表（05-E18）。
  - 急件不改路徑只改時效：結構化的需要完成日與急件原因，各關改用以小時計的急件時限並即時推播，簽核人可否決急件；急件比率列例外；流程類型選項 `allows_urgent` 與 `allows_emergency_path` 分開；先給後審只開放給資料可收回的情境（帳號、角色），資料授權不開放（06-3）。
  - L4 未公告資訊不允許先給後審；可預見的結帳需求以事前核准的「生效窗口」授權處理（綁循環事件，窗口外判定拒絕）；急件時限以小時計（09-F03）。
  - 止血用的暫停與給權的緊急路徑分開（03 對 D13，見 RA-16）；緊急安全修補路徑（03-19）；控制相關連線設定的緊急變更（07-15）。
  - **衝突**：(1) 事前核准——02-21 必須有一人事前即時核准；04-F09 見證人可事後確認、不擋生效（理由：深夜找不到人會耽誤事故處理）。(2) 資料授權能否先給後審——05-E18 的口頭先准情境正是資料授權，主張開放緊急核准入口；06-3、09-F03 主張資料授權（至少 L4 未公告資訊）不開放，因資料看過就收不回。(3) 補簽觸發——validation-cases「逾期自動收回並列為例外」以使用中為前提；04-F09 改為由「權限結束」觸發。
- **相關**：D13、A8、validation-cases「緊急路徑」；RA-47。

### RA-47 追認與補登

- **問題**：平台停擺或簽核人沒帳號時以 email 核准，事後用申請人名義補單並請主管「照 email 簽一下」，核准時間是三天後；對帳發現未核准權限後補一張起日填 7/1 的單，差異隨之消失；IdP 中斷一整天，財務長 email 同意、先用印；ERP 管理員直接改供應商主檔後補單；回溯調職後，舊主管在空窗期簽的單依新資料不成立；核決權限落差期間的單；資料擁有者在預告期內的決定。（01-7、01-8、05-E18、07-8、09-F16、08-3、09-F10、11-12、11-16）
- **對稽核過關的影響**：核准紀錄與實際決策時點不符，是最常見的「事後補做」型缺失；補單掩蓋未核准存取期間；不承認線下決定，它們就會變成假的線上決定（01-7）。
- **各立場的解法**：
  - 核心動作「線下決定登錄」：由登錄人（不是原決定人）上傳原始佐證（.eml、簽名掃描），填實際決定人、實際決定時間、原因；記「登錄時間」與「宣稱的決定時間」兩個時間；原決定人在系統內確認（新事件）；整張單標記「含線下決定」並自動列例外；停擺期間由平台產生停擺事件可對照；沒有平台帳號的簽核人比例超過上限列例外（01-7）。
  - IdP 中斷記為 `service_outage`；恢復後流程管理在緊急路徑上開「中斷期間的系統外決定」補登單，附證據與實際時間，列為例外，由未參與者複核才能結案（07-8）。
  - 授權起日不得早於核准完成日（平台強制）；補單必須引用對帳發現，發現不消失而轉為「已補核准」並保留未核准存在期間；簽核畫面第一眼顯示「這是追認，未核准期間 7/1–11/5」；追認型的單不得批次（01-8）。
  - 對帳發現與後補的申請自動連結，簽核人選「追認」或「不追認並撤除」，追認不消除例外（05-E18）。
  - 對帳一般化為「核准狀態 vs 實際狀態」（新 hook `describe_expected_state`）；補單標示「事後補正」並引用對帳例外編號，路徑自動加一關內部稽核或財會主管（09-F16）。
  - 回溯異動影響已完成的簽核列例外，由依新資料應簽的人追認（新事件，不改原紀錄）；不可撤銷的流程只能追認或記錄例外（08-3）。
  - 核決權限落差期間的單由權責主管逐筆追認或補簽（09-F10）。
  - **衝突**：(1) 09-F16 補單路徑「加一關內部稽核」與 01-15 稽核不得為簽核人衝突。(2) 登錄者——01-7「登錄人不是原決定人」、原決定人事後確認；07-8「流程管理開補登單、未參與者複核」。(3) 01-8「追認型的單不得批次」與 11-3 追認可批次衝突（見 RA-45）。
- **相關**：D16（01 建議補「線下決定登錄」動作）、K-FULFIL、資料授權規則「授權起迄申請人自填」；RA-41、RA-42、RA-46。

### RA-48 稽核的獨立性

- **問題**：公司把稽核主管排成設定變更的最後一關；稽核角色的指派由技術維運提出、流程管理者核准，受查單位可縮短稽核人員的角色期限；稽核的查閱紀錄同步到 MIS 監看的 SIEM、且「誰看過這張單」對申請人可見，暗中調查隔天走漏；多個立場的解法讓稽核擔任簽核、核准或結案角色。（01-15、01-16、10-P10，以及下列衝突來源）
- **對稽核過關的影響**：稽核參與受查事項的核准違反內部稽核準則，獨立性受損；稽核權限受受查者控制，等於讓被查的人決定稽核能看什麼。
- **各立場的解法**：
  - 引擎強制：持有稽核角色者不得被任何 resolver 解析為簽核人、執行人或例外結案覆核人（撞到時當作設定錯誤擋下）；稽核角色的授予與撤除自成一種設定變更，由稽核主管提出、由董事會或審計委員會指定的「稽核治理人」核准；撤除或縮短時通知稽核主管與稽核治理人；稽核可留言與被通知（01-15）。
  - 稽核的查閱照常寫入事件，但對一般使用者與當事人的查閱紀錄畫面不顯示；送 SIEM 時只送雜湊與類別或延後 N 天；完整內容只有稽核主管與稽核治理人看得到（01-16）。
  - 查閱紀錄只有稽核、個資窗口與該單流程管理者能查；不提供「誰看過我」給一般使用者（10-P10）。
  - 資料更正、初始基準等由稽核「收通知」或「見證」而非核准（07-11、11-9）；設定變更「稽核知會不簽」（02-6）。
  - **衝突**（其他議題中讓稽核擔任決定角色的解法）：
    - 頂層替代簽核人可為稽核主管（06-11，RA-28）。
    - 事後補正單「加一關內部稽核」（09-F16，RA-47）。
    - 證據保存類設定插入稽核關卡、職責分離與安全類由稽核或資安核准（10-P19）；保存年限調降需稽核室角色參與核准（02-5）（RA-31）。
    - 銷毀單由稽核核准（10-P3）或由紀錄擁有單位（法遵或稽核）核准（09-F08）（RA-09）。
    - 還原例外由稽核室結案（02-2，RA-05）。
    - 例外逾期升級到稽核主管（09-F17，RA-43）；行為型例外派給稽核（04-F01、08-23，RA-24）。
    - 稽核主管列為金鑰分持人（01-18、02-22、07-3，RA-11）。
    - 內部稽核可設定迴避對象（10-P17，RA-25）。
    - 10-P8 的稽核內容查閱「每月彙總通知該流程類型的流程管理者與個資窗口」，與 01-16「稽核查閱完整內容只有稽核主管與治理人看得到」衝突（RA-49）。
- **相關**：K-AUDITOR-READONLY、D12（角色指派走一般設定變更）、A4；RA-49、RA-50。

### RA-49 稽核查閱機密內容與匯出

- **問題**：稽核把全部 L4 人資申請匯出成 Excel 帶回座位、寄給會計師，說明欄寫著「調查某某主管的薪資異常」；稽核員順手打開總經理特助的調薪資料授權；機密欄位加密後稽核如何讀取未定義；匯出檔被轉寄，事務所遭勒索軟體攻擊時答不出交出去的檔案含哪些人的什麼資料。（01-17、10-P8、10-P9、02-16）
- **對稽核過關的影響**：稽核看不到機密就無法查核核准內容是否適當；看得到又全無控管，等於另開一條洩漏管道，資安與個資窗口會質疑。
- **各立場的解法**：
  - 稽核清單與證據頁預設顯示摘要（非機密欄位）；開啟機密內容需填查核目的（可引用查核專案編號）並留查閱紀錄；匯出分兩種：母體清單（不含機密，可給會計師）與含機密明細（逐筆浮水印、檔案加密、記筆數與檔案雜湊）（01-17）。
  - 稽核預設看「控制證據檢視」（關卡、簽核人、時間、規則代碼、版本雜湊、執行與核准是否一致、鏈驗證）；看內容時選查核計畫或填目的，解密寫事件，每月彙總通知流程管理者與個資窗口；統計只用不含內容的指標（10-P8）。
  - 每次匯出選用途，用途決定欄位預設範圍（例如外部查核預設不含 IP、裝置與機密欄位、人員以員工編號表示），加欄位需理由；檔案加密、帶匯出序號；事件記用途、欄位清單、筆數、涉及人數與雜湊（10-P9）。
  - 外部稽核的機密欄位預設不解密，由負責人逐張開放（02-16）。
  - **衝突**：(1) 預設可見——01-17 預設摘要（非機密欄位全可見）；10-P8 預設只看控制證據，內容需另開。(2) 稽核查閱的通知對象——10-P8 每月通知流程管理者與個資窗口；01-16 主張稽核查閱內容只有稽核主管與治理人可見，避免調查走漏。
- **相關**：K-AUDITOR-READONLY、A3、A4、D20、A19；RA-11、RA-48。

### RA-50 外部稽核的存取

- **問題**：會計師進場三週，公司借內稽帳號給他或開一個「可查全部」的 `auditor` 角色；另一家子公司的會計師只能看該子公司；子公司稽核依「可查全部」看得到母公司薪資單；查核結束帳號沒關。（02-16、09-F04、10-P8、01-24）
- **對稽核過關的影響**：借帳號使查詢記在內稽名下、紀錄失真；共用帳號本身是缺失；範圍過大讓會計師看到不需要的機密；結束後成為無人負責的權限。
- **各立場的解法**：
  - 外部稽核作為一種被授權者，透過申請流程取得依公司別、資料期間、有期限、唯讀的稽核權限，有內部負責人（稽核室主管），到期自動失效；每次查詢與匯出寫事件（02-16）。
  - 稽核角色帶範圍（公司別、流程類型、事件期間）；外部稽核沿用 A18 的外部人機制（內部保證人、到期日＝查核合約結束日、MFA），開通走一張單、由保證人以外的人核准；會計師自己下母體條件並以公開工具驗證；提供「重新判定」工具（以紀錄中的參數快照、路徑版本、內容版本重算級別、路徑與職責分離並比對）（09-F04）。
  - 外部稽核不另設角色，而是申請一筆「稽核查閱」授權（公司別、期間、流程類型），最長到查核結束日，由內部稽核主管核准（10-P8）。
  - 稽核角色帶公司別範圍，K-AUDITOR-READONLY 改為「稽核唯讀，可查其範圍內的全部」；範圍指派由稽核治理人核准（01-24）。
  - **衝突**：(1) 模型——帶範圍的稽核角色（01-24、09-F04）對比透過一般授權（02-16、10-P8）。(2) 核准人——稽核治理人（01-24）、保證人以外的人（09-F04）、內部稽核主管（10-P8）。
- **相關**：K-AUDITOR-READONLY「可查全部」、A18（只涵蓋執行人）、D15；RA-48。

### RA-51 稽核資料包、內控自評與重新執行

- **問題**：自評人員要用公司自己的內控編號（例如 CC-07、PU-12）查，平台用流程類型與規則代碼；12/31 的狀態會被 1 月的補簽與追認改變；稽核室要一份給審計委員會看的摘要而非幾千列 Excel；會計師要重新執行判定；交易所來函要三天內交出某資源在某期間的接觸者與時間；查核期間跨過切換日。（09-F17、12-B11、09-F04、09-F06、11-21）
- **對稽核過關的影響**：「證據自己產生」只做到明細，最後一哩仍靠人工整理；內控聲明書是董事會具名的法律文件，佐證要能對到公司自己的制度並在基準日凍結。
- **各立場的解法**：
  - 客戶自己的控制目錄 `company_control`（公司別、編號、名稱、對應規則與流程類型、負責單位），走 D12；可依公司控制編號查詢與匯出（09-F17）。
  - 期末快照 `evidence_snapshot`（公司別、基準日、範圍、雜湊、建立人、核准人），建立後不可改，後續變動另列「快照後異動」（09-F17）。
  - 產品內建控制對照表（由 `docs/audit/control-matrix.md` 產生），每列顯示控制目標、做法、期間內運作數量、例外與結案、證據連結；兩種標準報告（審計委員會摘要、自評或查核底稿）；報告封存產生條件、筆數、時間、雜湊並可重新產出比對；客戶可改措辭不能改口徑（12-B11）。
  - 重新判定工具（09-F04）；時間點授權查詢與「資源接觸報告」，實際存取未取得時明確標示（09-F06）。
  - 跨上線日自動附控制轉換說明（11-21）；可重現抽樣（RA-07）。
  - **衝突**：`evidence_snapshot` 的核准人未定；若由稽核核准，涉及 RA-48。
- **相關**：A2、A9、platform-vision「控制對照表上不能有空格」；RA-06、RA-07、RA-42。

## 六、未歸類

以下情境不在本文五個主題內，但從另一份彙整的可能分類（人事、個資、整合、維運、UX、採購）看，容易被當成「別人的題目」而漏掉。

| 情境 | 來源 | 為什麼可能被漏掉 |
|---|---|---|
| 授權機制到期或超量時不得阻擋撤銷、到期失效、驗證、對帳、稽核查詢與匯出（`K-LICENSE-NEVER-BLOCKS`） | 12-B16 | 看起來是商務條款，實際是一條會讓控制停擺的繞過途徑 |
| 排程停擺時 `check` 仍依 `grant.status` 回允許；有效性應在讀取時以時間計算，排程只負責通知與外部收回；停機期間只順延「要人做事的時限」、不順延授權到期 | 02-13、07-5 | 介於維運與證據之間；影響「事前擋得住」 |
| 催辦事件在「產生」時寫入，信件實際沒寄出也記為「已催辦」；寄送狀態應另成證據 | 07-7 | 看起來是通知功能，實際是逾時控制的證據真實性 |
| 執行 adapter 持有能設定全公司權限的憑證；後端被攻破即可繞過資料庫內的全部控制。交付內容由資料庫簽章、下游只套用驗簽通過者、或改為下游拉取 | 03-9 | 屬資安與整合，但直接決定「決定在資料庫裡被強制」這個前提是否成立 |
| 知悉人員名單的計算方式（成員依生效期間切片、查閱者、簽核與執行人、外部人）、保密與禁止交易告知確認、事件公告時自動凍結 | 09-F01、09-F02、10-P11 | 介於財會法遵、個資與證據；A6 只寫「由授權查詢與證據輸出提供」 |
| 對帳只比權限、不比主檔異動（例如 ERP 直接改供應商銀行帳號）；與既有 IGA 並存時需「權威來源」否則對帳產生大量假例外 | 09-F16、12-B22 | 屬整合，但決定例外清單是否可信 |
| 簽核人誤按後撤回自己的決定（直到下一關行動前），追加事件不刪原決定 | 05-E01 | 屬簽核動作；不處理會導致系統外協調，紀錄與真實決定不符 |
| 駁回沒有終局狀態、重送不連結前案，換名稱換人就能繞過駁回 | 04-F16、06-4 | 屬狀態機；本質上是「換人簽到過為止」的職責分離問題 |
| 申請人可控的自由文字以系統標示樣式出現（「財務長已同意」「續期無差異」），簽核人以為是系統判定 | 04-F18 | 屬 UX；直接影響核准的有效性與事後抗辯 |
