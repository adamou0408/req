# 真實情境檢查裁決

對 `00-consolidated-a.md`（RA-01–51）、`00-consolidated-b.md`（RB-01–71）、兩份的未歸類情境，以及 `docs/audit/control-matrix.md` 缺口彙整的每一項做裁決。裁決編號 D25 起，已寫入 [decision-log.md](../decision-log.md)。納入契約的工作見 pending-amendments A15。

判斷標準：選現實中行得通的最佳解；「之後再做」只在現在做會做錯時成立。優先順序：稽核過關 → 安全 → 簽核人的速度與正確性 → 通用性 → 成本。

結構：第 1 節總表；第 2 節是八個重大問題的設計、理由與殘餘風險；第 3 節依骨幹章節列修改清單；第 4 節檢討既有決策；第 5 節是專案負責人要知道的取捨；第 6 節列出需要同步的其他文件。

## 1. 總表

範圍欄：**核心**＝第一版核心；**包:名稱**＝第一版某流程包；**維運**＝維運文件與部署；**不做**＝明確不做。寫「見 2.x」的議題，設計與理由在第 2 節。

## 2. 重大問題的設計、理由與殘餘風險

以下多處用到「控制負責人」（`control_owner`）：公司的第二線（內控、法遵、資安、個資窗口），依流程類型、受管系統或設定類別指派。它承接各立場原本想交給稽核的核准、覆核與結案工作。

### 2.1 資料庫不再信任後端傳入的身分（RA-13、RA-14、RA-15）

問題的本質：商業邏輯全在 SQL，但「是誰」這個輸入來自後端。只要身分是後端說了算，資料庫裡的職責分離與雜湊鏈都建立在可偽造的前提上。解法是讓資料庫自己驗證由身分提供者或使用者裝置簽發的證明，後端只負責轉送。

**設計**

1. **session 由資料庫建立。** `api.session_begin()` 發出一次性的 nonce；使用者在身分提供者登入；後端把原始的 ID token 交給 `api.session_open(p_id_token)`；資料庫以登記的 `identity_provider_key` 驗章，檢查 `iss`、`aud`、`exp`、`nonce`，以不重用的識別碼對到 `person_identity` 與有效的 `employment`，建立 `auth_session`（人、來源、`auth_time`、`acr` 與 `amr` 的原值、到期與閒置時限）。後端手上沒有任何能造出 session 的東西。
2. **`api` 的 function 第一個參數改為 `p_session`**，行為人由資料庫查出。架構測試：`api` 內沒有任何 function 接受人員 id 作為行為人。hook 仍收 `p_actor`，只由核心呼叫。
3. **動作目錄 `sgn.action`**：每個動作有類別與最低證明等級；等級寫在核心，設定只能調高（`approval.proof_level`，依流程類型與級別）。

   | 等級 | 取得方式 | 適用的動作 |
   |---|---|---|
   | `session` | 有效的 session | 讀取、草稿、提問與回覆、準備備註 |
   | `idp_stepup` | 身分提供者以挑戰值為 nonce 重新驗證後簽發的 token | 送審、申請人確認、一般級別的決定、憑證登記 |
   | `passkey` | 平台登記的 WebAuthn 憑證對挑戰值簽章，要求使用者驗證 | 最高級別與重大案件的決定、設定變更的核准、高風險動作（代理、轉簽、加簽、助理設定、緊急宣告、暫停或撤銷他人的授權、憑證作廢）、外部人員的所有決定 |

4. **決定證明綁定內容。** `api.challenge_issue(p_session, 動作, 對象清單)`：資料庫算出清單（每個對象的單號、內容版本雜湊、顯示快照雜湊、決定種類），產生一次性、5 分鐘內有效的 `decision_challenge`。使用者以 passkey 簽章，或向身分提供者重新驗證；資料庫驗章，並檢查憑證屬於該 session 的人、已過冷卻期、來源網域、使用者驗證旗標與計數器（或 token 的 `nonce`、`auth_time`、`amr`）。驗章與決定在同一個交易內完成；`decision_proof` 保存原始簽章資料，事件骨架引用它的雜湊。批次是一份清單、一次簽章。沒有「幾分鐘內免再驗」的時間窗。
5. **驗章在資料庫內以 PL/pgSQL 實作**（RS256 與 ES256）。驗章只處理公開資料，沒有金鑰外洩的旁路問題；以公開測試向量驗證正確性；列為受保護路徑。
6. **連線角色依用途拆分**，每個角色只能執行自己 schema 的 function：`sgn_app`（人員介面，`api`）、`sgn_job`（排程，`api_job`）、`sgn_sync`（人事同步，`api_sync`）、`sgn_integration`（機器介面，`api_int`）、`sgn_idp_sync`（只能匯入身分提供者的簽章金鑰）。決定類 function 只存在於 `api`，且都要求證明；排程、同步、整合的帳號碰不到。`sgn_owner` 平時不可登入。機器呼叫方的寫入類請求（對帳回報、執行結果、代建草稿）以 `private_key_jwt` 簽章，同樣由資料庫驗章。
7. **身分提供者的簽章金鑰是受控設定。** 初次登記走設定變更；輪替的新金鑰由 `sgn_idp_sync` 匯入後先為 `pending`，延遲 `authn.idp_key_activation_hours`（預設 24）生效並告警資安，可被否決；來不及時走設定變更的快速路徑。
8. **偵測與告警。** 每筆事件記資料庫連線角色、來源位址、`application_name`、session 與證明。`sgn_app` 從未登記的位址連線、證明驗不過、同一 session 的來源突變，都寫 denied 事件並告警。「每筆決定類事件都有驗得過的證明」是每小時自我檢查與離線驗證工具都會檢查的不變條件。憑證登記事件隨檢查點外部錨定，事後換公鑰會被發現。

結果：只拿到 `sgn_app` 密碼的人，開不了 session、做不出證明；能做的只有呼叫會被拒絕並留下紀錄的 function。冒名需要同時取得當事人的裝置與生物特徵，或身分提供者的簽章金鑰。證明隨證據匯出，第三方可以離線重驗「這個憑證的持有人簽了這份內容」。

**放棄的方案**

- 只做帳密保管（保管庫、短效憑證、限制來源位址）：必要，列入維運文件，但拿到連線帳號的人仍可冒名。
- 後端驗章、資料庫只記結果：信任點沒有移動。
- 另設驗證閘道，以獨立的資料庫角色寫入「已驗證」紀錄：只是把信任從後端搬到另一個同樣由維運管理的服務。
- 以資料庫擴充套件驗章：工程規範只允許 `pgcrypto`，代管的資料庫也常不能安裝；先以 PL/pgSQL 實作。
- 平台自己驗 TOTP、簡訊、推播：不綁內容、可被釣魚代理轉送。這些因子只會出現在身分提供者內部，以 `amr` 表達。

**殘餘風險**

1. 資料庫 superuser 與 `sgn_owner` 可以改 function 或公鑰。擋不住，只能偵測：物件指紋、`pgaudit` 外送、憑證登記與檢查點的外部錨定、離線重驗。
2. 被攻破的前端或後端可以讓使用者看到甲、簽下乙。挑戰值綁的是資料庫算出的內容與顯示快照，事後能證明簽的是什麼，不能證明螢幕上顯示了什麼。緩解：決定後由資料庫產生的通知摘要、「我的決定」清單、同裝置與過短審閱的偵測。
3. `session` 等級的動作可被劫持 session 的人冒用；機密欄位另有 2.2 的保護。
4. 身分提供者的管理員可冒名登入並登記新憑證；靠冷卻期、通知本人與主管、他人確認來發現。
5. 純 PL/pgSQL 的 ES256 驗章效能尚未實測，列為實作的第一項技術驗證（門檻：單次驗章 p95 小於 150 毫秒）。不達標時改用只做驗章的資料庫擴充套件，並修改工程規範。

### 2.2 證據層：鏈、錨定、還原、保存、多公司、機密內容（RA-01、02、05、08、09、11、12、RB-36、38、39、47）

這個結構必須在寫 DDL 之前定案；上線後再改，等於重算全部既有雜湊。

1. **事件分骨架與封套。** 骨架（序號、時間、事件類型、行為人的內部 id、申請單、規則代碼、公司別、各封套的承諾、決定證明的雜湊）以 RFC 8785 正規化後的 bytes 保存並進鏈。封套有兩種：內容（申請內容、附件、顯示快照、意見文字）與軌跡（姓名等判定依據快照、IP、裝置），以逐單的資料金鑰加密。骨架對每個封套放兩個值：密文雜湊（不解密就能驗儲存完整）與明文的加鹽承諾（鹽在封套內，有權解密的人可驗內容與承諾相符）。
2. **分段與封印。** 鏈依月分段；段落結束產生 `audit_segment_seal`（段根、筆數、首末序號）並外部錨定。驗證可從任一封印開始，依月平行。
3. **檢查點與外部錨定**（RA-01）：每小時一次，至少兩個 sink，至少一個在資訊維運之外。
4. **還原偵測與環境身分**（RA-05）：啟動時與外部錨點比對；遺失的區間明寫，不重算、不偽裝連續；副本不對外動作。
5. **保存與銷毀。** 保存期依（流程類型、紀錄類別）設定，並有起算基準 `retention_basis`（終局日、失效日、年度決算日）。核心預設終局後 5 年、硬下限 5 年；資料授權規則的「10 年（待稽核室確認）」以流程包參數表達；議事錄類別永久。期滿的銷毀是銷毀該單的資料金鑰並寫事件；骨架保留。行為人的可識別資料在他最後一張相關單期滿後抹除，骨架從此不可識別。只銷毀已錨定、已過期、不在法律保全範圍內的資料。整段移除只能在段內所有內容都已銷毀之後做，是一張設定變更，並留下封印。
6. **個資的刪除請求**：保存期內拒絕並標「限制處理」；期滿依第 5 點。
7. **多公司。** 單一主鏈；每個檢查點對每家公司計算該區間事件的 Merkle 根。子公司的會計師拿到該公司的事件與檢查點，就能自行驗證完整性，不會看到其他公司的內容。
8. **機密內容不經過平台後端**（RB-36）。瀏覽器憑資料庫簽發、綁定人、單號與用途的一次性許可，直接向金鑰 port 的「機密內容服務」讀寫機密欄位與附件；該服務持有解包後的資料金鑰，依流程定義計算分級用的衍生值並附鑑別碼，資料庫驗過才採用；每次解密由該服務獨立記錄，可與查閱紀錄勾稽。該服務應部署在技術維運以外的管理範圍；做不到的小型公司可同機部署，但列為有期限的角色衝突例外（RA-30）。

**放棄的方案**

- 以整段移除作為主要的銷毀手段（01-25、07-4）：同一段內各單的保存期不同，等最長者會超期保存。
- 假名對照表（01-25）：對照表本身仍是集中的個資，也不解決內容的銷毀。
- 每家公司一條鏈加集團主鏈（07-23）：跨公司事件要原子寫入多條鏈，全域順序與 as-of 截止點不再唯一。
- 硬體 WORM、區塊鏈（調查 R-N05）：稽核要的是可偵測與可驗證。
- 在瀏覽器端計算分級用的衍生值：申請人可以竄改，等於可以自選級別。

**殘餘風險**：錨定間隔內（最長一小時）的尾端可被重算；兩個 sink 的管理者共謀；資料金鑰遺失等於內容不可讀（以分持、每季可解密性檢查、年度演練降低）；被竄改的前端程式可在使用者瀏覽時取得機密內容。

### 2.3 三條不能退讓的界線（RA-28、RA-48、RA-39）

**頂層升級不落到技術維運。** 骨幹第 7 節的「升級給系統管理員群組」刪除。

- 每個路徑必須有 `top_resolver`（依公司別與流程類型設定，值是治理角色：董事長、審計委員會召集人、指定的獨立董事、母公司指定的主管）；沒有設定的路徑不能啟用。
- 出缺時的解析順序：人資派代的代理主管 → 上一層單位主管 → 路徑宣告的出缺替代人 → `top_resolver`。都沒有時案件停住（`K-RESOLVE-HALT`），開高優先例外給流程擁有單位主管。
- 技術維運、流程管理、人資、稽核都不能逐張指定簽核人，也不能代簽。補救一律是結構性的：人資登記代理主管（人事事實），或以設定變更補上替代人。等不及的事走急件或緊急路徑。
- 理由：逐張挑簽核人就是「挑人簽」的舞弊手法；結構性的補救一次解決所有卡住的單，而且留下可稽核的設定紀錄。06-10、11-7、08-10 的逐張指定因此不採。
- 補償：頂層申請人的單生效時自動通知稽核主管並列入複查；部屬簽上級的單在畫面與紀錄上標示。

**稽核不做任何決定。** `K-AUDITOR-INDEPENDENT` 由引擎強制：持有稽核角色的人不會被任何 resolver 解析為簽核人、執行人、驗證人、例外的責任人或覆核人、設定變更核准人、金鑰分持人；撞到時當作設定錯誤擋下。稽核能做的是查閱、匯出、驗證、留言、提出 `audit_remark`（進追蹤報告）、被通知、見證。稽核角色的授予、範圍與撤除由稽核主管提出、`audit_governor`（董事會或審計委員會指定）核准，受查單位改不了。各立場中讓稽核做決定的提案一律改寫：

| 原提案 | 改為 |
|---|---|
| 頂層替代簽核人可為稽核主管（06-11） | `top_resolver` 的治理角色；稽核主管只收通知 |
| 事後補正單加一關內部稽核（09-F16） | 加一關控制負責人 |
| 證據保存類設定、保存年限調降由稽核核准（10-P19、02-5） | 法遵為控制負責人；稽核收通知 |
| 銷毀單由稽核核准（10-P3、09-F08） | 法遵或個資窗口核准；稽核收通知並有異議期 |
| 還原例外由稽核室結案（02-2） | 控制負責人覆核結案 |
| 例外逾期升級到稽核主管；行為型例外派給稽核（09-F17、04-F01、08-23） | 升級與指派給控制負責人；稽核主管收通知 |
| 稽核主管為金鑰分持人（01-18、02-22、07-3） | 不擔任 |
| 內部稽核設定迴避對象（10-P17） | 稽核只能以調查申請的申請人身分提出 |
| 離職回查清單交稽核指定的人（08-6） | 資安與控制負責人 |

**正式建置沒有假時鐘。** 刪除參數 `system.allow_fake_clock`；正式的發行包不含讀取 `sgn.fake_now` 的程式路徑。取得時間只有 `sgn_internal.now()` 一個入口；假時鐘的實作放在只供測試的 migration 集（`db/testing/`），不進發行包，而且只在 `environment.kind = 'test'` 時可安裝。發行版的物件指紋檢查會確認時間函式是正式版本。事件時間一律取資料庫時鐘，另記 `business_time`；時間倒退照常寫入並另開例外。理由：只要是參數，兩個熟人就能經設定變更打開它。

### 2.4 母體、抽樣、例外（RA-06、RA-07、RA-43、RA-51）

- **取號**：單號在送審的交易內依（公司別、流程類型、年度）無間隙取號；草稿不取號、不進母體，刪除草稿寫事件。完整性的證明是「送審事件與單號一一對應，且與檢查點的事件筆數一致」；無間隙的單號讓人工核對不需要解釋跳號。
- **母體定義與 as-of**：`population_definition` 有版本（送審、核准、生效於期間內；期間內任一時點有效；期末時點有效），加事件序號截止點 `as_of_seq`。同一定義、同一截止點，任何時候產出的結果相同。資料包第一頁列出定義版本、參數、產出人、筆數與檔案雜湊；產出本身寫事件。跨公司單同時出現在兩家公司的母體。
- **每張單都有終點**：新增終局狀態 `rejected`；退回逾時自動取消；申請人離職時由被授權者負責人接手或取消。
- **可重現抽樣** `audit_sample`：記母體定義、截止點、母體雜湊、種子、演算法版本、樣本數、分層與必抽；以 SHA-256(種子‖單號) 排序取樣；平台外可重算。不內建固定樣本數。
- **期末快照** `evidence_snapshot`：基準日凍結母體、例外與狀態，之後的補簽與追認另列為「快照後異動」。
- **重新判定工具**：以事件中的參數快照、路徑版本、內容版本、函式雜湊重算級別、路徑與職責分離，並與當時的結果比對。
- **例外是核心實體** `exception`：種類（規則代碼）、偵測時間、對象、責任人、嚴重度、根因分類、改善計畫（負責人、預定與實際完成日）、佐證、狀態（`open` → `in_progress` → `pending_review` → `closed` 或 `risk_accepted`）。
  - 責任人依受管系統或流程類型指派，不得是造成例外的人；執行不一致的例外送業務擁有單位主管，不送回執行者。
  - 條件自己消失時只轉為待覆核。結案與接受風險要由責任人與造成者以外的人覆核；接受風險有到期日。
  - 不得批次結案（可以批次指派）。同類再發自動關聯前案。
  - 逾期升級給責任人的主管與控制負責人；稽核主管收通知。每季產出追蹤報告。
  - 稽核準備度把「轉換中」（期初待追認、在途承接）與「真正的例外」分開；轉換中逾期即轉為真正的例外。
- **客戶自己的控制目錄** `company_control`：公司的控制編號對應到規則代碼與流程類型，可依公司的編號查詢與匯出。產品內建控制對照表，每列帶期間內的運作數量、例外與證據連結。

### 2.5 導入、線下決定、追認（RA-40、RA-41、RA-47）

- **啟動模式與期初基準**：安裝後只能指派第一批管理角色與提交 `sys_baseline`（全部設定的快照、雜湊與白話的基準報告）。由公司指定的至少兩位主管核准（流程擁有者與控制負責人）；導入顧問是提出人；稽核見證。核准後不能回到啟動模式；基準雜湊是第一個外部錨點。不設「不算數」的試營運模式。
- **上線範圍** `rollout_scope` 依資源分批、有版本、走設定變更；資源一上線，任何部門取用都必須經平台。受管系統有涵蓋狀態（已納管、排定納管與日期、不納管與理由），排定逾期列例外。
- **既有權限**匯入為 `grant.origin = migrated`，不冒充核准，報表上與正常授權分開。
  - 依風險分波：第一波（最高級別、可匯出、久未使用、主管已離任）30 天；整體上限 180 天。每位擁有者每週的上限是配速，不延長期限。
  - 轉正走追認路徑：資料擁有者與被授權者負責人兩個不同的人，最高級別加資安長。產生來源為 `ratified` 的單，起日是追認日，並保留「未核准存在期間」。
  - 以分群為單位確認；久未使用的不得成組。到期日錯開（只縮不長）。
  - 逾期先 `suspended` 並列例外，再過 30 天撤銷。
  - 授給個人的既有規則承接為 `legacy_individual` 被授權者（只能由匯入產生、強制結束日、不能續期或擴大；`K-LEGACY-TRANSITION`）。對不到人的帳號必須歸入四類之一（離職者、共用帳號、服務帳號、回任多帳號）並各有處置。
- **線下決定登錄** `offline_decision`：登錄人不是原決定人；上傳原始佐證；記「登錄時間」與「宣稱的決定時間」兩個時間；原決定人在系統內以決定證明確認（新事件）。整張單標記「含線下決定」並自動列例外，由未參與的人覆核結案。平台的 `service_outage` 事件可供對照。
- **追認不掩蓋未核准期間**：
  - `K-NO-BACKDATE`：授權的起日不得早於核准完成時間，核心強制。
  - 事後補單必須引用對帳發現；發現不消失，轉為 `ratified` 並保留未核准存在的期間。
  - 簽核畫面第一眼顯示「這是追認，未核准期間為某日至某日」；簽核人選「追認」或「不追認並撤除」。
  - 追認型的單不得批次，路徑自動加一關控制負責人。
  - 回溯的人事異動使已完成的簽核不成立時，列例外，由依新資料應簽的人追認（新事件，不改原紀錄）。

### 2.6 批次、複查、急件與緊急（RA-44、RA-45、RA-46）

**批次核准**（取代 D3）。調查確認稽核反對的是「只簽封面」與逐筆沒有紀錄，不是批次本身。所以保留批次，但加上品質條件：

- 可進批次的單必須同時符合：
  - 內容無差異：與來源單相同；來源單已到期者，須在 `renewal.max_gap_days`（預設 30、硬上限 120）以內。
  - 情境無差異：依目前規則重判的級別相同；專案與 agent 的成員無增加（團隊的成員變動在參數以內）；負責人相同；資料分級未變；所屬單位未改組；沒有未結的例外或對帳差異；前一期有使用紀錄；沒有受益人衝突。
  - 不屬於不可批次的類別：最高級別、綁定敏感事件的資源、追認型的單。這些提供逐張的快速核准。
- 不符合的單踢出批次並寫明原因。
- 每批上限 `approval.batch_max_items`（預設 20、硬上限 50）；逐列勾選，沒有全選；每列顯示成員異動與風險事實。
- 一次決定證明涵蓋清單上每張的版本雜湊與顯示快照雜湊；每張單各有一筆事件並帶批次編號；批次的每筆審閱時間進統計與偵測。
- 另一種批次「同一標準範本的新申請」（05-E20）預設關閉；開啟是放寬類的設定變更，且只限最高級別以下。

放棄：以前期使用紀錄以外的條件全面禁止批次（量大時逐張點擊同樣是盲簽）；追認可批次（11-3，改為 2.5 的分群確認並排除高風險）。

**定期複查。**

- 活動開始時凍結母體（快照、雜湊、筆數）；範圍含上次活動以來曾經有效的授權，已撤銷的也列出。
- 兩段：被授權者負責人確認仍然需要（需求側）→ 資源擁有者決定（控制側）。`K-REVIEW-SOD`：控制側的複查人不得是該授權的申請人、受益人，撞到時找替代複查人。
- 有風險訊號（久未使用、沒有使用資料、負責人或成員異動、職責衝突、期初承接）的項目逐筆決定並填理由；其餘依被授權者分組確認（每組上限 20 筆）；沒有全選。
- 未回應先升級，再暫停，不預設保留。撤銷直接執行，由下次對帳確認外部已移除。
- 錯開發送，每人每日有上限。活動由控制負責人簽核完成。全組確認比例、平均時間、撤銷率進資料包。

**急件、緊急路徑、暫停是三件事。**

| 機制 | 作用 | 條件 |
|---|---|---|
| 急件（`allows_urgent`） | 不改路徑，只改時效：以小時計的時限、即時推播 | 結構化的需要完成日與原因；簽核人可否決急件；急件比率列例外 |
| 緊急路徑（`allows_emergency_path`） | 先執行，限時內補核與覆核 | 只開放給可收回的權限（帳號、角色、特權、緊急變更）；資料授權不開放，因為資料看過就收不回 |
| 暫停（`suspended`） | 止血：`check` 立即拒絕，可恢復 | `security_responder` 發動，1 個工作天內由資安長覆核（RA-16） |

緊急路徑的防濫用：

- 必填事件或工單編號。
- 預設要有一位合格的人即時事前核准（不得是宣告人或執行人）；`emergency.preapproval_wait_minutes`（預設 15）內無人回應時，值勤中的宣告人可先行，該筆自動列為較高嚴重度的例外。
- 有效期以小時計，`emergency.max_hours` 預設 4、硬上限 24，不得續期。
- 權限結束（到期或提前收回）一律產生事後覆核，不以「還在使用中」為前提。覆核人不得是宣告人、事前核准人、兩者的下屬或同一直屬主管下的同事。覆核畫面附期間的實際操作紀錄，取不到時標示「自報」。
- 覆核結論三選一：確屬緊急；不應走緊急（計入宣告人與核准人的統計）；拒絕（自動撤銷並開調查例外）。`emergency.review_due_hours` 預設 72，逾期自動收回並列例外。
- 依人、系統、流程類型統計使用率，90 天內超過門檻列例外。

放棄：一律事前核准（02-21）會在深夜找不到人時逼出共用的最高權限密碼；一律事後確認（04-F09）則讓事前控制完全消失。口頭先准的資料授權（05-E18）以急件加手機核准處理，真的發生在系統外的決定走線下決定登錄。

### 2.7 利害關係、內線資訊、會議決議、供應商變更（RA-21、RA-25、RB-32、RB-68–71）

**受益人與利害迴避。**

- 關卡分兩種：需求側（`demand`，證明業務需要，例如主管關）與控制側（`control`，獨立把關，例如資料擁有者、資安、法遵）。
- `K-SOD-BENEFICIARY`：被授權者的負責人、成員、agent 的使用對象，不得簽任何控制側關卡，也不得執行、驗證或複查。需求側關卡不得由申請人、填單人簽；專案與 agent 的直接成員也不得簽；依人資組織推導的團隊，其主管可以簽需求側關卡。
- 會產生授權的路徑至少要有一個控制側關卡（`K-STAGE-CONTROL-SIDE`，啟用路徑時檢查）。
- 撞到時找路徑宣告的迴避替代人，再往上，最後是 `top_resolver`；不得落到當事人的代理人或下屬。
- 理由：「受益人一律不得簽」（03-8、04-F02）會讓所有團隊申請的主管關上推一層，由更不了解需求的人簽，反而形式化；「提示後可簽」（05-E16）對客觀可判定的受益關係太弱。分成兩側後，主管仍為需求背書，獨立性由控制側保證；人頭申請人的手法在控制側被擋下。
- `K-SOD-INTEREST`：可判定但較間接的利害關係（流程包 hook `detect_interest` 回報、交易對象在 `related_party` 名單、年度申報的關係）出現時，簽核人必須選擇迴避或揭露後簽（必填理由，進例外報表）；流程類型或級別可宣告強制迴避。
- `K-SOD-RECUSAL`：申請單的迴避名單（機密）。名單上的人不被指派、不能認領、看不到、收不到通知。只能由法務、法遵、個資窗口設定，或由調查類申請的申請人提出、第一關核准後才生效；不得用來排除正常的簽核人。調查用授權是資料授權包的路徑變體（法遵主管 → 審計委員會召集人或指定的獨立董事 → 資安長 → 執行），不經資料擁有者；擁有者的授權總覽顯示「另有 1 筆受保密的授權」。
- agent 的權限上限（控制對照表 C-45）：以「帶 `on_behalf_of` 時取 agent 與該使用者授權的交集」實作，不以「不超過負責人的權限」實作，因為服務帳號的負責人通常是系統管理人，本人並沒有該資料的權限。

**內線資訊與知悉名單。** 核心提供與領域無關的 `sensitive_event`（代碼、擁有人、狀態、預定與實際公告時間、是否循環、公告後的降級目標）與 `roster_entry`。

- 名單以自然人與時間切片計算。授權生效、成員加入、查閱、簽核、執行、外部人登錄，都自動寫入一筆（人、開始知悉時間、依據）。
- 新進名單者在平台確認保密與禁止交易的義務，未確認列例外。外部人由擁有人登錄，另一人覆核。
- 事件由擁有人按「已公告」並填公告編號才觸發，不依預定時間自動觸發；逾預定時間未確認列例外。預定時間的變更走設定變更，由擁有人以外的人核准，並試算受影響的授權。
- 公告時名單凍結，產出帶雜湊的匯出檔。循環事件公告後自動開下一期。
- 生效窗口（`effective_window`）：授權可綁循環事件或行事曆，窗口外 `check` 拒絕，每次開關留紀錄；一次核准多期，仍受有效期上限與定期複查約束。
- `grants` 查詢支援 `as_of` 與期間；「某資源在某期間的接觸者」報告（與 RB-45 是同一能力）。綁定敏感事件的資源不可批次。

**會議決議作為關卡。** `policy_stage.mode` 新增 `resolution`：決定者是會議（董事會、審計委員會），不是人。`governance_meeting`（會議別、日期、議案編號、決議內容、出席與迴避、議事錄）可對應多張單，決議內容須含單號與金額，系統比對一致才放行；議事單位一人登錄、另一人確認；事件記決定者為該會議、登錄者為紀錄人；時限依下次會議日計算；議事錄屬永久保存類別。

**供應商銀行帳號變更**（流程包規則）：回撥只能用變更前已存在 N 天的主檔聯絡資料；驗證用的電話等於申請附件中的電話，自動檢查即失敗；核准後 48 小時冷卻期並通知付款系統暫停付款；新帳號與員工薪資帳戶、其他供應商帳戶做雜湊比對。對帳涵蓋主檔異動（`describe_expected_state`），直接改主檔會成為「未核准的異動」。

### 2.8 簽核人的日常（RA-19、RA-26、RA-27、RB-17–20、RB-04、RB-09）

| 項目 | 決定 |
|---|---|
| 反悔 | `K-DECISION-WITHDRAW`：下一關尚未決定、尚未被認領、尚未進入執行前，簽核人可撤回自己的決定（追加事件、必填原因、需決定證明）；下一關已開啟的畫面即時失效 |
| 提問計時 | 提問暫停本關的計時，上限 `approval.question_pause_max_workdays`（預設 3）；可問本單的任一參與者；回覆不能夾帶內容修改；問答綁內容版本 |
| 徵詢意見 | 新動作 `consult`：指定一人、沒有否決權、不暫停計時、寫查閱紀錄、意見進事件；保密單須簽核人確認可讓對方看 |
| 退回與駁回 | 退回可逐欄寫意見；申請人修改時即時預告會從哪一關繼續。駁回是終局，重送連結前案 |
| 申請人縮小與附註 | `K-APPLICANT-REDUCE`：送審中申請人可直接縮小，不重簽，通知已簽與待簽者。錯字用不屬於內容版本的 `case_note` |
| 助理 | `assistant_link`：委託人以 passkey 建立；助理可看清單、代提問、寫準備備註、標記建議；不能決定；保密流程預設排除 |
| 代填 | `case.drafted_by`；申請人確認後才送審；`K-SOD-DRAFTER` |
| 代理範圍 | 公司別、流程類型、級別上限、金額上限、是否含保密單；可多段；自助上限 30 天，超過需委託人的主管核准，硬上限 90 天；不得回溯；控制側角色只能代理給 `designated_deputy` 名單；任一方有人事異動時暫停；代理人是申請人、填單人、受益人時自動跳過 |
| 轉簽與加簽 | 轉簽對象限該關 resolver 可解析者或指定代理人，每關一次，保留轉出者的檢查與意見。加簽限路徑宣告的 `addable_roles`；保密單的加簽人只看簽核人勾選的非機密欄位 |
| 多公司兼任 | 待簽清單與每個簽核工作標示「以哪家公司的什麼身分簽」；時限依該身分所屬公司與據點的行事曆與時區；職責分離以自然人判斷 |
| 交接與重派 | 每關開始時解析，決定時重驗；人事事件到達時主動重派，新工作帶著問答與備註；生效日前預告「有 N 張待簽將移交」；升級對象可交回一次 |
| 決定驗證 | 每個決定一次 passkey（生物辨識一觸），手機與電腦相同；批次一次涵蓋整批；沒有 passkey 時以身分提供者的再驗證完成一般級別的決定；上線前檢查每位簽核人的憑證登記 |
| 通知分級 | 即時（被提問、緊急路徑、24 小時內將升級、決定被撤回）、彙整（每天一到兩次，時間自選）、僅站內。催辦與升級預告不能關，只能改通道。通道是 port：第一版提供 email、Teams、LINE WORKS 與 PWA 推播的 adapter。決定一律回到平台內完成；回信自動回覆「回信不會核准」並記錄。每封標示為什麼收到；保密單在任何通道只顯示「你有一張待簽」；範本的連結由系統產生；信中顯示使用者自訂的辨識片語 |

放棄：在郵件或聊天卡片直接核准（無法做決定證明）；原生 App（PWA 已能推播與使用 passkey）；Slack 與企業微信的 adapter 在第一版不交付，因為沒有可對測的環境（D5），port 與合約測試已備妥。
