# 真實情境檢查 02：會計師事務所的資訊稽核人員

## 立場與查核方式

我是簽證會計師事務所的資訊稽核（IT audit）。每年期中與期末各進場一次，查這家公司的資訊一般控制（ITGC：存取、變更、作業），並判斷財報查核團隊能不能依賴這個平台產出的資訊（IPE：Information Produced by the Entity）。

我不看系統說明書承諾什麼，只看三件事：

1. **控制是預防性還是偵測性？** 預防性控制只要設計有效、整年沒被關掉，我測一次加上變更控制就能依賴；偵測性控制我要看整年每一次都有人看、有人追。
2. **有權限的人能不能繞過？** 資料庫管理員、平台維運、身分系統管理員、能改設定的人。只要有一條路能不留痕跡地改結果，而且沒有獨立的偵測，我就不能依賴這個平台的紀錄，整個「證據自己產生」就失效。
3. **系統產出的報表我能不能自己驗證完整與正確？** 我不接受「系統產出的，所以是對的」。我要能自己從原始資料重算，或至少能證明報表的母體沒有被挑過。

以下情境以一年內、一家上市櫃公司（或集團子公司）上線後實際會發生的事為準。人物沿用 `docs/contract/seed-directory.md`。只列沒涵蓋或部分涵蓋的。

## 1. 拿到後端連線帳號的人可以用任何人的身分簽核

**情境**：2027 年 3 月，資訊部工程師林冠宇負責平台維運，部署設定檔裡有 `sgn_app` 的資料庫密碼。季底業績壓力下，業務分析部急著要一份 L4 資料，財務長蘇慧敏出國。林冠宇用 `psql` 以 `sgn_app` 連線，直接呼叫 `api.approve_task(p_actor => 蘇慧敏的 id, ...)`。

**系統現在的反應**：骨幹第 1 節與工程規範第 2 節規定 `sgn_app` 只能 `EXECUTE` `api` 的 function，每個 function 的第一個參數是 `p_actor`。資料庫完全信任後端傳進來的 `p_actor`。稽核事件會記下「蘇慧敏核准」，雜湊鏈完整，IP 是應用伺服器本身。

**結果**：紀錄上看不出任何異常。我在查核時只要問「誰拿得到 `sgn_app` 的密碼？資料庫怎麼確認 `p_actor` 真的是本人？」，答案是「維運人員都拿得到；資料庫不確認」。我會判定**簽核紀錄的歸屬（who approved）不可依賴**，連帶影響平台上所有核准證據。這是整個平台最根本的一條。

**對照現有設計**：沒涵蓋。`K-SOD-*`、`K-AUDIT-CHAIN` 都建立在 `p_actor` 正確的前提上；D20 讓維運「看不到內容」，但沒有讓維運「冒不了名」。

**替代方案**：
- A. 管好 `sgn_app` 密碼（放 vault、定期輪換、限制來源 IP）。仍然是「後端說是誰就是誰」，後端主機的管理員一樣做得到。只能降低機率，不能讓我依賴。
- B. 資料庫驗證身分提供者簽發的 token（例如 OIDC ID token 的簽章）。需要在 PostgreSQL 裡做 JWT 驗證，只用 `pgcrypto` 做得到 RS256 驗證有困難；token 也可能被後端重放。
- C. 資料庫自己發行並驗證「簽核工作階段」：登入完成後，由資料庫建立 session 紀錄（只存雜湊），每個 `api` function 改收 session token，從 session 推出 actor；簽核決定另外需要一次性的決定憑證（MFA 或身分提供者的 step-up 結果），由資料庫比對。

**最佳解**：C，並補上 A 的基本做法。
- `api` function 不再接受裸的 `p_actor`，改收 `p_session`；actor 由資料庫依 session 查出。session 由一個只有登入流程能呼叫的 function 建立，必須帶上身分提供者回傳、可由資料庫驗證的資料（例如 `pgcrypto` 能驗證的 HMAC，金鑰不放在應用伺服器上，由身分提供者端的元件或 HSM 持有）。
- 簽核、撤銷、設定變更這類「決定」動作，另外需要一次性的決定憑證（MFA 結果），稽核事件記錄憑證的來源與驗證方式。
- 稽核事件同時記錄資料庫看到的 `session_user`、`application_name` 與 session id，讓「用 psql 直接連」在紀錄上看得出來。
- 架構測試加一條：任何 `api` 決定類 function 在沒有有效 session 時一定失敗（「試著繞過」的測試）。

**理由**：稽核過關排第一。A 只能讓冒名變難，我仍然會把它寫成控制缺失；C 讓冒名需要同時取得使用者的身分與 MFA，維運人員單獨做不到。成本較高，但這是「決定可問責」的地基。

## 2. 資料庫超級使用者重算整條雜湊鏈或截掉尾端

**情境**：資料庫由資訊部的 DBA 管理，具有 PostgreSQL superuser。某次稽核前，有人想讓一張越權核准的單「從來沒存在過」。DBA 執行 `set session_replication_role = replica`（讓 trigger 不觸發），刪掉那張單之後的所有事件，再從那一點用同樣的演算法重算後面每一筆的雜湊。另一種更簡單的做法：從備份還原到三天前，三天內的事件全部消失。

**系統現在的反應**：工程規範第 5 節的架構測試確認稽核表「擋下 UPDATE、DELETE、TRUNCATE」，但 superuser 可以停用 trigger、可以 `ALTER TABLE`、可以還原備份。雜湊鏈的驗證只能證明「這條鏈內部一致」，不能證明「這條鏈就是當初那一條」。整條重算或截掉尾端，鏈都驗證得過。

**結果**：platform-vision 說「雜湊鏈可由第三方驗證」，但沒有外部的錨點，第三方驗證的只是自我一致。我會判定雜湊鏈**只能偵測外行人的竄改，對有 superuser 的人無效**。

**對照現有設計**：部分涵蓋。`K-AUDIT-APPEND`、`K-AUDIT-CHAIN` 有；00-spine 第 11 節有 `audit_feed` 輸出到 SIEM，但沒有規定定期把鏈頭雜湊送到平台與 DBA 都改不了的地方，也沒有規定還原備份要留痕跡。

**替代方案**：
- A. 依賴 PostgreSQL 權限管控，不給任何人 superuser。地端部署做不到，總要有人能維護資料庫。
- B. 稽核事件即時串流到 SIEM，以 SIEM 為準。SIEM 通常由資訊部或資安室管，也可能保存期限短；而且只送事件、不送鏈頭，SIEM 那邊無法證明完整。
- C. 定期錨定：每隔固定時間（例如每小時）把「最後一筆序號＋鏈頭雜湊」寫到平台管理員與 DBA 都無法修改的外部位置，並由一個獨立的檢查定期比對。

**最佳解**：C，外部位置採「至少兩處、由不同單位控制」。
- 錨點內容：時間、最後一筆序號、鏈頭雜湊、該期間的事件筆數；錨點本身也串成鏈。
- 錨點去處：(1) WORM 儲存（物件鎖定），帳號由資安室或稽核室持有；(2) 每日把當日錨點以 email 自動寄到稽核室的信箱（稽核室可以自己留存，這是現實中最便宜、最難被 IT 一手遮天的做法）；選配 RFC 3161 時間戳記服務。
- 驗證工具在檢查鏈的內部一致之外，還要比對錨點：序號減少、鏈頭不符、錨點中斷，都列為最高等級的例外。
- 還原備份、`session_replication_role` 變更、停用 trigger、DDL 都由 PostgreSQL 的稽核設定（例如 `pgaudit` 或 event trigger＋log 輸出）記錄並送到外部，還原後第一筆事件必須是「系統已從 X 時點還原，遺失序號 N–M」，並列為例外由稽核室結案。

**理由**：沒有外部錨點，「紀錄改不掉」這個承諾對我來說不成立，平台三大承諾少一個。成本只是排程與一個 WORM 桶，沒有理由不做。

## 3. 直接改業務資料表，稽核事件沒有對應

**情境**：某張 L4 授權在 2027-04-30 到期。申請人找上 DBA 李志偉：「到期日填錯了，幫我改成 10-31」。李志偉直接 `update sgn.grant set valid_to = '2027-10-31'`。他不覺得這是竄改，他覺得是「修資料」。資訊部每月平均會有幾次這種「資料修正」，這在每一家公司都一樣。

**系統現在的反應**：稽核事件只增不改，但 `grant`、`case`、`case_task` 這些業務表是一般資料表，DBA 可以改。稽核事件裡沒有任何紀錄，雜湊鏈也完全正常。權限判定介面（`check`）讀的是 `grant` 表，所以 5 月之後仍回答「允許」。

**結果**：稽核事件說到期，現況說有效，兩者不一致，卻沒有人發現。我抽樣時會以事件重建每張單的狀態，和畫面對照。只要抽到一張不一致，我就要擴大樣本，並判定「資料修正」程序無效。

**對照現有設計**：沒涵蓋。只保護了稽核表，沒有保護「現況」與「紀錄」的一致性；也沒有「資料修正」的正式程序。

**替代方案**：
- A. 業務表也加 trigger 擋 UPDATE。業務表本來就要被 `api` function 更新，trigger 分不出是 function 還是 DBA；DBA 也能停 trigger。
- B. 完全事件溯源：現況只由事件重算出來。理論最乾淨，但效能與實作代價大，而且 DBA 一樣能改事件以外的投影表。
- C. 每日自動一致性檢查：由稽核事件重播出每張單、每筆授權應有的狀態與關鍵欄位，與業務表比對；不一致就是例外。加上「資料修正」本身也是一種申請單。

**最佳解**：C，外加兩項：
- 每筆業務表的列帶「最後一筆事件序號＋列內容雜湊」；一致性檢查只要比對雜湊，每天全量跑得動。結果寫成稽核事件並納入稽核準備度畫面。
- 新增核心流程「資料修正申請」：說明原因、修正前後、由資料擁有者與另一位非執行人核准，由平台的 function 執行修正並產生事件。這樣 DBA 就沒有理由直接改資料。
- `pgaudit` 記錄所有不是 `sgn_owner` 執行升版、也不是 `sgn_app` 的 DML，送到外部（與第 2 節同一條管道）。

**理由**：我要的是「改了會被發現，而且有正式的路可走」。C 是偵測性控制，加上資料修正流程讓預防面有替代路徑；B 對一般維運團隊太重，A 擋不住真正有權限的人。

## 4. 平台本身的程式與流程包升版不受變更控制

**情境**：平台上線後，第一年改版 20 次以上。2027 年 6 月，開發人員修了一個「升級後找不到主管」的 bug，順手把 `resolve_stage_assignees` 裡的職責分離檢查改成只比對 `person_id`、不比對代理人。這個 commit 以 `wip:` 開頭推上 main（D7），由同一位開發人員用 `sgn_owner` 在正式環境執行 migration。另外，流程管理者想把 L4 的資安長關改成選擇性，發現 D12 的設定變更要雙人覆核，但「流程定義由流程包的升版腳本載入」（platform-vision 第一版範圍、engineering-standards「路徑只能透過 migration 變更」），所以請開發人員改升版腳本直接上。

**系統現在的反應**：平台沒有記錄「正式環境目前跑的是哪個版本、誰部署的、誰核准上線」。`sgn_owner` 執行 migration 不產生稽核事件。D12 的設定變更簽核與升版腳本是兩條並存的路，後者沒有雙人覆核。

**結果**：程式變更是 ITGC 三大塊之一。我會問：開發與上線是否分離？上線前誰核准、誰測過？正式環境的程式與核准的版本一致嗎？目前三題都答不出來。更嚴重的是，第 1–3 節所有預防性控制都可以被一次 migration 改掉，所以**變更控制無效時，我不能依賴任何自動化控制**。

**對照現有設計**：沒涵蓋。D12 只管理「設定」，不管理「程式與 migration」；engineering-standards 與 D12 對路徑怎麼改的說法互相矛盾（SSOT 缺陷）；D7 允許未驗證的 commit 進 main，這在開發期可以，但沒有區分正式環境的上線條件。

**替代方案**：
- A. 依賴公司既有的程式變更流程（變更單＋上線核准）。平台本來就要把「程式變更上線」做成流程包（D13），卻不用在自己身上，稽核會覺得矛盾；而且平台不會知道正式環境實際跑什麼。
- B. 平台自己的升版走自己的「程式變更上線」流程包，並由資料庫記錄每一次 migration。
- C. 只做版本指紋：每天計算 `sgn`、`sgn_internal`、`api`、`pack_*` 所有 function 與表定義的雜湊，與核准的版本比對。

**最佳解**：B＋C。
- 所有 migration（核心與流程包）透過一個升版程序執行：程序先檢查「這個版本有一張已核准的程式變更上線申請單、核准人不是開發人、上線人不是開發人」，才允許套用；套用前後各寫一筆稽核事件，含 migration 檔案的雜湊。
- 每天計算資料庫物件定義的指紋（`pg_get_functiondef` 等），與最近一次核准上線的指紋比對，不一致就是最高等級例外（偵測到繞過升版程序的直接修改）。
- 流程定義與路徑的變更只有一條路：D12 的設定變更申請單。流程包升版腳本只能載入「初始版本」，之後的修改一律走 D12；修正 engineering-standards 的矛盾敘述。
- D7 維持開發期的做法，但正式環境只能部署打了版本標籤、測試全過、有核准紀錄的 commit。

**理由**：平台宣稱讓客戶的程式變更稽核過關，自己的變更卻沒管，第一次查核就會被我寫成缺失。B 是預防，C 是偵測；兩者都有，我才能只測樣本，不必每次都全查。

## 5. 用參數關掉控制

**情境**：上線三個月後，高階主管抱怨手機簽核每次都要 MFA。系統管理員提出設定變更，把 `approval.mobile_mfa_required` 改成 false，理由寫「提升效率」，由資訊部同事核准。另一個情況：儲存空間不足，有人把 `audit.retention_years` 從 10 改成 2，清除作業刪掉了三年前的事件。再一個：測試環境的設定匯出後匯入正式環境，`system.allow_fake_clock` 變成 true，之後有人用 `set sgn.fake_now` 把核准時間設在期限內。

**系統現在的反應**：00-spine 第 5 節說核心規則「流程包不能關閉」，但第 8 節又把 `approval.mobile_mfa_required` 做成可設定；`K-MOBILE-MFA` 實際上可以被關。保存年限可以調降，沒有下限。假時鐘的開關是一個執行期參數，不是部署層級的固定設定。

**結果**：我會把「控制是否可以被參數關掉」列為必問題。只要能被關、而關掉只需要兩個資訊部的人同意，我就要測全年每一天的參數值，並把這些參數當成「影響控制的設定」。關過一天，那段期間的控制就無效。

**對照現有設計**：部分涵蓋。D12 讓參數變更有雙人覆核與紀錄，但沒有區分「一般參數」與「削弱控制的參數」，也沒有下限。

**替代方案**：
- A. 把這些參數全部拿掉，寫死在程式。失去通用性，不同公司的保存年限確實不同。
- B. 參數保留，但定義允許範圍：保存年限下限、MFA 只能從 false 改成 true 不能反向。仍無法因應合理的例外。
- C. 參數定義加上「控制影響」分類：削弱控制的方向需要更高層級核准（含控制負責人與稽核室知會），並有不可低於的硬下限；部署層級的開關（假時鐘）完全不放在參數表。

**最佳解**：C。
- `setting_definition` 增加 `control_effect`（none／strengthen_only／weakening_requires_control_owner）與 `hard_floor`、`hard_ceiling`。
- `approval.mobile_mfa_required` 取消，改為核心規則固定；如需例外，只能依級別調整「是否允許電腦簽核免 MFA」，不能讓手機免 MFA。
- `audit.retention_years` 下限設為法定與查核需要的年限（例如 7 年），調降需要稽核室的角色參與核准；清除作業只刪「已錨定、已匯出到長期保存、且超過年限」的事件，刪除前後鏈頭寫入錨點。
- `system.allow_fake_clock` 改為部署時的環境變數，正式映像檔建置時不包含 `fake_now` 的程式路徑；架構測試在正式組態下確認 `sgn.fake_now` 無作用。每筆稽核事件同時記錄資料庫的 `clock_timestamp()`，和業務時間分開存。
- 稽核資料包附上「期間內所有控制相關參數的值與變更歷程」，讓我一次看完全年。

**理由**：通用性要留，但不能以犧牲預防性控制為代價。C 讓合理的差異可以設定，削弱的方向則變成看得見、難以單方面決定的事。

## 6. 設定變更申請單：誰有資格核准、能否回溯生效、上線基準

**情境**：D12 上線後，資訊部經理謝明哲提出「把財務長關的升級時限從 2 天改成 10 天」，同部門的林冠宇核准。另一張設定變更把某參數的生效時間填成上個月 1 日，讓上個月一張已逾期的單在紀錄上變成「未逾期」。上線當天的所有初始設定，則是由導入顧問用腳本一次載入，沒有任何核准紀錄。

**系統現在的反應**：D12 只寫「由提出人以外的人核准」。沒有規定核准人的資格（任何其他人都可以？），沒有規定生效時間不能早於核准時間，也沒有提到上線基準。

**結果**：「提出人以外的任何人」對我來說不是有效的覆核，同部門同事互相核准是最常見的形式化覆核。回溯生效等於事後改寫依據。上線基準沒有核准，代表期初的控制設定本身不可依賴。

**對照現有設計**：部分涵蓋（D12、A10）。

**替代方案**：
- A. 設定變更一律由稽核室核准。稽核室不該參與管理決策，這會破壞稽核的獨立性。
- B. 設定變更的簽核路徑本身也是一條 `approval_policy`，依設定的種類決定關卡。
- C. 只固定「提出人以外＋不同單位」。

**最佳解**：B。
- 設定變更是一種核心流程類型，路徑依「設定所屬的流程類型與 `control_effect`」決定：一般參數＝提出人以外的流程管理者；路徑、角色指派、削弱控制的參數＝流程擁有單位的主管＋控制負責人（例如資安長或財務長），稽核室知會（不簽核，只收通知並可查）。
- 生效時間不得早於最後一關核准時間，資料庫層強制；試算影響要列出「生效後會改變結果的進行中申請單」。
- 上線基準：上線時產生一張「期初設定基準」申請單，內容是全部設定的快照與雜湊，由流程擁有者與控制負責人核准；此前的設定事件標為「導入期」。
- 設定變更路徑本身的修改，也只能透過設定變更，且需要兩個不同單位的人。

**理由**：用平台自己的路徑能力解決，不新增特例，符合通用性；同時讓我看到「核准的人有資格」與「沒有回溯」，這是我判斷變更控制有效的兩個要件。

## 7. AD 群組同步直接給平台角色，繞過簽核

**情境**：導入時為了方便，把 AD 群組 `GRP-MIS` 對應到平台的 `mis` 角色，`GRP-Audit` 對應到 `auditor`。2027 年 2 月，AD 管理員（資訊部，不是平台的管理員）因為工單要求，把一位新進的外包工程師加進 `GRP-MIS`。下一次同步，這位外包人員就能在平台上認領 MIS 群組的單、按「已套用」。

**系統現在的反應**：`role_assignment` 有「來源」欄位，代表角色可以來自外部同步。D12 說角色指派要走設定變更，但從外部來源同步進來的角色指派不經過 D12。

**結果**：平台的存取控制實際上由 AD 群組決定，而 AD 群組的變更不在平台的簽核與紀錄裡。我會把平台的角色存取控制判定為依賴 AD 的控制，必須把 AD 群組管理也納入查核範圍；若 AD 那邊沒有核准紀錄，平台角色就沒有核准紀錄。

**對照現有設計**：沒涵蓋。D12 與 role_assignment 的「來源」之間的關係沒有定義。

**替代方案**：
- A. 禁止外部同步角色，全部在平台內指派。大公司 MIS、稽核群組本來就在 AD 管，重複維護會造成兩邊不一致。
- B. 允許同步，但同步進來的變更變成「待確認的角色指派」，必須在平台走 D12 核准後才生效。
- C. 允許同步立即生效，事後每日產生差異報表給控制負責人覆核。

**最佳解**：依角色的敏感度分開處理：
- 會影響控制的角色（`mis`、`auditor`、流程管理、技術維運、資安長、財務長、印鑑管理人、資料擁有者等）一律採 B：同步只能「提議」，平台內核准後生效；同步移除則立即生效（縮小免簽，與原則 ③ 一致）。
- 只用於路由的一般屬性（部門、職稱）可採 C。
- 角色定義上新增 `assignment_source_policy`，由設定變更管理。

**理由**：給權限要事前擋，收權限要立即生效，這與平台自己的「縮小免簽、擴大重簽」完全一致；一般屬性用偵測性控制即可，不會拖慢日常同步。

## 8. 身分對應被改綁，A 登入後變成 B

**情境**：員工「王志明」離職，同年又有一位同名的新進員工。身分系統管理員為了省事，沿用舊帳號重新啟用。另一種情形：身分提供者的管理員把某個 `external_id` 對應到財務長的 `person`。

**系統現在的反應**：`person_identity` 是「provider＋external_id → person」的對應表，由人員與組織 port 同步。沒有規定對應被改時要通知誰、要不要核准，也沒有規定已停用的身分不得重新指向另一個人。

**結果**：新的王志明登入後，看到舊王志明的申請單與授權，甚至成為某些授權的負責人；被改綁到財務長的帳號可以簽財務長的關卡。我會問「身分對應的變更怎麼控制」，目前答不出來。

**對照現有設計**：沒涵蓋。

**替代方案**：
- A. 身分只信任 email。email 會被重用，更糟。
- B. 對應關係只增不改：一個 `external_id` 一旦對應過某個 person，就不得改指向別人；需要改時建立新的對應並停用舊的，並寫稽核事件。
- C. B 加上：任何對應變更都通知被影響的 person 與其主管，並對「已停用的 person 被重新啟用」「同一 external_id 改指他人」列為例外。

**最佳解**：C。對應改指他人在資料庫層直接拒絕；重新啟用已離職的 person 需要人資角色核准；同名人物一律是新的 person。

**理由**：身分是所有紀錄的鍵，拒絕改綁是預防性控制，成本很低。

## 9. 人資資料晚到，離職者在離職日之後仍簽核

**情境**：通路業務組組長劉俊傑 2027-05-31 離職。人資系統 6 月 10 日才登錄（實務上常見，離職手續跑完才登錄），而且回溯生效日為 5 月 31 日。6 月 3 日，劉俊傑在手機上仍有效的 SSO session 核准了部屬何宗翰的一張 L3 申請。另一種情形：人員與組織的同步排程因為 LDAP 憑證過期，連續兩週失敗，沒人發現。

**系統現在的反應**：`K-OWNER-CONTINUITY` 處理授權負責人離職，但沒有處理「簽核人在離職生效日之後做的決定」。同步失敗沒有被定義為例外。

**結果**：我每年一定會測「離職人員離職日之後是否仍有活動」。這張核准在紀錄上是有效的，而且平台沒有自己找出來。同步中斷兩週，表示這兩週的升級對象、職責分離比對都用舊資料。

**對照現有設計**：部分涵蓋（K-OWNER-CONTINUITY、validation-cases 的依事件到期）。

**替代方案**：
- A. 要求人資即時登錄。平台控制不了人資的作業。
- B. 簽核當下即時查詢人員狀態。只能擋即時已知的離職，對回溯登錄無效。
- C. B 加上回溯偵測：人員狀態變更帶有生效日時，平台自動找出「生效日之後該人做的所有決定」，列為例外並要求重新處理。

**最佳解**：C，再加同步監控。
- 決定類動作在資料庫層檢查 `person` 的狀態與生效期間（擋即時已知的情況），並記錄當時使用的組織資料版本（同步批次編號）。
- 收到回溯的離職或調職時，自動產生例外「離職後的決定」：列出每一個決定，對仍在進行或仍有效的授權，該關重新指派並重簽；已完成的列給稽核準備度畫面追蹤到結案。
- 人員與組織同步：每次記錄筆數、異動數、來源的時間戳；超過設定時間沒有成功同步、或異動數異常（例如一次停用 30% 人員）就是例外並暫停自動化的負責人撤銷。
- 離職生效時撤銷該人在平台的所有 session。

**理由**：回溯登錄是常態，不是例外。B 只解決一半，C 讓平台在我抽到之前就找出來，正是「例外自己浮現」的承諾。

## 10. 上線時既有權限的期初資料沒有核准紀錄

**情境**：平台 2027-01-01 上線。DC 裡已經有 340 條既有的資料權限規則，人資系統裡有 60 個帳號。導入顧問把它們匯入平台，建成「生效中」的授權，好讓對帳不要一上線就爆出幾百筆差異。

**系統現在的反應**：沒有定義期初資料。匯入的授權在平台上看起來和正常核准的一樣，或者根本沒有對應的申請單。

**結果**：我抽樣期中的授權時，會抽到這些期初授權，然後問核准紀錄在哪裡。如果平台把它們和正常授權混在一起，我會判定授權報表的母體不可靠。如果不匯入，對帳一上線就出現幾百筆「沒核准卻存在」，例外清單失去意義，大家開始忽略例外。

**對照現有設計**：沒涵蓋。

**替代方案**：
- A. 全部重新申請。幾百張單同時湧入，簽核人會一律核准，形式化且造成上線阻力。
- B. 匯入但標記為「期初承接」，不需要核准。我仍然不能依賴這些授權。
- C. 匯入並標記為「期初承接」，給一段過渡期，期間內必須完成一次由擁有者執行的複查（複查即核准）；未複查的自動撤銷或列為例外。

**最佳解**：C。
- 核心新增授權來源 `migrated`：記錄來源系統、匯入檔案雜湊、匯入人、匯入時的核對（筆數與來源系統的報表一致）。
- 上線後 N 天內（參數，預設 90 天）自動開一場複查活動，負責人逐筆確認保留、縮小或撤銷；確認保留的就產生一筆正式的核准紀錄。
- 稽核資料包與授權報表上，`migrated` 與正常授權分開呈現，過渡期結束後未處理的列為例外。

**理由**：C 讓期初資料有一個有時限、有紀錄的轉換路徑，既不會因為一次湧入而形式化，也不會讓未核准的權限無限期存在。

## 11. 稽核資料包「沒有遺漏」無法被證明

**情境**：期末查核，我請公司提供 2027 年度所有 L4 資料授權申請單。公司按一鍵產出稽核資料包，裡面有 412 張單。我問：「怎麼證明是全部？」對方說「系統產的」。我看單號，發現有跳號（PostgreSQL sequence 在交易回滾時本來就會跳號）。我又問報表的篩選條件是「建立日期」還是「送審日期」、跨年度的單算哪一年、被取消的草稿算不算，沒人說得清楚。

**系統現在的反應**：platform-vision 與 A2 承諾「可證明沒有遺漏」，但沒有定義怎麼證明。

**結果**：這是 IPE 的典型問題。如果我不能驗證報表的完整與正確，我就不能用它做抽樣母體，必須自己找替代方法（例如請 DBA 下查詢），而 DBA 的查詢我一樣要驗證。整個「稽核自己查得到」的價值大打折扣。

**對照現有設計**：部分涵蓋（A2 只有目標）。

**替代方案**：
- A. 單號用無跳號的計數器。可以做到，但仍無法證明「沒有單被刪掉」，也不解決篩選邏輯的問題。
- B. 資料包附上完整的事件匯出，讓稽核自己重算。完整但對大多數稽核人員太重。
- C. 資料包本身帶有完整性證明：期間起訖的事件序號、起訖鏈頭雜湊（對得上第 2 節的外部錨點）、每張單建立事件的序號，加上公開的報表規格。

**最佳解**：C，同時提供 B 作為選項。
- 資料包的清單列出每張單「建立事件」的序號；期間內所有「建立申請單」事件的序號與清單一一對應，並與錨點的事件數一致，就證明沒有遺漏。單號跳號因此不再重要，但單號仍改用不跳號的計數器，避免無謂的解釋。
- 報表規格（篩選以哪個事件時間為準、哪些狀態納入、時區）寫在 `docs/audit/` 並在資料包第一頁列出；規格有版本，產出時記錄使用的版本、參數、產出人、產出時間、筆數與檔案雜湊，並寫成稽核事件。
- 提供公開的驗證工具與原始事件匯出（JSON Lines），讓我能用自己的環境重算清單與鏈頭。

**理由**：只要完整性能被我自己驗證，我就可以直接把它當母體，省掉每年的替代程序。這是平台對稽核最有感的價值。

## 12. 第三方無法獨立重算雜湊

**情境**：我拿到事件匯出檔與驗證工具。工具是平台提供的，我不能只用它的結果。我自己寫程式重算，發現算不出一樣的雜湊：內容欄位是 `jsonb`，鍵的順序、數字格式（`1.0` 與 `1`）、時間戳的精度與時區，在匯出時都和雜湊時不同。兩年後公司升級 PostgreSQL 大版本，`jsonb` 輸出的格式細節改變，平台自己的驗證也開始對不上。

**系統現在的反應**：K-AUDIT-CHAIN 說雜湊鏈可驗證，platform-vision 說可由第三方驗證，但沒有規定雜湊的輸入怎麼序列化。

**結果**：第三方無法重算，「可由第三方驗證」就不成立；PostgreSQL 升級後驗證失敗，在稽核眼中與竄改無法區分。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 雜湊 `jsonb::text`。依賴 PostgreSQL 內部格式，升版會壞。
- B. 採用公開的 JSON 正規化標準（RFC 8785 JCS），每筆事件存「被雜湊的那串 bytes」。
- C. 自訂欄位串接格式。第三方要另外讀規格，容易出錯。

**最佳解**：B。每筆事件同時保存 `hashed_payload`（UTF-8 bytes，依 RFC 8785 正規化）與雜湊；驗證只需要 bytes 與 SHA-256，不需要 PostgreSQL。演算法與格式寫成公開規格並附測試向量；驗證工具開源、可以離線執行。雜湊演算法帶版本，以後要換演算法時新舊並存。

**理由**：存下原始 bytes 是讓十年後還驗證得過的唯一可靠做法；空間成本可以接受。

## 13. 到期排程失敗，授權超過期限仍判定允許

**情境**：2027 年農曆年連假，資料庫主機重開機後，排程服務沒有自動啟動。到期失效、確認逾期撤銷、負責人寬限期撤銷全部停了 9 天。期間有 23 筆授權過期，DC 端的規則沒有收回，權限判定介面也繼續回答「允許」，因為 `grant.status` 還是 `active`。

**系統現在的反應**：骨幹有 `scheduler_run`，但沒有規定排程沒執行時誰會知道；`check` 依據什麼判定「有效」也沒有定義。

**結果**：作業控制（job monitoring）是 ITGC 的一塊。我會調全年的排程執行紀錄，找中斷的期間，再看那段期間到期的授權是否在到期日之後還被使用。只要一次中斷沒人發現，自動到期這項控制就要判為無效。

**對照現有設計**：部分涵蓋（`K-EXPIRE`、`scheduler_run`）。

**替代方案**：
- A. 加強排程監控（告警）。仍然依賴有人看告警，而且告警系統本身也可能失效。
- B. 有效性在讀取時計算：`check` 與授權查詢一律以 `valid_from <= now < valid_to and status = active` 判定，排程只負責「通知與收回外部設定」。
- C. 兩者並用。

**最佳解**：C。
- 判定與查詢一律以時間計算有效性（預防：排程停了也不會說錯話）。
- 排程每次執行寫 `scheduler_run`，且有「心跳」：超過設定時間沒有成功執行，下一次登入的流程管理者與技術維運都會在首頁看到例外；稽核準備度畫面列出全年中斷的期間。
- 排程恢復後自動補跑，補跑的事件註明「延遲處理，原應處理時間為 X」。
- 對外推送的到期事件同理補發；對帳會把「應收回卻仍存在」列為例外。

**理由**：B 把關鍵的控制從偵測性變成預防性；A 讓剩下依賴排程的動作（通知、外部收回）失效時看得見。

## 14. 對帳檔由設定權限的人自己匯出上傳

**情境**：人資系統是外購的雲端服務，由人資部的楊淑惠擔任系統管理人（D19），整合方式是「檔案交換」（D21）。每季她從人資系統匯出帳號與角色清單，上傳到平台對帳。她私下給了一位外部顧問薪資模組的檢視權限，匯出時用篩選條件把這個帳號排除。對帳結果：零差異。另一種情形：純人工整合的系統，管理人按「已套用」，再上傳一張截圖當證據。

**系統現在的反應**：D21 與 A21 規定檔案與人工整合「產生同樣格式的證據」，A7 有人工獨立驗證，但沒有規定對帳檔的完整性怎麼確保，也沒有規定上傳的人不能是設定權限的人。

**結果**：對帳的母體由被稽核的人自己提供，我不會依賴這個對帳結果。這正是 D19 說的「稽核的盲區」，現在的設計沒有真正補起來。截圖我也不接受當作執行證據，它無法證明是哪個系統、哪個時間、有沒有被裁切。

**對照現有設計**：部分涵蓋（D19、D21、A7、A21）。

**替代方案**：
- A. 只接受 API 整合。外購系統大多沒有，現實行不通（D21 的出發點）。
- B. 匯出與上傳由系統管理人以外的人執行（例如資安或稽核室），平台記錄。需要對方系統給該人唯讀的匯出權限。
- C. B 加上完整性檢查：檔案帶來源系統的匯出參數、匯出時間、總筆數；平台與上一期比對，總筆數的變動必須能被期間內的核准與撤銷解釋；不能解釋的列為例外。

**最佳解**：C。
- 受管系統登記「對帳執行人」角色，不得與系統管理人、執行人重疊（職責分離由核心強制）。
- 上傳檔附「匯出條件」欄位（平台定義每個系統的標準匯出條件，偏離就是例外），以及原始檔的雜湊；平台保存原始檔。
- 筆數前後期比對：上期筆數＋期間核准新增－期間撤銷＝本期應有筆數，差異列為例外。
- 人工整合的執行驗證：獨立驗證人必須親自在系統上檢查（由平台給的檢查清單逐項勾選並填觀察值），截圖只當附件，不當驗證本身；驗證人與執行人不得是同一單位的同一人或其下屬。
- 每年由稽核室（或我）隨機挑選期別，在現場重新執行一次匯出；平台提供「與上傳檔比對」的功能。

**理由**：外購系統的權限是最常出事的地方。C 讓「自己匯出、自己上傳、自己說沒問題」在設計上不可能發生，同時不要求對方系統有 API。

## 15. 定期複查流於形式，母體與呈現內容沒有留存

**情境**：每季的授權複查活動，業務副總方國華名下有 180 筆。他在 3 分鐘內全部按「保留」。另一位負責人勾選「撤銷」12 筆，但 DC 端的規則一個月後還在。我要測這個控制時，需要知道：複查開始時的母體是什麼？每一筆呈現給複查人的資訊是什麼（最後使用時間、使用情境、是否有職責衝突）？撤銷有沒有真的落實？

**系統現在的反應**：00-spine 第 11 節只列出 `access_review_campaign`、`access_review_item`，細節在尚未完成的 05-integration。

**結果**：複查是我一定會測的控制，而且我會測它的「精確度」（reviewer 真的看過、有依據）。如果平台只留「誰按了保留」，我無法判斷覆核的品質；撤銷沒落實，複查就沒有效果。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 只留存每筆結果。不足以支持精確度測試。
- B. 留存母體快照與每筆呈現的內容、決定時間；撤銷產生正式撤銷事件並進入對帳追蹤。
- C. B 加上防形式化設計：大量保留時要求抽樣說明、顯示「最後使用時間」、對 90 天未使用的強制單獨決定。

**最佳解**：C。
- 活動開始時凍結母體（快照＋雜湊＋筆數），活動結束時對帳：每一筆都有決定或已升級。
- 每筆記下呈現給複查人的事實（版本化的 `summarize_content` 結果＋使用資訊）與決定時間；批次保留是允許的，但「未使用」「有職責衝突」「期初承接」的項目不能批次。
- 決定撤銷即觸發核心撤銷，並在下一次對帳確認外部系統已移除，未移除列為例外。
- 產出複查統計（每位複查人平均每筆耗時、保留率），給控制負責人看。

**理由**：複查是偵測性控制，我依賴它的前提是看得到它被認真執行；C 用資料讓這件事可以被證明，而不是靠訪談。

## 16. 外部會計師與子公司查核人員的帳號

**情境**：我（事務所）進場查核三週，需要在平台上自己查詢、匯出。另一家子公司的簽證會計師是另一家事務所，只能看該子公司的資料。公司 IT 的做法是借我一個內部稽核黃淑芬的帳號，或者開一個 `auditor` 角色給我。

**系統現在的反應**：`K-AUDITOR-READONLY` 是「唯讀，可查全部」。沒有外部稽核的身分類型，也沒有依公司別與期間限縮稽核角色的設計；A18 的外部人員只針對執行人。

**結果**：借帳號會讓我所有查詢記在內稽名下，紀錄失真。給我「可查全部」，則讓另一家事務所看到不屬於其查核範圍的子公司資料，也可能讓我看到薪資等不需要的機密內容。查核結束後帳號沒有關，又會變成一筆沒人負責的權限。

**對照現有設計**：沒涵蓋（D15 多公司、A18 外部人員都沒有談到外部稽核）。

**替代方案**：
- A. 由內部稽核代為查詢並提供資料。我必須另外驗證他們給的資料，失去「稽核自己查得到」的價值。
- B. 給外部稽核一個 `auditor` 角色的帳號。範圍過大、沒有期限。
- C. 外部稽核作為一種被授權者：透過平台的申請流程取得「依公司別、資料期間、有期限、唯讀」的稽核權限，有內部負責人（稽核室主管）。

**最佳解**：C。
- 稽核角色可帶 `scope_ref`（公司別、流程類型）與資料期間；外部稽核帳號必須有內部負責人、有結束日，到期自動失效（沿用 K-OWNER-CONTINUITY、K-EXPIRE）。
- 機密欄位的內容預設不對外部稽核解密；查核需要時，由負責人逐張開放，並寫查閱事件。
- 外部稽核的每次查詢與匯出都寫事件；匯出檔帶產出人與浮水印。

**理由**：用平台自己的授權能力管外部稽核的存取，正好是最好的示範；同時解決紀錄失真與範圍過大兩個問題。

## 17. 自行設定的代理等於未經核准的權限移轉

**情境**：資安長賴政達長期出差，自行把代理人設為資安工程師許文豪，期間一年。實際上一整年 L4 的資安長關都是許文豪簽的。另一種情形：財務長把代理人設成自己的秘書，秘書幫她「點核准」。

**系統現在的反應**：`delegation`（委託人→代理人、期間、原因）與 `K-DELEGATE`（紀錄寫明誰代誰簽）有。沒有規定誰能設代理、代理人的資格、期間上限。

**結果**：簽核權限是一種權限。代理等於把簽核權限移轉給另一個人，卻不需要任何核准，而且可以無限期。我會判定「核決權限」的控制可以被代理設定繞過。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 禁止代理。現實中不可行，人一定會請假。
- B. 代理人只能從事先核准的名單中選（例如 seed 裡的「資安長代理人」角色）。
- C. B 加上期間上限與例外：代理超過 N 個工作天需要委託人的主管核准；代理人的職級或角色資格由流程定義；代理統計（某關有多少比例由代理人簽）列入稽核準備度。

**最佳解**：C。代理人資格由各關的 resolver 定義（例如「同一角色的其他持有人」或「指定的代理人角色」）；短期代理自行設定即可，超過上限就是一張需要核准的申請單；代理期間與比例超過門檻列為例外。代理人簽核仍須通過委託人自己的 MFA 以外、代理人本人的 MFA。

**理由**：保留代理的便利，但讓長期、不合資格的代理不能無聲發生；速度與正確性都兼顧。

## 18. 找不到上一層主管時升級給系統管理員

**情境**：總經理高志遠本人申請一筆資料授權，主管關由「上一層」接手，但他沒有上一層。或是財務長蘇慧敏的關卡逾時，要升級給她的主管總經理，總經理又剛好是申請人。骨幹第 7 節：「找不到上一層時，升級給系統管理員群組處理」。系統管理員群組是資訊部經理謝明哲。

**系統現在的反應**：如上，交給資訊部處理。

**結果**：資訊人員實質上替總經理的申請做業務決定，這在我看來是嚴重的職責分離問題：技術管理者不應有業務核准權。也沒有定義「處理」是指核准、重新指派還是暫停。

**對照現有設計**：部分涵蓋（有處理路徑，但路徑本身不正確）。

**替代方案**：
- A. 維持現狀，但要求系統管理員只能「重新指派」不能核准。仍由資訊部決定誰來簽，等於間接決定。
- B. 由流程定義指定「最高層的替代簽核人」，例如董事長、審計委員會指定的人或獨立董事；沒有設定時案件停住並列為例外。
- C. 申請人是最高層時，該關直接改由另一個指定角色（例如稽核室知會＋財務長）。

**最佳解**：B。
- `approval_policy` 必須定義 `top_of_chain_resolver`（指定角色），設定變更走 D12；沒有定義的流程不得啟用。
- 找不到人時永不交給技術維運或流程管理角色；案件停在該關並產生例外，由流程擁有者處理。
- 高階主管的申請與核准，列入稽核準備度的「高風險人員」清單，方便我直接抽查。

**理由**：高層的申請正是稽核最關注的樣本；把它交給 IT 會直接造成我的查核發現。

## 19. 電腦上簽核沒有加強驗證，也沒有記錄驗證強度

**情境**：業務副總方國華的筆電在會議室沒鎖，旁人用他已登入的 SSO session 核准了一張 L4 申請。`K-MOBILE-MFA` 只規定手機要 MFA。另一個情形：公司的 SSO session 有效期是 12 小時，主管早上登入，下午在任何電腦上都能直接簽。

**系統現在的反應**：只有手機要求 MFA；電腦上的簽核只依賴 SSO 登入狀態。稽核事件記錄「MFA」欄位，但沒有記錄 SSO 的驗證方式與驗證時間。

**結果**：我會問「怎麼確定按下核准的是本人」。手機與電腦的風險差別不大，只對手機加強說不過去。也看不出哪些核准是用強驗證完成的。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 所有簽核都要 MFA。最安全，但對每天要簽幾十張的人很痛，會被抱怨而推動「關掉 MFA」（見第 5 節）。
- B. 依級別：L4、重大、設定變更、撤銷以外的高風險動作一律 step-up；其他依 SSO 驗證時間（例如 30 分鐘內驗證過 MFA 就免）。
- C. 只依裝置區分。現狀。

**最佳解**：B。決定類動作要求「最近 N 分鐘內的強驗證」（N 依級別設定，有硬上限），不論裝置；強驗證可由身分提供者的 `acr`／`amr`／`auth_time` 提供。每筆決定事件記錄驗證方式、驗證時間與裝置類型。批次核准一次 step-up 可以涵蓋整批。

**理由**：B 讓安全與速度兼得：高風險的決定都有強驗證證據，日常的單只在第一次需要 MFA。

## 20. 對外介面的金鑰管理，與平台停機時其他系統放行

**情境**：示範用的其他系統呼叫 `check`。平台週末升級停機 4 小時，該系統的開發人員把逾時的處理寫成「查不到就允許」，以免業務中斷。另一個情形：某系統的 `api_client` 金鑰寫死在程式碼裡，被推到公開的 Git 倉庫；有人用這把金鑰呼叫對帳介面，回報「實際權限與核准一致」，蓋掉了真正的差異。

**系統現在的反應**：00-spine 第 11 節說 `api_client` 有各自的金鑰與範圍、每次呼叫留紀錄，「實際擋下存取的仍是各系統自己」。沒有規定 `api_client` 的建立與範圍變更要走 D12，也沒有規定呼叫方失敗時的預設行為與證據。

**結果**：fail-open 的系統，等於在平台停機時沒有控制；我會要求看停機期間的存取紀錄。`api_client` 能被任意建立或金鑰外洩，對帳結果就不可依賴。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 在文件裡建議呼叫方 fail-closed。平台無法強制，也看不到。
- B. 提供可以離線使用的快照：呼叫方可快取帶簽章與到期時間的授權清單，停機時用快取判定，快取到期才拒絕。
- C. B 加上：`api_client` 是一種受控的設定，建立、範圍、金鑰輪換都走設定變更；對帳回報只能由該受管系統登記的 client 送出，並與第 14 節的完整性檢查同樣處理。

**最佳解**：C。
- `check` 的回應帶簽章與「最長可快取時間」，呼叫方 SDK 預設 fail-closed，快取用完才拒絕；SDK 回報自己的降級期間。
- `api_client` 的建立與範圍變更是設定變更申請；金鑰定期輪換、到期失效、可撤銷；異常呼叫（新來源 IP、頻率突變）列為例外。
- 平台停機期間（由技術維運的維護紀錄或心跳缺口推算）列入稽核準備度，並列出呼叫方回報的降級期間。

**理由**：平台無法控制別的系統，但可以讓「正確的行為」最省事、讓「錯誤的行為」被看見，這符合 D10 的界線。

## 21. 緊急路徑變成常態

**情境**：緊急路徑（先執行、限時補簽核，validation-cases、D13）上線後，MIS 發現走緊急路徑不用等主管，一年內有 30% 的系統權限申請都標為緊急。每一張都有補簽核，所以全部「合規」。

**系統現在的反應**：有「逾期自動收回並列為例外」，但沒有限制緊急路徑的使用條件與頻率，也沒有要求事後審查「是否真的緊急」。

**結果**：我會把緊急變更／緊急權限全部抽出來看。若緊急比例高、且補簽核都是形式上的追認，我會判定正常路徑的預防性控制被系統性繞過。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 緊急需要事前一位主管口頭同意，事後補登。口頭沒有紀錄。
- B. 緊急路徑需要指定的「緊急核准人」在手機上即時核准（一關，數分鐘內），事後再走完整路徑。
- C. B 加上：事後審查人要判定「是否確屬緊急」，非緊急的列為違規例外；緊急比例超過門檻通知控制負責人。

**最佳解**：C。緊急需要至少一個人在事前即時核准（不得是申請人或執行人）；緊急的有效期以小時計且不得續期；事後審查的結論分為「確屬緊急」與「不應走緊急」，後者列入申請人與核准人的統計，每月給控制負責人。

**理由**：緊急路徑是必要的，但若沒有事前的最低核准與事後的判定，它就是正常控制的後門。

## 22. 機密欄位的金鑰在十年保存期內遺失或無法交給稽核

**情境**：D20 規定機密欄位進資料庫前就加密，金鑰由平台維運以外的人保管（例如人資主管楊淑惠）。兩年後楊淑惠離職，金鑰的保管方式只有她清楚；或公司更換金鑰管理設備，舊金鑰沒有轉移。我要查 2027 年一張薪資資料授權的實際內容，結果解不開。另一個情形：金鑰輪換後，舊資料仍以舊金鑰加密，但稽核事件的雜湊是以密文還是明文計算沒有定義。

**系統現在的反應**：A19 提到金鑰 port 與不存在資料庫，沒有規定金鑰的生命週期、託管、輪換與保存期間的可讀性。

**結果**：紀錄保存十年卻讀不出來，等於沒有紀錄；我必須判定這部分的查核證據無法取得。

**對照現有設計**：部分涵蓋。

**替代方案**：
- A. 不加密，靠存取控制。違反 D20 的初衷。
- B. 由單一保管人保管金鑰。單點失效。
- C. 金鑰託管採門檻分持（例如 3 取 2，由人資、稽核室、資安室各持一份），並把金鑰生命週期做成平台的受控流程。

**最佳解**：C。
- 金鑰由 KMS／HSM 管理，平台只取得資料金鑰；主金鑰的恢復由多方分持，任何一方不得單獨恢復。
- 金鑰保管人也是一種有負責人的授權，負責人離職時套用 K-OWNER-CONTINUITY；輪換與恢復都是設定變更並寫事件。
- 雜湊鏈對密文計算（讓不持金鑰的人也能驗證），另外保存明文的雜湊（加密前計算），供有權解密的人核對內容未變。
- 每年自動做一次「隨機抽一筆舊資料解密」的演練，結果寫成事件。

**理由**：保存期限內的可讀性是證據的一部分；只有加密沒有託管，等於把證據交給運氣。

## 23. 平台自身的管理角色集中在同一人

**情境**：依 seed-directory，資訊部經理謝明哲同時是 `sys_admin`、`mis` 群組成員，也是部屬李志偉、林冠宇的直屬主管。實際上線時這很常見：小型 IT 團隊一人身兼數職。他可以提出設定變更、讓部屬核准；可以認領 MIS 關卡；也可以在技術維運面直接存取主機。A20 把平台管理拆成三種角色，但沒有規定同一人不得同時持有。

**系統現在的反應**：骨幹的 `K-SOD-*` 只針對一張申請單內的關卡，沒有針對「平台角色之間」的職責衝突。

**結果**：我查平台自身的存取時，會列出每個人在平台的角色組合。只要有人同時能「改設定」與「核准設定」、或「維運主機」與「執行授權」，我就要求補償控制，否則判定有缺失。

**對照現有設計**：部分涵蓋（A20、validation-cases 的職責衝突矩陣，但沒有套用在平台自己的角色上）。

**替代方案**：
- A. 文件建議不要讓同一人持有多個角色。無法強制。
- B. 把平台角色納入職責衝突矩陣（D13 已經要做），由核心強制：衝突的組合不能同時生效。
- C. B 加上：無法避免時（小公司），允許以「有期限的例外核准」持有衝突組合，並對該人的所有動作產生複核清單，每月由其他人審。

**最佳解**：C。核心預載平台角色的衝突矩陣（技術維運 × 流程管理 × 稽核 × 設定變更核准人 × 執行人等），指派時檢查；例外核准有期限且列入稽核準備度；設定變更的核准人不得是提出人的直屬部屬（避免第 6 節的上下級互相核准）。

**理由**：平台要讓客戶的職責衝突檢查過關，自己的管理角色就必須先過；C 也誠實面對小型 IT 團隊的現實。
