# 真實情境檢查 12：採購方的評選委員

立場：一家員工約兩千人的上市公司（旗下有七家子公司，其中一家是金融相關、一家在越南、一家在中國蘇州），正在評選「簽核與權限治理平台」。評選委員會由三種人組成：

- **資訊長**：在意能不能接上現有的 AD、人資系統、ERP 與既有簽核系統，裝得起來、升得上去、壞了救得回來，以及原廠倒了怎麼辦。
- **採購**：在意授權與計價方式、總持有成本、合約條款、退場時資料帶不帶得走。
- **使用單位代表**（財會、人資、業務、稽核室各一位）：在意每天用的人覺不覺得好用、流程能不能自己改、成效拿得出數字。

我們同時在比的對象：台灣常見的簽核與 BPM 產品（EasyFlow、Agentflow、UOF X 等，見 `docs/research/04-market-workflow-grc.md`），以及身分治理產品（Microsoft Entra ID Governance、SailPoint、Okta 等，見 `docs/research/03-market-identity-data-governance.md`）。評選表上的每一項，都是「沒有就扣分」或「沒有就不買」。

依據的文件：`docs/platform-vision.md`、`docs/contract/00-spine.md`（以下稱「骨幹」）、`docs/decision-log.md`、`docs/validation-cases.md`、`docs/contract/pending-amendments.md`、`docs/packs/data-access/rules.md`、`docs/packs/seal/rules.md`、`docs/ux-acceptance.md`、`docs/engineering-standards.md`、`docs/contract/seed-directory.md`。人物沿用種子名單（母公司）。

判斷優先順序依 platform-vision：稽核過關 → 安全 → 簽核人的速度與正確性 → 通用性 → 成本。已完整涵蓋的情境不列。已在其他立場的檢查中詳細處理的題目（例如期初權限、雜湊鏈被重算、緊急路徑），這裡只寫採購方看到的不同面向。

## B01 公司用 ADFS（SAML）與 Windows 整合登入，平台只準備了 OIDC

**情境**：資訊部經理謝明哲在評選表填「單一登入」。公司的身分來源是地端 AD，對外是 ADFS 提供 SAML 2.0；部分子公司已搬到 Microsoft Entra ID；工廠的共用電腦用 Windows 整合登入（Kerberos）。公司的 MFA 是 Entra 的 Authenticator 推播，ADFS 這一側則是另一家廠商的 OTP。

**現在的設計會怎麼反應**：骨幹第 12 節的模擬環境只有 OIDC 身分提供者；`person_identity` 有 provider 欄位，但沒有說明支援哪些協定。`K-MOBILE-MFA` 要求手機簽核時通過 MFA，卻沒有寫是平台自己做 MFA，還是信任身分提供者回傳的驗證強度；`case_task` 記了「MFA」，但不知道記的是什麼。

**結果**：評選表「SAML 2.0」一欄只能寫「需客製」，直接扣分。若導入後由平台自己做 MFA，員工要多綁一套驗證器，抱怨不斷；若信任 ADFS，則平台無從證明「這次核准時真的有做 MFA」，會計師問 MFA 證據時拿不出東西（同 02 的第 19 點）。

**涵蓋**：部分涵蓋。登入是可替換的介面（data-access rules「整合」節），但協定、步升驗證（step-up）與證據格式都沒定。

**替代方案**：
1. 只支援 OIDC，要求客戶自己架一個身分代理（例如 Keycloak）轉接 SAML。客戶多一套要維運的系統，資訊長不會接受。
2. 平台自己做 MFA（TOTP 或 passkey），不依賴身分提供者。證據完整，但和公司既有的 MFA 重複，員工要多管一套。
3. **同時支援 OIDC 與 SAML 2.0，MFA 優先採用身分提供者的步升驗證並記錄其回傳的驗證強度；身分提供者做不到時，才用平台自己的 passkey。**

**最佳解**：採 3。
- 登入 port 提供 OIDC 與 SAML 2.0 兩種 adapter，模擬環境各一個（Keycloak 可同時扮演兩者），合約測試都要跑過。Windows 整合登入經由 ADFS 或 Entra 間接支援，不在平台內實作 Kerberos。
- 做決定前要求步升驗證：OIDC 用 `acr_values`／`max_age`，SAML 用 `RequestedAuthnContext` 與 `ForceAuthn`。回傳的 `acr`／`amr`／`AuthnContextClassRef` 與驗證時間原樣寫進稽核事件，不只記「有 MFA」。
- 回傳的強度不足或身分提供者不支援步升驗證時，改用平台的 passkey（WebAuthn）。哪一種來源可接受是參數，修改走設定變更申請單（D12）。
- 對外公布支援清單與設定手冊（ADFS、Entra ID、Google Workspace、Okta 各一份），列入評選回覆。

**理由**：稽核要的證據是「這次核准時的驗證強度」，必須來自真實的驗證結果；沿用公司既有的 MFA，員工不必多學一套，也符合簽核人的速度。SAML 在台灣企業仍是主流，沒有它就進不了短名單。

## B02 人資系統只能每天丟 CSV，一次匯入錯誤讓八百人換了主管

**情境**：人資經理楊淑惠負責的人資系統是外購的套裝軟體，主管關係只在人資系統裡（AD 的 manager 欄位多年沒人維護）。廠商只能每天凌晨匯出 CSV 或開一個資料庫 view。某天廠商改版，CSV 欄位順序變了，八百位員工的直屬主管被對到錯的人。

**現在的設計會怎麼反應**：骨幹第 12 節的人員與組織來源是 LDAP；engineering-standards 寫「由人員與組織 port 同步」。沒有 CSV 或資料庫 view 的 adapter，也沒有「同步結果異常時先擋下」的機制。`reporting_line` 帶生效期間，錯誤一旦寫入就立刻生效。

**結果**：當天早上送出的兩百張單全部指派給錯的主管，有些人因此成為自己同事的簽核人；`K-SOD-DISTINCT` 只檢查同一張單上不同人，擋不住「錯的人」。稽核抽到這幾天的單，簽核人資格對不上人資的正式紀錄。

**涵蓋**：部分涵蓋。來源是可替換的 port，但只有 LDAP 一種，也沒有異常保護。

**替代方案**：
1. 要求客戶先把主管關係整理進 AD 再接。台灣多數公司做不到，導入延後數月。
2. 每次同步都直接套用，靠事後的例外報表發現。錯誤已經造成錯誤指派，事後才發現，等於稽核缺失。
3. **提供 LDAP、SCIM 2.0、CSV／資料庫 view 三種 adapter；每次同步先算差異，超過門檻就暫停套用，交由人資確認。**

**最佳解**：採 3。
- adapter：LDAP／AD、SCIM 2.0（接收端）、排程的 CSV 或資料庫 view（欄位以名稱對應，不以順序）。每種都對著 `sim/` 跑合約測試。
- 每次同步先產出差異（新增、離職、換單位、換主管的筆數與名單），存成一筆同步紀錄並寫入稽核事件。
- 變動比例超過門檻（例如換主管超過 3% 或離職超過 1%）時暫停套用，通知人資的資料負責人確認；確認者與同步帳號的管理人不得是同一人。離職異動可以設成一律立即套用（離職延遲套用的風險比錯誤套用大）。
- 門檻是參數，依公司別設定，變更走 D12。

**理由**：簽核人資格的正確性是稽核的第一個問題（誰決定、有沒有資格）。人資資料品質是導入時最常出問題的地方，平台必須假設來源會出錯，而不是假設它永遠正確。

## B03 公司資料庫標準是 SQL Server，沒有 PostgreSQL 的 DBA

**情境**：資訊部的資料庫全是 SQL Server 與 Oracle，兩位 DBA 只會這兩種。評選時資訊長問：「可以跑在 SQL Server 上嗎？備份、監控、升級誰負責？」

**現在的設計會怎麼反應**：data-access rules 的「技術」節寫明 PostgreSQL，商業邏輯全部放在 SQL function；engineering-standards 的安全模型（`sgn_app` 只能執行 `api` 的 function、`SECURITY DEFINER`）依賴 PostgreSQL 的權限機制。沒有說明客戶需要什麼能力的人來維運資料庫。

**結果**：評選表上「資料庫是否符合公司標準」打叉；就算買了，PostgreSQL 由沒經驗的人維運，備份沒驗證、版本過期沒升，出事時救不回來，稽核紀錄的保存承諾落空。

**涵蓋**：部分涵蓋。選 PostgreSQL 有理由（控制寫在資料庫裡繞不過去），但沒有處理「客戶沒有能力維運它」。

**替代方案**：
1. 改寫成支援多種資料庫。商業邏輯與權限模型都要重做，控制的強度會降到最弱的那個資料庫，違反稽核過關優先。
2. 維持 PostgreSQL，要求客戶自己培養 DBA。中型公司做不到，最後就是沒人管。
3. **維持 PostgreSQL，但把資料庫當成平台的一部分交付：內建備份、還原驗證、監控、升版與健康檢查；另提供原廠或合作夥伴的代管服務。**

**最佳解**：採 3。
- 部署包內含固定版本的 PostgreSQL 與其設定，平台的升版腳本同時處理資料庫的小版本升級；大版本升級提供腳本與停機時間估算。
- 內建每日備份與每週自動還原驗證（還原到隔離環境、跑雜湊鏈驗證），結果顯示在技術維運畫面並寫入稽核事件；還原驗證失敗列為例外。
- 監控指標以 Prometheus 格式輸出，讓客戶接到既有的監控系統，不要求客戶懂 PostgreSQL 內部。
- 也支援客戶的雲端代管 PostgreSQL（AWS RDS、Azure Database for PostgreSQL、GCP Cloud SQL）；列出支援的版本與必要的設定。
- 公布「維運者需要具備的能力」與代管服務的範圍，作為評選回覆。

**理由**：控制寫在資料庫裡是稽核過關的根本，不能為了相容性放掉；但客戶維運不好，紀錄保存就會失敗，所以平台要把維運的負擔收回來。

## B04 RFP 要求 RPO 15 分鐘、RTO 1 小時、異地備援，平台沒有高可用規格

**情境**：採購的 RFP 第 7 章寫：「系統可用率 99.9%；RPO 15 分鐘、RTO 1 小時；需提供異地備援架構並每年演練一次，演練紀錄供稽核查核。」資訊長特別問：主機切換的那一刻，排程跑到一半的到期失效怎麼辦？稽核事件的序號會不會斷？

**現在的設計會怎麼反應**：骨幹只有 `scheduler_run`、`notification_outbox` 兩個實體，沒有提到排程只能由一台機器執行、切換時如何接手；`audit_event` 的序號與雜湊鏈在主備切換、非同步複寫遺失最後幾筆時如何處理，沒有說明。deploy/ 目錄存在，但沒有任何架構規格。

**結果**：RFP 這一章無法回覆，直接出局。若勉強上線，切換時非同步複寫遺失最後幾秒，DC 已經套用的權限在平台上沒有紀錄（01 的第 3 點）；或兩台都以為自己是主機，到期排程執行兩次，產生重複事件。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 只提供單機加每日備份，高可用交給客戶的虛擬化平台（VM 自動重啟）。RTO 勉強可以，RPO 做不到 15 分鐘，也沒有異地。
2. 雙主架構。簽核與雜湊鏈需要單一順序，雙主會讓鏈分岔，不可行。
3. **一主多備的參考架構（同步複寫的本地備援加非同步的異地備援），排程以資料庫鎖保證只有一個執行者，切換後以對帳補齊外部系統的狀態，並提供演練工具。**

**最佳解**：採 3。
- 公布三種參考架構與各自的 RPO／RTO：單機（RPO 依備份）、本地高可用（PostgreSQL 同步複寫，RPO 0）、本地加異地（異地非同步，RPO 以秒計）。應用層是無狀態的多台。
- 排程與通知外送以資料庫的 advisory lock 選出單一執行者；每次執行有冪等鍵，重做不產生重複事件。
- 切換後自動執行一次「外部狀態對帳」：向 DC 與其他受管系統查詢切換前後的變動，與平台的紀錄比對，差異列為例外。雜湊鏈若在異地切換時遺失尾端，新的主機在鏈上寫入一筆「切換事件」，記下最後確認的序號與遺失區間，不重算、不偽裝成連續。
- 提供演練腳本：切換、驗證雜湊鏈、對帳、切回；演練結果自動產出報告並寫入稽核事件，作為年度演練的證據。
- 平台停機時其他系統如何處理權限判定（失敗時拒絕或依快取）由 05-integration 定義（02 的第 20 點）。

**理由**：可用性本身就是稽核會查的「電腦作業」控制；切換時的紀錄完整性又直接影響「證據自己產生」。這些必須在架構上設計好，事後補不了。

## B05 金融子公司要地端、越南子公司要雲端、中國子公司資料不能出境

**情境**：集團七家子公司。金融相關的子公司受主管機關規範，系統必須放在自己的機房；越南子公司沒有機房，只能用雲端；蘇州子公司的員工個資依中國《個人資訊保護法》出境要做安全評估或標準合約，法務建議資料留在當地。總部希望集團看得到整體的稽核準備度。

**現在的設計會怎麼反應**：D15 支援集團多公司，但明確「不做雲端多租戶的資料隔離」，所有公司在同一個資料庫。platform-vision 只說「多公司（多租戶）不在第一版範圍」，D15 又把多公司納入，兩處說法需要對齊。沒有「多個獨立部署之間如何協作」的設計。

**結果**：只能三選一：全部放總部（蘇州子公司法務不同意、金融子公司主管機關不接受）、各自獨立部署（集團稽核要登入七個系統，跨公司申請無法表達）、或放棄這個平台。

**涵蓋**：部分涵蓋。D15 處理了同一部署內的多公司，沒處理「同一集團、多個部署」。

**替代方案**：
1. 做真正的雲端多租戶 SaaS，所有子公司放同一個雲端。解決越南，解決不了金融與蘇州。
2. 每家子公司一套獨立部署，互不相通。合規沒問題，但集團稽核與跨公司簽核做不到。
3. **單一部署內多公司（D15）為主；需要隔離的公司另外獨立部署，部署之間只交換最小的資訊：跨部署的身分對照、跨公司申請的參照，以及彙總後的稽核準備度指標。**

**最佳解**：採 3。
- 部署模式明確分三種並列入產品規格：地端單一部署（含多公司）、客戶自己的雲端帳號（同一套安裝）、原廠代管的雲端。三者是同一套軟體，不分版本。
- 新增「聯盟」：各部署登記彼此的身分與簽章金鑰。跨部署的申請單在申請端的部署建立，對方部署的關卡以簽章過的請求送過去，在對方部署內簽核並留紀錄；兩邊的稽核事件互相保存對方的事件雜湊，不搬移內容本身。
- 集團總部只收各部署匯出的彙總指標（例外數、逾期數、複查完成率），不含個資；每家子公司的稽核資料包仍由自己的部署產出。
- 釐清 platform-vision 第一版範圍界線的文字與 D15 一致。

**理由**：資料落地與主管機關要求是不可協商的限制；集團稽核需要整體視野。只交換雜湊與彙總指標，可以同時滿足兩者。

## B06 越南與日本子公司需要越南文、日文；時區、日期格式、表單欄位名稱

**情境**：越南子公司的現場主管只看得懂越南文；日本子公司的社長要求日文介面。越南時間比台灣慢一小時，日本快一小時。財會的表單欄位「未公告財報」在英文介面上仍是中文。

**現在的設計會怎麼反應**：D17 提供繁體中文與英文，文案與通知範本採多語架構。engineering-standards 的文案來源是 `web/src/i18n/zh-Hant.ts`，是程式檔，客戶不能自己加語言。骨幹的 `form_schema`、`process_tier` 名稱、`rule` 說明、錯誤訊息都是單一語言。時區與工作天曆沒有提到使用者或公司別的時區。

**結果**：越南主管拿到英文介面一樣看不懂，改由台灣同事代簽或代為說明，簽核的有效性出問題（05 的 E22 從簽核人立場已提）。採購這一側看到的是：要加一種語言就得找原廠改程式、重新發版。

**涵蓋**：部分涵蓋。D17 只到兩種語言，而且語言包綁在程式裡。

**替代方案**：
1. 原廠每增加一個市場就做一種語言。客戶要等原廠的時程，不符合「客製不靠原廠」。
2. 介面整合機器翻譯即時翻譯。介面用語不穩定，法務與稽核不接受控制文字是機器翻的。
3. **語言包做成資料：介面文案、通知範本、表單欄位標籤、級別名稱、規則說明都有多語欄位；客戶可以新增語言，以設定變更申請單上線。申請內容的自由文字另提供可選的翻譯輔助，原文永遠是證據。**

**最佳解**：採 3。
- 介面文案從程式檔轉為可匯入的語言包（建置時有預設的繁中與英文，執行時可加）；新增或修改語言包走 D12，含預覽。缺翻譯的 key 退回英文並在流程管理畫面顯示缺漏清單。
- `form_schema` 的標籤、說明、選項，以及級別、關卡、規則說明都改為多語欄位。
- 每個人有偏好語言與時區；每家公司有預設語言、時區與行事曆。畫面上的時間依檢視者時區顯示並標示時區；稽核事件一律存 UTC。
- 第一版附帶的語言維持繁中與英文；簡中、日文、越南文由合作夥伴或客戶提供，原廠提供翻譯檢查工具（找出缺漏與過長的字串）。

**理由**：簽核人看不懂就不是有效的決定（D17 的依據本身）；把語言做成資料，才能讓多國子公司不必等原廠。

## B07 員工不看 email，看 LINE WORKS 與 Teams；要推播但不想再裝 App

**情境**：使用單位代表（業務管理部經理周文傑）在評選會上說：「業務在外面跑，email 一天看一次；我們公司內部溝通都在 LINE WORKS，總部用 Teams。原本的簽核系統有 App 推播，你們只有寄信？」

**現在的設計會怎麼反應**：data-access rules：「第一版先以獨立網站＋SSO＋mail 通知設計」。骨幹的 `notification_outbox` 與 `notification_template` 沒有通道的概念。ux-acceptance 以手機網頁為主，沒有推播。

**結果**：通知到不了簽核人，逾時與升級大量發生；大家改在 LINE 群組喊「請幫我簽一下」，甚至直接在 LINE 回一句「OK 准」，那句話不在任何紀錄裡。評選表「行動推播」打叉。

**涵蓋**：部分涵蓋。有手機網頁與 MFA，沒有 email 以外的通道。

**替代方案**：
1. 做原生 App（iOS、Android）。開發與上架成本高，企業要做行動裝置管理，員工抗拒裝 App；而且仍不解決大家已經在 LINE WORKS／Teams 裡的事實。
2. 在 Teams／LINE WORKS 的訊息卡片上直接按「核准」。速度最快，但卡片上要顯示足夠的內容才能做決定，機密內容會留在通訊軟體的伺服器上；步升驗證與版本綁定的證據也不可靠。
3. **通知通道做成 port：email、Microsoft Teams、LINE WORKS、Slack、企業微信，加上可安裝的網頁應用（PWA）推播。通知只帶非機密的摘要與深層連結，決定一律回到平台上做。**

**最佳解**：採 3。
- 通知 port 支援多通道，每人可選偏好通道，公司別可設預設；所有通道送出的內容與時間寫入 `notification_outbox` 並保留，作為催辦的證據。
- 保密的申請單（A3）在任何通道都只顯示「你有一張待簽的單」與連結。
- 連結開啟後直接到該張單的簽核畫面（行動版），SSO 已登入時只差步升驗證；T2 的步數上限不變。
- PWA 推播讓不想用通訊軟體的人也有推播；不做原生 App。
- 明確不提供「在聊天訊息裡直接核准」，並在評選回覆說明理由：證據完整性與機密內容。

**理由**：推播是簽核人速度的關鍵，但決定必須留在能綁定版本與驗證強度的地方。把通知和決定分開，同時顧到速度與稽核。

## B08 既有簽核系統不換，員工要一個待辦匣；ERP 要能觸發申請單

**情境**：公司的請假、請購、出差都在 Agentflow，已用了八年，不會換。新平台只管權限、程式變更、供應商銀行帳號變更等稽核重點流程。總經理高志遠說：「我不要每天開兩個系統看待簽。」另外，供應商銀行帳號的變更是在 ERP（SAP）的供應商主檔畫面發起的，財務專員不會想到要去另一個系統開單。

**現在的設計會怎麼反應**：骨幹第 11 節的對外介面是「讓其他系統使用授權結果」（判定、查詢、事件、對帳）。沒有「其他系統建立申請單」的介面，也沒有「把待簽工作提供給入口網站或既有簽核系統」的介面。data-access rules 寫「現有簽核系統……做成可替換的介面」，但沒有內容。

**結果**：主管漏看新平台的待簽，升級率高；財務專員直接在 SAP 改了銀行帳號，事後才想到要補單（或根本沒補），正是供應商銀行帳號變更流程要防的情況。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 把平台的簽核嵌進既有簽核系統當成其中一關（由 Agentflow 呼叫平台）。核准實際發生在別的系統，職責分離、版本綁定、MFA 都由別人做，平台的控制失效。
2. 要求公司把所有流程都搬進新平台。採購不會買單，也不是平台的定位。
3. **雙向但不讓渡決定權：平台對外提供「建立申請單」與「待辦工作清單」兩組介面，讓 ERP 發起申請、讓入口網站或既有簽核系統顯示平台的待簽數與連結；決定一律回到平台上做。另外用對帳把「沒走申請就改了」的情況找出來。**

**最佳解**：採 3。
- 申請單建立介面：外部系統以登記過的 `api_client` 代表申請人建立草稿（不得直接送審，送審要申請人本人確認），預填內容並帶回來源系統的參照編號。
- 待辦工作介面：提供某人目前待處理工作的清單（數量、標題的非機密摘要、到期時間、深層連結），格式盡量採公開標準，讓入口網站、Teams、既有簽核系統的待辦匣可以顯示。
- ERP 端的對帳：供應商銀行帳號這類流程，ERP 的變更紀錄定期回報給平台，沒有對應核准單的變更列為例外（D21 的檔案方式即可）。
- 在 05-integration 列出這兩組介面，並各用一個模擬的使用方驗證（D9 的做法）。

**理由**：平台必須接受「它不是公司唯一的簽核系統」這個現實；讓別人看得到待辦、能發起申請，但不讓別人代為決定，才同時顧到好用與稽核。

## B09 串接好的系統在平台升版後壞掉：API 沒有版本與棄用政策

**情境**：資訊部工程師李志偉花了一個月把 BI 平台接上權限判定介面、把 EIP 接上待辦工作介面。半年後平台升版，回傳格式改了一個欄位名稱，BI 平台的判定全部失敗，週一早上沒人看得到報表。

**現在的設計會怎麼反應**：骨幹第 11 節說「盡量採用公開標準的格式」，細節留給尚未完成的 05-integration。engineering-standards 的路由表是 `packages/contract` 的單一來源，但沒有對外版本、相容性承諾、棄用期間，也沒有供客戶開發用的沙箱。

**結果**：客戶不敢升版，安全修補也一起被擋住；或者升了版、整合壞掉，判定失敗時各系統的處理方式不一，有的放行、有的全擋。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 對外介面永不改變。不實際，最後會出現第二套平行的介面。
2. 每次升版附上變更說明，由客戶自行調整。等於把成本推給客戶。
3. **對外介面有明確的版本號與相容性規則：同一主版本內只增不改；主版本變更時新舊並行至少兩年；每個版本都有公開的 OpenAPI 規格與可重現的沙箱。**

**最佳解**：採 3。
- 對外介面的路徑帶主版本（例如 `/v1/`）；同一主版本內只能新增欄位與端點，不得改名或移除；這條規則由 CI 對 OpenAPI 規格做差異檢查強制執行。
- 主版本變更時，舊版至少再支援兩年（與長期支援版本的週期一致，見 B19）；每次呼叫舊版的 `api_client` 列在整合狀態畫面上，提醒負責人。
- 提供沙箱：同一套 `sim/` 打包成客戶可以自己啟動的開發環境，內建種子資料，讓客戶的工程師不必碰正式環境。
- 採用的標準在 05-integration 寫明（例如權限判定用 OpenID AuthZEN、事件用 CloudEvents 與 OpenID Shared Signals、帳號佈建用 SCIM 2.0），並說明不採用時的理由。

**理由**：整合一旦失敗，實際存取控制就失效；客戶因為怕壞而不升版，安全修補也跟著停擺。穩定的介面是安全與稽核的前提，不只是方便。

## B10 總經理問「導入後簽核快了多少」，平台拿不出可信的數字

**情境**：上線三個月後，總經理在經營會議上問資訊長：「當初說能讓簽核更快，現在到底快了多少？哪一關最慢？」業務副總方國華則擔心：如果平台把每位主管的簽核速度排名公開，會變成績效壓力。

**現在的設計會怎麼反應**：platform-vision 把「簽核人的速度」列為第三優先，ux-acceptance 用步數衡量單一任務，但沒有任何營運指標或儀表板。骨幹第 10 節的畫面沒有報表；「稽核準備度」只顯示例外。沒有導入前的基準資料。

**結果**：資訊長只能從資料庫撈資料用 Excel 算，每次口徑不同，總經理不信；導入成效說不清楚，下一年度的預算與擴大導入卡住。評選時「成效指標如何呈現」一欄空白，對手的 BPM 產品都有內建報表。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 不做報表，提供資料匯出讓客戶自己用 BI 做。口徑由各家自行定義，彼此不一致，也容易被質疑是挑過的數字。
2. 做一個可自由拖拉的報表工具。開發成本高，口徑一樣不統一，還會繞過申請單保密（A3）。
3. **內建一組定義固定的營運指標，全部從稽核事件計算（單一來源），附上定義文件與計算期間；另提供唯讀的彙總資料介面給 BI。個人層級的指標只給本人與其主管看。**

**最佳解**：採 3。
- 指標（依流程類型、級別、公司別、關卡、期間）：送審到生效的時間（中位數與第 90 百分位）、各關停留時間、逾時率與升級率、退回率與重簽率、手機決定比例、批次比例、一次通過率、提問次數，以及申請人在填單階段的放棄率。
- 每個指標的定義寫在文件與畫面上（例如「工作天」怎麼算、退回後的時間算給誰），計算結果附上母體筆數與產出時間，可以追到明細單號。
- 導入前基準：提供匯入舊系統的簽核時間樣本（只需單號、送出與完成時間、關卡數），產出前後對照；匯入資料標示來源，不與平台自己的數字混算。
- 可見範圍：部門與流程層級的指標給流程管理者與高階主管；個人層級的指標只給本人與其直屬主管，避免排名公開造成的勞資爭議與個資疑慮。
- 唯讀的彙總資料介面供 BI 使用，只含彙總與非機密欄位。

**理由**：沒有可信的成效數字，平台在公司內部活不下去；從稽核事件算，數字和證據同源，不能被挑。個人指標的可見範圍屬於資料安全的範疇，必須預設保守。

## B11 稽核室要年度內控自評與董事會報告用的標準報表

**情境**：稽核室主任鍾國強每年要做內部控制制度自行評估，每季要向審計委員會報告稽核發現的追蹤情形。他問評選小組：「平台能不能直接產出『資訊循環』的自評底稿？能不能一鍵出一份給董事會看的摘要，而不是幾千列的 Excel？」

**現在的設計會怎麼反應**：A2 規定了一鍵稽核資料包（全部申請單清單、完整紀錄、例外清單）與稽核準備度畫面；platform-vision 提到控制對照表（`docs/audit/control-matrix.md`），但該文件尚未存在，也沒有說會在產品內呈現。資料包是給查核人員抽樣用的明細，不是給管理階層與董事會看的摘要。

**結果**：稽核室還是要自己把資料包整理成自評底稿與董事會報告，正是「證據不需要人事後整理」想消除的工作；評選時對手的 GRC 產品展示了現成的報告範本。

**涵蓋**：部分涵蓋（A2 提供明細，缺管理層級的報告與控制對照）。

**替代方案**：
1. 提供報表設計器讓稽核室自己做。稽核室沒有時間，且自行設計的報表口徑不受控。
2. 只提供資料包，報告由客戶用自己的工具做。同上述結果。
3. **把控制對照表做進產品：每項控制有狀態（設計、運作、例外數），可以直接產出「控制運作摘要」與「自評底稿」兩種標準報告；報告與資料包一樣封存產生條件、筆數與雜湊。**

**最佳解**：採 3。
- 產品內建控制對照表（由 `docs/audit/control-matrix.md` 產生，A9），每一列顯示：控制目標、系統怎麼做到、期間內的運作數量、例外數與結案情形、證據連結。
- 標準報告兩種：給審計委員會的摘要（一到兩頁、圖表加重點例外）；給自評或查核人員的底稿（依控制逐項列出測試方式與證據位置，格式可匯出 Excel 與 PDF）。
- 報告的產生條件、母體筆數、產出時間、雜湊一併封存（呼應 02 的 IPE 要求），並可重新產出比對。
- 報告範本的文字是語言包的一部分（B06），客戶可調整措辭，但不能改計算口徑。

**理由**：稽核過關的最後一哩是「把結果講給管理階層與會計師聽」；如果這一步仍靠人工整理，「證據自己產生」只做了一半。

## B12 評選現場：請總務在 30 分鐘內自己建一個新流程

**情境**：評選的實機展示環節，委員請總務主任洪美惠上台：「請在 30 分鐘內建一個『公務車借用』流程：一般借用主管核准；跨夜或外縣市加會總務；超過三天加會副總。」對手的 BPM 產品用拖拉式設計器 15 分鐘做完並當場試跑。

**現在的設計會怎麼反應**：D12 讓流程定義、路徑、參數可以在管理畫面修改，每次修改是一張雙人覆核的設定變更申請單；D14 讓分級、縮小方向、摘要欄位可以宣告。但 platform-vision 第一版範圍界線仍寫「不提供拖拉式的流程設計器」，ux-acceptance 沒有流程管理者的任務與步數上限；也沒有「先在測試環境試跑」的能力，只有「可試算影響」。

**結果**：洪美惠在展示現場要面對宣告格式或 JSON，做不出來；評選委員的結論是「這平台要靠原廠設定」，和產品的「流程管理者自己就能調整」承諾相反。

**涵蓋**：部分涵蓋（D12、D14 提供了能力，缺可用的編輯介面、試跑與驗收標準）。

**替代方案**：
1. 自由畫布式的拖拉設計器。展示效果好，但自由畫布會產生迴圈、跳關等難以驗證的結構，與核心的職責分離規則衝突（研究 04 第 1 點：台灣產品把跳關做成功能）。
2. 維持宣告檔案，由原廠或顧問協助建立。不符合「客製不靠原廠」。
3. **結構化的流程編輯器：以表單填寫的方式建立欄位、級別條件、關卡（從固定的 resolver 種類挑選），即時顯示流程圖；送出前可在沙箱用模擬人員試跑；上線仍走設定變更申請單。**

**最佳解**：採 3。
- 編輯器只能產生核心允許的結構（關卡順序、並行群組、條件分支），職責分離等核心規則在編輯時就提示衝突，不能關閉。
- 「試跑」：選擇幾位模擬或真實（唯讀複製）的申請人，輸入範例內容，看到分級結果、實際會指派給誰、各關時限，產出試跑報告附在設定變更申請單上給覆核人看。
- 在 ux-acceptance 新增流程管理者的任務：建立一個三關、含兩個條件的新流程（電腦，非 IT 人員 30 分鐘內）；修改一個金額門檻（電腦，6 步內，含送出設定變更）；看懂某張單為何走到某一關（3 步內）。
- 修正 platform-vision 第一版範圍界線的文字，與 D12 一致。

**理由**：「流程管理者自己就能調整」是平台與一般簽核系統的差別，也是 D12 的承諾；做不到就是承諾落空。結構化編輯器在不犧牲控制的前提下，讓非 IT 人員做得到。

## B13 客戶自己寫的流程包，在核心升版後失效

**情境**：資訊部工程師林冠宇依 D14 的出口，為「研發資料外帶」流程寫了兩個 hook（SQL function）與一個專屬輸入元件。半年後核心升版，`find_overlaps` 的回傳結構多了一個必要欄位，客戶的流程包在升版腳本中被擋下，升版中止。

**現在的設計會怎麼反應**：骨幹第 6 節固定了 hook 的簽章，核心在登記時檢查函式存在、簽章正確、擁有者為 `sgn_owner`。沒有說明 hook 介面如何演進、相容性怎麼保證、客戶自寫的流程包怎麼測試、怎麼經過變更控制（02 的第 4 點從稽核角度提到升版不受變更控制）。

**結果**：客戶被迫在「不升版」與「找原廠改」之間選；「客製不靠原廠」只在第一次成立。另外，客戶自寫的 hook 是以 `sgn_owner` 身分執行的 SQL，等於取得最高權限，寫錯或惡意的程式可以繞過所有控制。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 不讓客戶寫 hook，只能用宣告。宣告表達不了的流程只能等原廠。
2. 讓客戶寫，但不承諾相容性。等於把升版風險全推給客戶。
3. **流程包 SDK：hook 介面有版本與相容性承諾，附帶測試框架；客戶的流程包以受限的身分執行，上線走設定變更申請單。**

**最佳解**：採 3。
- hook 介面帶版本號（例如 `hook_api_version`）；核心同時支援目前與前一個主版本的 hook，新增欄位一律有預設值；移除或改變語意必須跨一個主版本並提前公告。
- 流程包 SDK：範本專案、本機測試框架（含 `sim/`）、相容性檢查工具；升版前可以先對客戶的流程包跑一次檢查，產出報告。
- 客戶自寫的 hook 不以 `sgn_owner` 執行，改由權限受限的角色執行：只能讀核心視圖、不能寫核心資料表、不能呼叫網路；核心在登記時檢查 hook 的權限。
- 流程包的安裝與升版是一張設定變更申請單（D12），附上程式差異、測試結果，由提出人以外的人核准。

**理由**：客製能力若沒有相容性與隔離，最後一定變成原廠綁定或安全漏洞；兩者都違反稽核與安全優先。

## B14 五年後換系統，十年保存期的證據怎麼帶走、怎麼繼續驗證

**情境**：採購在合約談判時要求加一條：「合約終止時，原廠應於 30 日內交付全部資料，格式可由第三方讀取，且客戶得於終止後十年內繼續驗證紀錄未遭竄改。」原廠的業務當場答不出來。

**現在的設計會怎麼反應**：骨幹第 11 節有 `evidence`、`audit_feed`，可以把稽核事件輸出給 GRC、SIEM 並驗證；data-access rules 規定 Excel 清單與 PDF 證據頁。沒有「全部資料」的匯出格式（含附件、設定歷史、流程定義版本、機密欄位的處理），也沒有獨立於平台的驗證工具，或停用後的唯讀模式。`audit.retention_years` 是 10 年，但平台本身的授權不一定那麼久。

**結果**：換系統時只能交出 Excel 與 PDF，雜湊鏈無法離開平台驗證；為了保住十年的證據，客戶只好繼續付維護費留著舊平台，這正是採購最怕的綁定。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 只承諾匯出 Excel 與 PDF。證據可讀，但不能驗證未被竄改。
2. 停用後繼續提供舊平台的唯讀授權。可行，但仍依賴原廠存在（見 B15）。
3. **公開的完整匯出格式加上開源的獨立驗證工具；另提供不需授權的唯讀封存模式。**

**最佳解**：採 3。
- 完整匯出：每類資料一個 JSON Lines 檔（申請單、版本、決定、稽核事件、設定歷史、流程定義各版本、授權、對帳與複查結果）、附件原檔、一份清單檔（每個檔案的筆數與 SHA-256），整包用平台金鑰簽章並附上時間戳記。格式規格公開，任何人都可以讀。
- 機密欄位保持加密匯出，另附金鑰的交付程序（金鑰由客戶的保管人交付，不經原廠）；這與 01、02 提到的金鑰十年保存是同一件事。
- 開源的命令列驗證工具：輸入匯出包，重算雜湊鏈、核對清單，輸出驗證報告；不需要連線平台，也不需要原廠授權。
- 唯讀封存模式：平台可以切換成只能查詢與匯出的狀態，授權到期不影響查詢與驗證（與 B16 一致）。
- 這些寫進產品規格與標準合約。

**理由**：稽核紀錄要保存十年，平台的合約可能只有三五年；證據的可驗證性不能依賴原廠是否還在、客戶是否還付費。

## B15 原廠被併購或倒閉，地端系統沒人能維護

**情境**：資訊長在評選會上問：「你們是新創公司。三年後如果被併購、產品停賣，或公司倒了，我們地端的系統誰來修？」研究 03 提到的 Microsoft Identity Manager 2016 支援只到 2029 年，委員們剛經歷過類似的事。

**現在的設計會怎麼反應**：所有文件都沒有提到原廠存續風險、原始碼取得、支援終止的處理。engineering-standards 的品質關卡與 `sim/` 讓系統可以被重建，但那是給開發方用的，不是對客戶的承諾。

**結果**：大型客戶的採購規範通常要求原始碼託管或同等保障，缺這一項直接不能決標；即使決標，倒閉時客戶只能凍結在最後一個版本，安全修補全停，資通安全的檢查一定被列缺失。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 原始碼託管給第三方（律師事務所或專業託管機構），特定條件發生時釋出。業界常見，但託管的程式碼往往建不起來，也沒人知道怎麼維護。
2. 完全開源。客戶最安心，但原廠的商業模式要重新設計，不在這份檢查的範圍內可以決定。
3. **對付費客戶提供完整原始碼與可重現的建置環境（source-available，授權客戶為內部使用而修改）；另外託管給第三方，每年由託管機構實際建置一次驗證；並培養在地的合作夥伴。**

**最佳解**：採 3。
- 每個發行版本附上完整原始碼、相依套件清單（SBOM）、建置腳本；客戶依授權可為內部用途修改與建置。
- 第三方託管：每次大版本存入託管，託管機構每年依建置手冊從零建置並跑完測試，結果出具報告；釋出條件（停止營業、停止支援、併購後終止產品）寫入合約。
- 文件、契約、測試都在原始碼裡（本專案的做法本身就是優勢：規格與規則代碼可追溯），讓第三方工程師能接手。
- 至少培養兩家在台的合作夥伴，能進行導入與二線支援。
- 公布產品生命週期政策：停止支援前至少提前 24 個月公告。

**理由**：稽核紀錄要保存十年、控制要持續有效，平台本身的延續性就是控制的一部分。可建置的原始碼比單純託管更能保證這一點。

## B16 按人頭計價時，外部廠商、agent、稽核、子公司員工怎麼算；授權到期時控制被鎖住

**情境**：採購比較報價時發現：如果按「使用者」計價，兩千名員工都可能是申請人，但經常簽核的只有三百人；另外還有外部廠商人員（A18）、AI agent 與服務帳號（被授權者）、外部會計師、七家子公司。去年另一套系統授權到期未續，系統直接鎖住登入，連撤銷權限都做不到。

**現在的設計會怎麼反應**：沒有任何授權或計價的設計。沒有說明授權超量或到期時，哪些功能會停。

**結果**：計價單位不明，採購無法比價；更嚴重的是，若授權機制在到期或超量時擋下登入或功能，撤銷、到期失效、稽核查詢都可能停擺，例外大量產生，正好在稽核前發生。按人頭計價還會誘使客戶少開帳號、讓人共用帳號，違反「禁止共用帳號」的要求（研究 01 第 7 點）。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 按所有登入過的使用者計價。最常見，但誘使共用帳號，直接傷害控制。
2. 按核准者人數計價。看似合理，但誘使公司把簽核集中給少數人，降低職責分離品質。
3. **按公司員工規模級距加上啟用的流程包與受管系統數量計價；外部人員、agent、稽核角色、僅申請者不另計；授權機制永遠不阻擋控制功能。**

**最佳解**：採 3，並把「授權機制不得阻擋控制」寫成核心規則。
- 計價單位：依集團員工規模級距（例如 500、2,000、5,000 人）訂基本費，加上啟用的流程包與連接的受管系統數。不會因為多開一個稽核或廠商帳號而多付錢，就沒有共用帳號的誘因。
- 新增核心規則（例如 `K-LICENSE-NEVER-BLOCKS`）：授權到期或超量時，只停用「建立新的申請單」與新增流程；撤銷、到期失效、負責人異動、驗證、對帳、稽核查詢與匯出、雜湊鏈驗證一律照常運作。授權狀態的變化寫入稽核事件，並在稽核準備度畫面顯示。
- 這條規則有自動測試（假時鐘跑到授權到期日，驗證控制仍運作）。
- 報價單公開計價公式，讓採購能比價。

**理由**：計價方式會影響使用行為，進而影響控制；授權機制若能讓控制停擺，就是一個由原廠控制的繞過途徑，稽核與安全優先都不允許。

## B17 導入時程四個月：舊系統五年的簽核紀錄要搬、五種流程不可能同時上線

**情境**：專案時程是四個月內上線，因為會計師下一次期中查核在五月。現有的權限申請是 Agentflow 上的紙本電子化表單，五年內約一萬兩千張；會計師要求「上線前的期間仍要能查」。使用單位只能先導入資料授權與系統帳號權限兩種，其他三種要等明年。

**現在的設計會怎麼反應**：D13 決定五種流程都納入第一版，validation-cases 說明是「同時用來驗證平台」，不是同時上線。沒有歷史紀錄匯入的設計；期初權限（01 的第 6 點、02 的第 10 點）已被其他立場指出。沒有導入方法、時程範本、上線準備清單。

**結果**：歷史紀錄留在舊系統，稽核要查兩個地方；舊系統的授權為了查歷史必須續約，採購不滿。若勉強把舊紀錄匯入成平台的申請單，等於偽造了平台產生的證據。五種流程一起導入則時程失控。

**涵蓋**：沒涵蓋（歷史匯入與分階段導入）。

**替代方案**：
1. 不搬歷史紀錄，舊系統保留唯讀。最安全，但雙系統查核，舊系統授權持續付費。
2. 把歷史紀錄轉成平台的申請單。查詢方便，但會混淆「平台產生的證據」與「匯入的資料」，稽核不接受。
3. **歷史紀錄以「外部歷史」的獨立類型匯入：保留原系統的編號、原始檔案與其雜湊、匯入人與覆核人；可查詢、可匯出，但明確標示不是平台產生的證據，也不參與平台的控制判斷。流程類型可以逐一啟用。**

**最佳解**：採 3。
- 歷史匯入：獨立的資料表與畫面，匯入批次本身是一張設定變更類的申請單（匯入人與覆核人不同）；原始匯出檔的雜湊寫入稽核事件，任何人可以比對舊系統的原始檔。稽核查詢可以一次查詢平台與歷史紀錄，結果清楚區分來源。
- 期初權限依 01、02 的建議處理（盤點、轉為受管授權並安排首次複查）。
- 流程類型可以依公司別逐一啟用；未啟用的流程不出現在申請畫面。D13 的「五種流程都在第一版」維持為平台的驗證範圍，但在導入方法上明確「依客戶的稽核重點分階段上線」。
- 提供導入方法文件：時程範本（資料盤點、身分與組織接入、流程設定、試跑、平行運作、切換）、上線準備清單、各階段的驗收條件。

**理由**：稽核接受「不同來源但標示清楚」的資料，不接受「看起來一樣但其實是匯入的」資料。分階段上線是現實的導入方式，不影響平台本身的驗證範圍。

## B18 子公司資訊人員只有兩位，湊不出 D20 要求的角色分離

**情境**：越南子公司三百人，資訊人員兩位，一位管網路與主機，一位管 ERP。D20 要求技術維運、流程管理、稽核三種角色獨立，A19 要求金鑰由平台維運以外的人保管，D12 要求設定變更由提出人以外的人核准。採購問：「最少要幾個人才能維運？」

**現在的設計會怎麼反應**：D20 與 A20 定義了角色分離，但沒有說明最小人力配置、小型子公司如何由集團共用，也沒有在角色重疊時的補償控制。研究 01 引用了金管會的缺失：「資訊部門僅有一名員工……未建立覆核機制」。

**結果**：子公司為了湊人，把稽核角色給總務、把金鑰交給同一位資訊人員保管，形式上分開、實質上沒有；或者乾脆所有角色給同一人，平台照樣運作，直到會計師發現。評選時「維護人力」一欄寫不出數字。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 降低要求，允許小公司由一人兼任所有角色。違反職責分離，稽核不接受。
2. 堅持要求，小公司無法使用。集團客戶的子公司多半是小公司，等於放棄市場。
3. **角色分離以「集團」為單位滿足：子公司的技術維運、流程管理、金鑰保管可以委派給集團總部或其他公司的人；同一人兼任衝突角色時系統擋下，無法避免時以補償控制加例外追蹤處理。**

**最佳解**：採 3。
- 公布最小人力配置：單一公司部署至少需要三位不同的人（技術維運、流程管理、核准設定變更與保管金鑰的另一人），稽核角色可由外部或集團稽核擔任；集團部署時，子公司可以沒有自己的技術維運。
- A20 的角色委派支援跨公司（例如集團資訊處擔任越南子公司的技術維運，越南的 ERP 管理人擔任流程管理）。
- 系統檢查衝突角色組合（例如技術維運與金鑰保管人為同一人、設定變更的提出人與核准人為同一人）並擋下；若客戶以設定變更明確接受某個組合，列為永久例外顯示在稽核準備度畫面，並要求補償控制（例如每月由集團稽核覆核該人的所有操作紀錄）。
- 金鑰保管可以使用分持（例如 3 人中 2 人），保管人可以是法務或稽核等非資訊人員，搭配 HSM 或雲端金鑰服務。
- 原廠或合作夥伴提供代管服務時，原廠人員以 A18 的外部人員身分擔任技術維運。

**理由**：職責分離是稽核核心；但要求必須在中小型子公司做得到，否則客戶會用「形式上的分離」應付，結果更糟。以集團為單位配置，是台灣集團企業共享服務的現實。

## B19 每季升版都要重做驗收，沒有長期支援版本與安全修補時限

**情境**：資訊長問：「多久出一個版本？每次升版要停機多久？升版後我們要不要重新驗收？發現高風險弱點，多久會有修補？」金融子公司的變更管理規定，正式環境的每次升版都要測試報告與使用單位簽核，一次要兩週。

**現在的設計會怎麼反應**：D7 決定「有進度就推上 main；尚未驗證的 commit 以 `wip:` 開頭」，這是開發方式，不是發行政策。沒有發行節奏、長期支援版本、安全修補時限、升版停機時間、升版對控制的影響說明。02 的第 4 點從稽核角度提出平台自身升版的變更控制。

**結果**：客戶每季升版都要花兩週驗收，於是一年只升一次或乾脆不升；安全修補跟著延後。會計師查變更控制時，客戶拿不出「這次升版改了哪些控制」的說明。評選時 D7 的做法若被看到，會被解讀為「沒有發行管理」。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 頻繁發行，由客戶自己決定要不要升。客戶會停在舊版，原廠要支援無數版本，最後兩邊都不安全。
2. 一年只發行一次。安全修補太慢。
3. **長期支援版本加安全修補時限：每年一個長期支援版本，支援兩年；長期支援版本只出安全與錯誤修補；每個版本附上「控制影響說明」，對應到控制對照表。**

**最佳解**：採 3。
- 發行政策：每年一個長期支援版本（支援 24 個月，重疊 12 個月）；期間的功能版本給想要新功能的客戶。長期支援版本的修補版只修正錯誤與弱點，不改行為，客戶可以縮短驗收。
- 安全修補時限：CVSS 9 以上 7 天內、7 以上 30 天內提供修補或緩解方式；公告管道與通知對象寫進合約。
- 每個版本附上「控制影響說明」：列出哪些規則代碼、控制對照表的哪些列有變動，以及自動測試的結果；沒有變動也要明說「無控制變動」。客戶可以把它直接附在自己的變更申請單上。
- 升版腳本支援預檢（在備份上試跑，估算停機時間）；一般修補版不需停機。
- D7 維持為內部開發方式，但發行版本必須來自已驗證、帶簽章的標籤，與 main 的 `wip:` 提交分開。

**理由**：客戶不升版，安全就失守；客戶升版卻說不清楚改了什麼，變更控制就過不了。長期支援版本與控制影響說明，同時解決兩件事。

## B20 資安長要第三方滲透測試報告、SBOM、弱點通報時限

**情境**：資安長賴政達的供應商資安評估問卷有四十題，其中必填：最近一年的第三方滲透測試報告摘要、原廠的 ISO 27001 證書、軟體物料清單（SBOM）、弱點通報與修補流程、是否允許客戶自行滲透測試、開發過程是否有原始碼掃描。他還順口問：「聽說你們的程式大量用 AI 寫，誰為程式品質負責？」

**現在的設計會怎麼反應**：engineering-standards 有完整的品質關卡（Trivy 的弱點、設定錯誤與授權掃描、hadolint 等）。D23 說明各階段使用的模型與「最好的模型驗收」的做法。沒有對外的資安保證文件：第三方滲透測試、SBOM 對外提供、弱點揭露政策、客戶自行測試的規則、安全強化手冊。

**結果**：問卷上大半寫「規劃中」，資安長不同意上線；或者上線後客戶自己的滲透測試打到正式環境，觸發誤報、鎖帳號。D23 若被問到，沒有一份可以拿給客戶看的說明。

**涵蓋**：部分涵蓋（內部的檢查已有，缺對外的保證與證據）。

**替代方案**：
1. 只提供內部掃描結果。客戶的問卷大多明確要求第三方。
2. 由客戶每次自費做滲透測試。每家客戶重複花錢，結果也不會回饋到產品。
3. **原廠每年委託第三方做滲透測試與原始碼檢測，報告摘要在保密協議下提供；每個版本對外提供 SBOM 與簽章；公開弱點揭露政策；提供客戶自行測試的規則與安全強化手冊。**

**最佳解**：採 3。
- 每年一次第三方滲透測試（涵蓋網頁、API、資料庫權限模型、多公司隔離、機密欄位），大版本前加做一次；摘要報告與修補追蹤提供給客戶。
- 每個發行版本附上 CycloneDX 格式的 SBOM，容器映像與套件有簽章，客戶可以驗證來源。
- 公開弱點揭露政策與聯絡方式，修補時限與 B19 一致。
- 客戶自行滲透測試：提供規則（範圍、事先通知、用測試環境）與一套隔離的測試部署方式。
- 安全強化手冊：預設安全的設定清單，以及每項設定對應的資通系統防護基準條目（研究 01）。
- 開發方式的說明：對外說明 AI 輔助開發的品質把關機制（規格先行、自動測試、試圖繞過的測試、人工與第三方檢測），由原廠法人承擔產品責任。

**理由**：資安評估是採購的必經關卡；平台本身就是控制的載體，客戶的資安長有義務確認它不會成為弱點。

## B21 視障同仁用 NVDA 中文報讀申請；MFA 與逾時登出擋住他

**情境**：公司依身心障礙者權益保障法進用了一位視障的分析師，他用 NVDA 中文語音報讀。某天要申請客戶主檔資料：資料範圍選擇器是樹狀加勾選，報讀只念出「核取方塊，未勾選」，不知道是哪個欄位；MFA 畫面要辨識圖形；填到一半被逾時登出，草稿不見。另外，有政府持股的子公司被要求取得無障礙標章。

**現在的設計會怎麼反應**：ux-acceptance 有 axe-core 無 serious／critical、WCAG AA 對比、只用鍵盤可完成、欄位有標籤。這些是自動檢查，沒有實際用螢幕報讀軟體走完任務的驗收；沒有涵蓋 WCAG 2.2 的新要求（例如無障礙驗證、焦點不被遮擋），也沒有逾時的規定。資料授權的專屬輸入元件（`custom`）由流程包提供，不一定被自動檢查涵蓋到。

**結果**：自動檢查全過，但實際上視障同仁無法自己完成申請，只能請同事代填，申請人身分與實際操作者不一致（06 的第 8 點相關）。評選時若被要求提供無障礙符合聲明（ACR／VPAT），拿不出來。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 維持自動檢查。自動工具只能找出約三到四成的無障礙問題，關鍵的報讀流程測不到。
2. 提供一個「無障礙版」的簡化介面。兩套介面維護成本高，也違反「同一個概念全站一致」，且常被遺忘更新。
3. **同一套介面，驗收加上用螢幕報讀軟體實際走完關鍵任務；目標提高到 WCAG 2.2 AA；公布無障礙符合聲明。**

**最佳解**：採 3。
- ux-acceptance 新增人工驗收：T2、T5、T6、T7、T12 等關鍵任務，分別用 NVDA＋Chrome（繁中語音）與 iOS VoiceOver 實際走完；流程包的專屬元件同樣適用。
- 目標由 WCAG AA 明確為 WCAG 2.2 AA（涵蓋台灣的網站無障礙規範）；加入 2.2 的新項目，特別是「無障礙驗證」（MFA 不得要求辨識圖形或記憶，支援 passkey 與密碼管理器）與「焦點不被固定按鈕遮住」（手機底部固定的核准按鈕）。
- 逾時：登入逾時前提醒並可延長，草稿自動儲存，逾時後回到原畫面不遺失內容。
- 每個版本產出無障礙符合聲明（ACR），列出例外與改善時程。

**理由**：無法自己完成申請的人只能請人代填，紀錄上的申請人就不是真正的操作者；可及性也是採購的條件，尤其是有政府股份的子公司。

## B22 和 IGA 比：連接器數量、複查時沒有使用紀錄、已經在用 Entra ID Governance

**情境**：評選表上身分治理產品列了「預建連接器 300 個以上」「存取複查時顯示最後登入時間並建議移除」「角色探勘」。公司的 M365 已買了 Entra ID Governance，Teams 與 SharePoint 的存取由 access package 管。委員問：「你們跟 Entra 是取代還是並存？兩邊都在給權限，誰是真相？」

**現在的設計會怎麼反應**：D21 的整合方式是 API、檔案、人工三種；骨幹第 11 節對外提供判定、查詢、事件、對帳、複查。沒有預建的連接器清單，沒有使用紀錄（最後登入、最後查詢）進入複查畫面，沒有說明與既有 IGA 並存時的權責劃分。`resource_system` 記錄整合方式，但沒有「這個系統的權限以哪個系統為準」。

**結果**：評選表這幾項全空白，被認為是「簽核系統而不是治理產品」。若並存，同一個 SharePoint 網站的權限有兩條核准途徑，對帳時平台把 Entra 核准的權限全部列為「沒核准卻存在」，例外清單爆量，最後沒人看。複查只能看「誰有權限」，看不到「有沒有在用」，負責人只好全部按保留（01 的第 11 點）。

**涵蓋**：部分涵蓋。

**替代方案**：
1. 自己寫幾百個連接器，與 IGA 正面競爭。成本極高，維護不完，也偏離「稽核級簽核」的定位。
2. 只支援檔案與人工，連接器全交給客戶。對中大型客戶不夠，評選分數低。
3. **以標準協定取代大量專屬連接器（SCIM 2.0 佈建與匯入、OpenID 的事件標準），只做少數高價值的連接器並提供連接器 SDK；每個受管系統宣告權威來源，與既有 IGA 明確分工；複查畫面納入使用紀錄。**

**最佳解**：採 3。
- 連接器：SCIM 2.0（支援 SCIM 的 SaaS 都能接）、AD／Entra 群組、M365，以及資料授權用的 DC；其他系統用 D21 的檔案或人工，或用 SDK 由客戶或合作夥伴寫。評選回覆以「支援 SCIM 的系統即可接」說明涵蓋範圍。
- `resource_system` 增加「權威來源」：本平台、外部 IGA（指名）、或混合。外部 IGA 為權威時，平台只做對帳與證據收集（匯入對方的核准紀錄並標示來源），不重複核准；平台為權威時，平台核准後透過 API 指派對方的 access package。對帳只對「本平台為權威」的部分產生「沒核准卻存在」。
- 複查與對帳的檔案或 API 可以帶使用紀錄（最後登入、最後使用時間）；複查畫面顯示「90 天未使用」，並可依此建議移除。使用紀錄只作參考，決定仍由負責人做。
- 角色探勘不在第一版；評選回覆中說明定位差異：平台的強項是核准綁定內容、執行後驗證、紀錄可驗證，這些是研究 03 中 IGA 產品普遍沒有的。

**理由**：採購比的是「能不能管到我所有的系統」；用標準協定與明確的權威來源，比數量競賽更務實，也避免兩套系統互相製造假例外。

## B23 法務問：系統上的核准算不算電子簽章，用印與重大核准要不要憑證

**情境**：法務主任簡志豪看了合約用印流程後問：「財務長在手機上按一下核准，將來若有爭議，法院會不會認？依電子簽章法，這算不算電子簽章？有些往來銀行要求重大授權要用工商憑證簽，平台能不能做？」

**現在的設計會怎麼反應**：骨幹記錄決定、裝置、MFA，雜湊鏈證明紀錄未被竄改。但沒有對每一個決定做數位簽章（以簽核人或平台的金鑰），沒有可信時間戳記，也沒有支援憑證簽章（例如工商憑證、自然人憑證）。雜湊鏈只能證明「鏈沒有被改」，不能證明「是這個人在這個時間做的」對第三方的效力。

**結果**：發生爭議時，公司只能請資訊人員出庭說明系統紀錄；評選時法務把「電子簽章效力」列為疑慮，傾向保留紙本用印簽核，平台的用印流程形同虛設。

**涵蓋**：沒涵蓋。

**替代方案**：
1. 所有決定都要求個人憑證簽章。安全，但每次簽核都要插卡或安裝元件，簽核速度大降，手機做不到。
2. 不處理，說明紀錄本身就是證據。對內部稽核足夠，對外部爭議與銀行要求不夠。
3. **每個決定由平台以自己的金鑰簽章並取得可信時間戳記（RFC 3161）；流程可依級別要求簽核人以個人憑證或 passkey 對決定內容簽章。**

**最佳解**：採 3。
- 平台對每一個決定事件（含內容版本的雜湊、簽核人身分、驗證強度）以平台金鑰簽章，並定期向可信的時間戳記服務取得時間戳記（可以對一段期間的鏈頭取一次，降低成本）。這同時強化 02 第 12 點的第三方驗證。
- 流程定義可以宣告某級別需要「個人簽章」：電腦上以工商憑證或自然人憑證（透過讀卡機元件）簽章，手機上以 passkey 簽章並記錄；預設不開，給法務與銀行有要求的流程（例如重大用印、銀行授權）使用。
- 證據頁顯示簽章與時間戳記的驗證結果，獨立驗證工具（B14）也能驗證。
- 對外提供說明文件，請客戶的法務依電子簽章法判斷；平台不替客戶做法律結論。

**理由**：稽核過關看的是內部證據，但用印與對外授權會面對外部爭議；以時間戳記和選用的個人簽章補強，不影響一般簽核的速度。
