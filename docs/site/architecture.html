資料庫裡的四種帳號

每種帳號只能做自己的事。這是「拿到後端帳號也冒用不了別人」的基礎。

帳號誰在用能做什麼

一次核准是怎麼被保護的

  1. 主管在待簽清單點開一張單，按核准。
  2. 資料庫產生一個挑戰值，綁定這張單、這個內容版本、「核准」這個動作。
  3. 主管的裝置用通行金鑰簽署這個挑戰值（需要指紋或臉部辨識）。
  4. 後端把簽署結果原封不動交給資料庫。
  5. 資料庫自己驗證簽章，並檢查：是這個人的金鑰、挑戰值沒用過、單號與內容版本相符、他有資格簽、不是申請人本人。
  6. 通過才寫入核准，同一筆交易內寫進雜湊鏈。

測試過擋得住的攻擊：偽造簽章、拿別人的證明、重放舊的證明、把甲單的證明用在乙單、改過內容再用舊證明。

每個外部系統都要先登記，有自己的金鑰和可用範圍（OAuth 2.0），只看得到自己範圍內的資源；每次呼叫都留紀錄。

一筆授權在系統之間怎麼流動

  1. 核准：申請在平台上走完簽核。
  2. 交付：平台產生規則，交給該資源所屬系統的管理人。
  3. 設定：外部系統照規則設定權限，回報完成。這時授權才算生效。
  4. 驗證：平台請外部系統用被授權者的身分試查：查得到該查的、查不到不該查的。
  5. 使用：使用權限的系統在存取前向平台查詢，得到允許或拒絕。
  6. 異動：授權被縮小、到期或撤銷時，平台通知訂閱的系統，外部系統收回權限。
  7. 對帳：外部系統定期回報實際權限。和核准的不一致，平台就開出例外並追蹤到結案。

原則：簽核完的結果由系統傳給系統，不經過人

核准的內容由人轉述或手動設定，就有打錯、漏做、多做、拖延的空間，核准的和實際的就會對不上。所以：

  • 系統對系統是預設，也是目標。規則由平台直接送進外部系統，外部系統自動回報結果，中間沒有人經手。
  • 送出的內容有平台的簽章，外部系統可以確認它真的來自平台、沒被改過。
  • 送不到會自動重送；一直送不到就開出例外，而不是改由人去設定。
  • 人工只是不得已的退路。只有外部系統真的沒有任何介面時才允許，而且會被標示成較弱的控制、列在稽核準備度上。
方式人有沒有經手怎麼運作控制強度
系統對系統（預設）沒有平台送出規則 → 外部系統套用並回報 → 自動驗證 → 定期自動對帳強
檔案交換只經手檔案，不經手內容平台產生有簽章的規則檔，外部系統匯入；權限清單由系統匯出後上傳比對中
人工（退路）有管理人照畫面設定並回報；必須由沒參與的人獨立確認弱，列為常設例外

平台停擺時

  • 查不到平台時，使用方預設拒絕；判定結果可以短時間快取，時間到就要重新問。
  • 事件有序號，外部系統恢復後從上次的序號接續，不會漏。
  • 平台只提供判定與資訊；它停擺不會讓已經設定在外部系統裡的權限消失。

已知的限制

  • 有資料庫最高權限的人可以換掉驗證程式；只能事後偵測，要靠職務分離與資料庫稽核日誌外送。
  • 最後一次外部摘要之後的紀錄，被改了抓不到。稽核畫面會明確標示「尚未有外部摘要涵蓋」。
  • 人員同步的帳號若被濫用，目前只做到「看得到」；加上冷卻期的修正正在做。
  • 還沒有在真的手機上操作過，用的是電腦瀏覽器模擬手機寬度。
