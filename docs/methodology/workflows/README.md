# 工作流程腳本

三支通用的多代理工作流程腳本，專案專屬的內容都由 `args` 傳入。每支腳本開頭是 `export const meta = {...}`（純字面值），註解裡有 args 格式與範例。

共同注意事項：

- 每個工作流程同時執行的代理數有上限。要更多平行，就分成多個工作流程啟動。
- 共用背景（`context`）放最前面，所有代理相同，利於快取。
- 大量閱讀與蒐集用較省的模型；審查、裁決與最終查證用最好的模型。
- 代理只寫指定的檔案，不 commit；產出由主代理驗證後再提交。

## 三支腳本

| 腳本 | 何時用（SKILL.md 步驟） | args |
|---|---|---|
| `research-and-verify.js` | 步驟 2：依主題調查，每份再由獨立代理查證 | `{context, topics:[{slug,title,scope}], outDir, researchModel, verifyModel}` |
| `reality-check.js` | 步驟 3：多個立場各列出真實情境與最佳解 | `{context, readFirst:[...], lenses:[{slug,title,focus}], outDir, model}` |
| `contract-draft-attack-revise.js` | 步驟 6：一份契約的撰寫、對立審查、修訂 | `{context, outFile, draftPrompt, lenses:[{key,prompt}], draftModel, criticModel}` |

- **research-and-verify**：主題之間不相依，可同時調查；每個主題內部是調查完才查證。`researchModel` 用較省的，`verifyModel` 用最好的。輸出 `<outDir>/<slug>.md`。
- **reality-check**：骨幹或第一版設計已有、情境檢查之前使用。`readFirst` 列出定位、骨幹、決策紀錄、驗收標準。每個立場輸出 `<outDir>/<slug>.md`，並回傳結構化摘要供下一步的去重與裁決。
- **contract-draft-attack-revise**：骨幹定案後才啟動。一份契約一個工作流程，多份契約各自啟動。`draftPrompt` 寫清楚撰寫者的角色與契約內容；`lenses` 是對立立場（攻擊者、串接者、實作者）。

傳 args 的方式：啟動工作流程時，把上面格式的物件作為 `args` 帶入；腳本內以 `args.xxx` 讀取。

## 十二個立場的建議清單

`reality-check.js` 的 `lenses` 建議至少涵蓋下列立場，視產品增減。每個 `focus` 寫成「你是誰、你關心什麼、你會怎麼遇到問題」。

| # | 立場 | 關注重點 |
|---|---|---|
| 1 | 一般使用者（日常操作者） | 第一次用能不能不看說明完成任務；常做的事是否太多步；出錯時知道怎麼辦 |
| 2 | 管理者與決策者 | 要在忙碌、手機、資訊不全時做決定；需要的事實是否第一眼可見；批次與委派 |
| 3 | 資料或系統擁有者 | 想知道誰在用、用到什麼程度；撤銷與複查是否不費力 |
| 4 | 內部驗收或稽核 | 不靠別人就能查到任何一筆紀錄、自行驗證沒被改過；控制是否強制而非靠自律 |
| 5 | 外部驗收方（主管機關、客戶稽核、認證機構） | 能否拿出符合其格式與期間的證據；系統管不到的部分如何說明 |
| 6 | 資安 | 身分冒用、越權、列舉、重放、供應鏈、機密資料的存放與外洩路徑 |
| 7 | 想走捷徑或舞弊的人 | 如何繞過控制、串通、事後補資料、利用例外路徑；規則被繞過時是否看得見 |
| 8 | 維運 | 安裝、升級、備援、還原、監控、排查問題；排程失敗與資料量成長 |
| 9 | 組織異動 | 離職、調動、代理、合併與分割、兼任、外部人員；負責人消失時東西歸誰 |
| 10 | 法遵與法務 | 個資與隱私、資料保存與刪除、跨境、電子紀錄與簽署的效力、保密與調閱 |
| 11 | 導入顧問 | 第一天怎麼把既有資料與流程搬進來；客製與設定的界線；教育訓練與抗拒改變 |
| 12 | 採購方 | 總持有成本、廠商鎖定、與既有系統整合、授權與部署模式、退場時資料能否帶走 |
