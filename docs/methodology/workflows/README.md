# 工作流程腳本

三支多代理工作流程腳本，專案專屬的內容都由 `args` 傳入。每支開頭是 `export const meta = {...}`（純字面值），註解裡有 args 格式與範例。步驟編號對應 `.claude/skills/product-from-zero/SKILL.md`，流程順序：釐清(0) → 定規範(1) → 調查(2) → 骨幹初稿(3) → 架構探針(4) → 情境檢查(5) → 裁決(6) → 骨幹定稿(7) → 契約(8) → 擴展(9) → 驗收(10)。

## 怎麼執行

- **需要 Claude Code 的 Workflow 工具。** `agent`、`parallel`、`pipeline`、`phase`、`log`、`args` 是它提供的全域變數，不能用 `node` 直接執行。主代理以 Workflow 工具執行腳本檔，並把下表格式的物件作為 `args` 帶入；確切的呼叫參數以該工具當下的說明為準（寫新腳本前先載入 `workflow-authoring` skill）。
- **沒有 Workflow 工具時**照同樣的結構手動做：腳本裡的 `CTX` 加上每個項目的那段提示詞，就是一個子代理的提示詞。`parallel` 的項目同時啟動多個子代理（同一輪送出）；`pipeline` 的兩段依序做（調查完才查證）；契約腳本依序做撰寫 → 各立場審查（平行）→ 修訂 → 確認，確認有未修就再修訂一輪。要求結構化回傳的，在提示詞最後貼上腳本裡的 schema，要求以 JSON 回傳。
- 每個工作流程同時執行的代理數有上限。要更多平行，就分成多個工作流程啟動。
- 共用背景（`context`）放最前面，所有代理相同，利於快取。
- 代理只寫指定的檔案，不提交；產出由主代理驗證後再提交。
- 這三支腳本是從上一個專案實際用過的工作流程整理出來的；整理後的檔案，以及本次修訂（確認階段、情境數上限）都還沒有實際執行過。

| 腳本 | SKILL 步驟 | args |
|---|---|---|
| `research-and-verify.js` | 2 調查 | `{context, topics:[{slug,title,scope}], outDir, researchModel, verifyModel}` |
| `reality-check.js` | 5 情境檢查 | `{context, readFirst:[...], lenses:[{slug,title,focus}], outDir, model, maxPerLens}` |
| `contract-draft-attack-revise.js` | 8 契約 | `{context, outFile, draftPrompt, lenses:[{key,prompt}], draftModel, criticModel, maxRounds}` |

- **research-and-verify**：主題之間平行；每個主題調查完才查證。`researchModel` 用較省的，`verifyModel` 用最好的。
- **reality-check**：骨幹初稿與架構探針完成後使用。`readFirst` 放產品定位、骨幹初稿、探針的交接紀錄、決策紀錄、驗收標準。`model` 用次一級；裁決才用最好的。`maxPerLens` 預設 10，小專案用 5。只回報頻率乘影響為中以上的情境。
- **contract-draft-attack-revise**：骨幹定稿後才啟動，一份契約一個工作流程。修訂後由審查方確認每個 blocker、major 是否已修，未修的再修訂，最多 `maxRounds` 輪（預設 2）；回傳的 `unresolved` 不為空就不算完成。

## 情境檢查的立場

這是立場清單的唯一來源。必選的一律要有；其他依「何時選」挑，挑選理由記進決策紀錄。數量依規模（README 第 3 節）。每個 `focus` 寫成「你是誰、你關心什麼、你會怎麼遇到問題」。

| # | 立場 | 選用 | 何時選 | 關注重點 |
|---|---|---|---|---|
| 1 | 一般使用者（日常操作者） | 必選 | 一律 | 不看說明能否完成任務；常做的事是否太多步；出錯時知道怎麼辦 |
| 2 | 資安 | 必選 | 一律 | 依 STRIDE 逐項：身分冒用、竄改、否認、資訊外洩、阻斷服務、越權；加上列舉、重放、供應鏈、機密的存放 |
| 3 | 維運 | 中、大必選 | 要上線給別人用 | 安裝、升級、備援、還原、監控、排查；排程失敗與資料量成長 |
| 4 | 管理者與決策者 | 視產品 | 有審核、核准或報表 | 忙碌、手機、資訊不全時做決定；需要的事實是否第一眼可見；批次與委派 |
| 5 | 資料或系統擁有者 | 視產品 | 產品管理別人的資料或權限 | 想知道誰在用、用到什麼程度；撤銷與複查是否不費力 |
| 6 | 內部驗收或稽核 | 視產品 | 受稽核，或要證明紀錄沒被改過 | 不靠別人就能查到任何紀錄並驗證沒被改；控制是否強制 |
| 7 | 外部驗收方（主管機關、客戶稽核、認證機構） | 視產品 | 要對外提出證據 | 能否拿出符合其格式與期間的證據；系統管不到的部分如何說明 |
| 8 | 想走捷徑或舞弊的人 | 視產品 | 有金錢、權限或考核相關的流程 | 繞過控制、串通、事後補資料、利用例外路徑；被繞過時是否看得見 |
| 9 | 組織異動 | 視產品 | 多人、多部門或多組織使用 | 離職、調動、代理、合併、兼任、外部人員；負責人消失時東西歸誰 |
| 10 | 法遵與法務 | 視產品 | 處理個資、受管制資料或有法律效力的紀錄 | 個資、保存與刪除、跨境、電子紀錄與簽署效力 |
| 11 | 導入顧問 | 視產品 | 要取代既有系統或流程 | 第一天怎麼搬資料與流程；客製與設定的界線；抗拒改變 |
| 12 | 採購方 | 視產品 | 賣給組織，由別人決定買不買 | 總持有成本、廠商鎖定、整合、部署模式、退場時資料能否帶走 |
