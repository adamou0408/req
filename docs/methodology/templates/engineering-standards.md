# 工程規範

這份文件是程式碼品質要求的唯一來源。所有人和所有代理動手前都要先讀。

## 1. 單一真相來源（SSOT）

每一種資訊只能有一個來源，其他地方用「讀取」或「產生」取得，不得手抄。

| 資訊 | 唯一來源 | 其他地方怎麼取得 |
|---|---|---|
| 業務規則的定義與規則代碼 | `docs/contract/00-spine.md` 第 5 節加各契約的「規則」章節（小專案：`docs/design.md`） | 文件、測試名稱、事件紀錄都引用代碼，不重寫 |
| 業務規則的實作 | `<實作位置，例如資料庫函式或領域層>` | 其他層不得重寫任何業務判斷 |
| 錯誤代碼、訊息、狀態碼 | `<錯誤目錄>` | 各層只透過同一個入口丟錯；前端直接顯示後端回傳的訊息 |
| 狀態、級別等列舉值 | `<列舉的定義位置>` | 由產生器輸出到各語言 |
| 設定值與預設值 | `<設定表>` | 透過同一個讀取入口 |
| 對外介面（路徑、參數、回應型別） | `<機器可讀的介面定義檔，例如 openapi.yaml>` | 後端依它註冊；前端依它產生呼叫函式；參考文件由腳本產生 |
| 介面文案 | `<文案檔>` | 元件只引用 key |
| 環境變數 | `<設定定義檔>` | `.env.example` 由測試比對，不一致就失敗 |
| 套件版本 | `<lock 檔>` | 一律用 lock 檔安裝 |
| 技術債 | `docs/tech-debt.md` | 程式裡只寫編號 `TD-<n>` |
| 工程規範 | 本文件 | `CLAUDE.md` 只引用本文件 |

規則：

- 產生的檔案放在 `generated/` 或 `docs/reference/`，檔頭註明「自動產生，請勿手動修改」。CI 會重新產生並檢查沒有差異。
- 設計階段的契約在實作完成後，以產生的參考文件為準，設計契約標示為「已由參考文件取代」。
- 發現同一件事寫在兩個地方，就視為缺陷，要收斂成一處。

## 2. 架構

依賴方向只有一個：`<上層> → <中層> → <底層>`。越靠近底層，責任越重。

### <底層，例如資料庫或領域層>

- <分區或命名空間，各自的責任與權限邊界；應用程式身分只有最小權限>
- 每一類橫切邏輯只有一個入口：授權檢查、錯誤丟出、取得現在時間。任何地方不得自己另寫一套。
- 已經套用到任何環境的 migration 不得修改，只能新增。

### <中層，例如後端>

- 分層：<路由表 → 通用 handler → 呼叫底層>。
- 對外系統一律走 port 與 adapter：<列出本專案的外部系統>。
- 業務判斷只放在 <業務規則的實作位置>，其他層不重寫。

### <上層，例如前端>

- 分層：頁面 → 共用元件 → API 呼叫層。頁面不直接呼叫網路函式。
- 手機優先：每個頁面在 390px 寬不得水平捲動，觸控目標至少 44px。
- UI/UX 驗收標準見 [ux-acceptance.md](ux-acceptance.md)，不通過就不算完成。

### 抽象層：會變的東西都要能換

凡是「之後可能換」的東西，程式只認抽象，不認具體的值、人名或系統。換的時候改資料或換 adapter，不改規則程式。

| 會變的東西 | 抽象 | 規定 |
|---|---|---|
| 參數（時限、上限、開關） | `<參數定義>`：型別、單位、預設值、允許範圍 | 一律透過同一個讀取入口。程式裡不得出現寫死的天數、數量或門檻 |
| 人員身分 | 內部 id；外部帳號另外對應 | 不得用外部帳號、email 或姓名當主鍵 |
| 角色 | `<角色定義>` | 程式不得寫死任何人、群組名稱或部門 |
| 外部系統 | port 與 adapter：<列出> | 每個 port 至少有一個模擬 adapter 和一份合約測試；真實 adapter 通過同一份合約測試就能替換 |
| 介面文案 | `<文案檔>` | 元件不寫死文字 |
| <其他會變的東西> | <抽象> | <規定> |

檢查方式：審查時逐項確認；能自動檢查的（例如程式裡不得出現寫死的時限）寫成測試。

### 視產品而定：受稽核、工作流程或多組織的產品

- 每一類橫切邏輯另加單一入口：狀態轉移、事件紀錄、通知寫入。
- 狀態轉移由一張轉移表驅動，不散落在 `if` 裡；中層不得依狀態、角色、級別做判斷。
- 畫面顯示哪個按鈕，依後端回傳的「可執行動作」清單，不自行推斷。
- 參數值帶生效時間、只增不改，依「最具體的適用範圍 → 全域 → 預設值」取值；每次決定用到的參數值記進事件紀錄。
- 組織樹與「誰向誰報告」分開存，都帶生效期間；角色指派（人或群組 → 角色）可帶適用範圍與生效期間；找主管與升級透過同一個解析入口。
- 流程路徑與規則集是帶版本的資料；通知內容放範本表，改文字不需重新部署。
- 事件紀錄只增不改，資料庫層擋下修改與刪除。

## 3. 可讀性

- 命名：<各語言的命名慣例>。同一個概念全專案只用一個名字。
- 長度：函式超過約 <行數> 行，就拆出有名字的小函式。
- 註解寫「為什麼」，不寫「做了什麼」。和業務規則有關的地方標上規則代碼。
- 對外的每個函式或端點都要有說明：用途、誰可以呼叫、對應的規則代碼。
- 格式交給工具決定（<formatter>），不人工爭論。
- 型別檢查開到最嚴，不使用 `any` 之類的逃生口；lint 與 formatter 零警告。
- 不留 `TODO`、`FIXME`、被註解掉的程式碼、沒有用到的程式碼。欠下的事登記在 `docs/tech-debt.md`，程式裡只寫編號 `TD-<n>`。
- 不用假資料或空殼充數。做不到或沒做完的事，寫進交接紀錄並在回報中說明。

## 4. 套件管理

- 專案結構：<單一 repo 或 workspace 的結構>。只有根目錄有 lock 檔。
- 執行環境版本寫在 `<版本檔，例如 .nvmrc 與 engines>`。
- 版本一律精確鎖定，安裝一律依 lock 檔（<指令，例如 npm ci>）。
- 共用設定放在根目錄，各子專案繼承。
- 新增套件的門檻：標準函式庫做得到、或 30 行內寫得完，就不加。要加時在交接紀錄說明用途。不得有功能重複的套件。
- CI 只執行 `tools/check.sh`（見第 6 節）。

## 5. 測試

- 測試先行：契約的驗收案例在實作前由最好的模型寫成可執行、目前會失敗的測試（SKILL.md 步驟 8）。實作者不得修改這些測試；認為測試錯了就回報。
- 每條規則代碼至少有一個測試，測試名稱包含規則代碼，並包含「試著繞過」的測試。`tools/check.sh` 檢查每個代碼都有測試。
- 架構測試：把本文件第 2 節的規定寫成自動檢查（例如每個對外函式都有說明、應用程式身分沒有多餘權限）。
- 測試用的機制（後門參數、假登入、跳過驗證的開關）不得存在於正式建置；寫一個建置或設定測試證明它們在正式設定下不存在。
- 契約測試：介面定義引用的每個函式都存在且參數相符；每個函式都有對應的介面，或明確列為只供內部使用。
- 不得為了讓測試通過而跳過、停用或放寬測試。測試失敗就修程式。
- 整合測試與端對端測試使用 `<模擬環境目錄>` 的環境：用真實協定的服務（<列出>）。模擬替身只用在單元測試。每個外部 port 的真實 adapter 都要對著模擬環境跑過合約測試。

## 6. 品質關卡

所有檢查只有一個入口：`tools/check.sh`（範本見 `docs/methodology/templates/check.sh`）。本機和 CI 執行同一支腳本，任何一項失敗就算失敗。檢查工具用 `tools/install-dev-tools.sh` 安裝，版本固定。依規模取捨：小專案只開格式、lint、測試；中型加型別與資安；大型全部。

| 類別 | 檢查 | 工具 |
|---|---|---|
| 格式與靜態檢查 | 格式、lint、型別 | <formatter、linter、型別檢查器> |
| | 沒用到的檔案、匯出與套件 | <例如 knip> |
| | 資料庫或查詢語言的格式與靜態分析（視產品而定） | <例如 sqlfluff；PostgreSQL 函式用 plpgsql_check> |
| | Shell 腳本、容器檔、CI 設定 | <例如 shellcheck、hadolint、actionlint> |
| 資安 | 套件弱點（HIGH 以上失敗） | <例如 Trivy、npm audit> |
| | 誤放進 repo 的密碼與金鑰 | <例如 Trivy secret> |
| | 部署設定的錯誤設定 | <例如 Trivy misconfig> |
| | 套件授權 | <例如 Trivy license> |
| 測試 | 各層測試與瀏覽器端對端 | 見第 5 節 |
| 一致性 | 產生檔重新產生後沒有差異 | 產生器 |
| | 每個規則代碼都有測試 | `check.sh` 內建 |
| | 測試裡沒有 `.skip`、`.only`；程式裡沒有 `TODO`、`FIXME`；每個 `TD-<n>` 都已登記 | `check.sh` 內建 |

規則：

- 不得全域關閉規則或整個目錄忽略來讓檢查通過。確實需要例外時，逐項寫明原因，放在該工具的設定檔裡，並在審查時列出。
- 每個步驟完成、合併進主分支之前，都要跑過 `tools/check.sh`。

## 7. 工作方式

- 動手前先讀：本文件、骨幹第 5 節與任務相關的契約段落、`docs/handoff/` 裡的交接紀錄。
- 只修改自己負責的範圍。需要動到別人的範圍時，寫進交接紀錄並回報。
- 完成前必須實際執行驗證（安裝、建置、lint、測試），並在回報中附上指令與結果。
- 完成時寫 `docs/handoff/<工作塊>.md`（範本 `docs/methodology/templates/handoff.md`；工作塊名稱同契約切分）。
