# 用 AI 從零做出產品的方法

> 先讀 [00-core.md](00-core.md)：目標、五條策略、修正規則。本文件是「做法」這一層，可以替換；與核心衝突時以核心為準。

一位負責人帶一個 AI 主代理和它指揮的子代理，從一個想法做到驗證過、可以上線的產品。這份文件只寫「為什麼」；怎麼做寫在 `.claude/skills/product-from-zero/SKILL.md`，各步驟的完成條件也只寫在那裡。

這套方法有兩個目的，同樣重要：

1. 做出對的產品。
2. **越用越聰明**：每做一個專案，負責人需要糾正的次數就比上一個少。這是判斷方法有沒有用的唯一成功標準（見第 6 節）。

**實際走過的範圍**：釐清、規範、調查、情境檢查、裁決、骨幹、契約（依舊順序，在一個受稽核的簽核平台上走過一次）。**尚未實戰驗證**：新順序本身、架構探針、擴展、驗收、上線與維運、規模分級的縮減方式；`templates/` 的兩支腳本只有 `check.sh` 在空專案跑過，`install-dev-tools.sh` 沒有實際執行過。

**執行環境假設**：Claude Code，能啟動子代理並指定模型；工作流程腳本需要 Workflow 工具，沒有時有手動做法（見 `workflows/README.md`）。用量以可取得的計量為準：訂閱方案看用量百分比，API 計費看金額或 token。

| 檔案 | 用途 |
|---|---|
| `.claude/skills/product-from-zero/SKILL.md` | 執行步驟、完成條件、管理 AI 的規則 |
| `docs/methodology/lessons-log.md` | 教訓紀錄（每個新專案步驟 0 先讀） |
| `docs/methodology/templates/` | 新專案複製的範本；`templates/README.md` 列出每份何時建立 |
| `docs/methodology/workflows/` | 多代理工作流程腳本；情境檢查的立場清單 |
| `docs/methodology/reviews/` | 對方法論本身的審查與處理結果 |

方法論與教訓紀錄不屬於任何單一專案。目前暫放在這個 repo；正式用法是放在獨立的 repo 或使用者層級（例如 `~/.claude/skills/`），每個新專案引用同一份，教訓才帶得走。

## 1. 這套方法要解決什麼

| 失敗 | 表現 | 對應的支柱 |
|---|---|---|
| 做錯東西 | 照字面做了，沒解決真正的問題 | 原則（第 2 節） |
| 做得淺或做過頭 | 只處理想得到的情況；或設計很深卻沒驗證 | 流程（第 3 節） |
| 看起來完成 | 回報完成，但沒驗證或驗證的是假資料 | 關卡（第 4 節） |
| 失控 | 子代理做了不該做的事、重複做、把額度燒光 | 管理 AI（第 5 節） |
| 同樣的錯一再發生 | 負責人每個專案都要糾正同一類問題 | 越用越聰明（第 6 節） |

## 2. 原則

**三條規則的取捨。**「選最佳解」管的是範圍內每個決定的品質：一個決定該怎麼做，就選現實中行得通的最好做法，不因省事而降級。「做多深、做多少」不歸它管，由規模分級（第 3 節）和「先用程式驗證再往下設計」決定。用量或時間不夠時，停下來回報，由負責人決定縮範圍或延後；不得悄悄降低品質，也不得因為「要選最佳解」而自行加碼。所以產品定位裡的優先順序只比品質面向，不把「速度與成本」列進去跟品質比。

每一條原則都來自實際發生過的問題（見 `lessons-log.md`）。

### 目標

1. **先找出真正要解決的事。** 負責人說的是手段，要往回推到目的，拆成「必須成立的條件」清單；每個條件都要有檢驗方式。
2. **訂一個可以檢驗的終極目標**，其他目標排在它後面。條件由系統做到、可以測試，不靠人自律。
3. **誠實寫出系統做不到的部分**，設計成看得見的例外。
4. **好用是目標的前提。** 難用的系統會被繞過，繞過之後所有保證都失效。

### 決定

5. **選現實中行得通的最佳解。**「行得通」指有已知的實例，或能用探針證明。「之後再做」只在現在做反而會做錯（缺少必要資訊）時成立；工作量大不是延後的理由，但可以是縮範圍的理由，由負責人決定。
6. **衝突時依明訂的優先順序決定**，記進決策紀錄。
7. **看似二選一時，先懷疑是不是假的二選一。** 例：「要能自己設定」和「變更要可稽核」，解法是設定變更本身也走核准。
8. **會變的東西做成抽象層**：參數、人員與角色、外部系統、文案。不寫死任何單位、人名或門檻。
9. **方向衝突由 AI 先判斷並記錄**，只在兩種情況問負責人：只有他知道的事實；無法回頭或成本很大的動作。
10. **被取代的決定保留並標示**，判斷過程可以追溯。

### 設計

11. **每種資訊只有一個來源**，其他地方引用或產生。同一件事寫在兩處就是缺陷。
12. **設計沒想到的，要系統性地找**：多個代理各扮演一個真實立場，列出上線後一定會遇到的具體情境。
13. **先調查再定細節**：每個事實附來源；查不到就寫查不到；關鍵論點由沒參與的代理重新查核。
14. **區分強制、建議、實務。** 對外的說法只用查證過的依據。
15. **先用程式驗證，再往下設計。** 真正的不確定性只有動手才會暴露。契約之前的設計深度上限是一份骨幹初稿。做過頭的訊號：一段設計對應不到目標對照表的任何要求，或沒有程式能驗證它。

### 品質

16. **靠機制把關，不靠自律**：規則有測試，規範寫成自動檢查，不得跳過或放寬測試。
17. **用真實協定的環境測試**；模擬替身只用在單元測試。
18. **獨立審查**：重要設計由沒參與的代理從對立角度審查，修訂後再由審查方確認。
19. **不留半成品**：不留 TODO、不用假資料；做不到的寫進技術債清單並回報。
20. **如實回報**：分清楚「文件完成」「程式寫完」「驗證通過」。

## 3. 流程

順序：**釐清 → 定規範 → 調查（依規模）→ 骨幹初稿 → 架構探針 → 情境檢查 → 裁決 → 骨幹定稿 → 契約 → 擴展 → 驗收**（步驟 0–10）。各步驟做什麼、產出什麼、完成條件，見 SKILL.md。

為什麼是這個順序：

- **探針提前。** 上一個專案先做完調查、情境檢查、裁決、骨幹、契約才準備寫程式，架構的根本問題拖到很晚才發現。所以骨幹只寫到初稿就做一條最窄的完整路徑，對著真實環境跑。探針失敗就退回骨幹初稿。
- **情境檢查對照骨幹初稿與探針的結果**，找的是現實會遇到、而初稿和探針沒涵蓋的情況；有東西可對照，情境才具體。
- **會被後面推翻的不先做。** 骨幹定稿前不寫契約；契約定案前不大量實作。為省時間而平行、結果重寫，是最貴的做法。
- **不相依的才平行。** 調查的各主題、情境檢查的各立場、各份契約。

### 依規模縮減

規模在步驟 0 決定，記在產品定位；中途改變就走需求變更。縮減的是步驟的份量，不是品質；教訓的收集與提煉不縮減。

| 步驟 | 小（一兩天、單一角色、無外部整合） | 中（一兩週，或有外部整合） | 大（一個月以上、多模組、受稽核或多組織） |
|---|---|---|---|
| 0 釐清 | 衝突題 ≤3 | 完整 | 完整 |
| 1 規範 | 工具只留格式、lint、測試；工程規範只留用得到的節 | 加型別與資安掃描 | 全部關卡 |
| 2 調查 | 只查競品與痛點，不另做查證 | 依主題調查，關鍵論點查證 | 全部主題，逐份獨立查證 |
| 3–4 骨幹初稿、探針 | 初稿寫進設計文件；探針就是第一個功能 | 照做 | 照做 |
| 5 情境檢查 | 3–4 個立場（含必選的使用者與資安），每個 ≤5 個情境 | 必選加相關的選用立場，每個 ≤10 | 依風險選，每個 ≤10 |
| 6–7 裁決、骨幹定稿 | 合併成一份設計文件 `docs/design.md` | 分開 | 分開 |
| 8 契約 | 併入設計文件；由一位沒參與的代理審查 | 核心契約走撰寫、審查、修訂 | 全部契約 |
| 9–10 擴展、驗收 | 照做；走查頁只含主要任務 | 照做 | 照做 |

### 視產品而定

- **平台類產品**：領域無關的能力和領域知識分成兩層；用至少兩個結構不同的案例證明通用；能用宣告設定的就不寫程式。
- **受稽核或多組織的產品**：組織與角色帶生效期間；事件紀錄只增不改；狀態轉移表驅動；後端回傳「可執行動作」；目標對照表的依據標強度；情境檢查依立場表的「何時選」加入相關立場。範本裡這些內容都標了「視產品而定」。

## 4. 關卡

「看起來完成」只能靠機制擋：規則有測試、靜態檢查與資安掃描、產生檔無差異、真實環境的整合測試、獨立審查、每種使用者的任務步數上限、目標對照表（要求 → 做法 → 測試 → 證據）。所有檢查只有一個入口 `tools/check.sh`，本機和 CI 跑同一支。內容見範本 `engineering-standards.md` 第 5–6 節、`ux-acceptance.md`、`control-matrix.md`。

契約的驗收案例在實作前先寫成會失敗的測試，實作者不得修改它們：對 AI 實作來說，這是防止「看起來完成」最便宜的機制。

## 5. 管理 AI

規則寫在 SKILL.md 的「管理子代理」與「用量」，這裡只說理由：

- **啟動前先問四件事**（現在做合理嗎、哪一級模型、產出什麼、怎麼驗收），因為最大的浪費是在依賴未定案時就開工。
- **模型分級**：錯誤由驗收把關，不是靠每一步都用最貴的模型（教訓 L2）。
- **停損條件要能觀察**（用量倍數、多久沒產出），才不會因為已經花了成本而硬撐。
- **跨階段的連貫靠 repo 裡的文件**，不靠對話記憶，所以任何階段結束都能停、隔週能接續。

## 6. 越用越聰明

這是方法的核心目的。規則寫進文件不等於學到；只有變成會被執行的東西、而且之後負責人糾正得更少，才算學到。

**收集。** 四種訊號發生當下就記進 `lessons-log.md`：負責人的糾正、停損、審查找到的問題、被推翻的假設。每筆寫發生什麼、為什麼事前沒想到、屬於哪一類。**負責人的糾正是最有價值的訊號**：它代表方法和 AI 都沒擋下、只能靠人發現的錯。

**提煉。** 每個階段結束時，把這階段的紀錄變成會被執行的東西，依這個順序挑第一個做得到的：

1. 自動檢查（`check.sh`、測試、腳本的 schema）
2. 範本的必填項
3. SKILL 的步驟或完成條件
4. 最後才是文件裡的一句話

**驗證。** 每個專案結束時統計：負責人糾正的次數、重做的工作量、同類錯誤是否再犯、各階段估計與實際用量。**成功標準：負責人需要糾正的次數逐個專案下降。** 同類錯誤再犯，代表上次的提煉沒有效，要往上一層提煉（例如從一句話改成必填項或檢查）。

**淘汰。** 一條規則在連續兩個專案都沒有擋下任何問題，就合併或刪除。README 與 SKILL 合計長度要有上限的意識：新增一條之前，先看能不能合併或取代舊的。

**帶走。** 教訓紀錄與方法論放在不屬於單一專案的位置；每個新專案步驟 0 先讀教訓紀錄。

## 7. 與業界現成做法的關係

| 做法 | 這裡的對應 | 直接沿用 | 這套方法多了什麼 |
|---|---|---|---|
| 規格驅動（spec-driven、API-first） | 骨幹與契約 | 對外介面用機器可讀的格式（OpenAPI、JSON Schema）當唯一來源 | 契約前先用探針驗證骨幹；對立立場審查 |
| 測試驅動（TDD） | 驗收案例先成為會失敗的測試 | 先寫失敗的測試再實作 | 測試由最好的模型寫，實作代理不得修改 |
| 架構決策紀錄（ADR） | 決策紀錄 | 狀態、背景、決定、後果、取代關係 | 標明 AI 判斷或負責人決定，以及待確認 |
| 設計審查、pre-mortem、威脅建模 | 情境檢查、契約審查 | 資安立場用 STRIDE；情境依頻率乘影響排序 | 多個 AI 代理各扮一個真實立場，平行找情境 |
| walking skeleton、tracer bullet | 架構探針 | 最窄的完整路徑 | 有明確的風險清單與退回規則 |
| 需求追溯矩陣（RTM） | 目標對照表 | 要求到測試的對照 | 每欄在哪一步填、加上證據欄 |
| 事後回顧（retrospective） | 越用越聰明 | 階段與專案結束時回顧 | 提煉成會被執行的東西；以負責人糾正次數衡量 |
