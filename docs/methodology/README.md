# 用 AI 從零做出產品的方法

這份文件記錄一套可以重複使用的做法：由一位專案負責人帶一個 AI 主代理，加上它指揮的子代理，從一個想法做到驗證過、可以上線的產品。適用於任何軟體產品；只適用於平台類產品的內容另外標示。

版本：第一版，涵蓋「從零到設計完成」。實作、整合、驗收、上線各階段完成後會補上該階段的教訓（見最後一節）。

配套：

| 檔案 | 用途 |
|---|---|
| `.claude/skills/product-from-zero/SKILL.md` | 讓 Claude 在新專案自動照這套方法執行 |
| `docs/methodology/templates/` | 新專案直接複製的空白文件 |
| `docs/methodology/workflows/` | 可重複使用的多代理工作流程腳本 |

## 1. 這套方法要解決什麼

沒有方法時，AI 做產品會出現四種失敗：

| 失敗 | 表現 |
|---|---|
| 做錯東西 | 照字面做了被要求的功能，但沒有解決真正的問題 |
| 做得淺 | 只處理設計時想得到的情況，現實中會遇到的都沒涵蓋 |
| 看起來完成 | 回報「完成」，但沒有驗證過，或驗證的是假資料 |
| 失控 | 子代理做了不該做的事、重複做、或把額度燒光 |

對應的四個支柱是：原則（判斷依據）、流程（順序與進入條件）、關卡（怎麼知道做對了）、運作方式（怎麼管理 AI）。

## 2. 原則

每一條都來自實際發生過的問題。

### 目標

1. **先找出真正要解決的事。** 使用者說的是手段，要往回推到目的。用第一性原理把需求拆成「必須成立的幾件事」，再從那幾件事推出系統的形狀。
2. **訂一個可以檢驗的終極目標，其他目標都排在它後面。** 目標要拆成由系統做到、可以測試的條件，不能靠人自律。
3. **誠實寫出系統做不到的部分**，並設計成「看得見的例外」，不要假裝涵蓋。
4. **好用是目標的前提。** 難用的系統會被繞過，繞過之後所有保證都失效。每一種使用者都要有驗收標準。

### 決定

5. **選現實中行得通的最佳解，不選省事的。** 「之後再做」只有在現在做反而會做錯（缺少必要資訊）時才成立；工作量大不是理由。
6. **衝突時依明訂的優先順序決定**，並記在決策紀錄。專案一開始就要訂出這個順序。
7. **兩個要求看似衝突時，先懷疑是不是假的二選一。** 例：「要能自己設定」和「變更要可稽核」，解法是讓設定變更本身也走核准流程。
8. **會變的東西做成抽象層**：參數、人員與角色、流程路徑、外部系統、文案。程式只認抽象，要換時改資料或換轉接器。不得寫死任何單位、人名或門檻。
9. **方向衝突由 AI 先判斷並記錄**，只有兩種情況才問負責人：只有他知道的事實；無法回頭或成本很大的動作。
10. **被取代的決定保留並標示**，讓判斷過程可以追溯。

### 設計

11. **每種資訊只有一個來源**，其他地方用讀取或產生的。同一件事寫在兩處就是缺陷。
12. **設計沒想到的，要系統性地找**：讓多個代理各扮演一個真實角色（使用者、稽核、攻擊者、維運、導入顧問、採購方等），列出上線後一定會遇到的具體情境。
13. **先調查再定目標**：法規、競品、痛點、標準。每個事實附來源；查不到就寫查不到；由沒參與的代理重新查核關鍵論點。
14. **區分「強制」「建議」「實務」**。對外的說法只能用查證過的依據。
15. **設計不要做過頭。** 設計到一定深度後效益遞減，真正的不確定性只有動手才會暴露。先做最窄的一條完整路徑來驗證架構，再擴展。

### 品質

16. **靠機制把關，不靠自律**：每條規則有測試；架構規範寫成自動檢查；產生的檔案由 CI 比對；不得跳過或放寬測試。
17. **用真實協定的環境測試**，模擬替身只用在單元測試。對外介面沒有實測過不算驗證。
18. **獨立審查**：重要的設計由沒參與撰寫的代理從對立的角度審查（攻擊者、要來串接的工程師）。撰寫者承認有風險但沒有解法的地方，通常就是審查會抓到的地方。
19. **不留半成品**：不留 TODO、不用假資料充數；做不到的事明確寫出來並回報。
20. **如實回報**：分清楚「文件完成」「程式寫完」「驗證通過」。沒有驗證過的不能說完成。

## 3. 流程

每個階段有進入條件和產出。條件沒滿足就不往下走。

| # | 階段 | 做什麼 | 產出 | 可以往下的條件 |
|---|---|---|---|---|
| 0 | 釐清 | 用第一性原理分析需求；列出不清楚的地方；找出方向上的衝突，一次問完 | 目標、不做的事、優先順序 | 負責人確認 |
| 1 | 定規範 | 工程規範、品質關卡、決策紀錄、驗收標準 | 規範文件、`CLAUDE.md` | 規範進 repo，子代理啟動時會讀到 |
| 2 | 調查 | 法規、競品、痛點、標準；每份調查再由獨立代理查證 | 調查文件、綜合結論 | 關鍵論點都查核過 |
| 3 | 情境檢查 | 多個立場各列出真實情境與解法 | 情境文件 | 涵蓋使用、稽核、攻擊、維運、導入、採購 |
| 4 | 裁決 | 去重分群，逐項決定最佳解與範圍 | 裁決文件、更新決策紀錄 | 每個議題都有決定與理由 |
| 5 | 骨幹 | 固定命名、核心概念、狀態、介面、範圍 | 骨幹文件 | 主代理複核過；之後所有契約以它為準 |
| 6 | 契約 | 依骨幹寫各模組的詳細契約；獨立審查後修訂 | 契約文件、驗收案例 | 審查的重大問題都已處理 |
| 7 | 最窄路徑 | 做一條從頭到尾的完整路徑，對著真實環境跑 | 可執行的程式與測試 | 架構被證明可行 |
| 8 | 擴展 | 依序加入其餘功能 | 程式與測試 | 每一塊都通過品質關卡 |
| 9 | 驗收 | 自動檢查、獨立審查、負責人看過成品 | 驗收紀錄、畫面走查 | 負責人確認 |

兩條順序規則：

- **會被後面推翻的東西不要先做。** 骨幹沒定案前不寫契約；契約沒定案前不大量實作。為了省時間而平行，結果重寫，是最貴的做法。
- **不相依的才平行。** 調查、情境檢查、模擬環境彼此不相依，可以同時做。

平台類產品另外適用：把領域無關的能力和領域知識分成兩層；用至少兩個結構不同的案例證明通用；能用宣告設定的就不寫程式。

## 4. 關卡

| 關卡 | 內容 |
|---|---|
| 規則有測試 | 每條業務規則至少一個測試；腳本檢查沒有漏掉的規則；包含「試著繞過」的測試 |
| 靜態檢查 | 格式、lint、型別、未使用的程式碼；資料庫程式的靜態分析；腳本與部署設定的檢查 |
| 資安掃描 | 套件弱點、誤放的機密、部署設定錯誤 |
| 一致性 | 產生的檔案重新產生後無差異；契約與實作相符 |
| 真實環境 | 對著真實協定的模擬服務做整合與端對端測試 |
| 獨立審查 | 正確性、資安、可實作性，由沒參與的代理審查 |
| 使用體驗 | 每種使用者的任務有步數上限；手機可用；無障礙檢查；獨立審查看真實畫面；最後由負責人確認 |
| 目標對照 | 一張對照表：要求 → 系統怎麼做到 → 哪個測試證明 → 拿什麼當證據。不能有空格 |

所有檢查只有一個入口，本機和 CI 執行同一支腳本。不得用忽略清單讓檢查通過。

## 5. 運作方式：怎麼管理 AI

### 子代理

- **啟動前**確認四件事：現在做是否合理（依賴的東西定案了沒）、用哪一級模型、預期產出什麼、怎麼驗收。答不出來就不啟動。
- **一個代理把一塊工作從寫到測到修做完**，不拆成多個代理各讀一遍背景。
- **提示詞精簡、結構化**：目標、範圍、驗收條件、回報格式。共用的背景放在最前面且每個代理相同，以利用快取。
- **規範放在 repo**（`CLAUDE.md` 引用工程規範），不要每次寫在提示詞裡。
- **跨階段的連貫靠 repo 裡的文件**，不靠對話記憶。每個代理完成時寫交接紀錄。
- **執行中要看得到**：定期確認它在做什麼、有沒有產出。
- **結束後自己驗證**，不只看回報。

### 停損

出現下列任何一種就停掉，不因為已經花了成本而硬撐：

- 它依據的前提已經改變，做完也要重來。
- 花費明顯超過這件工作該有的規模。
- 長時間沒有產出，或在重複同樣的動作。
- 用了不必要的高階模型。

### 模型分級

| 工作性質 | 模型 |
|---|---|
| 規劃與驗收：目標、裁決、骨幹、核心契約、審查、最終查證 | 最好的 |
| 一旦寫錯就影響目標的核心實作 | 次一級，寫完由最好的模型驗收 |
| 照契約就能完成的工作、大量閱讀與蒐集 | 較省的 |

錯誤由驗收把關，而不是靠每一步都用最貴的模型。

### 額度

- **一開始就量消耗速度**：請負責人隔幾分鐘提供兩次用量數字，算出每分鐘的消耗。
- **每個階段開始前先估用量**並告知；超過就停下來回報。
- **大量閱讀的工作交給較省的模型**，最好的模型只讀彙整後的結果。
- 主代理自己的每一輪也有成本；對話很長時，把幾件事合併在同一輪處理。

### 溝通

- 分析先講結論；用表格比較；不用內部代號。
- 需要負責人決定時，一次問完，每題附建議的做法。
- 成品用手機可讀的 HTML 呈現。
- 有進度就存進 repo；尚未驗證的標示清楚。
- 每個階段結束都是一個可以停的點，狀態寫在 repo，隔週可以接續。

## 6. 專案一開始要建立的文件

| 文件 | 內容 |
|---|---|
| `CLAUDE.md` | 一句話說明專案；引用工程規範；列出必讀文件 |
| 產品定位 | 終極目標與檢驗條件、要解決的問題、優先順序、範圍界線 |
| 工程規範 | 單一真相來源、架構分層、抽象層、可讀性、套件管理、品質關卡、測試、工作方式 |
| 決策紀錄 | 每筆：衝突是什麼、怎麼決定、依據；開頭寫明做決定的標準 |
| 驗收標準 | 每種使用者的任務與上限；自動檢查與人工檢查；驗收流程 |
| 骨幹 | 命名、核心概念、狀態、介面、範圍；所有契約的依據 |
| 待增修清單 | 契約撰寫期間新增的要求，修訂時逐項納入後刪除 |
| 目標對照表 | 要求 → 做法 → 測試 → 證據 |

## 7. 犯過的錯與對應的規則

| 發生的事 | 後果 | 規則 |
|---|---|---|
| 骨幹還在變動就平行寫契約 | 草稿要重寫 | 會被後面推翻的東西不要先做 |
| 用最好的模型跑實作類工作，同時開二十個代理 | 額度每分鐘消耗 1.5% | 模型分級；啟動前確認用哪一級 |
| 沒有一開始就量消耗速度 | 消耗了四分之一才發現 | 一開始就量；每階段先估用量 |
| 把「第二批再做」當成預設 | 必要的能力被延後，核心設計可能擋路 | 「之後再做」要有站得住的理由 |
| 把某個單位寫死成負責人 | 現實中很多系統不歸那個單位管 | 不寫死任何單位；負責人是可指派的角色 |
| 把「可設定」和「可稽核」當成二選一 | 做出客戶無法自己調整的平台 | 先懷疑是不是假的二選一 |
| 為了測試方便加了可在正式環境啟用的後門參數 | 成為可被濫用的漏洞 | 測試用的機制不得存在於正式建置 |
| 設計做得很深，還沒有驗證過的程式 | 架構的根本問題到情境檢查才發現 | 先做最窄的完整路徑驗證架構 |
| 讓執行期資料被提交進版本庫 | 要事後清理 | 一開始就設好忽略清單 |
| 草圖用了手機上難讀的呈現方式 | 負責人無法審閱 | 先確認負責人用什麼裝置看 |

## 8. 待補的階段

下列階段完成後，把教訓補進第 2、3、7 節：

- 核心契約與最窄路徑的實作
- 多個模組的整合
- 真實環境的端對端測試
- UI/UX 驗收
- 上線準備與交接
