# 決策紀錄

記錄方向上有衝突、由開發方自行判斷的決定。每一筆寫明衝突是什麼、怎麼決定、依據。專案負責人不同意任何一筆時，直接指出編號即可調整。

做決定的標準：選現實世界裡真正行得通的最佳解，不選比較省事的做法。「之後再做」只有在現在做反而會做錯（缺少必要資訊）時才成立；單純因為工作量大，不是延後的理由。被取代的決定保留在表中並標示「已由 … 取代」，讓判斷的過程可以追溯。

判斷依據是 [platform-vision.md](platform-vision.md) 的優先順序：稽核過關 → 安全 → 簽核人的速度與正確性 → 通用性 → 開發速度與成本。

D25 起是真實情境檢查（D18）的裁決，每筆的設計、放棄的替代方案與對骨幹的修改見 [reality-check/00-decisions.md](reality-check/00-decisions.md)。〔 〕內是後續裁決對該筆的修正或補充。

| D12 | 流程與參數要能由客戶自己設定（否則不算平台），但控管規則的變更必須可稽核 | **設定變更本身走簽核。** 流程定義、路徑、參數、角色指派都可以在管理畫面修改，但每一次修改都是一張「設定變更申請單」：由提出人以外的人核准（雙人覆核）、有版本、有生效時間、可試算影響、可回復，並留在同一條稽核紀錄裡。進行中的申請單繼續用送審當時的版本 〔由 D41、D42 修正：權威來源的事實不走簽核；核准人資格依控制類別與方向；「沿用送審當時的版本」只適用路徑與參數，不適用組織事實與角色持有人〕 | 兩個要求其實不衝突：稽核要的不是「不能改」，而是「改的人不能自己決定、而且改過什麼查得到」。平台用自己的簽核能力管自己的設定，也是最好的示範 |
| D13 | 把稽核必查的流程（程式變更上線、系統帳號與角色權限）排到第二批比較省事，但「讓稽核過關」需要它們，而且它們會逼出核心必要的能力 | **五種流程都納入第一版**：資料授權、合約用印、程式變更上線、系統帳號與角色權限（含特權、緊急、委外人員）、供應商銀行帳號變更。緊急路徑、職責衝突矩陣、核決權限表、人工的獨立驗證都做進核心 〔由 D49 修正：緊急路徑拆成急件、緊急、暫停，緊急路徑只開放給可收回的權限。D55 另增全宣告的治理範本包〕 | 這些能力在真實環境一定會用到；等到第二批才發現核心設計擋路，代價更高 |
| D14 | 領域邏輯全部寫成 SQL function 最有彈性，但客戶自己新增流程時不可能都寫 SQL | **宣告優先，程式為輔。** 分級規則、縮小的方向、重複的判斷、摘要欄位都可以在流程定義裡用宣告的方式設定（例如「金額調降算縮小」「金額達門檻為重大」）；只有宣告表達不了的領域邏輯（例如資料授權的涵蓋判定）才寫成 hook function 〔D44、D43 補充：增加累計與組合兩種宣告；hook 帶版本並以受限角色執行〕 | 多數流程不需要寫程式就能上線；複雜的領域仍有出口 |
| D15 | 地端單一客戶部署不需要多租戶，但上市櫃集團幾乎都有子公司 | **支援集團多公司**：公司別是核心的一個維度，流程、路徑、參數、角色、行事曆、可見範圍都可以依公司別區分；跨公司的申請與簽核要能表達。不做雲端多租戶的資料隔離（那是另一種部署模式） 〔D31 補充：多公司延伸到證據層；跨部署聯盟不做〕 | 多公司是目標客群的常態；事後才加會動到幾乎所有資料表 |
| D16 | 規則文件只寫了「退回」，但實務上的簽核動作不只這些 | 補齊簽核動作：**駁回**（終止，不同於退回修改）、**提問與回覆**（不改變關卡，避免為了問一句話就退回）、**加簽**（多請一位審查，只增不減）、**轉簽**（改由他人簽，對象要有資格並通過職責分離檢查）、**撤回**（申請人在生效前取回）。每個動作都有規則代碼並留紀錄 〔D39、D50、D53 補充：增加徵詢、決定撤回、申請人縮小、線下決定登錄、轉為正確流程；駁回是終局狀態〕 | 少了這些，使用者會回到 email 和口頭處理，流程外的決定就沒有紀錄，稽核過不了 |
| D17 | 介面先做繁體中文比較快，但集團有海外子公司與外籍主管 | 文案與通知範本都以多語架構製作，第一版提供繁體中文與英文 〔D59 補充：語言包是資料；流程類型宣告以哪個語言為準〕 | 簽核人看不懂就無法做出有效的決定 |
| D18 | 還有哪些真實世界會遇到、設計時沒想到的情況，無法靠一個人列舉完 | 由十二個不同立場（內部稽核、會計師資訊稽核、資安、舞弊者、高階主管、申請人、MIS 維運、人資異動、財會法遵、個資法務、導入顧問、採購方）各自列出會發生的情境並提出解法，再統一裁決，結果納入契約 | 系統性地找，比事後一個一個補可靠 |
| D19 | 先前把「執行設定」和「控管規則負責人」都定為 MIS，但很多系統不歸 MIS 管：例如人資系統由人資單位外購、由廠商維運，資料連 MIS 都不能碰 | **每個受管系統各有自己的擁有單位與管理人，不預設是 MIS。** 核心新增「受管系統」：記錄業務擁有單位、系統管理人（可以是業務單位的人，也可以是有內部保證人的外部廠商人員）、整合方式、平台維運人員能否查閱其內容。執行、驗證、對帳都交給該系統的管理人；資安合規檢查與執行設定拆成兩件事，可以由不同的人做。控管規則的負責人也依流程類型或系統指派，預設才是 MIS 〔D37 補充：驗證改為讀回比對；對帳資料由獨立的對帳執行人提供〕 | 現實中權限最容易失控的，正是資訊單位管不到的系統；這也是稽核的盲區與市場缺口 |
| D20 | 平台由 MIS 維運，但有些申請的內容連 MIS 都不能看 | 三層做法：(1) **平台不存受保護的資料本身**，只存「誰可以看什麼」的描述；驗證只回報通過與否，不回傳資料。(2) 流程類型可以把欄位標為機密：這些欄位在進資料庫之前就加密，金鑰由平台維運以外的人保管，維運人員與資料庫管理員讀不到。(3) 平台管理拆成三種互相獨立的角色：技術維運（部署、備份；看不到內容）、流程管理（各業務單位管自己的流程與目錄）、稽核 〔由 D54、D34 修正：機密內容不經後端；金鑰保管改為角色與分持，稽核不持有；管理角色之間有衝突矩陣〕 | 稽核過關與安全優先；平台自己不能成為洩漏管道 |
| D21 | 對外系統沒有 API（外購的套裝或雲端服務常見），無法自動交付規則與對帳 | 每個受管系統可選整合方式：API、檔案交換（管理人匯出現有權限的清單上傳，平台比對）、純人工（管理人依交付內容設定後回報，由另一人獨立驗證）。三種都產生同樣格式的證據 〔D37 補充：三種整合方式的證據格式相同，但讀回都不得由執行人提供〕 | 不能因為對方系統沒有 API 就管不到；檔案與人工是多數外購系統的現實 |
| D22 | 好用與稽核過關誰優先 | **好用是稽核過關的前提，不是排在後面的目標。** 流程難用，人就會繞過系統用 email 和口頭處理，那些決定沒有紀錄，稽核一樣過不了；沒人願意用，也沒人會買。優先順序維持不變，但每個角色都訂出方便程度的驗收標準，任何一個角色不通過就不算完成 | 專案負責人指示；也是實務上流程失敗最常見的原因 |
| D23 | 全部用最好的模型品質最穩，但成本高 | 依工作性質分級：**規劃與驗收用最好的模型**（契約設計、裁決、交叉審查、資安審查、UI/UX 驗收、最終查證）；規則核心的實作（職責分離、狀態機、雜湊鏈、授權檢查）用次一級的模型，並一律經過最好的模型驗收；照契約就能完成的工作（畫面、轉接層、腳本、文件整理、資料蒐集）用較省的模型 〔D43 補充：安全關鍵模組另須人工資安審查〕 | 專案負責人指示；錯誤由驗收把關，而不是靠每一步都用最貴的模型 |
| D24 | 契約草稿與調查、情境檢查同時進行可以省時間，但草稿是依舊的骨幹寫的，之後要大改；最好的模型的額度消耗也過快 | 改成依序進行：調查查證與情境檢查（用較省的模型）→ 由最好的模型裁決並更新骨幹 → 依定案的骨幹寫契約 → 實作。已停止依舊骨幹撰寫的核心契約與畫面規格草稿，以及用最好的模型執行的骨架工作；已完成的檔案保留，之後接續 | 依會變動的骨幹寫出來的草稿，修訂成本高於重寫；最好的模型留給裁決與驗收 |
| D25 | 商業邏輯全在 SQL，但資料庫完全信任後端傳入的 `p_actor`：拿到後端連線帳號就能冒用任何人 | **資料庫自己驗證身分與決定。** session 由資料庫驗身分提供者簽的 token 後建立，`api` 改收 `p_session`；每個決定類動作都要綁定內容的決定證明（passkey 簽章，或以挑戰值為 nonce 的再驗證 token），由資料庫以 PL/pgSQL 驗章，不分裝置、沒有「幾分鐘內免再驗」；`K-MOBILE-MFA` 改為 `K-DECISION-PROOF`，刪除 `approval.mobile_mfa_required`；新憑證有冷卻期；SAML 經身分中介轉 OIDC。殘餘風險（superuser、畫面與簽章不一致、身分提供者管理員）只能偵測 | 稽核過關與安全：簽核紀錄的歸屬不可依賴時，其他證據全部失效。細節見 reality-check/00-decisions.md 2.1 |
| D26 | 直接改庫與平台自身的特權不在控制內 | 連線角色依用途拆分（`sgn_app`、`sgn_job`、`sgn_sync`、`sgn_integration`、`sgn_idp_sync`），決定類 function 只在 `api`；`sgn_owner` 不是 superuser、平時不可登入；業務表每列帶 `row_hash`，`check` 與決定讀取時比對（`K-STATE-CONSISTENT`）；事件重播比對、物件與設定指紋、`pgaudit` 外送；被擋下的操作寫入事件（`K-AUDIT-DENIED`）；平台的特權存取走自己的特權流程，故障時用封存的破窗帳號並補登 | 把「改了還能用」從事後偵測提前到當下擋住；不採完全事件溯源 |
| D27 | 雜湊鏈要長期可驗證，又要能依法銷毀與抹除個資；決定當時的事實不能隨主檔漂移 | 事件分骨架（進鏈，以 RFC 8785 正規化並保存被雜湊的 bytes）與封套（內容與個資，逐單金鑰加密，鏈上放密文雜湊與加鹽承諾）；鏈依月分段封印；每筆決定存判定依據快照、顯示快照、hook 版本與函式雜湊；人員與組織資料採雙時間；公開演算法並提供獨立的離線驗證工具 | 這個結構必須在寫 DDL 前定案；雜湊承諾同時滿足「快照入鏈」與「鏈上不放個資」 |
| D28 | 鏈可被整條重算；從備份還原會無聲地少掉紀錄；副本會對真人與真系統動作 | 每小時（硬上限每日）產生檢查點並推到至少兩個外部錨定位置，至少一個不由資訊維運管理，不足不能離開啟動模式；啟動時與外部錨點比對，落後即唯讀，還原後第一筆事件寫明遺失區間、不重算；環境身分不符即隔離（排程不跑、對外不送）；還原例外由控制負責人結案 | 錨定間隔就是可被重算的時間窗；RFC 3161 是選用的錨定位置，不強制 |
