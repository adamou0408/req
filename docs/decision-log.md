# 決策紀錄

記錄方向上有衝突、由開發方自行判斷的決定。每一筆寫明衝突是什麼、怎麼決定、依據。專案負責人不同意任何一筆時，直接指出編號即可調整。

做決定的標準：選現實世界裡真正行得通的最佳解，不選比較省事的做法。「之後再做」只有在現在做反而會做錯（缺少必要資訊）時才成立；單純因為工作量大，不是延後的理由。被取代的決定保留在表中並標示「已由 … 取代」，讓判斷的過程可以追溯。

判斷依據是 [platform-vision.md](platform-vision.md) 的優先順序：稽核過關 → 安全 → 簽核人的速度與正確性 → 通用性 → 開發速度與成本。

| # | 衝突 | 決定 | 依據 |
|---|---|---|---|
| D1 | 要做通用平台，但也要讓資料授權盡快可用 | 核心與流程包分開；資料授權是第一個流程包，規則完全不變；另做合約用印流程包來證明通用 | 通用性不能犧牲第一個實際流程的完整度 |
| D2 | 簽核路徑要「之後可以換」，但先前決定「路徑不開放在設定頁修改」 | ~~路徑做成有版本的資料，只能透過升版變更並留紀錄；管理畫面只能檢視~~ 已由 D12 取代 | 同 D8 |
| D3 | 「一律從嚴」與「第一版就要批次核准」 | 保留批次核准，但只限與前案無差異的續期；每張單各留一筆紀錄 | 稽核過關優先；調查若顯示稽核不接受批次核准，再進一步限制 |
| D4 | 主管與資料擁有者並行簽可以更快，但先前決定逐關簽 | 把「並行」做成路徑設定的能力，預設仍逐關簽 | 不自行改變已定的控管方式 |
| D5 | 用模擬替身開發比較快，但要求用真實環境 | 整合與端對端測試一律對著真實協定的模擬環境；模擬替身只用在單元測試 | 稽核過關優先：對外介面沒有實測過就不能算驗證 |
| D6 | 不計 token 與注意成本效益 | 品質與查證優先；在不影響品質的前提下減少重複讀取與重工 | 專案負責人最新的指示 |
| D7 | 「驗證過才進 main」與「有進度就進 main」 | 有進度就推上 main；尚未驗證的 commit 以 `wip:` 開頭，README 的「目前狀態」寫明哪些已驗證 | 專案負責人最新的指示 |
| D8 | 流程設計器（拖拉設定流程）會讓平台更通用，但流程是控管規則 | ~~第一版不做設計器；流程定義由流程包的升版腳本載入~~ 已由 D12 取代 | 原判斷把「可設定」和「可稽核」當成二選一，是錯的 |
| D9 | 對外介面要通用，但只有資料授權一個真實使用方 | 介面用通用的主體、資源、動作、限制條件描述，並採用公開標準；用模擬的 DC 與示範系統兩個不同的使用方驗證 | 通用性；避免介面被單一使用方的需求綁住 |
| D10 | 「讓稽核一定過關」與系統做不到的事（公司是否照規定使用、外部系統是否照規則設定） | 目標定為：稽核會查的控制，系統全部強制執行並自動留證據；系統管不到的部分，用對帳與例外追蹤讓它們提早浮現 | 不承諾系統無法保證的事，但把風險變成看得見的例外 |
| D11 | 驗證案例要有說服力（人資薪資、財會資料），但這兩個和資料授權是同一種流程，證明不了平台通用 | 分兩層：人資與財會作為資料授權流程包的資料領域；另以不同種類的流程證明通用。~~分三批~~ 批次已由 D13 取代 | 稽核過關與通用性都要兼顧 |
| D12 | 流程與參數要能由客戶自己設定（否則不算平台），但控管規則的變更必須可稽核 | **設定變更本身走簽核。** 流程定義、路徑、參數、角色指派都可以在管理畫面修改，但每一次修改都是一張「設定變更申請單」：由提出人以外的人核准（雙人覆核）、有版本、有生效時間、可試算影響、可回復，並留在同一條稽核紀錄裡。進行中的申請單繼續用送審當時的版本 | 兩個要求其實不衝突：稽核要的不是「不能改」，而是「改的人不能自己決定、而且改過什麼查得到」。平台用自己的簽核能力管自己的設定，也是最好的示範 |
| D13 | 把稽核必查的流程（程式變更上線、系統帳號與角色權限）排到第二批比較省事，但「讓稽核過關」需要它們，而且它們會逼出核心必要的能力 | **五種流程都納入第一版**：資料授權、合約用印、程式變更上線、系統帳號與角色權限（含特權、緊急、委外人員）、供應商銀行帳號變更。緊急路徑、職責衝突矩陣、核決權限表、人工的獨立驗證都做進核心 | 這些能力在真實環境一定會用到；等到第二批才發現核心設計擋路，代價更高 |
| D14 | 領域邏輯全部寫成 SQL function 最有彈性，但客戶自己新增流程時不可能都寫 SQL | **宣告優先，程式為輔。** 分級規則、縮小的方向、重複的判斷、摘要欄位都可以在流程定義裡用宣告的方式設定（例如「金額調降算縮小」「金額達門檻為重大」）；只有宣告表達不了的領域邏輯（例如資料授權的涵蓋判定）才寫成 hook function | 多數流程不需要寫程式就能上線；複雜的領域仍有出口 |
| D15 | 地端單一客戶部署不需要多租戶，但上市櫃集團幾乎都有子公司 | **支援集團多公司**：公司別是核心的一個維度，流程、路徑、參數、角色、行事曆、可見範圍都可以依公司別區分；跨公司的申請與簽核要能表達。不做雲端多租戶的資料隔離（那是另一種部署模式） | 多公司是目標客群的常態；事後才加會動到幾乎所有資料表 |
| D16 | 規則文件只寫了「退回」，但實務上的簽核動作不只這些 | 補齊簽核動作：**駁回**（終止，不同於退回修改）、**提問與回覆**（不改變關卡，避免為了問一句話就退回）、**加簽**（多請一位審查，只增不減）、**轉簽**（改由他人簽，對象要有資格並通過職責分離檢查）、**撤回**（申請人在生效前取回）。每個動作都有規則代碼並留紀錄 | 少了這些，使用者會回到 email 和口頭處理，流程外的決定就沒有紀錄，稽核過不了 |
| D17 | 介面先做繁體中文比較快，但集團有海外子公司與外籍主管 | 文案與通知範本都以多語架構製作，第一版提供繁體中文與英文 | 簽核人看不懂就無法做出有效的決定 |
| D18 | 還有哪些真實世界會遇到、設計時沒想到的情況，無法靠一個人列舉完 | 由十二個不同立場（內部稽核、會計師資訊稽核、資安、舞弊者、高階主管、申請人、MIS 維運、人資異動、財會法遵、個資法務、導入顧問、採購方）各自列出會發生的情境並提出解法，再統一裁決，結果納入契約 | 系統性地找，比事後一個一個補可靠 |
| D19 | 先前把「執行設定」和「控管規則負責人」都定為 MIS，但很多系統不歸 MIS 管：例如人資系統由人資單位外購、由廠商維運，資料連 MIS 都不能碰 | **每個受管系統各有自己的擁有單位與管理人，不預設是 MIS。** 核心新增「受管系統」：記錄業務擁有單位、系統管理人（可以是業務單位的人，也可以是有內部保證人的外部廠商人員）、整合方式、平台維運人員能否查閱其內容。執行、驗證、對帳都交給該系統的管理人；資安合規檢查與執行設定拆成兩件事，可以由不同的人做。控管規則的負責人也依流程類型或系統指派，預設才是 MIS | 現實中權限最容易失控的，正是資訊單位管不到的系統；這也是稽核的盲區與市場缺口 |
| D20 | 平台由 MIS 維運，但有些申請的內容連 MIS 都不能看 | 三層做法：(1) **平台不存受保護的資料本身**，只存「誰可以看什麼」的描述；驗證只回報通過與否，不回傳資料。(2) 流程類型可以把欄位標為機密：這些欄位在進資料庫之前就加密，金鑰由平台維運以外的人保管，維運人員與資料庫管理員讀不到。(3) 平台管理拆成三種互相獨立的角色：技術維運（部署、備份；看不到內容）、流程管理（各業務單位管自己的流程與目錄）、稽核 | 稽核過關與安全優先；平台自己不能成為洩漏管道 |
| D21 | 對外系統沒有 API（外購的套裝或雲端服務常見），無法自動交付規則與對帳 | 每個受管系統可選整合方式：API、檔案交換（管理人匯出現有權限的清單上傳，平台比對）、純人工（管理人依交付內容設定後回報，由另一人獨立驗證）。三種都產生同樣格式的證據 | 不能因為對方系統沒有 API 就管不到；檔案與人工是多數外購系統的現實 |
| D22 | 好用與稽核過關誰優先 | **好用是稽核過關的前提，不是排在後面的目標。** 流程難用，人就會繞過系統用 email 和口頭處理，那些決定沒有紀錄，稽核一樣過不了；沒人願意用，也沒人會買。優先順序維持不變，但每個角色都訂出方便程度的驗收標準，任何一個角色不通過就不算完成 | 專案負責人指示；也是實務上流程失敗最常見的原因 |
| D23 | 全部用最好的模型品質最穩，但成本高 | 依工作性質分級：**規劃與驗收用最好的模型**（契約設計、裁決、交叉審查、資安審查、UI/UX 驗收、最終查證）；規則核心的實作（職責分離、狀態機、雜湊鏈、授權檢查）用次一級的模型，並一律經過最好的模型驗收；照契約就能完成的工作（畫面、轉接層、腳本、文件整理、資料蒐集）用較省的模型 | 專案負責人指示；錯誤由驗收把關，而不是靠每一步都用最貴的模型 |
| D24 | 契約草稿與調查、情境檢查同時進行可以省時間，但草稿是依舊的骨幹寫的，之後要大改；最好的模型的額度消耗也過快 | 改成依序進行：調查查證與情境檢查（用較省的模型）→ 由最好的模型裁決並更新骨幹 → 依定案的骨幹寫契約 → 實作。已停止依舊骨幹撰寫的核心契約與畫面規格草稿，以及用最好的模型執行的骨架工作；已完成的檔案保留，之後接續 | 依會變動的骨幹寫出來的草稿，修訂成本高於重寫；最好的模型留給裁決與驗收 |
