# 決策紀錄

記錄方向上有衝突、由開發方自行判斷的決定。每一筆寫明衝突是什麼、怎麼決定、依據。專案負責人不同意任何一筆時，直接指出編號即可調整。

判斷依據是 [platform-vision.md](platform-vision.md) 的優先順序：稽核過關 → 安全 → 簽核人的速度與正確性 → 通用性 → 開發速度與成本。

| # | 衝突 | 決定 | 依據 |
|---|---|---|---|
| D1 | 要做通用平台，但也要讓資料授權盡快可用 | 核心與流程包分開；資料授權是第一個流程包，規則完全不變；另做合約用印流程包來證明通用 | 通用性不能犧牲第一個實際流程的完整度 |
| D2 | 簽核路徑要「之後可以換」，但先前決定「路徑不開放在設定頁修改」 | 路徑做成有版本的資料，只能透過升版變更並留紀錄；管理畫面只能檢視 | 稽核過關優先：控管規則的變更必須可追溯 |
| D3 | 「一律從嚴」與「第一版就要批次核准」 | 保留批次核准，但只限與前案無差異的續期；每張單各留一筆紀錄 | 稽核過關優先；調查若顯示稽核不接受批次核准，再進一步限制 |
| D4 | 主管與資料擁有者並行簽可以更快，但先前決定逐關簽 | 把「並行」做成路徑設定的能力，預設仍逐關簽 | 不自行改變已定的控管方式 |
| D5 | 用模擬替身開發比較快，但要求用真實環境 | 整合與端對端測試一律對著真實協定的模擬環境；模擬替身只用在單元測試 | 稽核過關優先：對外介面沒有實測過就不能算驗證 |
| D6 | 不計 token 與注意成本效益 | 品質與查證優先；在不影響品質的前提下減少重複讀取與重工 | 專案負責人最新的指示 |
| D7 | 「驗證過才進 main」與「有進度就進 main」 | 有進度就推上 main；尚未驗證的 commit 以 `wip:` 開頭，README 的「目前狀態」寫明哪些已驗證 | 專案負責人最新的指示 |
| D8 | 流程設計器（拖拉設定流程）會讓平台更通用，但流程是控管規則 | 第一版不做設計器；流程定義由流程包的升版腳本載入 | 稽核過關優先於通用性 |
| D9 | 對外介面要通用，但只有資料授權一個真實使用方 | 介面用通用的主體、資源、動作、限制條件描述，並採用公開標準；用模擬的 DC 與示範系統兩個不同的使用方驗證 | 通用性；避免介面被單一使用方的需求綁住 |
| D10 | 「讓稽核一定過關」與系統做不到的事（公司是否照規定使用、外部系統是否照規則設定） | 目標定為：稽核會查的控制，系統全部強制執行並自動留證據；系統管不到的部分，用對帳與例外追蹤讓它們提早浮現 | 不承諾系統無法保證的事，但把風險變成看得見的例外 |
| D11 | 驗證案例要有說服力（人資薪資、財會資料），但這兩個和資料授權是同一種流程，證明不了平台通用 | 分兩層：人資與財會作為資料授權流程包的資料領域；另以不同種類的流程（合約用印，之後是程式變更上線、系統帳號與角色權限）證明通用。選擇與批次見 validation-cases.md | 稽核過關與通用性都要兼顧；先做稽核必查的項目 |
