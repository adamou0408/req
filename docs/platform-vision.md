# 產品定位：稽核級簽核平台

## 終極目標：讓稽核過關

這個平台的成敗只看一件事：**使用它的公司，在簽核與權限這一塊的稽核能不能過關。** 其他目標（簽得快、好用、通用）都排在它後面。

「過關」拆成四個可以檢驗的條件，每一個都要由系統做到，不靠人自律：

| 條件 | 意義 | 怎麼檢驗 |
|---|---|---|
| **事前擋得住** | 稽核會查的每一項控制，系統都強制執行，設定和操作都繞不過去 | 每項控制都有自動測試，包含「試著繞過」的測試 |
| **證據自己產生** | 稽核要的證據不需要人事後整理、截圖或補簽 | 任選一段期間，一鍵產出稽核資料包：全部申請單的清單（可證明沒有遺漏）、每張單的完整紀錄、例外清單 |
| **例外自己浮現** | 逾期未簽、該複查沒複查、實際權限和核准不一致、負責人已離職，這些會在稽核發現之前就被系統找出來並追蹤到結案 | 「稽核準備度」畫面隨時顯示未結案的例外；每種例外都有測試 |
| **稽核自己查得到** | 稽核人員不用透過 IT 就能查到任何一張單，並能自行驗證紀錄沒被改過 | 稽核角色的端對端測試；雜湊鏈可由第三方驗證 |

控制項目的來源是法規與稽核實務的調查（`docs/research/`）。調查完成後會整理成一張控制對照表（`docs/audit/control-matrix.md`）：法規條文 → 控制目標 → 系統怎麼做到 → 哪個測試證明 → 稽核時拿什麼證據。對照表上不能有空格。

要誠實說明的界線：稽核還會查系統以外的事，例如公司有沒有照規定使用這個系統、外部系統有沒有照核准的規則設定。平台做不到替公司保證這些，但會把它們變成看得見的例外（例如對帳發現的差異），不讓它們到稽核時才被發現。

## 好用是過關的前提

流程難用，人就會繞過系統，改用 email 和口頭處理。那些決定沒有紀錄，稽核一樣過不了；沒人願意用，也不會有人買單。所以每一種使用者的方便程度都是驗收條件，任何一個角色不通過就不算完成（見 [ux-acceptance.md](ux-acceptance.md)）：

| 使用者 | 要讓他覺得 |
|---|---|
| 申請人 | 不用學就會填；知道卡在誰；同樣的東西不用重填 |
| 簽核人 | 手機上幾秒內看懂、做對決定；想問一句話不用退回 |
| 資料或系統擁有者 | 一眼看到誰有我的權限；撤銷與複查不費力 |
| 系統管理人（資訊單位、業務單位或外部廠商） | 清楚知道要設定什麼；回報完成很簡單；沒有 API 也能配合 |
| 流程管理者 | 自己就能調整流程與參數，不用找原廠 |
| 稽核 | 自己查、自己匯出、自己驗證，不用拜託別人 |
| 技術維運 | 裝得起來、升得上去、出問題找得到原因 |

## 不是所有系統都歸資訊單位管

很多系統由業務單位自己採購、由廠商維運，資訊單位管不到，有些資料甚至不該讓資訊單位看到（例如人資系統裡的薪資）。這些系統的權限最容易失控，也是稽核的盲區。平台因此不預設「資訊單位負責執行」：

- 每個受管系統有自己的擁有單位與管理人，執行、驗證、對帳都交給他們。
- 沒有 API 的系統用檔案交換或人工回報，一樣留下同格式的證據。
- 平台只存「誰可以看什麼」的描述，不存受保護的資料本身；標為機密的申請內容，連平台的維運人員都讀不到。

## 方向衝突時的優先順序

兩個要求互相衝突時，依這個順序決定，並記在 [decision-log.md](decision-log.md)：

1. 稽核過關
2. 資料與權限的安全
3. 簽核人做決定的速度與正確性
4. 通用性（不綁領域、可替換）
5. 開發速度與成本

## 要解決的問題

市面上的簽核系統把重點放在「把表單送到對的人手上」。對需要接受稽核的公司來說，這不夠。稽核要問的是另外四件事，而現有工具通常答不出來：

| 稽核會問 | 一般簽核系統 | 這個平台 |
|---|---|---|
| 這個決定是誰做的？他有沒有資格做？ | 靠流程設定的慣例，設錯了也不會擋 | 職責分離由引擎強制執行：每關不同人、申請人不能簽自己的單，設定繞不過去 |
| 他核准的內容，和最後執行的內容是同一份嗎？ | 核准後還能改，改了不一定重簽 | 每次修改都產生新版本；簽核綁定內容版本；縮小免簽、擴大重簽 |
| 核准之後真的照做了嗎？現在還該有效嗎？ | 簽完就結束 | 決定 → 執行 → 驗證 → 存續 形成閉環：執行後要驗證；有效期到期自動失效；沒人負責就失效；隨時可撤銷 |
| 紀錄可以相信嗎？ | 存在一般資料表，有權限的人就能改 | 紀錄只增不改並用雜湊鏈串接；每筆記下依據哪條規則、當時的參數值、當時的流程版本 |

所以平台的三個承諾是：**決定可問責、內容不走樣、紀錄改不掉**。

## 核准的結果要能被其他系統使用

簽核的結果如果只存在簽核系統裡，實際的權限還是由各系統各自設定，兩邊遲早會對不上。所以平台同時是公司裡「誰現在可以做什麼」的依據，提供通用的介面給其他系統：

- **查詢與判定**：其他系統可以查某個主體目前有哪些有效授權，或直接問「這件事現在能不能做」。
- **即時通知**：授權生效、到期、撤銷時，訂閱的系統會收到通知，不用等人工處理。
- **對帳**：其他系統回報實際設定的權限，平台找出沒核准卻存在、或超出核准範圍的權限。
- **定期複查**：定期請負責人確認授權是否仍然需要。
- **證據輸出**：稽核紀錄可以提供給稽核、GRC、SIEM 系統，並可驗證沒被竄改。

細節見 [contract/00-spine.md](contract/00-spine.md) 第 11 節。

## 平台不綁定特定領域

平台分成兩層：

- **核心（kernel）**：和領域無關的簽核能力。任何需要「有人負責、留下證據」的流程都用同一套。
- **流程包（pack）**：某一種申請的領域知識。新增一種流程只需要新增一個流程包，不修改核心。

| | 核心提供 | 流程包提供 |
|---|---|---|
| 表單 | 依欄位定義動態產生表單、版本化保存內容 | 欄位定義；需要時提供專屬的輸入元件 |
| 分級 | 依級別決定路徑與參數 | 怎麼從內容判定級別 |
| 簽核 | 路徑（資料）、找簽核人、職責分離、代理、催辦、升級、退回、批次、手機核准與 MFA | 這種流程有哪些關卡、每關怎麼找人 |
| 修改 | 版本、差異顯示、縮小免簽與擴大重簽的規則 | 怎麼判斷一次修改是縮小還是擴大 |
| 重複 | 擋下或要求說明的流程 | 怎麼判斷重複或重疊 |
| 執行 | 執行佇列、認領、標記完成 | 要交給外部系統的內容、怎麼交付 |
| 驗證 | 驗證紀錄、申請人確認、逾期處理 | 測試案例怎麼產生、怎麼執行 |
| 存續 | 有效期間、到期提醒與失效、續期、撤銷、負責人異動 | 是否需要有效期間、上限是多少（參數） |
| 證據 | 稽核紀錄、雜湊鏈、證據頁、匯出 | 這種流程的規則代碼 |
| 其他 | 人員與組織、角色、參數、通知、排程、行事曆、附件 | 專屬的參數、通知範本、資料表 |

## 第一版包含的流程包

| 流程包 | 用途 | 規則來源 |
|---|---|---|
| **資料授權**（`data_access`） | 第一個實際要上線的流程：L3、L4 資料的授權申請 | [packs/data-access/rules.md](packs/data-access/rules.md) |
| **合約用印**（`seal`） | 示範用。刻意選一個完全不同的領域，用來證明核心不綁定資料授權 | [packs/seal/rules.md](packs/seal/rules.md) |

「不綁定領域」的驗收方式：合約用印流程包完成時，核心的資料庫程式、後端核心、前端核心都沒有因為它而修改；檢查腳本會確認核心程式裡沒有出現任何流程包的名稱。

## 第一版的範圍界線

- **流程定義用資料描述，由流程包的升版腳本載入。** 管理畫面可以檢視流程定義與路徑，但不提供拖拉式的流程設計器。流程屬於控管規則，變更要經過有紀錄的升版。
- **流程包的領域邏輯寫成 SQL function。** 核心透過固定的介面呼叫它們。
- 多公司（多租戶）不在第一版範圍；資料表設計不阻礙之後加入。
